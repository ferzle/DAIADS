Recursion

Overview

A recursive algorithm solves a problem by applying the same algorithm to smaller versions of that problem. Instead of trying to solve the whole problem at once, the algorithm handles one layer of the task and leaves the rest to one or more recursive calls.

For example, to compute the sum of the first n positive integers, we can first compute the sum of the first n - 1 positive integers and then add n. To search a sorted array, we can compare against the middle item and then recursively search only the left half or the right half. In both cases, the recursive call solves a smaller version of the original problem.

Recursion is closely related to mathematical induction. A base case handles a smallest instance directly, and the recursive case explains how to solve a larger instance using smaller ones. This same pattern will appear throughout the course in divide-and-conquer algorithms, tree processing, backtracking, recurrence relations, and dynamic programming.

The Three Requirements

Every recursive algorithm needs three pieces: a base case, a recursive case, and progress toward the base case. These pieces work together to make sure the algorithm eventually stops and produces the correct answer.

  • Base case: One or more small inputs that can be solved directly, without making another recursive call.
  • Recursive case: A rule that solves the current problem using one or more smaller instances of the same problem.
  • Progress: A guarantee that each recursive call moves closer to a base case.

The base case tells the algorithm when to stop. The recursive case tells it how to reduce the problem. The progress condition connects the two: it ensures that repeated reductions will eventually reach a base case.

If any of the three are missing, the recursive algorithm is likely to fail. If there is no base case, the recursive calls will never end. If there is no recursive case, the algorithm is not really using recursion to reduce the problem. If there is no progress, the function may keep calling itself on inputs that never reach a base case.

Example: Factorial

The factorial function gives a simple first example because its definition is already recursive. For a nonnegative integer \(n\), \(n!\), read "n factorial", means the product of all positive integers from \(1\) through \(n\). For example, \(4! = 4 \cdot 3 \cdot 2 \cdot 1 = 24\). The values of \(0!\) and \(1!\) are both \(1\). For any integer \(n > 1\), the value of \(n!\) is \(n \cdot (n - 1)!\). This naturally leads to the following recursive method: 

int factorial(int n) {
    if (n <= 1) {
        return 1;
    }
    return n * factorial(n - 1);
}

In this method, the base case is n <= 1, which returns 1 without another recursive call. The recursive case is the final line, which computes n * factorial(n - 1). The method makes progress because each recursive call decreases n by 1, so an input larger than 1 eventually reaches the base case.

For example, evaluating factorial(4) produces the chain of calls factorial(4), factorial(3), factorial(2), and factorial(1). The last call reaches the base case and returns 1. After that, the earlier calls finish in reverse order, multiplying by 2, then 3, and finally 4 to obtain 24.

This version assumes that the input is nonnegative. A full implementation might check for negative inputs and report them as invalid.

The Call Stack

When one method calls another method, the first method does not disappear. It pauses and waits for the called method to finish. The computer keeps track of these paused and active method calls using the call stack.

Each active method call has its own stack frame. A stack frame stores the information needed for that call, including its parameter values, local variables, and the place where execution should continue after another method returns.

Recursive calls use the call stack in the same way as any other method calls. The only unusual feature is that several calls to the same method can be active at the same time, each with its own parameter values.

The stack grows as recursive calls are made. After the base case returns, the stack unwinds: the most recent call finishes first, then the call that was waiting for it, and so on back to the original call.

The maximum number of active stack frames is the recursion depth. For this factorial method, the recursion depth grows in direct proportion to n, so larger inputs create longer chains of waiting calls. This is one reason recursion is not always better than iteration: a loop can compute the same factorial values without building up a chain of stack frames.

Tracing Recursive Code

Tracing recursive code means recording the calls the program makes and the values those calls return. A written trace does not need to show every detail stored in a stack frame, but it should keep the calls separate and show the order in which they are created and finished.

A reliable hand trace follows these steps.

  1. Write the current call: Record the function name and argument values.
  2. Check the base case: If it applies, record the return value or output.
  3. Record the recursive call: If the function recurses, write the new call underneath the current one.
  4. Keep calls separate: Treat each call as having its own parameters and local variables.
  5. Unwind in reverse order: After the base case returns, finish the waiting calls from newest to oldest.

Work Before and After the Recursive Call

The position of the recursive call affects when work happens. If the method does work before the recursive call, that work happens as the stack is growing. If the method does work after the recursive call, that work happens as the stack is unwinding.

In this first example, the method prints before making the recursive call. 

void countdown(int n) {
    if (n > 0) {
        print(n);
        countdown(n - 1);
    }
}

The call countdown(4) prints 4 3 2 1. Each value is printed before the next recursive call is made.

In the next example, the same two lines appear in the opposite order. 

void countup(int n) {
    if (n > 0) {
        countup(n - 1);
        print(n);
    }
}

The call countup(4) prints 1 2 3 4. The recursive calls happen first, so the print statements wait until the calls return.

This is a common source of mistakes when writing or tracing recursion. Work before the recursive call happens on the way down; work after the recursive call happens on the way back up.

Tracing Return Values

Some recursive methods print output, but many recursive methods return a value. When tracing return values, record what each call is waiting for. A call cannot finish its computation until the recursive call it depends on has returned.

For instance, the method below returns the sum of the first n positive integers. The base case returns 0, and each recursive call waits for the smaller sum before adding n. 

int sumFirst(int n) {
    if (n <= 0) {
        return 0;
    }
    return n + sumFirst(n - 1);
}

The method sumFirst(n) returns the sum 1 + 2 + ... + n. To trace a concrete example, we will use sumFirst(4), whose final answer should be 1 + 2 + 3 + 4 = 10. The original call cannot return immediately; it must wait for smaller calls to return first.

The trace has two phases. First, the calls go down toward the base case. During this phase, each call waits for a smaller call to return.

Step Call What it is waiting for
1 sumFirst(4) Needs sumFirst(3) before it can return 4 + sumFirst(3).
2 sumFirst(3) Needs sumFirst(2) before it can return 3 + sumFirst(2).
3 sumFirst(2) Needs sumFirst(1) before it can return 2 + sumFirst(1).
4 sumFirst(1) Needs sumFirst(0) before it can return 1 + sumFirst(0).
5 sumFirst(0) Base case. Returns 0.

Once the base case returns, the calls finish in reverse order. Each return value is passed back to the call that was waiting for it.

Step Returning call Value from smaller call Value returned
6 sumFirst(1) sumFirst(0) returned 0 1 + 0 = 1

The original call, sumFirst(4), returns last because it depends on all of the smaller calls. Its final return value is 10.

Of course, summing the first n positive integers is usually better solved with a loop or even with a formula. The recursive version is useful here because it gives a simple example of how return values move back through a chain of recursive calls.

Branching Recursion

The examples so far have made one recursive call at a time. These calls form a single chain: each call waits for one smaller call, which waits for one even smaller call, and so on. Some recursive methods make more than one recursive call from the same method call. This is called branching recursion.

A simple example is the Fibonacci sequence: \(0, 1, 1, 2, 3, 5, 8, 13, \ldots\). Each number after the first two is the sum of the two numbers before it. That is, \(F_0 = 0\), \(F_1 = 1\), and for \(n > 1\), \(F_n = F_{n-1} + F_{n-2}\). Fibonacci numbers appear in many places in mathematics and computer science, partly because they are a simple example of a sequence defined in terms of earlier values.

This definition leads directly to a recursive method: if n == 0 or n == 1, return n; otherwise recursively compute the two previous Fibonacci values, add them and return the result. Here is a simple implementation of the idea: 

int fib(int n) {
    if (n <= 1) {
        return n;
    }
    return fib(n - 1) + fib(n - 2);
}

Note that in this implementation, we are assuming that n is a non-negative integer.

For example, fib(5) calls both fib(4) and fib(3). Then fib(4) calls fib(3) and fib(2). Instead of forming a single chain of calls, the computation forms a call tree.

Although this is a valid and natural way to compute Fibonacci numbers from the definition, it is not an efficient solution to the problem. The trace reveals repeated work: fib(3) appears more than once, and so does fib(2). The recursive method is correct, but it recomputes the same values many times. Later, when we study dynamic programming, we will see how to keep the recursive structure while avoiding this repeated work. For now, it is useful because it shows that recursive calls can branch into a tree rather than forming a single chain.

In the next section, we will see a better example of branching recursion: one where the recursive calls solve different parts of the problem instead of repeating the same work.

Designing Recursive Solutions

Designing a recursive solution usually starts by deciding what one function call means. Once that meaning is precise, you can treat the recursive call as a helper that already solves a smaller version of the same problem. The current call only has to reduce the problem and use the smaller answer correctly.

A useful design process is:

  1. State the meaning of the function: Be precise about what one call computes or does.
  2. Choose the base case: Identify an input that can be answered immediately.
  3. Choose the smaller problem: Decide what smaller instance the recursive call should solve.
  4. Combine the answer: Use the smaller answer or answers to finish the current call.
  5. Check progress: Make sure every recursive path eventually reaches a base case.
Example 1: Palindrome Test

A string is a palindrome if it reads the same forward and backward. For example, "racecar" and "level" are palindromes. A recursive way to check this is to compare the first and last characters. If they do not match, the string is not a palindrome. If they do match, the only remaining question is whether the substring between them is also a palindrome, and we can check that recursively.

Let isPalindrome(s, left, right) mean: return true if the part of s from index left through index right is a palindrome.

  • Base case: If left >= right, there are zero or one characters left to check, so return true.
  • Immediate failure: If s.charAt(left) and s.charAt(right) are different, return false.
  • Smaller problem: If the outside characters match, recursively check the inside substring from left + 1 through right - 1.
  • Progress: Each recursive call moves the two indices closer together.

Here is the implementation:

boolean isPalindrome(String s, int left, int right) {
    if (left >= right) {
        return true;
    }

    if (s.charAt(left) != s.charAt(right)) {
        return false;
    }

    return isPalindrome(s, left + 1, right - 1);
}

For example, checking "racecar" moves inward one pair of characters at a time:

  • "racecar": Compare 'r' with 'r'. Since they match, recursively check the inside substring "aceca".
  • "aceca": Compare 'a' with 'a'. Since they match, recursively check the inside substring "cec".
  • "cec": Compare 'c' with 'c'. Since they match, recursively check the inside substring "e".
  • "e": There is only one character left, so the base case returns true.

That true value is passed back through the earlier recursive calls, so the original call also returns true.

A non-palindrome can stop much earlier. For example, checking "robot" first compares 'r' with 't'. Since they do not match, the method returns false immediately without checking the inside substring.

This is single-chain recursion. Each recursive call has at most one smaller recursive call to wait for.

Example 2: Generating Binary Strings

A binary string is a string made only from the characters 0 and 1. For example, the binary strings of length 2 are "00", "01", "10", and "11".

For any length greater than 0, every binary string starts with either 0 or 1. After choosing that first character, the rest of the string is a shorter binary string. This makes the problem naturally branching: one branch handles strings whose next character is 0, and the other branch handles strings whose next character is 1.

Let printBinary(prefix, remaining) mean: print every binary string that begins with prefix and has remaining more characters after that prefix. For example, printBinary("10", 2) should print "1000", "1001", "1010", and "1011". To print all binary strings of length n, we start with an empty prefix by calling printBinary("", n).

This meaning leads directly to the recursive structure:

  • Base case: If remaining == 0, the prefix is a complete binary string, so print it.
  • First branch: Add 0 to the prefix and recursively fill the remaining positions.
  • Second branch: Add 1 to the prefix and recursively fill the remaining positions.
  • Progress: Each recursive call decreases remaining by 1.

This gives the following implementation: 

void printBinary(String prefix, int remaining) {
    if (remaining == 0) {
        print(prefix);
        return;
    }

    printBinary(prefix + "0", remaining - 1);
    printBinary(prefix + "1", remaining - 1);
}

To print all binary strings of length 3, we would call: 

printBinary("", 3);

The trace below shows the calls made by printBinary("", 3). Indentation shows recursive depth: deeper lines are calls made by the line above them. When the next line is farther left than the previous line, one or more recursive calls have finished, and the computation has returned to an earlier call. 

printBinary("", 3)
  printBinary("0", 2)
    printBinary("00", 1)
      printBinary("000", 0) prints 000
      printBinary("001", 0) prints 001
    printBinary("01", 1)
      printBinary("010", 0) prints 010
      printBinary("011", 0) prints 011
  printBinary("1", 2)
    printBinary("10", 1)
      printBinary("100", 0) prints 100
      printBinary("101", 0) prints 101
    printBinary("11", 1)
      printBinary("110", 0) prints 110
      printBinary("111", 0) prints 111

This is branching recursion because each non-base case makes two recursive calls. Unlike the naive Fibonacci method, the two branches do different work: one branch extends the current prefix with 0, and the other extends it with 1. Together, the branches generate every binary string of the requested length exactly once.

Recursion Versus Iteration

It is useful to separate the recursive idea from the recursive implementation. A problem may have a recursive structure because it can be described in terms of smaller versions of itself. That does not always mean the final code should use recursive method calls.

Many problems can be solved either recursively or iteratively. Recursion is often helpful when the problem naturally contains smaller versions of itself. Iteration is often better when the recursive version is only repeating a simple loop, or when the loop is just as clear.

Recursive calls also have some overhead. Each call creates a new stack frame, and a long chain of recursive calls can use more memory than a loop. For that reason, if the recursive and iterative versions are equally clear, the iterative version is usually preferred.

Example: When Iteration Is Better

Summing the first n positive integers can be written recursively because sumFirst(n) is equal to n + sumFirst(n - 1). That is a valid recursive description: solve the smaller problem of summing the first n - 1 positive integers, then add n. However, the recursive version is mostly a loop in disguise because it processes the numbers one at a time in a simple sequence. 

int sumFirstRecursive(int n) {
    if (n <= 0) {
        return 0;
    }
    return n + sumFirstRecursive(n - 1);
}

A loop expresses the same idea without building up a chain of waiting calls. 

int sumFirstIterative(int n) {
    int total = 0;
    for (int i = 1; i <= n; i++) {
        total += i;
    }
    return total;
}

In this case, the iterative version is the better practical implementation. It is simpler, avoids extra stack frames, and uses less memory. The recursive version is valid, but it adds implementation overhead for a task that a loop handles directly.

Example: A Recursive Idea with an Iterative Implementation

The palindrome test from the previous section has a natural recursive idea. Once the first and last characters match, the remaining question is whether the substring between them is a palindrome. That is the same problem on a smaller piece of the string.

The final implementation does not have to be recursive, though. The same idea can be implemented with a loop that moves two indices inward: 

boolean isPalindromeIterative(String s) {
    int left = 0;
    int right = s.length() - 1;

    while (left < right) {
        if (s.charAt(left) != s.charAt(right)) {
            return false;
        }
        left++;
        right--;
    }

    return true;
}

This iterative version is probably the better practical implementation: it avoids recursive calls and uses only a few variables. Still, the recursive way of thinking helped identify the structure of the solution: compare the outside characters, then move inward to the smaller remaining problem.

Example: Recursion Fits Branching Choices

We saw a recursive solution for generating binary strings. This is a case where both the recursive idea and the recursive implementation are natural. At each step, there are two choices for the next character: 0 or 1. The recursive method turns those two choices into two recursive calls.

An iterative solution is possible, but it needs extra machinery to keep track of the unfinished choices. The version below uses a stack, which is a structure for storing items and removing the most recently added item first. We will study stacks later; for now, the important point is that the iterative version has to manage the partially built strings itself. 

void printBinaryIterative(int n) {
    Stack prefixes = new Stack();
    prefixes.push("");

    while (!prefixes.isEmpty()) {
        String prefix = prefixes.pop();

        if (prefix.length() == n) {
            print(prefix);
        } else {
            prefixes.push(prefix + "1");
            prefixes.push(prefix + "0");
        }
    }
}

This code still follows the same branching idea: each unfinished prefix creates two longer prefixes, one ending in 0 and one ending in 1. However, the iterative version must explicitly store and retrieve the unfinished prefixes. In the recursive version, that bookkeeping is handled by the call stack, so the code more directly reflects the branching structure of the problem.

Recursion is most useful when the problem naturally breaks into smaller subproblems or branching choices. Even then, a recursive idea does not always require a recursive implementation. If the same idea can be implemented with a simple loop, the iterative version is often preferred because it avoids the overhead of recursive calls. Recursive implementations are strongest when they make the structure of the problem clearer than the equivalent iterative code.

Common Mistakes

Recursive code can be short, but small mistakes can change its behavior dramatically. When a recursive method fails, it is usually because one of the basic requirements is missing or because the recursive answer is used incorrectly.

  • No base case: The method always calls itself again. Since no call ever returns directly, the recursion continues until the program runs out of stack space.
  • Base case too narrow: The code handles one stopping case but misses another possible small input. For example, a method that stops only when n == 0 may fail if a recursive call skips past 0 or if the original input is negative.
  • No progress: The recursive call uses the same arguments or moves away from the base case. For example, factorial(n) should call factorial(n - 1), not factorial(n) again.
  • Progress in the wrong direction: The recursive call changes the input, but not toward the base case. For example, if the base case is n <= 0, then calling the method with n + 1 moves in the wrong direction for positive inputs.
  • Wrong combination: The recursive call may correctly solve the smaller problem, but the current call uses that answer incorrectly. For example, sumFirst(n) should return n + sumFirst(n - 1), not just sumFirst(n - 1).
  • Forgetting to return the recursive answer: A method may make the right recursive call but fail to return its result. This is common in methods that compute a value instead of printing output.
  • Confusing work before and after the recursive call: Code before the recursive call happens while the stack is growing. Code after the recursive call happens while the stack is unwinding. Reversing these can produce output in the opposite order.
  • Unexpected stack growth: The code may work for small inputs but fail or waste space on large inputs because each unfinished call uses a stack frame. A loop may be a better choice when the recursive version is only a simple chain of calls.
  • Repeated subproblems: Some recursive methods recompute the same values many times. The naive Fibonacci method is a typical example: the same smaller Fibonacci values are computed again and again.
