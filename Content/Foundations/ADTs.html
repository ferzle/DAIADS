Abstract Data Types and Implementations

Overview

When we organize data in a program, several related terms are easy to mix up: data type, abstract data type, data structure, and implementation.

  • A data type describes a set of possible values together with operations on those values. For example, integers, characters, strings, arrays, and objects are all data types in many programming languages.
  • An abstract data type, or ADT, describes a kind of data by its behavior rather than by its representation in memory. It specifies what values can be stored, what operations are available, and what those operations mean.
  • A data structure is a particular way of organizing data so those operations can be performed efficiently.
  • An implementation is the actual code that uses a chosen data structure to provide the ADT's operations.

For example, a stack is an ADT with operations such as push, pop, and peek. The stack behavior says that the most recently pushed item is the first item removed. That behavior can be implemented using several different data structures, such as an array, a dynamic array, or linked nodes.

Some ADTs have a standard core idea shared by nearly all versions, along with details that can vary from one specification to another. For a stack, the last-in, first-out behavior is essential. Other details, such as whether pop on an empty stack causes an error, returns a special value, or is simply not allowed, are choices made by a particular stack specification.

This separation is one of the central ideas in data structures. Client code should be able to use the stack behavior without depending on how the stack is represented internally. The ADT says what clients may rely on; the implementation decides how to make it happen.

The ADT Contract

An ADT acts like a contract between two parts of a program. The client is the code that uses the ADT. The implementation is the code that stores the data and carries out the operations. The client should only need to know what the ADT promises, not how the data is stored internally.

A complete ADT description should answer several questions. The following uses a stack as an example, but the same questions apply to any ADT.

Part of the contract Question it answers Example for a stack
Stored values What kind of items can be placed in the ADT? A stack might store integers, strings, objects, or some other type of value.
Operations What actions are allowed? push, pop, peek, isEmpty, and size.
Operation behavior What does each operation do? pop removes and returns the most recently pushed item.
Preconditions What must be true before an operation is called? pop may require that the stack is not empty.
Postconditions What must be true after the operation finishes? After push(x), x is the top item on the stack.
Boundary cases What happens in special or extreme cases? A particular stack specification should say what happens when pop is called on an empty stack. One specification might require an exception, while another might return a special value.
Performance expectations How efficient should the operations be? A stack usually expects push, pop, and peek to be fast.

Some parts of an ADT are essential. A stack would not be a stack without last-in, first-out behavior. Other parts are choices that must be specified so clients and implementers agree on what the operations mean. For example, one stack specification might say that pop has a precondition that the stack is nonempty, while another might say that pop throws an error when the stack is empty. Once the contract states the choice, every correct implementation must follow it.

The contract does not normally describe private variables, array indices, linked nodes, resizing rules, or other internal details. Those choices belong to the implementation. The point of the contract is to say what outside code may rely on.

Example: Stack ADT

A stack is a last-in, first-out collection. This means that the most recently added item is the first item removed. Many different stack specifications are possible, but they all share this last-in, first-out rule. For this example, we will use a simple stack ADT that can grow as needed, so push does not fail because the stack is full. However, pop and peek require the stack to be nonempty.

The following table gives the public operations for this particular stack ADT. These are the operations client code is allowed to use. The table describes what each operation means, but it does not say how the stack is represented in memory.

Operation Behavior Precondition or boundary behavior
push(x) Add x so it becomes the top item. No full-stack case is considered in this ADT.
pop() Remove and return the current top item. The stack must be nonempty.
peek() Return the current top item without removing it. The stack must be nonempty.
isEmpty() Return whether the stack currently has no items. Always valid.
size() Return the number of items currently stored. Always valid; returns 0 for an empty stack.

Implementing an ADT

After an ADT contract has been specified, an implementer must decide how to represent the data internally. The client should still see only the public operations, but the implementation must store enough information to make those operations work correctly.

For example, one implementation of the growable stack ADT could use a dynamic array named items and an integer named size. The array stores the stack values, and size records how many values are currently in the stack.

An implementation usually depends on a representation invariant: a rule that describes when the internal state is valid. For this array-based stack, a possible invariant is:

  • The stack contents are stored in items[0] through items[size - 1].
  • If the stack is nonempty, the top item is stored at items[size - 1].
  • The value of size is always between 0 and the length of the array, so the first size positions exist.

With this representation, push(x) can place x at items[size] and then increase size. If the array is full, the implementation first creates a larger array and copies the current items into it. Similarly, pop() can save items[size - 1], decrease size, and return the saved value. These steps are not part of the stack ADT itself; they are one way to implement the required behavior.

Other implementations can satisfy the same stack ADT using different internal representations:

Stack implementation Internal representation Possible invariant Tradeoff
Dynamic array Values are stored in an array that grows when needed. The stack occupies items[0] through items[size - 1], and the top item is at items[size - 1]. Usually fast, but occasional resizing copies many items.
Linked nodes Each value is stored in a node that points to the next node. The top reference points to the node containing the top item, and following links gives the rest of the stack. No array resizing, but each item needs extra storage for a link.

A fixed-size array could also be used for a different stack specification, one where push may fail when the stack is full. That would still be a valid stack-like ADT, but it would have a different contract from the growable stack described above.

The important point is that all implementations of a given ADT must give clients the same visible behavior. The client calls push, pop, peek, isEmpty, and size. The implementation decides what private variables and algorithms make those operations work.

Abstraction and Cost

The abstraction boundary is the line between what client code is allowed to rely on and what the implementation is allowed to change. For a stack, clients should know that pop removes the most recently pushed item. They should not need to know whether that item is stored at the end of an array or in the first linked node.

In many programming languages, a class or interface is used to express part of this boundary. However, an ADT is not the same thing as a class. The ADT is the behavioral idea; a class is one possible programming construct for implementing that idea.

This boundary is useful, but it does not mean implementation details never matter. Many ADT descriptions focus mostly on behavior, but programs often also depend on performance. If two implementations provide the same visible behavior but one makes an important operation much slower, that difference can determine which implementation is appropriate.

For example, a priority queue ADT might provide operations such as insert and removeMin. An unsorted array can implement those operations, but removeMin requires a scan through the stored items. A heap can implement the same priority queue behavior with more efficient operations for many uses. The ADT says what must happen; the data structure and implementation determine how expensive it is.

Reading Comprehension Questions

  1. Terminology: What is the difference between a data type and an abstract data type?
  2. ADT Contract: What kinds of information should an ADT contract specify?
  3. Stack Behavior: In the stack ADT from this section, after push(A), push(B), and push(C), what should pop() return?
  4. Boundary Cases: Why does a stack specification need to say what happens when pop() is called on an empty stack?
  5. Implementation: What is a representation invariant, and why does an implementation need one?
  6. Abstraction and Cost: If two implementations have the same visible behavior, why might one still be better than the other?
  1. Answer: A data type describes a set of values and operations. An ADT describes behavior without committing to a particular representation in memory.
  2. Answer: It should specify the stored values, operations, operation behavior, preconditions, postconditions, boundary cases, and possibly performance expectations.
  3. Answer: It should return C, because a stack removes the most recently pushed item first.
  4. Answer: Client code and implementation code need to agree on the behavior. The specification might require the stack to be nonempty, throw an error, or use some other defined behavior.
  5. Answer: A representation invariant is a rule that describes when the internal state is valid. It helps ensure that the private data still correctly represents the ADT.
  6. Answer: They may have different time or space costs. A slower or more memory-intensive implementation may be inappropriate even if it gives the same answers.
