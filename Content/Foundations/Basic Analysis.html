Basic Algorithm Analysis

Why Analyze Algorithms?

When we study an algorithm, we usually care about two broad questions: does it solve the problem correctly, and how efficiently does it use resources? This page focuses on the second question. Two algorithms can both solve the same problem correctly but behave very differently as the input gets larger. One algorithm might work well for a list of 20 items but become unusable for a list of 20 million items. Another might take more effort to understand or implement, but scale much better.

Algorithm analysis gives us a way to estimate an algorithm's resource use without depending too much on a particular computer, programming language, or implementation. Instead of asking only "How many seconds did this program take?", we ask questions like "How many basic operations does this algorithm perform?" and "How does that number grow as the input size grows?"

In this chapter, we will focus mostly on running time, but the same ideas also apply to memory use. The goal is not to predict exact timings. The goal is to recognize broad patterns of growth so we can compare algorithms, choose appropriate data structures, and make reasonable decisions about efficiency.

Wall Clock Time vs. Amount of Work

One way to compare algorithms is to implement them and measure how many seconds each program takes to run. This can be useful, but it does not tell the whole story. The running time of a program depends on the computer, programming language, compiler or interpreter, operating system, current system load, and many implementation details. The same algorithm may run in different amounts of time in different environments.

Algorithm analysis tries to separate the main idea of the algorithm from those machine and implementation details. Instead of measuring wall-clock time, we estimate the amount of work the algorithm performs. For example, we might count how many comparisons are made, how many times a loop runs, how many array positions are examined, how many assignments are performed, or how many function calls occur.

The exact operation we count depends on the algorithm and the question we are asking. When searching an array, counting comparisons with the target value is natural. When sorting, comparisons or swaps might be useful to count. When processing a data structure, we might count operations such as pushes, pops, insertions, deletions, or searches. The goal is to choose a reasonable basic operation and then estimate how the number of those operations grows as the input size grows.

Input Size

When we analyze an algorithm, we describe its work in terms of the size of the input. We often use \(n\) for input size, but \(n\) does not always mean the same thing. For an array problem, \(n\) might be the number of array elements. For a string problem, \(n\) might be the number of characters. For a graph problem, one number may not be enough: we may need both the number of vertices and the number of edges.

Choosing the input size carefully matters because the running time should be measured against the part of the input that can grow. If an algorithm processes every item in an array, its work depends on the number of items. If it processes every edge in a graph, its work depends on the number of edges. The table below gives several common examples.

Problem or Data Possible Input Size
Searching an array Number of array elements, \(n\)
Processing a string Number of characters, \(n\)
Sorting a list Number of values being sorted, \(n\)
Processing a two-dimensional table Number of rows and columns, often \(r\) and \(c\)
Graph problem Number of vertices \(n\), number of edges \(m\), or both

On this page, input size usually means the number of items being processed, such as the number of array elements, characters, records, vertices, or edges. In more advanced settings, input size may instead mean the number of symbols or bits needed to write the input. For now, we will use the more concrete interpretation unless stated otherwise.

Running-time bounds should be written in terms of the input size, not in terms of a temporary loop variable such as \(i\) or \(j\). For example, if a loop processes an array of length \(n\), the running time should be described in terms of \(n\), even if the loop variable is named \(i\). Also, a constant number of extra primitive inputs usually does not affect the size measure. For instance, searching an array of length \(n\) for one target value is usually analyzed in terms of \(n\), not \(n+1\).

Informal Big-O Notation

Big-O notation is a way to describe how the amount of work grows as the input size grows. It does not usually describe the exact number of operations. Instead, it gives a broad category of growth. For example, saying that an algorithm is \(O(n)\) means that its work grows roughly in proportion to the input size. If the input is twice as large, we expect the work to be about twice as large, ignoring lower-level details.

Big-O notation usually ignores constant factors and lower-order terms. For example, an algorithm that performs about \(5n + 20\) operations is described as \(O(n)\). The dominant term is \(n\), and the constant multiplier 5 and extra 20 operations do not change the overall growth pattern. Similarly, an algorithm that performs about \(3n^2 + 10n + 50\) operations is described as \(O(n^2)\), because the \(n^2\) term dominates the expression for large values of \(n\).

This simplification is useful because it lets us compare algorithms at a high level. An \(O(n)\) algorithm generally scales better than an \(O(n^2)\) algorithm, even if the \(O(n)\) algorithm has a larger constant factor. However, constants and implementation details can still matter in practice, especially for small inputs. Big-O notation is a tool for understanding long-term growth, not a replacement for careful implementation or testing.

Common Growth Rates

Some growth rates occur often enough that they are worth recognizing by sight. The table below lists several common categories, ordered from slower growth to faster growth. The Typical Pattern column describes code or design patterns that often lead to that growth rate, and the Example Algorithms or Operations column lists specific algorithms or operations that we will see later. These are useful guides, but they are not automatic rules. We still need to analyze the actual code or algorithm in context.

Keep in mind as you look at the table that we are using Big-O notation to describe how the amount of work grows as the input size grows. When comparing algorithms for the same problem, a slower-growing Big-O expression usually means better scaling. This is the key point: we want the work to grow slowly, not quickly. For example, an \(O(n)\) algorithm is usually more efficient than an \(O(n^2)\) algorithm for large enough \(n\), because the amount of work grows more slowly as the input grows.

This can feel backwards at first: a "larger" Big-O expression usually means more work, so it usually means a slower algorithm on large inputs. We are not trying to make the formula grow quickly; we are trying to keep the amount of work from growing too quickly. Constant, logarithmic, and linear growth are generally much more manageable than quadratic, exponential, or factorial growth.

Big-O Name Typical Pattern Example Algorithms or Operations
\(O(1)\) Constant Work does not grow with the input size Accessing one array element; checking whether a stack is empty; pushing onto a stack
\(O(\log n)\) Logarithmic Repeatedly cutting the problem size in half Binary search; searching in a balanced binary search tree
\(O(n)\) Linear Scanning all items once Sequential search; finding the maximum value in an array
\(O(n \log n)\) Linearithmic Dividing work into pieces and doing linear work at each level Merge sort; heapsort; average-case quicksort
\(O(n^2)\) Quadratic Comparing many pairs of items; some nested loops Selection sort; insertion sort worst case; bubble sort; checking all pairs
\(O(n^3)\) Cubic Some triple nested loops; some basic matrix algorithms Basic matrix multiplication; Floyd-Warshall shortest paths
\(O(2^n)\) Exponential Trying every subset of \(n\) items Brute-force subset sum; some backtracking algorithms in the worst case
\(O(n!)\) Factorial Trying every ordering of \(n\) items Brute-force traveling salesperson search; generating all permutations

Another useful way to read the table is to imagine doubling the input size. Constant work stays about the same. Logarithmic work grows by only a small additive amount. Linear work roughly doubles, quadratic work roughly quadruples, and exponential or factorial work grows so quickly that even moderate input sizes can become impractical.

The difference between these categories becomes more important as \(n\) grows. For small inputs, a simple algorithm with a worse growth rate may still be acceptable. For large inputs, the growth rate often determines whether an approach is practical at all. In general, when comparing algorithms for the same problem, the one with the slower-growing running time is the one that scales better. Remember: faster growth in the work usually means slower performance on large inputs. When designing algorithms, one important goal is to find an approach whose work grows slowly as the input size grows.

Simple Rules for Estimating Running Time

We can often estimate running time by looking at the structure of the code. The goal is not to count every small operation exactly. Instead, we look for the parts of the code that control how the amount of work grows as the input size grows.

  1. Constant-time statements: A statement that does a fixed amount of work is usually \(O(1)\). Assigning a value, comparing two values, doing one arithmetic operation, or accessing one array position are usually treated as constant-time operations.
  2. Single loops: A loop with \(n\) iterations and constant work per iteration is usually \(O(n)\). For example, a loop that scans every item in an array once has linear running time.
  3. Consecutive loops: Consecutive pieces of code have their costs added. For example, two separate loops that each run \(n\) times do about \(2n\) total iterations, which is still \(O(n)\). After adding costs, we keep the dominant term.
  4. Nested loops: Nested loops often multiply. If an outer loop runs \(n\) times and an inner loop runs \(n\) times for each outer iteration, the total number of inner-loop iterations is \(n^2\), giving \(O(n^2)\) time. However, nested loops should still be checked carefully because the inner-loop bounds may change.
  5. Halving or doubling: A loop that repeatedly halves a value, doubles a value, or cuts the remaining problem size by a fixed fraction often has logarithmic behavior. For example, repeatedly dividing \(n\) by 2 until it reaches 1 takes about \(\log_2 n\) steps, giving \(O(\log n)\) time.

These rules are starting points, not substitutes for analysis. They work well for many simple examples, but more complicated algorithms may require more careful counting, summations, or recurrence relations.

Best, Worst, and Average Cases

Some algorithms do the same amount of work for every input of a given size. Other algorithms do different amounts of work depending on the particular input. For example, sequential search might find the target immediately, or it might have to inspect every item. To describe these differences, we often discuss best-case, worst-case, and average-case running time.

When we do these analyses, we usually choose a generic input size \(n\) and ask how much work the algorithm does on inputs of that size. Best case, worst case, and average case are all measured for that same value of \(n\). In particular, the best case does not mean choosing \(n = 1\) or some other small input size. It means asking, among all inputs of size \(n\), which input makes the algorithm do the least work.

For example, if \(n = 1000\), the best case for sequential search is not a smaller array. It is an array of length 1000 where the target is found immediately. The worst case is an array of length 1000 where the target is last or missing. Both cases use the same input size; what changes is the arrangement of the input and where the target appears.

More formally, the best, worst, and average cases are defined as follows:

  • Best case: The least work the algorithm does on any input of size \(n\). Best-case analysis can be useful, especially for algorithms that may stop early, but it may describe unusually favorable inputs. By itself, it does not give a guarantee about how the algorithm will behave on typical or difficult inputs.
  • Worst case: The largest amount of work the algorithm does on any input of size \(n\). Worst-case analysis is often useful because it gives a guarantee: the algorithm will not do more than this much work for inputs of that size. We often care most about worst-case analysis because it gives an upper bound on the work and is often easier to analyze than average case.
  • Average case: The expected amount of work over inputs of size \(n\), based on some assumption about which inputs are likely. Average-case analysis can be useful, but it can be tricky because we must define what "average input" means. In informal discussions, people sometimes say "average case" when they really mean "typical case" or "what usually happens in practice." That kind of informal reasoning can be useful, but a formal average-case analysis requires a clear assumption about the distribution of inputs.

On this page, we will often focus on worst-case analysis, but best-case and average-case analysis are also important in practice, and we will include them when they are useful. For some algorithms, the average and worst cases are significantly different, so it is important to understand both and to consider when and how often each case occurs in practice.

Space Complexity

Time is not the only resource an algorithm uses. Algorithms also use memory. Space complexity describes how the amount of memory used by an algorithm grows as the input size grows.

When analyzing space, we often focus on extra space: memory used in addition to the input itself. For example, if an algorithm is given an array of \(n\) values, we usually do not count the input array as extra space. We count new variables, arrays, tables, stacks, queues, or other structures that the algorithm creates while it runs.

As with running time, we usually describe space use with Big-O notation. A few variables use \(O(1)\) extra space. A new array with one entry for each input item uses \(O(n)\) extra space. A table with \(n\) rows and \(n\) columns uses \(O(n^2)\) extra space.

Memory Used Extra Space
A few integer variables \(O(1)\)
A new array of length \(n\) \(O(n)\)
A stack that may hold up to \(n\) items \(O(n)\)
A table with \(n\) rows and \(n\) columns \(O(n^2)\)

Sample Analyses

The following examples show how the basic rules above can be applied to short pieces of code. In each example, let \(n\) be the number of values in the array unless another input size is specified.

Example 1: Find the Maximum

This code scans an array to find its largest value. It assumes the array is nonempty. 

int max = a[0];
for (int i = 1; i < a.length; i++) {
    if (a[i] > max) {
        max = a[i];
    }
}

The assignment max = a[0] takes constant time. The loop starts at index 1 and continues through the end of the array, so it runs \(n-1\) times. Each iteration does a constant amount of work: it compares a[i] with max, and sometimes updates max. Therefore, the running time is \(O(n)\). The code uses only a few variables besides the input array, so the extra space is \(O(1)\).

Example 2: Sequential Search

This method searches an array from left to right. It returns the index where target is found, or -1 if the target does not appear. 

int search(int[] a, int target) {
    for (int i = 0; i < a.length; i++) {
        if (a[i] == target) {
            return i;
        }
    }
    return -1;
}

The amount of work depends on where the target appears. In the best case, the target is at index 0, so the method finds it after one comparison. The best-case time is \(O(1)\). In the worst case, the target is at the last position or does not appear at all, so the loop examines all \(n\) items. The worst-case time is \(O(n)\). If the target is equally likely to appear at any position, the method examines about half the array on average, which is still \(O(n)\). The extra space is \(O(1)\).

Example 3: Compare All Pairs

This method checks whether an array contains duplicate values by comparing each value with all values that come after it. 

boolean hasDuplicate(int[] a) {
    for (int i = 0; i < a.length; i++) {
        for (int j = i + 1; j < a.length; j++) {
            if (a[i] == a[j]) {
                return true;
            }
        }
    }
    return false;
}

The worst case occurs when there are no duplicates. In that case, the method cannot return early, so it must compare every pair of positions before returning false.

Let \(n\) be the length of the array. When i is 0, the inner loop compares a[0] with the other \(n-1\) values. When i is 1, the inner loop compares a[1] with the remaining \(n-2\) values. Then it makes \(n-3\) comparisons, then \(n-4\), and so on, down to 1 comparison near the end.

So the total number of comparisons is \[ (n-1) + (n-2) + (n-3) + \cdots + 2 + 1. \] This is a familiar pattern. To find its value, write the same sum twice, once forward and once backward: \[ \begin{aligned} S &= 1 + 2 + 3 + \cdots + (n-2) + (n-1) \\ S &= (n-1) + (n-2) + (n-3) + \cdots + 2 + 1 \end{aligned} \] If we add the two lines column by column, each column adds to \(n\), and there are \(n-1\) columns. Therefore, \[ 2S = n(n-1), \] so \[ S = \frac{n(n-1)}{2}. \]

The exact number of comparisons is \(\frac{n(n-1)}{2}\), which is \(\frac{1}{2}n^2 - \frac{1}{2}n\). Since Big-O notation keeps the dominant term and ignores constant factors, the worst-case running time is \(O(n^2)\). The method uses only a few variables besides the input array, so the extra space is \(O(1)\).

Example 4: Repeated Halving

This loop repeatedly divides \(n\) by 2 until \(n\) reaches 1. 

while (n > 1) {
    n = n / 2;
}

This loop does not run \(n\) times. Each iteration cuts the value of n approximately in half. After one iteration, the value is about \(n/2\). After two iterations, it is about \(n/4\). After three iterations, it is about \(n/8\). After \(k\) iterations, it is about \(n/2^k\).

The loop stops when repeated halving has reduced the value to about 1. To estimate the number of iterations, we ask when \[ \frac{n}{2^k} = 1. \] Multiplying both sides by \(2^k\) gives \[ n = 2^k. \] The value of \(k\) that makes \(2^k = n\) is \(\log_2 n\). So after about \(\log_2 n\) iterations, the value has been reduced to 1.

Therefore, the running time is \(O(\log n)\). The base of the logarithm does not matter for Big-O notation, so we usually write \(O(\log n)\) instead of \(O(\log_2 n)\). The extra space is \(O(1)\), since the loop only changes the value of \(n\) and does not create a new data structure.

Example 5: Nested Loop with a Constant Inner Bound

Do not memorize "nested loops mean \(O(n^2)\)." Read the loop bounds. This code has a nested loop, but the inner loop always runs exactly 6 times: 

for (int i = 0; i < n; i++) {
    for (int j = 0; j < 6; j++) {
        process(a[i]);
    }
}

For each of the \(n\) values of i, the inner loop runs 6 times. The inner statement therefore runs \(6n\) times. Since Big-O notation ignores constant factors, the running time is \(O(n)\), not \(O(n^2)\).

Example 6: Function Calls with Hidden Costs

A method call is constant time only if the method itself does a constant amount of work. If the method contains a loop, recursion, or a data structure operation whose cost depends on input size, that cost must be included in the analysis. 

for (int i = 0; i < a.length; i++) {
    if (contains(b, a[i])) {
        matches++;
    }
}

If contains(b, a[i]) scans an array b of length \(m\), then each call may take \(O(m)\) time. The outer loop makes up to \(n\) calls, so the total running time may be \(O(nm)\). If b is a data structure with constant-time lookup, the same outer loop may be \(O(n)\).

Efficiency Tradeoffs

Algorithm analysis helps us compare choices, but it does not always identify one universally best approach. An algorithm with better running time may require more memory, stronger assumptions, or more complicated code. A simpler algorithm may be easier to implement and perfectly acceptable for small inputs, even if it scales worse for large inputs.

These tradeoffs appear throughout the study of algorithms and data structures. Sorting data before searching may cost extra time up front, but it can make repeated searches faster. A hash table may use extra memory to support fast lookup. A data structure may make one operation efficient while making another operation slower. Analysis gives us the vocabulary to describe these choices and decide which tradeoffs are reasonable for a particular problem.

Common Mistakes

  • Using the smallest input as the best case: Best case, worst case, and average case compare inputs of the same size \(n\). The best case is not found by shrinking the input.
  • Using loop variables in the final answer: Complexity should be expressed using input-size variables such as \(n\), \(m\), \(r\), \(c\), \(v\), or \(e\), not loop indexes such as i or j.
  • Treating every method call as \(O(1)\): A helper method or data structure operation may have its own running time. Include that cost when it depends on the input size.
  • Assuming every loop runs \(n\) times: A loop does not automatically contribute \(O(n)\) work. Its cost depends on its bounds and updates. A loop that runs \(m\) times, 100 times, or about \(\log n\) times should be analyzed differently.
  • Assuming every nested loop is quadratic: Nested loops often multiply, but the actual bound depends on how many times each loop runs.
  • Saying "average case" without assumptions: Average-case analysis needs a clear statement about which inputs are possible and how likely they are.
  • Counting the input as extra space: When analyzing extra space, do not count the memory already used by the input. Count additional arrays, tables, stacks, queues, or other structures created by the algorithm.
  • Overinterpreting Big-O for small inputs: Big-O notation describes growth for large inputs. A simpler algorithm with a worse Big-O bound may still be faster or easier to use for small inputs.

Summary

Algorithm analysis helps us estimate how much time and memory (space) an algorithm uses as the input size grows. Instead of relying only on wall-clock time, we count basic operations and describe how the amount of work grows with the input size.

Big-O notation gives a high-level way to describe that growth. It usually ignores constant factors and lower-order terms so we can focus on the dominant pattern. Common growth rates include constant, logarithmic, linear, linearithmic, quadratic, exponential, and factorial growth. In general, slower-growing running times scale better to large inputs.

We also considered best-case, worst-case, and average-case analysis, along with space complexity. Worst-case analysis gives a useful guarantee, while average-case analysis can describe expected behavior when we have a clear assumption about which inputs are likely. Space complexity describes how memory use grows, often focusing on extra memory beyond the input itself.

This page introduced these ideas informally. Later, the Analysis section develops them more carefully, including formal asymptotic notation, more detailed analysis of iterative algorithms, summations, recurrence relations, and recursive algorithm analysis. Depending on the course or context, you may read that section later. You are also welcome to read it sooner if you want a deeper treatment of these topics.
