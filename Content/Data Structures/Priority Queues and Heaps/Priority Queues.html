Priority Queues

Overview

A priority queue stores entries and supports removing the entry that should be processed next. An entry usually contains both a value and a comparable priority key. The keys do not need to be consecutive ranks such as 1, 2, and 3. They might instead represent times, distances, costs, deadlines, scores, or any other values that can be compared.

A priority rule determines which key is considered best. A min-priority queue selects the entry with the smallest key, while a max-priority queue selects the entry with the largest key. In either case, the selected entry is often described as having the highest priority. Thus, "highest priority" does not necessarily mean "largest numerical key."

Unlike a FIFO queue, a priority queue does not necessarily remove entries in arrival order. Consider a min-priority queue containing four tasks waiting to be processed. In this application, each task has an urgency key, and smaller keys represent more urgent work. Task D has key 1, so it is the next task removed even though it was not the first task inserted.

This drawing deliberately treats the priority queue as a collection of waiting entries. The cards are not meant to show an array, a list, a tree, or any other implementation. From a caller's point of view, the important guarantee is simply that the entry selected by the priority rule is returned next.

Priority queues appear whenever "most important next" is a better rule than "oldest next." Event simulations process the event with the earliest scheduled time, scheduling systems may choose among ready jobs according to urgency, and graph algorithms repeatedly select the vertex or edge with the most promising key. The meaning of the key, and whether its minimum or maximum represents the highest priority, depends on the application.

Core Operations

The table below gives the principal operations of a priority queue ADT. Exact method names and policies for empty or full priority queues vary by implementation and programming language.

Operation Description
insert(value, key) Add an entry containing value and its priority key. A bounded implementation must define what happens when its storage is full.
extract() Remove and return the entry selected by the priority rule, typically the entry with the smallest or largest key. This operation is also commonly called extractMin() for a min-priority queue or extractMax() for a max-priority queue. An empty priority queue must report underflow or follow another documented empty-queue policy.
peek() Return the entry that extract() would remove, but leave the priority queue unchanged. It has the same empty-queue issue as extract().
isEmpty() Report whether the priority queue currently contains no entries.
size() Return the number of entries currently stored.
changePriority(entry, newKey) (Optional) Change the priority key of a particular stored entry. Supporting this operation efficiently may require a handle or other way to locate that entry. Care must be taken not to change the key directly, since doing so may invalidate the representation's invariants or auxiliary bookkeeping without allowing the priority queue to repair them.

Insert

insert adds one entry to the logical collection. For example, inserting (D, 2) into a priority queue containing {(A, 5), (B, 3), (C, 7)} produces a collection with four entries. Because this page uses a min-priority queue, D immediately becomes the best entry: its key 2 is smaller than every key already present.

The ADT does not specify where the new entry is stored or how the implementation finds it later. Different representations may arrange the same logical collection in very different ways.

Extract

extract removes and returns the entry selected by the priority rule. If the queue contains {(A, 5), (B, 3), (C, 7), (D, 2)}, then extract() returns (D, 2). The queue afterward contains A, B, and C, and B is now the next entry because key 3 is the smallest remaining key.

Extracting from an empty priority queue is an underflow condition. An implementation might throw an exception, return an optional result, or use a language-specific sentinel such as null. The policy must not make a failed extraction look like a valid stored entry.

Peek

peek finds the same entry that extract would return, but leaves the priority queue unchanged. Before the extraction in the preceding example, peek() would return (D, 2). A second peek() would return the same entry unless an insertion, extraction, or priority change occurred between the calls.

Ties

Two entries may have the same priority key. When keys tie, the priority-queue specification may permit either entry to be returned, or it may define an additional tie-breaking rule. A stable priority queue extracts equal-key entries in their insertion order. One general way to provide stability is to store an increasing sequence number with each entry and compare sequence numbers when priority keys tie.

Important: Priority order does not automatically imply FIFO order among ties. Do not assume stability unless the interface or implementation promises it.

Implementation Options

Priority queues can be implemented in several ways. Common choices include:

  • sorted or unsorted arrays,
  • sorted or unsorted linked lists,
  • binary heaps,
  • balanced search trees, and
  • specialized structures designed for particular applications.

These representations make different tradeoffs among insertion, inspection of the best entry, and extraction. This page develops two simple approaches: a sorted representation and an unsorted representation. Both use a resizable array as the main model while also noting how linked-list versions differ. The page then compares standard library implementations. Binary heaps, the most common general-purpose implementation, are developed on the next page.

Before examining the two implementations, we need a way to represent each entry. Both implementations store a value together with its associated priority key. In code, an entry would usually be represented by a small class or structure with separate value and key fields. The array or linked list then stores these complete entry objects, rather than storing values and keys independently.

Implementation 1: Sorted Array or List

Basics

A sorted representation keeps the entries in priority order. The array A stores the entries in cells A[0] through A[count - 1], and count stores the number of entries currently present.

This implementation is a min-priority queue, but it stores entries from worse to better: larger keys appear on the left, and smaller keys appear on the right. The entry with the minimum key is therefore always in A[count - 1]. In the figures below, notation such as A:5 represents an entry with value A and priority key 5.

Keeping the best entry at the right end is an implementation choice, not a requirement of the priority queue ADT. This arrangement is useful because removing the final used array cell does not shift any remaining entries. A max-priority queue could use the same arrangement with the comparison reversed, placing the largest key at the right end.

A sorted linked list is usually arranged differently. The best entry can be kept at the head so that peek and extract operate there. Insertion must still walk through the list to find the correct sorted position.

How the Operations Work

Insert

Insertion works much like one step of insertion sort. Begin just after the final used cell and scan backward through the sorted entries. Any entry with better priority than the new entry must remain farther to the right, so copy it one cell to the right. Continue until reaching the beginning of the array or finding an entry that should remain to the left of the new entry. Store the new entry in the resulting opening and increment count.

For example, suppose the array contains [C:7, A:5, B:3, D:2] and we insert E:4. Start with the unused cell at index 4. Since D:2 and B:3 have better priority than E:4, shift both entries one position to the right. A:5 has worse priority than E:4, so the scan stops. Store E:4 at index 2.

Scanning from right to left combines the search for the insertion position with the shifts needed to open that position. A binary search could locate the insertion index using \(O(\log n)\) comparisons, but it would not eliminate the shifting. In the worst case, the implementation still moves \(n\) entries, so insertion remains \(O(n)\).

Peek and Extract

If count > 0, peek returns A[count - 1] without modifying the array or count.

extract saves the entry in A[count - 1], clears that cell, decrements count, and returns the saved entry. No entries need to shift because the best entry is already in the final used cell.

Clearing the now-unused cell is especially important in a language with managed object references. Otherwise, the backing array may keep an object reachable longer than necessary. Clearing is not part of the abstract priority queue operation, but it is a useful implementation detail.

Sorted-Array Pseudocode

The pseudocode assumes that better(x, y) reports whether entry x should be extracted before entry y. For the min-priority queue used here, an entry with a smaller key is better. The array is stored from worse to better. 

insert(value, key):
    if count == A.length:
        grow A

    entry = (value, key)
    i = count

    while i > 0 and better(A[i - 1], entry):
        A[i] = A[i - 1]
        i = i - 1

    A[i] = entry
    count = count + 1

peek():
    if count == 0:
        report underflow

    return A[count - 1]

extract():
    if count == 0:
        report underflow

    result = A[count - 1]
    A[count - 1] = empty
    count = count - 1
    return result

This insertion procedure can be made stable without storing sequence numbers. When keys tie, treat the existing entry as better than the new entry and shift it to the right. Thus, for a min-priority queue, the loop shifts entries whose keys are less than or equal to the new key. Earlier equal-key entries remain closer to the extraction end and are returned first.

Implementation Analysis

  • insert: \(O(n)\) in the worst case because existing entries may shift. Resizing can also copy \(O(n)\) entries, but shifting already makes the worst-case bound linear.
  • peek: \(O(1)\), since the best entry is always in A[count - 1].
  • extract: \(O(1)\), because removing the final used entry does not shift any other entries.
  • isEmpty and size: \(O(1)\) using count.

The resizable array uses \(O(n)\) space overall, although its capacity may be larger than the number of entries currently stored. A fixed-size version uses \(O(c)\) space for capacity \(c\) and must report overflow when full.

A sorted linked list has the same asymptotic operation costs when its best entry is stored at the head: insertion is \(O(n)\), while peek and extract are \(O(1)\). Like the array implementation, it uses \(O(n)\) space, but each node also stores a link to the next node. The linked list avoids unused array capacity and shifting entries, but it may still examine as many as \(n\) nodes to locate the insertion position.

Tradeoffs

This representation is attractive when the program performs many peeks or extractions after relatively few insertions. Once the entries are in order, repeatedly accessing and removing the best entry is simple. The disadvantage is that every insertion preserves more order than the priority queue ADT actually requires.

Arrays provide compact storage and good memory locality. Linked lists grow one node at a time and make removal at the head simple, but each node stores an additional link and the nodes may be scattered in memory. Neither version balances frequent insertions and extractions particularly well.

Implementation 2: Unsorted Array or List

Basics

An unsorted representation stores entries in any convenient order. The array A stores the entries in cells A[0] through A[count - 1], but their positions do not reflect their priority keys.

Insertion simply places a new entry in A[count] and increments count. No existing entries move, and no priority comparisons are needed. The work is postponed until peek or extract must find the best entry.

The order shown in the array has no significance. D happens to be at index 1, but a later insertion with a better key would be appended at the right end. Unless the implementation stores additional information, it must scan the used portion of the array whenever it needs to locate the best entry.

An unsorted linked list uses the same idea. A new entry can be inserted at the head in constant time, but finding the best entry still requires examining the entire list.

How the Operations Work

Insert

To insert an entry, first grow the backing array if it is full. Store the complete entry in A[count], then increment count. Since the representation has no ordering invariant, insertion does not compare keys or move any existing entries.

For example, inserting F:1 into [A:5, D:2, C:7, E:4, B:3] places F:1 in the next unused cell. Although F now has the best key, the implementation does not move it toward the front or record it in a special position.

Peek

To find the best entry, begin by treating A[0] as the best entry found so far. Scan cells A[1] through A[count - 1]. Whenever the current entry is better than the saved entry, remember its index instead. After the scan, peek returns the entry at the remembered index without modifying the array.

For the min-priority queue shown above, the scan compares keys 5, 2, 7, 4, and 3. It finishes with bestIndex = 1, so peek() returns D:2.

Extract

extract first performs the same scan to find bestIndex. It saves the entry at that index so it can be returned. Because the array is unsorted, the gap does not need to be filled by shifting every later entry. Instead, copy the final used entry into A[bestIndex], clear the final used cell, and decrement count.

If the best entry is already in A[count - 1], no copy is necessary; the implementation can simply clear that cell and decrement count. In either case, the removal work after the scan takes constant time.

Unsorted-Array Pseudocode

As before, better(x, y) reports whether entry x should be extracted before entry y. For the min-priority queue used here, an entry with a smaller key is better. 

insert(value, key):
    if count == A.length:
        grow A

    A[count] = (value, key)
    count = count + 1

findBestIndex():
    if count == 0:
        report underflow

    bestIndex = 0

    for i = 1 to count - 1:
        if better(A[i], A[bestIndex]):
            bestIndex = i

    return bestIndex

peek():
    bestIndex = findBestIndex()
    return A[bestIndex]

extract():
    bestIndex = findBestIndex()
    result = A[bestIndex]

    A[bestIndex] = A[count - 1]
    A[count - 1] = empty
    count = count - 1

    return result

Unlike the sorted-array implementation, this representation cannot use array position alone to preserve insertion order among tied keys. Extraction may move the final entry into an earlier cell, changing the physical order of the entries. A stable implementation can store an insertion sequence number in each entry and use it as a secondary comparison when keys tie.

Implementation Analysis

  • insert: \(O(1)\) amortized for a resizable array. Most insertions use one array write, but an occasional resize copies \(O(n)\) entries.
  • peek: \(O(n)\), because the best entry may be in any used cell.
  • extract: \(O(n)\) overall. Finding the best entry requires a linear scan, although filling the resulting gap takes only \(O(1)\) time.
  • isEmpty and size: \(O(1)\) using count.

The resizable array uses \(O(n)\) space overall, although its capacity may exceed the number of entries currently stored. A fixed-size version uses \(O(c)\) space for capacity \(c\) and must report overflow when full.

An unsorted linked list has the same asymptotic operation costs. Inserting at the head takes \(O(1)\), while peek and extract take \(O(n)\). During extraction, the scan must also remember the node preceding the best entry so that the best node can be unlinked. Like the array implementation, the linked-list version uses \(O(n)\) space, but each node also stores a link to the next node.

Tradeoffs

The unsorted representation is a reasonable choice when insertions are much more frequent than peeks or extractions, or when the priority queue remains small. It is also a useful first implementation because its behavior is direct: store each entry immediately, then search for the best entry when it is needed.

Its weakness appears when entries are repeatedly extracted. Extracting all \(n\) entries requires scans of sizes \(n\), \(n-1\), \(n-2\), and so on, for \(\Theta(n^2)\) total work. The sorted implementation performs comparable linear work during insertion instead. Binary heaps provide a better balance by making both insertion and extraction logarithmic.

Library Implementations

In everyday programming, a standard library priority queue is usually preferable to writing one from scratch. Library implementations are tested and efficient. Implementing the simple sorted and unsorted versions by hand is still valuable in a data structures course because it makes the ADT and its cost tradeoffs concrete.

All three library choices are heap-based rather than using the fully sorted or completely unsorted representations developed earlier. Java provides a heap-based priority queue, C++ maintains its underlying container using heap operations, and Python's heapq maintains a heap directly in a list. The next page, Binary Heaps, develops this representation and explains how it supports efficient insertion, inspection, and extraction.

Library defaults matter. Java places the least element first under its default ordering, while C++ places the greatest element first. Python's traditional heapq operations use a min-heap, while corresponding _max operations support max-heaps. Java and C++ customize ordering through comparators; in Python, a comparison key is typically included in each stored entry.

Where traversal is available, it does not necessarily visit entries in priority order. Java's iterator and the list used by Python expose an internal heap arrangement rather than a sorted sequence, while C++'s priority_queue does not provide an iteration interface. To process entries from best to worst, repeatedly use the extraction operation.

Finally, these basic library interfaces do not directly provide the abstract changePriority operation described earlier. A program may need additional position bookkeeping, a different data structure, or a strategy that inserts a replacement entry and later ignores the stale one.

Implementation Cost Summary

The sorted and unsorted implementations both require \(O(n)\) time for one of the main priority queue operations. A sorted array may shift many entries during insertion, while an unsorted array must scan all entries to find the best one during peek or extract. A binary heap avoids making either insertion or extraction linear, providing a more balanced set of operation costs.

Operation Sorted Array Unsorted Array Binary Heap
insert \(O(n)\) \(O(1)\) amortized \(O(\log n)\)
peek \(O(1)\) \(O(n)\) \(O(1)\)
extract \(O(1)\) \(O(n)\) \(O(\log n)\)
isEmpty \(O(1)\) \(O(1)\) \(O(1)\)
size \(O(1)\) \(O(1)\) \(O(1)\)
Storage \(O(n)\) \(O(n)\) \(O(n)\)

The best choice depends on the expected workload. A sorted array works well when insertions are relatively rare but peeks and extractions are frequent. An unsorted array is better when many entries are inserted but the best entry is requested only occasionally. When insertion and extraction are both common, a binary heap usually provides the best general-purpose balance.

In the sorted array, insertion may shift as many as \(n\) entries, but the best entry is always available at the used end. In the unsorted array, insertion usually appends in constant time, but peek and extract must scan the used cells. Resizable arrays may occasionally require \(O(n)\) time to grow, which is why unsorted-array insertion is described as \(O(1)\) amortized.

A binary heap avoids making either insertion or extraction linear. It keeps the best entry in a known position while maintaining only enough order to repair the structure in \(O(\log n)\) time after an insertion or extraction. This balance makes binary heaps the most common general-purpose implementation of priority queues. The next page on Binary Heaps develops this representation in detail. It uses max-heaps to demonstrate the max-oriented convention, although reversing the comparison produces the min-priority queues used on this page.

The linked-list versions of the sorted and unsorted representations have the same asymptotic operation bounds as their array counterparts. Their main differences involve memory layout, allocation overhead, unused array capacity, and the mechanics of insertion and removal.

Balanced search trees can also implement priority queues and may be useful when a program needs additional operations, such as searching for arbitrary keys or traversing all entries in sorted order. More specialized priority-queue structures make other tradeoffs, but binary heaps are the usual next step.

Applications

A priority queue is useful when a changing set of candidates must be processed one at a time according to a rank, cost, time, or urgency. The priority queue does not decide what "best" means; the application supplies the comparison rule.

  • Event simulation: Future events are stored using their scheduled times as priority keys. The event with the earliest time is extracted next, and processing it may insert additional future events.
  • Scheduling and service systems: Jobs, requests, or patients may be prioritized by urgency, deadline, estimated running time, or a combination of fields. A priority queue implements the selection rule, although additional policies may be needed to prevent low-priority entries from waiting indefinitely.
  • Graph and search algorithms: Dijkstra's shortest-path algorithm selects the unsettled vertex with the smallest known distance, Prim's algorithm selects a cheapest next connection, and best-first search selects the most promising state. These algorithms may need to update an entry's priority when better information is discovered.
  • Building a Huffman code: Huffman's algorithm repeatedly extracts the two items with the smallest frequencies, combines them, and inserts the combined item with its new frequency.
  • Merging sorted sequences: To merge several sorted lists or streams, place the smallest unprocessed item from each source in a min-priority queue. When an item is extracted, add the next item from the source it came from. Repeating this process produces all the items in sorted order.
  • Keeping the best \(k\) candidates: A bounded priority queue can retain the best \(k\) items seen in a stream without storing the entire stream. To retain the \(k\) largest values, for example, a min-priority queue provides quick access to the smallest retained value so that a better incoming value can replace it.

Common Pitfalls

Most priority-queue mistakes come from leaving the ordering rule implicit, assuming guarantees the ADT does not provide, or confusing the ADT with a particular representation.

  • Mixing min and max conventions: State whether smaller or larger keys represent better priority before tracing operations or configuring a library comparison rule.
  • Assuming equal priorities are FIFO: A priority queue is stable only if its specification or implementation provides an appropriate tie-breaking rule. Do not assume equal-key entries leave in insertion order.
  • Separating values from their keys: Move or copy each complete entry. If values and priority keys are stored in parallel arrays, every shift or replacement must update both arrays consistently.
  • Removing from the wrong end of a sorted array: In the layout used on this page, the best entry must be stored at the right end so that extraction does not shift the remaining entries. Storing it at the left end would make extraction linear.
  • Shifting an unsorted array unnecessarily: Because the representation has no ordering invariant, fill an extracted entry's gap with the final used entry instead of shifting all later entries.
  • Forgetting underflow: Both peek and extract need documented behavior when the priority queue is empty.
  • Assuming iteration follows priority order: A library priority queue may expose its entries without promising sorted traversal. Repeated extraction is the operation that guarantees priority order.
  • Changing a stored priority directly: Mutating a field used by the comparison rule may invalidate the representation's invariants or bookkeeping. Use a supported priority-change operation, or remove and reinsert the entry.

Summary

A priority queue stores entries containing values and priority keys and makes the best entry available next. A min-priority queue treats a smaller key as better, while a max-priority queue treats a larger key as better. The essential operations are insert, peek, and extract.

A sorted array uses \(O(n)\) insertion to provide \(O(1)\) peek and extract. An unsorted array provides \(O(1)\) amortized insertion but requires \(O(n)\) time for peek or extract. Linked-list versions make the same broad time tradeoffs with different memory layouts and allocation overhead. A binary heap provides a more balanced alternative, with \(O(1)\) peek and \(O(\log n)\) insertion and extraction.

The examples on this page use min-priority queues, but the comparisons in each implementation can be reversed to support max-priority queues. The next page on Binary Heaps develops the heap representation in detail and uses max-heaps to demonstrate the max-oriented convention.

  7. Unsorted Extraction: Why can the final used array entry be copied into the gap left by an extracted entry?

  1. Answer: A priority queue removes the entry selected as best by its priority rule. A FIFO queue instead removes the entry that arrived earliest, regardless of its key.
  2. Answer: A min-priority queue treats the entry with the smallest key as best. A max-priority queue treats the entry with the largest key as best.
  3. Answer: Both operations identify the entry selected by the priority rule. peek leaves that entry in the priority queue, while extract removes it.
  4. Answer: A stable priority queue extracts equal-key entries in their insertion order. One general implementation method is to store an increasing sequence number with each entry and use it to break ties.
  5. Answer: Removing the final used array entry does not shift any remaining entries. Keeping the best entry there therefore allows extract to run in \(O(1)\) time.
  6. Answer: Binary search can locate the insertion position using \(O(\log n)\) comparisons, but as many as \(n\) existing entries may still need to shift to open that position.
  7. Answer: The unsorted representation has no required order. Replacing the extracted entry with the final used entry therefore does not violate its representation invariant.
  8. Answer: The unsorted array is usually better. Its \(n\) insertions take \(O(n)\) total amortized time, and the single extraction takes \(O(n)\), for \(O(n)\) total time. Sorted-array insertion could take \(O(n^2)\) total time.
  9. Answer: A binary heap provides \(O(1)\) peek and \(O(\log n)\) insertion and extraction. Thus, neither insertion nor extraction requires the \(O(n)\) time needed by one of the two simple implementations.
  10. Answer: The priority-queue ADT guarantees which entry is returned by peek or extract, not the physical order of all stored entries. A heap-based library may expose its internal heap arrangement rather than a sorted sequence.
