Heap Construction and Heapsort

Overview

Given an array of values, there are two natural ways to build a binary heap:

  1. Repeated insertion: begin with an empty heap and insert the values one at a time, using siftUp after each insertion.
  2. Bottom-up construction: treat the array as a complete binary tree and apply siftDown to its internal nodes, working from the bottom of the tree toward the root.

Both methods produce a valid heap, but they do not take the same amount of time. Repeated insertion takes \(O(n \log n)\) time in the worst case. Bottom-up construction, usually called buildMaxHeap for a max-heap, reorganizes the existing array in \(\Theta(n)\) time.

This page first develops bottom-up heap construction and explains why its running time is linear. It then uses the resulting max-heap to perform Heapsort, which repeatedly moves the maximum remaining value into its final position.

The discussion assumes familiarity with the array representation of a binary heap and with siftUp and siftDown. These are developed on the Binary Heaps page.

siftDown with an Active Heap Size

The Binary Heaps page defines siftDown(H, i) for a heap object whose logical size is stored in H.size. Heap construction and Heapsort use the same repair process, but they operate directly on an array. In addition, Heapsort gradually shrinks the active heap while leaving the sorted values in the same array. We therefore use a modified version of siftDown that passes the active heap size explicitly: siftDown(A, i, heapSize).

Only indices 0 through heapSize - 1 belong to the heap. During bottom-up construction, heapSize is the full array length. During Heapsort, it decreases as values are moved into the sorted suffix. 

siftDown(A, i, heapSize):
    while leftChild(i) < heapSize:
        left = leftChild(i)
        right = rightChild(i)
        largerChild = left

        if right < heapSize and A[right] > A[left]:
            largerChild = right

        if A[i] >= A[largerChild]:
            return

        swap(A[i], A[largerChild])
        i = largerChild

This is the same downward-repair algorithm used for an ordinary binary heap. The only differences are that it uses the supplied heapSize rather than a size stored in a heap object and explicitly implements max-heap order using direct value comparisons.

Bottom-Up Heap Construction

Bottom-up construction views the array as a complete binary tree and builds valid heaps from the leaves toward the root. A leaf contains only one entry, so it already forms a valid heap. The algorithm can therefore begin with the lowest internal nodes and use those one-entry heaps as the base from which larger heaps are formed.

In a zero-based array of length \(n\), the node at index \(i\) has a left child only when \(2i+1<n\). It follows that the internal nodes occupy indices \(0\) through \(\lfloor n/2\rfloor-1\), while indices \(\lfloor n/2\rfloor\) through \(n-1\) are leaves. Since the leaves need no repair, the first node processed is the last internal node, at index \(\lfloor n/2\rfloor-1\).

The internal nodes are then processed in decreasing index order. Every child has a larger index than its parent, so by the time the algorithm reaches index \(i\), the subtrees rooted at its children have already been made into heaps. The precondition for siftDown is therefore satisfied: only the entry at index \(i\) may violate heap order. After siftDown finishes, the entire subtree rooted at \(i\) is a heap.

Processing the nodes from the root toward the leaves would not give the same guarantee. A child subtree repaired later could move a larger entry to its root and create a new violation with its parent. By processing children before parents, bottom-up construction ensures that each subtree is repaired once its smaller component heaps are already complete.

Example 1: Why a Forward Pass Fails

Consider the array [1, 2, 3, 4, 5, 6, 7]. Suppose we try to build a max-heap by processing the internal nodes from left to right, starting at the root.

After processing index 1, the subtree rooted there is a heap, but the whole tree is not: the root still violates max-heap order. A forward pass therefore does not work, because repairing a child subtree later can create a new violation above it.

The resulting algorithm is very simple: 

buildMaxHeap(A):
    n = length(A)

    for i = floor(n / 2) - 1 down to 0:
        siftDown(A, i, n)

After each iteration, the subtree rooted at index \(i\) is a max-heap. When index 0 has been processed, the subtree rooted at the root is the entire tree, so the whole array is a max-heap.

Heapsort

Heapsort turns the maximum-selection property of a max-heap into an in-place sorting algorithm. After buildMaxHeap finishes, the largest value in the array is at the root. Rather than removing that value from the array, Heapsort swaps it with the final value in the active heap. The maximum is then in its final sorted position.

The algorithm decreases heapSize so that this completed position is no longer part of the heap. The value moved to the root may violate max-heap order, but both of its child subtrees are still heaps, so one call to siftDown restores the active heap.

Repeating these steps places the remaining maximum values from right to left. The active heap shrinks by one position during each iteration while a sorted suffix grows at the end of the same array. When only one active value remains, the entire array is in nondecreasing order. 

heapsort(A):
    buildMaxHeap(A)
    heapSize = length(A)

    for end = length(A) - 1 down to 1:
        swap(A[0], A[end])
        heapSize = heapSize - 1
        siftDown(A, 0, heapSize)

One Array, Two Regions

During Heapsort, the array is divided into an active max-heap and a sorted suffix. The boundary between them moves one position to the left after each root swap.

Every child-bound check made by siftDown must use heapSize. Using the full array length would allow values from the completed suffix to reenter the active heap.

Time/Space Analysis

A naive analysis gives an \(O(n\log n)\) bound for bottom-up heap construction: there are \(\Theta(n)\) internal nodes, and each call to siftDown takes at most \(O(\log n)\) time. This bound is valid but not tight because most calls begin near the leaves and cannot move that far. About half of the nodes are leaves and require no work, about one quarter can move down at most one level, about one eighth can move down at most two levels, and progressively fewer nodes can move farther. These decreasing amounts of work add to \(\Theta(n)\), as shown in more detail in the Advanced Analysis section.

Heapsort performs the \(\Theta(n)\) construction phase once. It then performs \(n-1\) root swaps and downward repairs. Although the active heap gradually shrinks, every repair begins at its root, and each takes at most \(O(\log n)\) time. The sorting phase therefore takes \(O(n\log n)\) time. Because Heapsort is a comparison-based sorting algorithm, the \(\Omega(n\log n)\) worst-case lower bound for comparison sorting also applies. Its worst-case running time is therefore \(\Theta(n\log n)\).

Although the active heap gradually shrinks, every repair begins at its root rather than at nodes of different heights. Moreover, during the first \(n/2\) passes, the active heap still contains at least \(n/2\) entries and has height \(\Theta(\log n)\). Each of those repairs can therefore take \(\Theta(\log n)\) time in the worst case. The complete algorithm takes \(O(n\log n)\) time, with a worst-case running time of \(\Theta(n\log n)\).

With iterative siftDown, both algorithms use \(\Theta(1)\) auxiliary space beyond the input array. A recursive helper instead uses \(O(\log n)\) call-stack space. Heapsort is therefore an in-place sorting algorithm, but it is not stable: swaps between distant positions can reverse the relative order of entries with equal keys.

Advanced Analysis

Why Bottom-Up Construction Is Linear

A simple analysis observes that there are fewer than \(n/2\) internal nodes and that one call to siftDown takes at most \(O(\log n)\) time. Multiplying these bounds gives \(O(n\log n)\). This is a valid upper bound, but it is not tight because it treats every internal node as though it were the root of the entire tree.

The cost of a call depends on the height of the subtree where it begins. Nodes near the bottom can move only a short distance:

Location Approximate Number of Nodes Maximum Downward Movement Maximum Total Work
Leaves \(n/2\) 0 levels 0
Parents of leaves \(n/4\) 1 level \(n/4\)
Height 2 \(n/8\) 2 levels \(2n/8\)
Height 3 \(n/16\) 3 levels \(3n/16\)
Height \(h\) At most about \(n/2^{h+1}\) \(h\) levels At most about \(hn/2^{h+1}\)

Thus, apart from constant work performed by each call, the total number of possible downward steps is bounded by

\[ \frac{n}{4} + 2\left(\frac{n}{8}\right) + 3\left(\frac{n}{16}\right) + 4\left(\frac{n}{32}\right) + \cdots = n\sum_{h=1}^{\infty}\frac{h}{2^{h+1}}. \]

This infinite sum can be evaluated directly. Let

\[ T=\sum_{h=1}^{\infty}\frac{h}{2^h} =\frac12+\frac24+\frac38+\frac4{16}+\cdots. \]

Dividing by \(2\) and subtracting gives

\[ \begin{aligned} T-\frac{T}{2} &= \left(\frac12+\frac24+\frac38+\cdots\right) - \left(\frac14+\frac28+\frac3{16}+\cdots\right)\\ &= \frac12+\frac14+\frac18+\cdots\\ &=1. \end{aligned} \]

Therefore \(T=2\), and

\[ \sum_{h=1}^{\infty}\frac{h}{2^{h+1}} =\frac{T}{2} =1. \]

The idealized series evaluates to \(n\), showing that the total number of downward steps is bounded by a constant multiple of \(n\), even for an incomplete final level. The algorithm also makes \(\Theta(n)\) calls with constant overhead, so bottom-up heap construction takes \(\Theta(n)\) time.

The important point is not merely that each call is fast. It is that calls capable of traveling many levels are rare. Only the root can travel the full height, only a few nodes can travel almost that far, and most calls can move at most one or two levels.

Why Repeated Insertion Is Different

The alternative construction method inserts the values one at a time into an initially empty heap. The \(i\)th insertion begins at a new leaf and may move upward through a heap of height \(\Theta(\log i)\). Thus, the total cost of inserting the values one at a time is

\[ \sum_{i=1}^{n} O(\log i) = O\left(\log(n!)\right). \]

This quantity is \(\Theta(n\log n)\). For the upper bound, \(n!\leq n^n\), so \(\log(n!)\leq n\log n\). For the lower bound, the final \(n/2\) factors of \(n!\) are each at least \(n/2\), giving

\[ \log(n!) \geq \log\left(\left(\frac n2\right)^{n/2}\right) = \frac n2\log\left(\frac n2\right) = \Theta(n\log n). \]

Hence, \(\log(n!)=\Theta(n\log n)\).

This bound is attained in the worst case. If distinct values are inserted into a max-heap in increasing order, each new value is larger than every value already present and rises from its new leaf position to the root. The \(i\)th insertion therefore takes \(\Theta(\log i)\) time, so the total running time is \(\Theta(\log(n!))=\Theta(n\log n)\).

The two methods distribute their work differently. Bottom-up construction starts at existing nodes and charges each one according to its height; most nodes have very small height. Repeated insertion starts each new value at a leaf and may move it according to its depth; most later leaves have logarithmic depth. This difference allows bottom-up construction to run in linear time while repeated insertion can require \(\Theta(n\log n)\).

Comparisons and Tradeoffs

  • Bottom-up construction versus repeated insertion: both methods produce a valid heap, but bottom-up construction takes \(\Theta(n)\) time, while inserting all values individually can require \(\Theta(n\log n)\) time. Repeated insertion remains appropriate when values arrive over time rather than being available together in an array.
  • Compared with Quicksort: Heapsort guarantees \(\Theta(n\log n)\) worst-case time, whereas basic Quicksort has an \(O(n^2)\) worst case. In practice, however, well-chosen Quicksort implementations are usually faster. After Heapsort moves the maximum to the end of the array, the value swapped into the root comes from the final position of the active heap. That position is a leaf, so its value is often relatively small compared with values near the top of the heap. It may therefore travel through many levels during siftDown, causing several comparisons and swaps. These accesses also jump among array positions that are increasingly far apart. Quicksort instead performs much of its work through sequential scans of contiguous array regions, typically giving it better memory locality and smaller practical constant factors.
  • Compared with Mergesort: both algorithms guarantee \(\Theta(n\log n)\) running time. Heapsort uses only \(\Theta(1)\) auxiliary space when implemented iteratively, while the usual array-based Mergesort requires \(\Theta(n)\) auxiliary space. Mergesort is stable and usually has more sequential memory access; Heapsort is not stable.

Common Pitfalls

  • Beginning at the wrong index: leaves are already one-entry heaps and need no repair. In a zero-based array, bottom-up construction begins at the last internal node, \(\lfloor n/2\rfloor-1\).
  • Processing nodes from the root downward: siftDown assumes that both child subtrees are already heaps. Processing internal nodes in decreasing index order establishes this condition before each call.
  • Using the full array length during Heapsort: only indices below heapSize belong to the active heap. Using the full length in child-bound checks can move values from the sorted suffix back into the heap.
  • Using the wrong heap boundary: after swapping the root with A[end], the active heap contains indices 0 through end - 1. Thus, end is the new heapSize.
  • Skipping downward repair: the value moved from the end of the active heap to the root may be smaller than one of its children. Heap order must be restored with siftDown before the next pass.
  • Claiming stability: Heapsort swaps entries across distant positions, so equal-key entries need not remain in their original relative order.
  • Stopping at the loose construction bound: multiplying \(\Theta(n)\) internal nodes by the maximum \(O(\log n)\) cost of one repair gives a valid \(O(n\log n)\) bound, but most nodes can move only one or two levels. The tighter bound for bottom-up construction is \(\Theta(n)\).

Summary

An array can be converted into a heap either by repeated insertion or by bottom-up construction. Bottom-up construction treats every leaf as an existing one-entry heap, then processes the internal nodes in decreasing index order. When a node is reached, its child subtrees are already heaps, so siftDown can make the larger subtree rooted there into a heap. Although a naive analysis gives an \(O(n\log n)\) bound, the tighter running time is \(\Theta(n)\) because most nodes are near the leaves and can move down only a small number of levels.

Heapsort first builds a max-heap and then repeatedly swaps the root with the final entry in the active heap. Each swap places the largest remaining value into a growing sorted suffix. The active heap boundary moves left, and siftDown restores heap order within the remaining prefix. Heapsort runs in \(\Theta(n\log n)\) worst-case time and uses \(\Theta(1)\) auxiliary space with iterative downward repair. It is therefore in place, but it is not stable and is often slower in practice than Quicksort because of its repeated long downward repairs and less sequential memory access.
