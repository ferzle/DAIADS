Heap Construction and Heapsort

Overview

Sometimes values arrive one at a time, making ordinary heap insertion the natural update. In other situations, all values are already present in an array. Repeated insertion will produce a valid heap, but a bottom-up method can reorganize the entire array more efficiently.

This page develops two algorithms: buildMaxHeap, which converts an arbitrary array into a max-heap in place, and Heapsort, which repeatedly uses that heap to place values into sorted order. Both rely on the array representation and downward repair from the Binary Heaps page.

Downward Repair Review

The helper siftDown(A, i, heapSize) assumes that the left and right child subtrees of index i are already max-heaps. Only A[i] may be too small. The helper repeatedly swaps that value with its larger child until the max-heap property is restored. 

siftDown(A, i, heapSize):
    while true:
        largest = i
        left = 2 * i + 1
        right = 2 * i + 2

        if left < heapSize and A[left] > A[largest]:
            largest = left
        if right < heapSize and A[right] > A[largest]:
            largest = right

        if largest == i:
            return

        swap(A[i], A[largest])
        i = largest

A call can move through at most the height of the subtree rooted at \(i\). Its cost is therefore \(O(h_i)\), where \(h_i\) is that subtree’s height, and at most \(O(\log n)\) for the root.

Bottom-Up Heap Construction

In an \(n\)-entry heap array, every index from \(\lfloor n/2\rfloor\) through \(n-1\) is a leaf. A leaf is already a valid one-node heap, so no work is needed there. The last possible internal node is \(\lfloor n/2\rfloor-1\).

Starting at that node, process internal nodes from right to left toward the root. When index \(i\) is reached, both child subtrees have already been repaired, exactly satisfying the precondition of siftDown. After the root is processed, the entire array is a max-heap. 

buildMaxHeap(A):
    n = length(A)
    for i = floor(n / 2) - 1 down to 0:
        siftDown(A, i, n)

Worked example

Consider [4, 10, 3, 5, 1]. Indices 2 through 4 are leaves, so processing begins at index 1.

  1. Index 1 contains 10; its children are 5 and 1, so no swap is needed.
  2. Index 0 contains 4. Swap it with the larger child 10, giving [10, 4, 3, 5, 1].
  3. Continue downward from index 1. Swap 4 with 5, producing [10, 5, 3, 4, 1].

The final array is a max-heap. The algorithm changed values in place and did not allocate tree nodes or a second array.

Heapsort

Once an array is a max-heap, its largest value is at index 0. Swap that value with the final entry in the active heap. The maximum is now in its final sorted position. Reduce heapSize so the sorted suffix is no longer considered part of the heap, then repair the new root.

Repeating this process moves maxima from right to left. When only one active entry remains, the entire array is in nondecreasing order. 

heapsort(A):
    buildMaxHeap(A)
    heapSize = length(A)

    for end = length(A) - 1 down to 1:
        swap(A[0], A[end])
        heapSize = heapSize - 1
        siftDown(A, 0, heapSize)

Heap prefix and sorted suffix

During sorting, the same physical array represents two regions:

  • A[0 .. heapSize-1] is the active max-heap, and
  • A[heapSize .. n-1] is a sorted suffix in final positions.

Every child-bound check must use heapSize. Using the full array length would pull completed values back into the heap.

Time/Space Analysis

Bottom-up heap construction runs in \(\Theta(n)\) time. This result is sharper than multiplying the number of internal nodes by the maximum cost of one downward repair; the next section explains why.

Heapsort performs the linear construction phase once. It then performs \(n-1\) root swaps and downward repairs. Each repair costs at most \(O(\log n)\), so the complete algorithm takes \(O(n\log n)\) time, with a worst-case bound of \(\Theta(n\log n)\).

With iterative siftDown, both algorithms use \(\Theta(1)\) auxiliary space beyond the input array. A recursive helper adds \(O(\log n)\) call-stack space. Heapsort is in place, but it is not stable: root swaps can reverse equal-key entries that were far apart.

Advanced Analysis

Why the obvious \(O(n\log n)\) bound is loose

There are about \(n/2\) internal nodes, and one call to siftDown can cost \(O(\log n)\). Multiplying these values gives \(O(n\log n)\), which is a valid upper bound but treats every call as though it began at the root. Most calls begin much lower.

At most about \(n/2^{h+1}\) nodes have height \(h\). A node of height \(h\) can move down at most \(h\) levels, so the total work is bounded by

\[ \sum_{h=1}^{\lfloor\log n\rfloor} \frac{n}{2^{h+1}}\,O(h) = O(n)\sum_{h=1}^{\infty}\frac{h}{2^{h+1}} = O(n). \]

The infinite series converges to a constant. Intuitively, half the nodes are leaves and are skipped, about one quarter can move down only one level, about one eighth can move two levels, and only a tiny number can travel near the full height. The loop also examines \(\Theta(n)\) internal nodes in total, so the complete running time is \(\Theta(n)\).

Why \(n\) insertions do not receive the same bound

Inserting the values one at a time into an initially empty max-heap costs at most \[ \sum_{i=1}^{n} O(\log i)=O(\log(n!))=O(n\log n). \] Unlike the bottom-up method, this upper bound is tight in the worst case. Insert keys in increasing order. Every new key is larger than all earlier keys, so it rises from its new leaf position to the root. Its cost is \(\Theta(\log i)\).

Even after accounting for the smaller early heaps, a constant fraction of the insertions occur when \(i\) lies between \(n/2\) and \(n\). Each of those heaps has height \(\Theta(\log n)\), and each insertion in this input travels that height. Their total alone is \(\Theta(n\log n)\).

The difference is where the work begins. Bottom-up repair charges each existing node according to its height, and most nodes have very small height. Insertion always begins at a new leaf and may travel according to its depth; most later leaves have logarithmic depth. Both methods produce a valid heap, but they distribute work very differently.

Why the Algorithms Work

Bottom-up construction processes nodes in an order that maintains a simple invariant: before index \(i\) is repaired, both of its child subtrees are heaps. Downward repair then makes the subtree rooted at \(i\) a heap without disturbing already processed descendants. After index 0, the whole array satisfies heap order.

During Heapsort, the active prefix is a max-heap and the suffix contains the largest removed values in sorted order. Swapping the root with the last active entry places the largest remaining value immediately before that suffix. Downward repair restores the prefix invariant, so the argument repeats until no unsorted entries remain.

Common Pitfalls

  • Starting at a leaf: leaves need no repair; begin at \(\lfloor n/2\rfloor-1\).
  • Processing top-down: a parent cannot use downward repair safely until its child subtrees are heaps.
  • Using array length during sorting: the sorted suffix is outside the active heap.
  • Skipping the root repair: every root swap can violate heap order at index 0.
  • Claiming stability: in-place root swaps do not preserve the order of equal keys.
  • Stopping at the loose bound: \(O(n\log n)\) is true for construction but fails to describe its tighter \(\Theta(n)\) cost.

Summary

Bottom-up construction treats leaves as finished heaps and repairs internal nodes toward the root, producing a heap in linear time. Heapsort first performs that construction, then repeatedly moves the root into a growing sorted suffix. It sorts in place in \(\Theta(n\log n)\) time. The construction phase is linear because most nodes can move only a short distance; repeated insertion has no matching worst-case improvement because many inserted leaves may travel a logarithmic distance.

Reading Comprehension Questions

  1. Why are leaves omitted from the bottom-up loop?
  2. Why are internal nodes processed from right to left toward the root?
  3. What do heapSize and the physical array length mean during Heapsort?
  4. Why is \(O(n\log n)\) a valid but loose bound for bottom-up construction?
  5. What property of the tree makes the sharper construction bound linear?
  6. Why can increasing-order insertion into a max-heap require \(\Theta(n\log n)\) total time?
  7. Why is Heapsort not stable?
  1. Every leaf is already a valid one-entry heap.
  2. That order ensures both child subtrees are heaps before their parent is repaired.
  3. The logical size ends at the active heap prefix; the physical array also includes the completed suffix.
  4. It assigns the root’s maximum repair cost to every internal node, including nodes near the leaves.
  5. The number of nodes decreases exponentially as subtree height increases.
  6. Each new key is the largest so far and can rise from a deep leaf all the way to the root.
  7. Long-distance root swaps can reverse the relative order of equal-key entries.

In-Class Activities

  1. Bottom-Up Trace: Mark leaves and internal nodes, then record the array after each downward repair.
  2. Two-Region Trace: During Heapsort, color the active heap prefix and sorted suffix after every iteration.
  3. Loose-Bound Diagnosis: Identify which calls in a small construction trace cannot possibly take logarithmic time.
  4. Method Comparison: Create the same heap by bottom-up repair and repeated insertion, then count comparisons and swaps.

  7. Stability Investigation: Find a small input with duplicate keys whose relative order changes during Heapsort.
