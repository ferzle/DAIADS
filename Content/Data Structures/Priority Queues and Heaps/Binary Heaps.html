Binary Heaps

Overview

A binary heap is a tree-shaped data structure that keeps one extreme entry—the minimum or maximum—easy to access. It combines two rules: the tree has a complete shape, and every parent has at least as much priority as its children. Those rules are weak enough to maintain efficiently but strong enough to place the best entry at the root.

It is helpful to separate interface from representation. A priority queue is the abstract data type: it specifies operations such as insertion, inspecting the best entry, and removing the best entry. A binary heap is a concrete data structure that implements that interface. People sometimes speak informally of the “heap ADT” because a heap object exposes the same operations, but the important distinction is that the priority queue describes what clients may do while the binary heap describes how those operations are represented and maintained.

This page develops max-heaps, where larger keys have higher priority. Min-heaps use exactly the same structure and algorithms with the comparisons reversed. For the priority-queue interface and other implementation choices, review the Priority Queues page.

Structure and Invariants

Every valid binary heap satisfies a shape invariant and an order invariant. An operation is not finished until both are true.

Complete-tree shape

The heap is a complete binary tree: every level is full except possibly the last, and the last level is occupied from left to right. Consequently, a heap with \(n\) entries has height \(\lfloor\log_2 n\rfloor\). There is only one legal position for the next inserted entry and only one leaf that can be removed without creating a gap.

Heap order

  • In a max-heap, each parent’s key is greater than or equal to the keys of its children.
  • In a min-heap, each parent’s key is less than or equal to the keys of its children.

The rule is local, but it implies that the root is globally best. It does not order siblings or entries in different branches, and a heap should never be mistaken for a sorted array or a binary search tree. 

        90
      /    \
    72      85
   /  \    /  \
  31  60  40  10

This is a valid max-heap. Every parent dominates its children, even though values such as 72 and 85 do not appear in sorted order from left to right.

Array Representation

Completeness lets a binary heap use an array instead of linked tree nodes. Store the nodes in level order: root first, then each level from left to right. With zero-based indexing, the relatives of index \(i\) are:

  • left child: \(2i+1\),
  • right child: \(2i+2\), and
  • parent, when \(i>0\): \(\lfloor(i-1)/2\rfloor\).

For the example above, the array is [90, 72, 85, 31, 60, 40, 10]. The children of index 2 are at indices 5 and 6, and its parent is at index 0.

A resizable implementation stores both a backing array and a logical size. Only indices 0 through size - 1 belong to the heap; later cells are unused capacity. Child tests must therefore compare against size, not the physical array length.

Core Operations

The public operations match the priority-queue interface. The table uses max-heap names to make the selected extreme explicit; a generic class could instead use names such as peekBest and extractBest.

Operation Behavior Worst-Case Time
isEmpty() Report whether the logical size is zero. \(\Theta(1)\)
size() Return the number of stored entries. \(\Theta(1)\)
peekMax() Return the root without removing it. \(\Theta(1)\)
insert(entry) Add one entry and repair upward. \(O(n)\) on a resize; \(O(\log n)\) amortized
extractMax() Remove the root and repair downward. \(O(\log n)\)

Two private helpers do the structural repair. siftUp moves a newly inserted entry toward the root, while siftDown moves a replacement root toward the leaves. These helpers are implementation mechanisms, not additional priority-queue operations exposed to clients.

How the Operations Work

Inspecting the maximum

In a nonempty max-heap, the heap property guarantees that the maximum is at index 0. Inspection therefore requires no traversal. The implementation must still define an empty-heap policy, such as returning an optional result or raising an exception.

Insertion and upward repair

To preserve completeness, append the new entry at index size. The old heap remains valid, so the only possible order violation lies between the new leaf and its parent. Compare those two entries and swap while the child has higher priority.

For example, insert 88 into [90, 72, 85, 31, 60, 40, 10]. It first occupies index 7. It swaps with 31, then with 72, and stops below 90: 

[90, 72, 85, 31, 60, 40, 10, 88]
[90, 72, 85, 88, 60, 40, 10, 31]
[90, 88, 85, 72, 60, 40, 10, 31]

Downward repair with siftDown

Downward repair begins at an index whose left and right child subtrees are already valid heaps. Only the entry at that index may violate heap order. Compare it with both children, swap it with the higher-priority child when necessary, and continue from that child's index. The process stops at a leaf or when the entry already dominates both children.

This precondition matters: siftDown repairs one root-to-leaf path, not arbitrary disorder throughout a subtree. The demo lets you change one entry and follow each comparison and swap in the repair.

Extraction and downward repair

Removing the root directly would leave a gap at the top. Instead, save the root for return, move the final used entry to index 0, reduce the size, and repair downward. At each step, compare both children and swap with the higher-priority child. Choosing merely the left child can leave a violation with the right child.

Extracting 90 from [90, 72, 85, 31, 60, 40, 10] moves 10 to the root. It then swaps with 85 and finally with 40: 

[10, 72, 85, 31, 60, 40]
[85, 72, 10, 31, 60, 40]
[85, 72, 40, 31, 60, 10]

Pseudocode Implementation

The following pseudocode describes a max-heap backed by a resizable array. A min-heap changes only higherPriority. A stable priority queue can compare entries first by key and then by an insertion sequence number, as discussed on the Priority Queues page.

Index and comparison helpers

parent(i):
    return floor((i - 1) / 2)

leftChild(i):
    return 2 * i + 1

rightChild(i):
    return 2 * i + 2

higherPriority(first, second):
    return first.key > second.key

Basic queries

isEmpty(H):
    return H.size == 0

size(H):
    return H.size

peekMax(H):
    if H.size == 0:
        signal EMPTY_HEAP
    return H.A[0]

Insertion

insert(H, entry):
    if H.size == length(H.A):
        doubleCapacity(H.A)

    H.A[H.size] = entry
    H.size = H.size + 1
    siftUp(H, H.size - 1)

siftUp(H, i):
    while i > 0:
        p = parent(i)
        if not higherPriority(H.A[i], H.A[p]):
            return
        swap(H.A[i], H.A[p])
        i = p

Downward repair

siftDown(H, i):
    while true:
        best = i
        left = leftChild(i)
        right = rightChild(i)

        if left < H.size and higherPriority(H.A[left], H.A[best]):
            best = left
        if right < H.size and higherPriority(H.A[right], H.A[best]):
            best = right

        if best == i:
            return

        swap(H.A[i], H.A[best])
        i = best

Extraction

extractMax(H):
    if H.size == 0:
        signal EMPTY_HEAP

    best = H.A[0]
    H.size = H.size - 1

    if H.size > 0:
        H.A[0] = H.A[H.size]
        H.A[H.size] = EMPTY
        siftDown(H, 0)
    else:
        H.A[0] = EMPTY

    return best

Time/Space Analysis

A complete tree has logarithmic height. Both repair helpers follow only one path, so insertion and extraction take \(O(\log n)\) time in the worst case. Inspection, size, and emptiness checks use stored fields or the root and therefore take \(\Theta(1)\) time.

The heap stores \(n\) entries in \(\Theta(n)\) array space. Iterative repair uses \(\Theta(1)\) auxiliary space. A recursive downward repair instead consumes \(O(\log n)\) call-stack space. Array growth makes an occasional insertion take \(\Theta(n)\), but doubling capacity keeps insertion \(O(\log n)\) amortized because the logarithmic repair already dominates the constant amortized resizing cost.

Finding an arbitrary entry by value or key is still \(O(n)\). Heap order tells us where the best entry is, not where a particular non-root entry is. Applications needing fast arbitrary search often maintain a separate map from identifiers to heap indices.

Applications

  • Scheduling: choose the most urgent waiting job while allowing new jobs to arrive.
  • Graph algorithms: min-heaps commonly select the next lowest-cost vertex in shortest-path and minimum-spanning-tree methods.
  • Event simulation: process the event with the earliest scheduled time.
  • Top-\(k\) selection: keep a small heap of the best values observed in a much larger stream.
  • Huffman encoding: repeatedly obtain the two lowest-frequency trees from a min-priority queue.

Comparisons and Tradeoffs

  • Compared with a sorted array: both expose the best entry in constant time, but the heap avoids linear shifting during insertion.
  • Compared with an unsorted array: the heap spends more time inserting but avoids a linear scan during inspection or removal.
  • Compared with a balanced search tree: the heap is compact and specializes in an extreme entry; a search tree supports arbitrary ordered search and traversal.
  • Compared with linked trees: the array representation avoids child references and usually has good cache locality.

Variations and Extensions

  • Min-heaps: reverse the priority comparison.
  • d-ary heaps: use more children per node, reducing height while increasing child comparisons during downward repair.
  • Indexed heaps: maintain identifier-to-index mappings to support priority changes efficiently.
  • Meldable heap families: binomial, Fibonacci, and pairing heaps support different operation tradeoffs, especially when merging is important.

Common Pitfalls

  • Assuming total order: only parent-child order is guaranteed.
  • Mixing index conventions: zero-based and one-based heaps use different formulas.
  • Using capacity as size: unused array cells are not heap entries.
  • Choosing the wrong child: downward repair must compare both children.
  • Repairing in the wrong direction: insertion repairs upward; root replacement repairs downward.
  • Ignoring ties: a stable priority queue needs an explicit and consistently applied tie policy.
  • Forgetting empty behavior: inspection and extraction need a documented empty-heap policy.

Summary

A binary heap is a complete binary tree stored compactly in an array. Its local heap-order rule places the best entry at the root without fully ordering the remaining entries. As a priority-queue implementation, it provides constant-time inspection and logarithmic insertion and extraction using upward and downward path repairs.

Reading Comprehension Questions

  1. What is the difference between the priority-queue ADT and a binary heap?
  2. Why does completeness allow a binary heap to omit child references?
  3. What does max-heap order guarantee, and what does it leave unordered?
  4. Why can inspection return the maximum in constant time?
  5. Why does insertion repair upward rather than downward?
  6. Why must extraction compare both children during downward repair?
  7. Why is arbitrary search still linear in the worst case?
  1. The ADT specifies priority-based behavior; the heap is one concrete representation that provides it.
  2. A complete tree has no interior gaps, so level-order positions map to contiguous array indices.
  3. Each parent dominates its children and the root is maximum; siblings and separate branches need not be ordered.
  4. The maximum is always the root at index 0.
  5. The new entry is appended as a leaf, so only its ancestor path can contain a new violation.
  6. Swapping with the lower-priority child could leave a violation with the other child.
  7. Heap order identifies an extreme entry but provides no search direction for an arbitrary key.

In-Class Activities

  1. Index Mapping: Translate a seven-entry heap between array and tree views, labeling every parent and child index.
  2. Validity Check: Decide whether several arrays represent max-heaps and identify the first violated edge in each invalid example.
  3. Insertion Trace: Insert values that move zero levels, one level, and all the way to the root.
  4. Extraction Trace: Remove the root and record both child comparisons at every downward step.
  5. Comparator Swap: Convert a max-heap trace into a min-heap trace by identifying exactly which comparisons reverse.
