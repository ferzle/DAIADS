Maps

Overview

A map is an abstract data type that stores associations between distinct keys and values. The central question answered by a map is: What value is associated with this key? Maps are also called dictionaries or associative arrays.

Every key identifies at most one entry, but values do not need to be unique. For example, a map might associate each student ID with a student record, each word with its frequency, or each graph vertex with its current distance estimate. Different keys may have equal values associated with them.

Each card is one map entry. The blue part is the key used to locate the entry, and the white part is the associated value. The drawing represents only the logical contents of the map. The positions of the entries have no meaning, and the Map ADT does not specify how they are stored.

A map is closely related to a set. Both store distinct keys and must be able to locate a key efficiently. The difference is that a map stores additional information with each key. A set can answer whether a student ID is present; a map can use that ID to retrieve the student's name, record, grade, or other associated value.

A map is an ADT, not a particular representation. It can be implemented using an unsorted sequence, sorted array, balanced search tree, hash table, or direct-address table. These implementations use the key to locate an entry and then store or retrieve the value attached to that entry. We begin by defining the operations and guarantees of the Map ADT.

Core Operations

A map stores key-value entries and supports operations for locating, creating, changing, and removing associations. A typical map interface includes the following operations.

Operation Behavior
get(key) Return the value associated with an equal key, following a documented policy when the key is absent.
put(key, value) Insert a new entry when the key is absent. If an equal key is already present, replace its associated value.
containsKey(key) Return whether an entry with an equal key is present.
remove(key) Remove the entry with the equal key, if one exists. The operation often returns the removed value or whether an entry was removed.
size() Return the number of key-value entries.
isEmpty() Return whether the map contains no entries.
clear() Remove every entry from the map.
keys() (Optional) Visit every stored key once.
values() (Optional) Visit every associated value. Equal values may be visited more than once.
entries() (Optional) Visit every complete key-value association.

These operations closely parallel the Set ADT because both structures store distinct keys and support searching, insertion, removal, and iteration. The main difference is that a map stores an associated value with each key. Thus, containsKey(key) corresponds to contains(key) for a set, while put(key, value) extends set insertion by storing a value and replacing that value when the key is already present. Similarly, removing a key from a map removes its associated value as well. The additional operations get, values, and entries exist specifically because a map stores information beyond membership.

Lookup

The defining map query is get(key). It searches for a stored key equal to key and returns the value associated with that entry. The map searches by key, not by value. The interface must specify what happens when the key is absent. Common policies include returning a special value, throwing an exception, or returning an optional result that explicitly represents either a value or no value.

The operation containsKey(key) asks only whether an equal key is present in the map. It returns true or false without returning the associated value. This is useful when the program needs to distinguish between a missing key and a key that is present but associated with a value that might otherwise be used to represent "missing."

Insertion and Update

The operation put(key, value) has two cases. If the key is absent, the map stores a new key-value entry and increases the size by one. If the key is already present, the map replaces the old associated value and leaves the size unchanged. 

put(key, value):
    if containsKey(key):
        update the value associated with key to value
    else:
        store a new entry containing key and value
        size = size + 1

This pseudocode makes the value-storage responsibility explicit. When the key is already present, put changes the value stored with that key rather than creating another entry. When the key is absent, it stores a new entry containing both the key and its associated value.

A common use of put is to update a value based on its current value. For example, suppose a map stores the number of times each word has been encountered. The first occurrence of a word creates a new entry, while each later occurrence increases the existing count. 

if counts.containsKey(word):
    counts.put(word, counts.get(word) + 1)
else:
    counts.put(word, 1)

Many map libraries provide convenience operations that shorten patterns like this, but those operations and their exact behavior differ among languages.

Map interfaces differ in what put returns. Some return no value, some return the value that was previously associated with the key, and some return information indicating whether a new entry was inserted or an existing entry was updated. Returning the new value is generally unnecessary because the caller already supplied it. The Map ADT does not require one particular return convention, but an implementation should document which convention it uses.

Removal

The operation remove(key) removes the entry associated with key, if one exists. Because a map stores a value with each key, a useful convention is for remove to return the value that was associated with the removed key. If the key is absent, the operation leaves the map unchanged and returns a documented indication that no value was removed. 

remove(key):
    if containsKey(key):
        oldValue = get(key)
        remove the entry associated with key
        size = size - 1
        return oldValue
    else:
        return no removed value

Removing an entry removes both its key and its associated value. The size decreases only when the key was present. Map interfaces differ in how they represent the absence of a removed value; for example, an implementation might return a special value or an optional result. Some map interfaces instead return a Boolean indicating whether an entry was removed.

Size, Empty, Clear, and Iteration

The operation size() returns the number of distinct keys in the map, which is also the number of key-value entries. The operation isEmpty() reports whether the size is zero, and clear() removes every entry from the map.

Maps may also support iteration over their contents in several forms. keys() visits each stored key once, values() visits each associated value, and entries() visits each complete key-value association. Because values need not be unique, values() may visit equal values more than once.

We leave the exact iterator interfaces and traversal mechanisms unspecified. An implementation might return an iterator object, an iterable collection, a snapshot, or provide some other way to visit the contents. Unless the map interface explicitly guarantees an order, client code should not assume that keys, values, or entries are visited in sorted order or insertion order.

Example 1: Tracing Map Operations

Start with an empty map. For this example, put returns the previous value or none when the key was not already present, get returns the associated value or missing, and remove returns the removed value or missing.

Operation Return Value Entries Afterward Size Explanation
isEmpty() true {} 0 The map initially contains no entries.
put(A, 4) none {A: 4} 1 A new key-value entry is stored.
put(B, 9) none {A: 4, B: 9} 2 A second distinct key is stored.
put(A, 7) 4 {A: 7, B: 9} 2 The value associated with A is replaced, so the size does not change.
get(A) 7 {A: 7, B: 9} 2 The value associated with the present key A is returned.
get(C) missing {A: 7, B: 9} 2 No entry has key C, so the missing-key policy is used.
containsKey(B) true {A: 7, B: 9} 2 An entry with key B is present.
containsKey(C) false {A: 7, B: 9} 2 No entry has key C.
remove(B) 9 {A: 7} 1 The complete entry for B is removed and its associated value is returned.
remove(B) missing {A: 7} 1 B is already absent, so the map does not change.
size() 1 {A: 7} 1 Exactly one key-value entry remains.
clear() no return value {} 0 Every key-value entry is removed.

The braces describe the logical associations in the map. Writing {A: 7, B: 9} does not imply a physical storage order or an iteration order.

Implementation Options

Overview

The same basic data structures used to implement sets can also implement maps. In both cases, the representation must store distinct keys and support locating a key efficiently. The main difference is that a map must also store a value with each key and keep that value associated with the correct key whenever entries are inserted, moved, updated, or removed.

Because the key-location tradeoffs are largely the same as those discussed for sets, we will not repeat the full implementation details here. Instead, we focus on how each representation is extended to store key-value associations and on the additional responsibilities introduced by the value.

Implementation get put remove Where the Value Is Stored Iteration Order
Unsorted array or linked list \(O(n)\) \(O(n)\) \(O(n)\) In the same entry or node as the key May preserve insertion order
Sorted array \(O(\log n)\) \(O(n)\) \(O(n)\) In the entry that moves with the key Sorted by key
Balanced search tree \(O(\log n)\) \(O(\log n)\) \(O(\log n)\) In the tree node containing the key Sorted by key
Hash table Expected \(O(1)\) Expected \(O(1)\) Expected \(O(1)\) In the bucket entry or occupied table slot Usually unspecified
Direct-address table \(O(1)\) \(O(1)\) \(O(1)\) At the array position selected directly by the key Increasing key order when scanned

The bounds in the table are worst-case bounds unless marked as expected. Notice that they match the corresponding set representations: adding a value does not fundamentally change the cost of locating, inserting, or removing a key. What changes is what must be stored and maintained once the key has been located.

Storing Key-Value Entries

A set representation needs to store only keys. A map representation must store each key together with its associated value. Conceptually, the key and value form a single entry, even if the implementation stores the two parts separately.

One common representation uses an entry object or record containing two fields. 

Entry:
    key
    value

An array or linked-list map can store these entry records directly. A tree map can store the key and value in the same tree node, along with the child links and any balancing information. A hash map can store complete entries in buckets or table slots. In all of these representations, searches and comparisons use the key. The associated value is retrieved or changed only after the correct key has been located.

An array-based map can instead store keys and values in two parallel arrays. 

keys[0..capacity-1]
values[0..capacity-1]

In this representation, keys[i] and values[i] together form one logical map entry. The central invariant is that values[i] is always the value associated with keys[i]. Therefore, whenever an entry is shifted, copied, swapped, or removed, the key and its value must be moved together.

Example 2: Moving Complete Entries

Suppose an unsorted array map stores its keys and values in parallel arrays as shown below.

Index 0 1 2 3
Key A B C D
Value 12 5 19 8

Suppose the entry with key B is removed by replacing it with the final entry. Both the key D and its associated value 8 must move to index 1. Moving only D would incorrectly create the association D to 5.

Index 0 1 2
Key A D C
Value 12 8 19

The same requirement applies during insertion, shifting, resizing, tree restructuring, and hash-table movement: the representation may reorganize entries, but it must never change which value is associated with a key. This is the main storage responsibility that distinguishes a map implementation from the corresponding set implementation.

Arrays, Lists, and Trees

An unsorted array or linked-list map is nearly identical to the corresponding set representation, except that it stores complete key-value entries rather than keys alone. Lookup compares the keys of successive entries. When put finds an equal key, it updates that entry's value; when the key is absent, it stores a new entry. Lookup, put, and removal therefore take \(O(n)\) time in the worst case, just as they do for an unsorted sequential set.

A sorted-array map similarly extends a sorted-array set by storing a value with each key. Entries are sorted by key; the values do not participate in the ordering. Binary search locates a key or its insertion position in \(O(\log n)\) time, but insertion and removal may require shifting \(O(n)\) entries. Whenever an entry moves, its value must move with its key.

A balanced-search-tree map adds a value field to each node of the corresponding set representation. Comparisons use only the key to choose the search path and determine the tree structure. If put finds an existing key, it updates the value stored in that node rather than inserting another node. Because the tree remains balanced, lookup, put, and removal each take \(O(\log n)\) time in the worst case. An inorder traversal visits the entries in increasing order of their keys.

Thus, adding values does not change the basic search or update costs of these representations. The main additional requirement is that every operation preserve the association between each key and its value.

Hash Table

A hash-table map extends a hash-table set by storing a value with each key. The hash table still uses the key to determine where an entry should be searched for or stored. Once the key is found, get returns its associated value, and put can replace that value without creating another copy of the key.

With an appropriate hash function and resizing policy, get, put, and remove take expected \(O(1)\) time, although the worst-case running time is \(O(n)\). Hash-table maps generally do not provide sorted iteration.

Hash tables are one of the most common implementations of maps. Their representation, collision handling, resizing, and analysis are developed in detail on the later Hash Tables page.

Direct-Address Table

A direct-address table can implement a map when every key is an integer from a small fixed universe \[ \{0,1,\ldots,U-1\}. \] Instead of searching for a key, the implementation uses the key itself as an array index. Thus, key \(k\) is associated with position \(k\).

For a set, this idea requires only a presence array or bit vector indicating whether each possible key is present. A map must also store the value associated with each present key. One simple representation therefore uses two arrays. 

present[0..U-1]
values[0..U-1]

The entry for key \(k\) is present exactly when present[k] is true. When it is present, values[k] stores the value associated with \(k\). The implementation should not try to determine presence from values[k] alone, because a legitimate map entry might contain the same value that would otherwise be used to represent an unused position. Operations must reject or otherwise define the behavior for keys outside this universe. 

containsKey(key):
    return present[key]

get(key):
    if not present[key]:
        report that the key is missing
    return values[key]

put(key, value):
    if present[key]:
        values[key] = value
    else:
        present[key] = true
        values[key] = value
        size = size + 1

remove(key):
    if not present[key]:
        return no removed value

    oldValue = values[key]
    present[key] = false
    size = size - 1
    return oldValue

Each of these operations accesses only the array position corresponding to the key, so containsKey, get, put, and remove all take \(O(1)\) time. Maintaining the current number of entries in a variable also allows size() and isEmpty() to take \(O(1)\) time.

The tradeoff is that the representation allocates storage according to the size \(U\) of the entire key universe rather than the number \(n\) of entries actually stored. It therefore uses \(O(U)\) space even when only a few keys are present. Iterating through all entries may also require examining all \(U\) positions, so iteration takes \(O(U)\) time. Similarly, initializing or clearing the entire representation may require \(O(U)\) time.

Direct addressing is therefore most useful when the possible keys form a small, reasonably dense integer range. For example, it could be practical for mapping room numbers from 0 through 499 to room information, but it would waste substantial space for a map containing only a few integers drawn from a range of billions of possible keys.

Library Implementations

Most programs should use a map implementation supplied by the language's standard library. As with sets, the usual choice is between a hash-based implementation, which emphasizes fast exact lookup and updates, and an ordered implementation, which maintains keys in sorted order.

Language Hash-Based Map Sorted Map Other Relevant Behavior
Java HashMap<K,V> provides expected \(O(1)\) lookup, insertion, update, and removal. TreeMap<K,V> keeps keys sorted and provides \(O(\log n)\) basic operations. LinkedHashMap<K,V> preserves a defined iteration order.
C++ std::unordered_map provides average \(O(1)\) lookup, insertion, update, and removal. std::map keeps keys sorted and provides \(O(\log n)\) basic operations. Different access operations have different missing-key behavior; for example, some forms of indexing may insert a missing key with a default-constructed value.
Python The built-in dict type is hash based and supports lookup, insertion, update, removal, and iteration. Python does not provide a general-purpose built-in map that automatically keeps keys sorted. A dict preserves insertion order, but that is different from keeping keys in sorted order.

The underlying ADT is the same across these libraries, but the exact interfaces differ. In particular, languages may use different conventions for missing keys, the return values of put or remove, whether indexing inserts a missing entry, and what iteration order is guaranteed. Client code should therefore rely on the documented behavior of the specific library rather than assuming that all map interfaces behave identically.

Applications

Maps are useful whenever a program must retrieve or update information by a key. Common applications include the following.

  • Frequency tables: Associate each distinct item with the number of times it occurs. For example, a word-frequency map stores each word as a key and its count as the associated value.
  • Record lookup and indexes: Associate a unique identifier, such as a student ID, username, or product code, with a complete record or with the location of that record.
  • Graph algorithms: Associate each vertex with information maintained by an algorithm, such as its current distance, parent, color, discovery time, or adjacency collection.
  • Symbol tables: Associate each variable or function name with information about its type, scope, parameters, or storage location.
  • Caches and memoization: Associate an input, request, or subproblem with a result that has already been computed so that later occurrences can reuse it.
  • Sparse arrays and matrices: Associate only the indices whose values differ from a default value with the values stored at those positions. Indices not present as keys implicitly have the default value.
  • Configuration data: Associate each option or setting name with its current value, such as a display mode, file path, or numerical parameter.
Example 3: Memoization

Suppose a recursive algorithm repeatedly solves the same subproblems. A map can associate each subproblem with the result already computed for it. Before solving a subproblem, the algorithm checks whether its key is in the map. If so, it reuses the stored result; otherwise, it computes the result and adds the new association to the map.

A map is appropriate because each subproblem acts as a key and its computed result is the information that must be retrieved later. A set could record that a subproblem had been encountered, but it could not by itself store the result needed to avoid recomputing it.

Example 4: Sparse Storage

Suppose a very large array contains zero in almost every position. Instead of allocating storage for every position, a map can store only the nonzero entries, using an array index as the key and the nonzero array value as its associated value. An index that is not present in the map is interpreted as containing zero.

A map is appropriate because the program needs both pieces of information: which positions are exceptional and what value is stored at each one. This can save substantial space when the number of nonzero positions is small compared with the size of the full array.

Connections and Comparisons

Maps and sets are especially closely related because both organize their contents around distinct keys. Many of the same underlying data structures can implement either ADT. A set can even be implemented using a map by associating every stored key with the same unused marker value. Conversely, many set representations can be extended into map representations by storing an associated value with each key. 

set entry:  key
map entry:  key + associated value

Here is a brief comparison of several related structures:

Structure What It Stores How It Differs from a Map
Set Distinct keys only A set records whether each key is present. A map also stores a value associated with each key.
List Items in a sequence, possibly with duplicates A list preserves positions and sequence order. A map instead retrieves an associated value by key.
Multiset Distinct keys together with their multiplicities A multiset records how many times each key occurs. It can be implemented using a map from each key to its count.
Multimap Keys associated with one or more values An ordinary map has at most one current value for each key. A multimap allows a key to be associated with multiple values.

The choice of interface still matters. When only membership is needed, a set expresses that no additional information is associated with each key. When counts, labels, records, distances, or other information must be stored and retrieved by key, a map is the appropriate ADT.

Variations and Extensions

The basic Map ADT stores one value per key. Libraries and specialized data structures may strengthen the ordering guarantees or change the update model.

  • Sorted maps: Maintain keys in sorted order and may support additional operations such as finding minimum or maximum keys, predecessors and successors, and all entries whose keys fall within a range.
  • Insertion-ordered maps: Preserve the order in which keys were first inserted. Updating the value associated with an existing key normally leaves that key in its current iteration position.
  • Immutable maps: Cannot be changed after they are created. Operations that would normally update the map instead produce a new map with the requested association added, changed, or removed.
  • Persistent maps: Preserve earlier versions after an update. Different versions may share unchanged portions of their internal representation rather than copying every entry.
  • Multimaps: Allow one key to be associated with multiple values. A similar effect can often be obtained with an ordinary map whose value for each key is a list, set, or other collection.
  • Bidirectional maps: Support lookup both from key to value and from value to key. This generally requires values, like keys, to be unique so that the reverse lookup is unambiguous.

Common Pitfalls

  • Creating duplicate keys: When put receives a key that is already present, it must replace the value associated with that key rather than store a second entry with an equal key.
  • Losing the key-value association: When entries are shifted, swapped, copied, resized, or removed, each value must remain attached to its key. This is especially easy to mishandle when keys and values are stored in parallel arrays.
  • Mishandling missing keys: Client code must follow the documented behavior of get when no entry exists. If a special value such as null or zero can also be stored as an ordinary value, that result alone may not distinguish a missing key from a present key having that value.
  • Using inconsistent key rules: Lookup, insertion, update, and removal must use consistent rules for deciding when keys are equal. Hash-based and ordered implementations impose additional consistency requirements on hashing or comparison.
  • Modifying stored keys: Changing a key after insertion can make later searches fail if the change affects equality, hashing, or ordering. Changing the associated value normally does not cause this problem because the key still identifies the entry.
  • Assuming an iteration order: Client code should not assume sorted or insertion order unless the chosen map implementation explicitly guarantees it.
  • Using a map when a set is sufficient: If the program needs only membership, a set usually communicates the intended use more clearly and avoids storing an unnecessary associated value.
  • Choosing direct addressing for a sparse, large universe: A direct-address map uses space based on the size \(U\) of the possible key universe rather than on the number of entries actually stored.

Summary

A map stores key-value associations. Keys are distinct and identify entries; values are the information associated with those keys and may repeat. The core operations are get, put, containsKey, and remove, together with size, isEmpty, clear, and optional iteration operations. Inserting a new key increases the size, while replacing the value associated with an existing key does not.

Maps can be implemented using the same basic key-location structures as sets, but each stored key must also have an associated value. Arrays and linked lists may store complete entry records or use parallel key and value storage. Tree and hash-table representations similarly keep a value associated with each stored key. A direct-address map stores the value at the position selected by the key and normally uses separate presence information to distinguish missing keys from stored values.

The appropriate representation depends on the required operation costs, ordering guarantees, and restrictions on the keys. In most application code, a standard-library map should be preferred. A set is appropriate when only membership matters; a map is appropriate when additional information must be stored, retrieved, or updated for each key.
