Hash Tables

Overview

A hash table is a data structure for implementing maps and sets. Its goal is fast exact lookup: given a key, find the stored key or key-value entry without scanning the whole collection.

The central idea is to use a hash function to turn a key into an array index. If the hash function spreads keys out well and the table is kept at a reasonable load factor, lookup, insertion, and deletion are expected \(O(1)\).

Hash tables are implementation structures. The same table machinery can store a set of keys or a map of key-value entries. The ADT describes what the client sees; the hash table describes how the implementation organizes the entries internally.

Learning Goals

After reading this page, you should be able to:

  • describe the path from a key to a hash code, table index, and collision-resolution search;
  • explain why equal keys must have equal hash codes;
  • distinguish a hash function from a complete hash-table implementation;
  • trace lookup, insertion, update, and removal at a strategy-independent level;
  • compute load factor and explain why resizing requires rehashing; and
  • interpret expected, amortized, and worst-case operation costs correctly.

The Table Model

A hash table uses an array of \(m\) positions. The table currently stores \(n\) entries. The load factor is 

alpha = n / m

The load factor measures how full the table is. A higher load factor means the table uses space more tightly, but it also usually means more collisions and slower operations.

To place a key in the table, the implementation computes a hash code and converts it into a table index: 

index = hash(key) mod tableSize

The actual hash function may be more complicated than this sketch, especially for strings or objects. In introductory examples, integer keys and modulo arithmetic make the table behavior easier to trace.

The highlighted index is the key's home position: the first table location associated with the key. It is not necessarily the key's final physical location. A collision policy may keep several entries in a bucket at that index or may probe other array positions. Lookup must repeat the same policy used during insertion.

Hash Codes and Table Indices

Many programming environments separate hashing into two stages. First, a key supplies or is given a potentially large integer hash code. Second, the table mixes or reduces that code into the current index range \(0\) through \(m-1\). Keeping these stages separate lets the same key type be used with tables of many different capacities.

The notation \(h(k)\) is sometimes used for the hash code and sometimes for the final table index. When tracing an example, state which meaning is intended. This page uses hash(key) for the code and tableIndex(key) for the final home position. 

tableIndex(key):
    code = hash(key)
    mixedCode = mix(code)          // optional implementation step
    return nonnegative(mixedCode) mod table.length

Real implementations must also handle negative integer hash codes safely. Simply taking a language's remainder can produce a negative result in some languages, so the index-reduction rule must guarantee a valid nonnegative array index.

Collisions

A collision occurs when two different keys are assigned to the same table position. Collisions are unavoidable because there are usually many more possible keys than array positions.

For example, if \(h(k)=k \bmod 7\), then keys 10, 17, and 24 all map to index 3. A hash table is not complete until it says what to do when this happens.

The two collision-resolution families covered in this section are:

  • Separate Chaining: Each array position stores a small collection, often a linked list, of entries that hash to that position.
  • Open Addressing: Entries are stored directly in the table array, and collisions are handled by probing other slots.
Correctness requirement: different keys may share a hash code or home position, so a lookup must compare actual keys after reaching the relevant bucket or slot. A matching hash value narrows the search; it does not prove that two keys are equal.

Worked Example

Suppose a table has \(m=7\) positions and uses \(h(k)=k \bmod 7\). Insert keys 10, 3, 17, 8, and 24.

Key Hash Index Observation
10 3 Bucket or slot 3 is selected.
3 3 Collision with 10.
17 3 Another collision at index 3.
8 1 No collision if index 1 is empty.
24 3 Collision again at index 3.

This example has many collisions because the selected keys share the same remainder modulo 7. A real hash table tries to avoid patterns like this by using a better hash function and resizing when the load factor becomes too high.

At this general level, the trace intentionally stops after identifying home positions. It would be misleading to draw one final table without naming a collision strategy: separate chaining would keep the four colliding keys together at bucket 3, while linear probing would place them in a run of available slots beginning at 3. Core Operations

Search or Lookup

To search for a key, the table hashes the key to find the first place to look. Then it follows the table's collision strategy until it either finds the key or determines that the key is absent. 

lookup(key):
    index = tableIndex(key)
    search according to the collision strategy
    return the matching entry or report that key is absent

The search has two stopping conditions: finding an equal key or obtaining strategy-specific evidence that the key is absent. In chaining, reaching the end of the chosen bucket proves absence. In open addressing, reaching a never-used empty slot proves absence, but a tombstone does not.

Insert or Put

In a set, insertion stores a key. In a map, insertion stores a key-value entry. If the key already exists, a map usually updates the existing value and a set leaves the key unchanged.

Therefore insertion cannot blindly occupy the first available place. It must search far enough to determine whether an equal key is already present. Otherwise a hash set could store a duplicate or a hash map could store two entries for one key, violating the ADT contract.

Remove

Removal first finds the key, then deletes the entry according to the collision strategy. Deletion is especially delicate in open addressing because simply clearing a slot can break later searches. That is why open-addressed tables often use tombstones.

Iterate

Iteration visits every live entry, but it normally scans table structure as well. With \(n\) entries and capacity \(m\), a full traversal is typically \(O(n+m)\). The order reflects buckets or slots rather than sorted keys and may change after resizing even if the logical entries do not change.

Hash Functions

A good hash function should be deterministic, fast to compute, and spread likely keys across the table. It does not need to be random, but it should avoid predictable clustering for the data being stored.

  • Deterministic: The same key must hash to the same value while it is stored.
  • Uses the key's meaningful data: Equal keys must be treated consistently.
  • Spreads common inputs: Similar keys should not all land in the same small part of the table.
  • Fast: Hashing should not dominate the cost of lookup.

For object keys, the hash function and equality rule must agree: if two keys are equal, they must have the same hash code. The reverse is not required. Different keys may have the same hash code, which is exactly why collision handling is necessary.

Equal Keys Must Hash Equally

Suppose two student-ID objects are considered equal because both contain the text "A104". If they produce different hash codes, an entry inserted with one object might be searched for in a different location when the other equal object is supplied. The table could incorrectly report that the key is absent. Thus, equality determines a one-way rule: 

if a equals b, then hash(a) must equal hash(b)

The converse is false: equal hash codes do not imply equal keys. Collisions would be impossible if they did, but a finite integer range cannot uniquely encode every possible string or object.

Mutable Keys

If fields used by hashing or equality change while a key is stored, its new home position may differ from the position where the table placed it. The entry still occupies memory but may no longer be discoverable by normal lookup. Immutable keys—or at least keys whose identity fields remain stable—avoid this failure.

Load Factor and Resizing

Hash tables resize to keep operations fast. When the load factor crosses a chosen threshold, the implementation allocates a larger table and inserts all existing entries into the new table. This process is called rehashing. 

resize():
    oldTable = table
    table = new larger empty table
    size = 0
    for each entry in oldTable:
        insert entry into the new table

Rehashing is expensive when it happens because every entry is moved. If the table grows geometrically, such as doubling in size, the cost is spread across many insertions and the average insertion cost can still be treated as expected \(O(1)\).

Example: Why Rehashing Is Necessary

With capacity 5, key 12 has home index \(12 \bmod 5 = 2\). If the table grows to capacity 11, the same rule gives \(12 \bmod 11 = 1\). Leaving the entry at index 2 would cause future lookup to begin in the wrong place. Resizing must therefore recompute placement using the new capacity. 

old table: 12 mod 5  = 2
new table: 12 mod 11 = 1

A table may also shrink after many removals, though shrinking policies must avoid repeatedly growing and shrinking near one threshold. Open-addressed tables sometimes rebuild at the same capacity to remove accumulated tombstones even when the live-entry load factor is modest.

Time and Space Complexity

Operation Expected Cost Worst Case Why
Lookup \(O(1)\) \(O(n)\) Expected constant if entries are well distributed; linear if many keys collide.
Insert or put \(O(1)\) amortized expected \(O(n)\) Usually constant, but may scan a long collision group or trigger a resize.
Remove \(O(1)\) \(O(n)\) Deletion first has to find the key.
Iterate all entries \(O(n + m)\) \(O(n + m)\) The implementation may need to scan table positions as well as entries.

The space usage is usually \(O(n+m)\), where \(n\) is the number of entries and \(m\) is the table capacity. Some collision strategies add extra pointer or marker overhead.

Reading the Qualifiers

Expected \(O(1)\) relies on keys being distributed so that searches examine only a constant expected number of entries or slots. Amortized \(O(1)\) insertion accounts for occasional \(O(n)\) resizing by spreading that cost over many inexpensive insertions. Neither qualifier removes the \(O(n)\) worst case in which a search examines most of the stored entries.

These qualifiers describe different sources of variation. An individual insertion may be expensive because it triggers a resize even with excellent hashing; that is the amortized issue. A search may be expensive because many keys collide; that is the expected-versus-worst-case issue.

Implementation Planning

Before writing code for either collision strategy, make the following policies explicit. Most subtle hash-table bugs come from an omitted policy rather than from the hash calculation itself.

  • Entry type: store a key alone for a set or a key-value pair for a map.
  • Equality and hashing: define how keys compare and ensure equal keys hash equally.
  • Capacity: choose an initial table length and a growth rule.
  • Collision resolution: use buckets or a precisely defined probe sequence.
  • Duplicate-key behavior: ignore an existing set key or replace an existing map value.
  • Missing-key behavior: decide what lookup and removal return.
  • Resize threshold: monitor the strategy-appropriate notion of load.
  • Bookkeeping: distinguish capacity, live-entry count, and any deleted-slot count.
Implementation Exercise

Design a strategy-independent test suite before implementing the table. Include empty-table lookup and removal, insertion of colliding keys, duplicate set insertion or map update, removal from a collision group, lookup after removal, a resize, and lookup of every key after resizing. The same logical tests should be usable against separate chaining and open addressing.

Common Pitfalls

  • Assuming guaranteed constant time: Hash tables usually provide expected constant time, not worst-case constant time.
  • Ignoring collisions: A hash function alone is not a hash table implementation.
  • Letting the table get too full: High load factor makes collisions more expensive.
  • Mutating keys: If a key's hash or equality result changes after insertion, lookup may fail.
  • Assuming sorted order: Most hash tables do not keep keys in sorted order.
  • Using hashing for range questions: Hash tables are designed for exact-key lookup, not predecessor, successor, or range queries.

Applications

  • Hash sets: Fast membership testing and duplicate removal.
  • Hash maps: Fast key-value lookup, including frequency tables and indexes.
  • Caches: Store previously computed results by input or request key.
  • Graph algorithms: Store visited vertices, distances, parents, and adjacency lists keyed by vertex.
  • Compilers: Symbol tables map identifiers to declaration information.
  • Sparse data: Store only meaningful positions in a large logical array or matrix.

Summary

A hash table implements maps and sets by using a hash function to choose where entries belong in an array. Collisions are unavoidable, so every hash table needs a collision-resolution strategy. Separate chaining stores colliding entries in bucket collections. Open addressing keeps entries in the array and searches through a probe sequence. Load factor and resizing are what keep expected operation costs close to constant.

  2. Find collisions: Choose five integer keys that all collide when \(m=5\). Explain why they collide.
  3. Load-factor discussion: Compare two tables storing \(n=20\) entries, one with \(m=25\) and one with \(m=100\). What tradeoff is being made?

Homework Problems
