Hash Tables

Overview

A hash table is a data structure for implementing maps and sets. Its goal is fast exact lookup: given a key, find the stored key or key-value entry without scanning the whole collection.

Hash tables is organized around an underlying array with \(m\) positions. To store or find a key, the table uses a hash function to determine an array position associated with that key. If keys are spread through the table well and the table is kept at an appropriate size, lookup, insertion, and removal can have expected constant-time performance.

Hash-table keys do not have to be integers. They may be strings or more complicated objects. Such keys are first converted to an integer called a hash code. Programming languages typically provide a mechanism for computing hash codes for common types and for defining them for user-defined types.

For the rest of this introductory discussion, we will assume non-negative integer keys. This lets us focus on how the hash table converts an integer key into an array position. The same ideas apply when the integer was first obtained as the hash code of a string or object.

Different keys can be assigned to the same array position (called a collision), so a hash function by itself is not enough to implement a hash table. Every hash table also needs a collision-resolution strategy. The next two pages develop the two main strategies used in this text: separate chaining and open addressing. This page focuses on the ideas shared by both.

Hashing and the Table Model

A hash table stores its entries using an underlying array with \(m\) positions, numbered \(0,1,\ldots,m-1\). Each key is associated with one of these array positions, so the table needs a way to compute an array index from the key.

For non-negative integer keys, a simple hash function is

\[ h(x)=x\bmod m. \]

The value \(h(x)\) is always one of the valid array indices from \(0\) through \(m-1\). We call this index the key's home position. For example, if \(m=7\), then

\[ h(38)=38\bmod 7=3, \]

so key 38 has home position 3.

The modulo function is convenient for examples because it makes the computation easy to follow, but the important idea is more general: the hash function maps each key to one of the \(m\) available array positions.

Example: Inserting Keys into a Hash Table

Suppose a hash table has \(m=7\) positions and uses \(h(x)=x\bmod 7\). Insert the keys 8, 10, 19, and 24, in that order. A - represents an empty position.

Key \(x\) \(h(x)\) Table After Insertion Observation
8 \(8\bmod 7 = 1\) [ -, 8, -, -, -, -, - ] Store 8 at index 1.
10 \(10\bmod 7 = 3\) [ -, 8, -, 10, -, -, - ] Store 10 at index 3.
19 \(19\bmod 7 = 5\) [ -, 8, -, 10, -, 19, - ] Store 19 at index 5.
24 \(24\bmod 7 = 3\) [ -, 8, -, 10, -, 19, - ] Index 3 already contains 10.

The first three insertions are straightforward because their home positions are empty. But \(h(24)=3\), and position 3 already contains 10. The hash function does not tell us where to put 24, so we need an additional rule for handling this situation.

Collisions

A collision occurs when two different keys have the same home position. In the example above, 10 and 24 collide because

\[ h(10)=h(24)=3. \]

Collisions are unavoidable in general because there are usually far more possible keys than positions in the table. A hash function tells us each key's home position, but it cannot by itself tell us how to store multiple keys that have the same home position. Every complete hash table therefore needs a collision-resolution strategy.

We present two collision-resolution strategies on the next two pages:

  • Separate Chaining: each array position is associated with a collection that can hold multiple entries.
  • Open Addressing: entries are stored directly in the array, and another array position is tried when a collision occurs.
Important: A collision does not mean that two keys are equal. It only means that the hash function assigned them the same home position. The table must still compare the actual keys when performing a lookup.

Hash Functions and Keys

The choice of hash function has a major effect on the performance of a hash table. A useful hash function should be fast to compute and should spread the keys that are likely to occur across the available table positions. If many keys are sent to the same few positions, collisions become more frequent and operations become slower.

For our integer-key examples, we have been using

\[ h(x)=x\bmod m. \]

This function is simple and fast, and it always produces a valid index from \(0\) through \(m-1\). However, whether it distributes keys well depends on both the table size \(m\) and the pattern of keys being stored. For example, if \(m=10\) and all of the keys are multiples of 10, every key has home position 0.

In general, a useful hash function should have the following properties:

  • Deterministic: For a fixed table size, the same key must always produce the same home position.
  • Well distributed: The kinds of keys likely to occur should be spread across the available table positions rather than concentrated in a small number of them.
  • Fast: Computing the hash function should not dominate the cost of the hash-table operation.

No hash function can eliminate collisions altogether when there are more possible keys than table positions. The goal is instead to avoid unnecessary clustering so that collision resolution usually has little work to do.

Remark: Object Keys, Equality, and Mutation

Earlier we noted that keys do not have to be integers. Strings and other objects are typically converted to an integer hash code before the hash table applies its hash function. For such keys, equality and hash codes must be consistent:

\[ a=b \quad\Longrightarrow\quad \operatorname{hashCode}(a)=\operatorname{hashCode}(b). \]

The converse is not required. Two different keys may have the same hash code, just as two different integer keys may have the same value of \(h(x)\). The table must therefore compare the actual keys when determining whether an entry matches.

For example, suppose two student-ID objects are considered equal because both contain "A104". They must produce the same hash code. Otherwise, equal keys could be processed differently by the hash table, causing a lookup to fail even though the key is present.

A related issue arises with mutable keys. If a field used to determine a key's hash code or equality changes while the key is stored, later operations may no longer follow the same path used when the entry was inserted. For this reason, hash-table keys should usually be immutable, or at least the fields that determine their identity should remain unchanged while the key is stored.

How Hash Table Operations Work

Lookup, insertion, and removal all begin in the same way: compute the key's home position. From there, the collision-resolution strategy determines how the table searches for an equal key and how it recognizes that the key is absent.

  1. Compute the key's home position \(h(x)\).
  2. Follow the collision-resolution strategy beginning at that home position.
  3. Compare actual keys as needed.
  4. If the key is found, complete the requested operation: report or return the result, replace a map value, or remove the entry.
  5. If the key is absent, report failure for lookup or removal, or add the new entry for insertion.

A set and a map use the same search machinery. The main difference is what is stored: a set stores keys, while a map stores key-value entries. If an inserted key is already present, a set leaves the key unchanged, while a map usually replaces the value associated with that key.

The next two pages make these steps concrete. The exact search path, insertion rule, and removal rule depend on whether the table uses separate chaining or open addressing.

Load Factor, Resizing, and Performance

Suppose a hash table currently stores \(n\) entries in an array of capacity \(m\). The load factor is

\[ \alpha=\frac{n}{m}. \]

The load factor measures how full the table is relative to its capacity. As the load factor increases, collisions occur more frequently and generally require more work to resolve. Hash tables therefore monitor their load and usually allocate a larger table when the current table becomes too crowded for the chosen collision-resolution strategy.

The precise effect of \(\alpha\) depends on the strategy. Separate chaining can store more than \(m\) entries, so \(\alpha\) may exceed 1. Open addressing stores entries directly in the array, so it cannot store more than \(m\) live entries and is usually resized well before the table becomes full. The next two pages examine these differences in more detail.

Growing the table usually requires rehashing: creating a new array and reinserting the existing entries. This is necessary because the table capacity \(m\) is part of the hash function used to determine each key's home position.

Example: Why Rehashing Is Necessary

Suppose the hash function is \(h(x)=x\bmod m\). With capacity 5, key 17 has home position

\[ h(17)=17\bmod 5=2. \]

If the table grows to capacity 10, the hash function changes accordingly, and

\[ h(17)=17\bmod 10=7. \]

Leaving the entry at index 2 would therefore no longer place it where lookup begins in the new table. Existing entries must be rehashed using the new capacity.

Rehashing is expensive when it occurs because many or all entries must be processed. However, if the table grows geometrically, such as by approximately doubling its capacity, these occasional resizing costs can be spread over many insertions. The exact resize thresholds differ between separate chaining and open addressing, so those details are deferred to the corresponding pages.

Performance Preview

We have not yet specified a complete hash-table implementation, so we cannot justify precise running-time bounds on this page. The following table previews the standard performance achieved by both collision-resolution strategies under appropriate assumptions. The separate chaining and open addressing pages will analyze these bounds in detail.

Operation Expected Cost Worst Case
Lookup \(O(1)\) \(O(n)\)
Insert or put \(O(1)\) \(O(n)\)
Remove \(O(1)\) \(O(n)\)

Expected \(O(1)\) performance means that, under appropriate assumptions about the hash function and the load factor, an operation examines only a constant expected amount of table structure as \(n\) grows. It does not mean that every individual operation is guaranteed to take constant time.

In the worst case, many keys may collide in a way that forces an operation to examine a large fraction of the stored entries. This gives \(O(n)\) worst-case time. The exact form of such a bad configuration depends on the collision-resolution strategy.

Insertion has an additional issue: an individual insertion may trigger a resize and require \(\Theta(n)\) time to rehash the existing entries. With geometric growth, however, the total cost of resizing can be spread over many insertions, giving \(O(1)\) amortized resizing cost per insertion.

The table uses space for the \(n\) stored entries and for an array of capacity \(m\), giving \(O(n+m)\) space. When the resizing policy keeps \(m=\Theta(n)\), this simplifies to \(O(n)\) total space. Additional overhead depends on the collision-resolution strategy.

Common Pitfalls

The following pitfalls apply to hash tables generally, whether collisions are handled by separate chaining or open addressing. Each strategy has additional issues that will be discussed on its own page.

  • Assuming constant time is guaranteed: Hash tables are valued for expected constant-time operations, but poor collision behavior can still lead to \(O(n)\) worst-case time.
  • Ignoring collisions: A hash function determines a key's home position, but it does not say what to do when another key has the same home position. A complete hash table also needs a collision-resolution strategy.
  • Assuming a simple hash function always distributes keys well: A function such as \(h(x)=x\bmod m\) may work well for some sets of keys and poorly for others. The pattern of the keys and the choice of \(m\) both matter.
  • Assuming matching hashes imply matching keys: Different keys may have the same hash code or the same home position. The table must still compare the actual keys to determine whether it has found the desired entry.
  • Ignoring the load factor: As the number of entries grows relative to the table capacity, collision resolution generally requires more work. Resizing is used to keep the table from becoming too crowded.
  • Resizing without rehashing: When the table capacity changes, a key's home position may also change. Existing entries therefore generally cannot simply remain at the same numerical positions in the new table.
  • Changing a key's identity while it is stored: If data used to determine an object's hash code or equality changes, later operations may no longer follow the same path used when the key was inserted.
  • Expecting sorted order: Hash tables organize entries according to hashing rather than key order. They are therefore generally not appropriate when operations such as sorted traversal, predecessor, successor, or range searching are important.

Summary

A hash table implements maps and sets using an underlying array and a hash function that assigns each key a home position. Noninteger keys are typically first converted to integer hash codes. Different keys can have the same home position, so every complete hash table also needs a collision-resolution strategy.

A good hash function spreads likely keys across the available positions, while the load factor measures how many entries are stored relative to the table capacity. Resizing and rehashing help keep the table from becoming too crowded. Under appropriate assumptions, lookup, insertion, and removal have expected \(O(1)\) time, although \(O(n)\) worst-case operations are still possible.

The next two pages make these ideas concrete. Separate chaining associates each array position with a collection that can hold multiple entries, while open addressing stores entries directly in the array and searches additional positions when collisions occur.

  8. Load Factor: What is the formula for the load factor \(\alpha\), and what does it measure?
  9. Rehashing: Why may changing the table capacity \(m\) require all existing entries to be rehashed?
  10. Performance: Why does expected \(O(1)\) lookup not mean that every hash-table lookup is guaranteed to take \(O(1)\) time?

  2. Answer: A string or object can first be converted to an integer hash code. The hash table can then use that integer to determine a position in its underlying array.
  3. Answer: \(h(11)=4\), \(h(20)=6\), and \(h(31)=3\).
  4. Answer: The keys are processed as follows: \(h(7)=2\), \(h(14)=4\), \(h(3)=3\), \(h(12)=2\), \(h(9)=4\), and \(h(18)=3\). Thus the final table is [ -, -, 7, 3, 14 ]. Keys \(12\), \(9\), and \(18\) cannot be placed because their home positions are already occupied.
  5. Answer: A collision occurs when two different keys have the same home position. The hash function identifies that position but does not specify what to do when it is already associated with another key, so a collision-resolution strategy is also required.
  6. Answer: Every multiple of 10 has remainder 0 modulo 10, so all of those keys would have home position 0. This produces very poor distribution and many collisions.
