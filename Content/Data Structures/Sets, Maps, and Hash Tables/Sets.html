Sets

Overview

A set is an abstract data type that stores a collection of distinct keys. The central question answered by a set is: Is this key present? Each key is either present or absent, and adding a key that is already present does not create a second copy.

Sets are useful whenever a program cares about membership or uniqueness rather than position or frequency. For example, a set can track the vertices already visited during a graph search, record blocked words or user permissions, remove duplicates from a collection, or represent a mathematical set such as \(A\), \(B\), or \(A \cap B\).

The drawing represents only the logical contents of the set. The positions of the keys have no meaning, and the set does not provide indexed access. Some implementations support iteration, but the order may be sorted, insertion-based, or unspecified depending on the implementation.

Sets differ from several related data types. A list stores items in positions and may contain repeated values. A set stores distinct keys without meaningful positions. A map also stores distinct keys, but it associates a value with each key. Thus, a set is appropriate when only membership matters, while a map is appropriate when additional information must be stored with each key.

A set is an ADT, not a particular representation. It can be implemented using an unsorted sequence, sorted array, balanced search tree, hash table, or bit vector. These implementations provide the same basic set behavior, but they differ in running time, space usage, and ordering guarantees. We begin by defining the operations and guarantees of the Set ADT.

Core Operations

A set stores distinct keys and supports operations for testing and changing membership. A typical set interface includes the following operations.

Operation Behavior
contains(key) Return true exactly when the set contains a key equal to key.
add(key) Insert key if no equal key is already present. The operation often returns whether the set changed.
remove(key) Remove the equal stored key, if one exists. The operation often returns whether the set changed.
size() Return the number of distinct keys currently stored.
isEmpty() Return whether the set contains no keys.
clear() Remove every key from the set.
iterate() (Optional) Visit every stored key once. Unless the interface promises otherwise, the visitation order is unspecified.

Membership

The defining set query is contains(key). It searches for a stored key that is equal to key and reports whether such a key exists. Sets are often used specifically because a program needs frequent membership tests.

Membership depends on the set's equality rule. For example, two separately created strings containing the same characters normally represent the same key. The implementation must use equality consistently when searching, adding, and removing keys.

Insertion

The operation add(key) inserts the key only when no equal key is already present. If the key is absent, the size increases by one. If the key is already present, the logical contents and size remain unchanged. 

add(key):
    if the set contains a key equal to key:
        return false
    store key
    size = size + 1
    return true

This pseudocode describes the required behavior. An efficient implementation usually combines the membership test and insertion rather than performing two separate searches.

Removal

The operation remove(key) removes the equal stored key when it is present. Removing a key that is absent normally leaves the set unchanged. A Boolean return value can report whether a key was actually removed. 

remove(key):
    if the set does not contain a key equal to key:
        return false
    remove the stored key
    size = size - 1
    return true

Size, Empty, and Clear

The value returned by size() is the number of distinct stored keys, not the number of attempted insertions or the number of storage locations allocated by the underlying representation. Thus, repeatedly adding the same key does not increase the size. The operation isEmpty() is equivalent to testing whether the size is zero. After clear(), the size is zero and every membership query returns false.

Iteration

Many sets allow the client to iterate through all stored keys. Iteration is useful for printing, copying, or applying an operation to every key, but it is not indexed access. Unless the interface explicitly guarantees an order, client code should not assume that keys are visited in sorted or insertion order.

Example 1: Tracing Set Operations

Suppose add and remove return whether they changed the set. Starting with an empty set, consider the following sequence.

Operation Return Value Contents Afterward Explanation
add(4) true {4} The key was absent, so it was inserted.
add(9) true {4, 9} The key was absent, so it was inserted.
add(4) false {4, 9} The key was already present, so no duplicate was stored.
contains(7) false {4, 9} A membership query does not change the set.
remove(9) true {4} The key was present and was removed.
remove(9) false {4} The key was already absent.

The braces describe the logical contents of the set. Writing {4, 9} does not imply that 4 is physically stored before 9 or that iteration will visit it first.

Set Algebra Operations

In addition to the core operations, many set implementations provide higher-level operations corresponding to operations on mathematical sets. These operations are not required by the basic Set ADT because they can be constructed from membership, insertion, removal, and iteration.

Let \(A\) and \(B\) be sets. The most common set-algebra operations are shown below.

Operation Result Example
Union, \(A \cup B\) A set containing every key that appears in \(A\), in \(B\), or in both. If \(A=\{1,2,3\}\) and \(B=\{3,4\}\), then \(A \cup B=\{1,2,3,4\}\).
Intersection, \(A \cap B\) A set containing the keys that appear in both \(A\) and \(B\). \(A \cap B=\{3\}\).
Difference, \(A-B\) A set containing the keys that appear in \(A\) but not in \(B\). \(A-B=\{1,2\}\).
Symmetric difference, \(A \oplus B\) A set containing the keys that appear in exactly one of the two sets. \(A \oplus B=\{1,2,4\}\).
Subset test, \(A \subseteq B\) Return whether every key in \(A\) also appears in \(B\). \(A \subseteq B\) is false.

A set-algebra operation may either create a new set or modify one of its input sets. For example, a union operation may return a new set containing \(A \cup B\), or it may add every key from \(B\) directly to \(A\). An intersection operation may similarly return a new set containing \(A \cap B\), or it may remove from \(A\) every key that is not also in \(B\).

Constructing Set Operations

Set-algebra operations can be built from the core Set ADT operations. To compute an intersection, for example, iterate through one set, test each key for membership in the other set, and add the common keys to a new set. 

intersection(A, B):
    if A.size() <= B.size():
        smaller = A
        larger = B
    else:
        smaller = B
        larger = A

    result = empty set
    for each key in smaller:
        if larger.contains(key):
            result.add(key)

    return result

Choosing the smaller set to iterate through reduces the number of membership tests. The same basic ideas produce the other operations:

  • Union: Copy one set, then add every key from the other set.
  • Difference: Iterate through \(A\) and add a key to the result only when \(B\) does not contain it.
  • Symmetric difference: Add keys from \(A-B\) and \(B-A\).
  • Subset test: Check whether every key in \(A\) is contained in \(B\), stopping as soon as a missing key is found.

These algorithms provide general ways to construct set-algebra operations from the basic Set ADT operations. Some representations can perform the same operations more efficiently by taking advantage of their internal structure. Such representation-specific algorithms are beyond the scope of this overview.

Implementation Options

Overview

The Set ADT specifies what operations a set must perform, but it does not specify how the keys are stored. Several data structures can implement a set, and each provides a different balance among running time, space usage, ordering, and restrictions on the keys.

Implementation contains add remove Iteration Order Best Use
Unsorted array or linked list \(O(n)\) \(O(n)\) \(O(n)\) May preserve insertion order Small sets and simple implementations
Sorted array \(O(\log n)\) \(O(n)\) \(O(n)\) Sorted Mostly static sets with frequent membership tests
Balanced search tree \(O(\log n)\) \(O(\log n)\) \(O(\log n)\) Sorted Sets that need ordered traversal or range queries
Hash table Expected \(O(1)\) Expected \(O(1)\) Expected \(O(1)\) Usually unspecified Fast general-purpose membership and updates
Bit vector \(O(1)\) \(O(1)\) \(O(1)\) Increasing key order Sets drawn from a small, known integer universe

The bounds in the table are worst-case bounds unless marked as expected. For an unsorted sequence, insertion is \(O(n)\) because the implementation must first determine whether an equal key is already present. Removal also requires locating the key before deleting it.

We examine unsorted sequential representations and bit vectors in more detail because they illustrate two simple but very different approaches. We give briefer descriptions of sorted arrays, balanced search trees, and standard library implementations. Hash tables are introduced here as a common set representation, but their construction and analysis are developed in detail on a later page.

Unsorted Sequential Representation

The simplest way to implement a set is to store its keys in an unsorted array or linked list. The keys may appear in any physical order, but the representation must never contain two equal keys.

Membership

To implement contains(key), scan the stored keys until an equal key is found or every key has been examined. In the worst case, all \(n\) stored keys must be checked, so membership takes \(O(n)\) time. 

contains(key):
    for each storedKey in the set:
        if storedKey equals key:
            return true
    return false

This is just an implementation of the familiar sequential search algorithm.

Insertion

Insertion also requires a linear search. The implementation cannot simply append a key, because doing so might create a duplicate. If no equal key is found, the key is added at a location appropriate for the representation. 

add(key):
    if contains(key):
        return false

    insert key into the underlying representation
    size = size + 1
    return true

In an array implementation, the new key can be placed in the first unused position, provided the array has available capacity. If the array is full, a resizable implementation must allocate a larger array and copy the existing keys before inserting the new one. In a linked-list implementation, insertion can create a new node and link itat the front in \(O(1)\) time. It can also insert at the back in \(O(1)\) time if the representation maintains a tail pointer.

When space is already available, the actual insertion takes \(O(1)\) time for either representation. However, the preceding duplicate check takes \(O(n)\) time in the worst case. Therefore, the complete add operation is \(O(n)\).

Removal

Removal must first locate an equal key, which takes \(O(n)\) time in the worst case. In a linked-list implementation, the search can keep track of both the matching node and the node preceding it. Once they have been found, the matching node can be removed by changing one or two links.

In an array implementation, one option is to shift every later key one position to the left. This preserves the relative order of the remaining keys but may require \(O(n)\) additional work. If the physical order of the keys does not need to be preserved, the implementation can instead copy the final stored key into the removed key's position and then decrease the used size by one. 

remove(key):
    find the position of a key equal to key
    if no such key exists:
        return false

    remove the key from the underlying representation
    size = size - 1
    return true

Although the work performed after locating the key may be constant time, searching for the key takes \(O(n)\) time in the worst case. Therefore, the complete remove operation is \(O(n)\).

Other Operations

Iterating through the set takes \(O(n)\) time because every stored key must be visited. The operations size and isEmpty take \(O(1)\) time if the implementation maintains the current number of stored keys.

Summary

Operation Worst-Case Time Reason
contains(key) \(O(n)\) The key may require a scan of the entire representation.
add(key) \(O(n)\) The implementation must check for an existing equal key.
remove(key) \(O(n)\) The implementation must locate the key before removing it.
size() \(O(1)\) The current size can be stored in a variable.
isEmpty() \(O(1)\) The implementation tests whether the stored size is zero.
Iteration \(O(n)\) Each stored key is visited once.

A sequential representation may preserve insertion order, but this is an implementation choice rather than a requirement of the Set ADT. For example, shifting array elements during removal preserves their relative order, while replacing a removed key with the final key does not.

This representation is easy to implement and can work well for small sets. Its main limitation is that membership, insertion, and removal all require linear time. Larger or frequently searched sets usually benefit from a sorted representation, balanced search tree, hash table, or bit vector.

Sorted Array

A sorted array stores the keys in increasing order. To implement contains(key), the set uses binary search, so membership takes \(O(\log n)\) time.

To implement add(key), the set first uses binary search to determine whether the key is already present and, if not, where it belongs. The search takes \(O(\log n)\) time, but inserting the key may require shifting later keys one position to the right. Thus, insertion takes \(O(n)\) time in the worst case.

Removal works similarly. The set uses binary search to locate the key and, if it is present, shifts later keys one position to the left to close the gap. Therefore, remove(key) also takes \(O(n)\) time in the worst case.

A sorted array is most appropriate when the set changes infrequently but supports many membership tests. It also provides sorted iteration without any additional work.

Balanced Search Tree

A balanced binary search tree implements the Set operations using the ordinary binary-search-tree operations. The operation contains(key) performs a BST search, add(key) performs a BST insertion when the key is absent, and remove(key) performs a BST deletion when the key is present.

Because the tree remains balanced, its height is \(O(\log n)\). Membership, insertion, and removal therefore each take \(O(\log n)\) time in the worst case. The balancing work is handled by the underlying tree implementation and does not change the Set ADT interface.

An inorder traversal visits the keys in sorted order. The tree can also support ordered operations such as finding the minimum or maximum key, locating predecessors and successors, and reporting all keys in a range. These operations go beyond the basic Set ADT but are useful when ordered access is required.

This representation is appropriate when a set must support both frequent updates and sorted access. Balanced binary search trees and their operations are discussed in detail on the corresponding tree pages.

Hash Table

A hash table uses a hash function to determine where a key should be stored and searched for. A hash-based set stores only keys rather than key-value pairs. The operations contains, add, and remove use the key's hash value to examine a small portion of the table instead of searching through every stored key.

Different keys may be assigned to the same location, producing a collision. A hash table must use a collision-resolution method to distinguish and store such keys. It must also resize periodically as more keys are added so that the table does not become too crowded. With an appropriate hash function, collision policy, and resizing policy, membership, insertion, and removal each take expected \(O(1)\) time, although their worst-case running time is \(O(n)\).

Hash tables do not normally store keys in sorted or insertion order, so their iteration order is usually unspecified. They are nevertheless a common choice for general-purpose sets because their basic operations are fast in typical use. Hash functions, collisions, resizing, and hash-table implementations are developed in detail on the later Hash Tables page.

Bit Vector

A bit vector provides very fast set operations, but it applies only in a specialized situation. Every key must be an integer from a fixed universe \[ \{0,1,\ldots,U-1\}, \] and the representation reserves a membership position for every possible key, whether or not that key is present. Thus, its storage and initialization costs depend on \(U\), the size of the universe, rather than on \(n\), the number of keys actually stored.

This representation works well when \(U\) is reasonably small. For example, it may be appropriate for a set of course numbers between 0 and 999 or a set of character codes from a small alphabet. It is usually a poor choice when the possible integer range is enormous but only a few keys are present. It also cannot directly represent strings, objects, or arbitrary integers without first assigning them suitable integer positions.

For now, assume that the language provides a bit array present[0..U-1]. The bit present[k] is 1 exactly when \(k\) belongs to the set and is 0 otherwise.

For example, suppose \(U=8\) and the set is \(\{1,4,6\}\). Its bit vector is:

Key 0 1 2 3 4 5 6 7
Bit 0 1 0 0 1 0 1 0

Membership

Membership is determined by reading the bit corresponding to the key. 

contains(key):
    return present[key] == 1

Accessing one position of the bit array takes \(O(1)\) time, so contains takes \(O(1)\) time.

Insertion and Removal

Insertion sets the corresponding bit to 1. If the bit was already 1, the key was already present and the set does not change. 

add(key):
    if present[key] == 1:
        return false

    present[key] = 1
    size = size + 1
    return true

Removal sets the corresponding bit to 0. If the bit was already 0, the key was not present. 

remove(key):
    if present[key] == 0:
        return false

    present[key] = 0
    size = size - 1
    return true

Both operations access one membership position, so add and remove each take \(O(1)\) time.

Operation Costs and Appropriate Use

If the current number of stored keys is maintained in a variable, size and isEmpty also take \(O(1)\) time. Iteration is less favorable: the implementation may need to examine all \(U\) positions to find the keys whose bits are 1. Thus, iteration takes \(O(U)\) time, even if the set contains only a small number \(n\) of keys. Initializing or clearing the representation may also require \(O(U)\) time.

Operation Worst-Case Time Reason
contains(key) \(O(1)\) Read the membership position for the key.
add(key) \(O(1)\) Set one membership position.
remove(key) \(O(1)\) Clear one membership position.
size() \(O(1)\) The current size can be stored in a variable.
Iteration \(O(U)\) All possible key positions may need to be examined.
clear() \(O(U)\) Every membership position may need to be reset.

A true bit vector uses \(U\) bits of storage. This can be extremely compact when the universe is small, but the representation still allocates space for absent keys. For example, representing a few integers drawn from the range 0 through one billion would require roughly one billion bits, even if the set contained only ten keys.

Bit vectors can also perform some set-algebra operations efficiently. Union corresponds to applying OR to corresponding bits, intersection corresponds to AND, and difference can be implemented using AND together with complement. A packed implementation can process many membership bits in one machine operation.

Practical Representation

Many languages provide arrays of Boolean values, but a Boolean array does not necessarily store one value in one bit. Each entry may occupy a byte or even a larger amount of memory. Such an array implements the same logical idea and supports the same operation times, but it may use substantially more than \(U\) bits of storage.

A space-efficient implementation packs the bits into an array of unsigned machine integers. For example, an array of 32-bit unsigned integers stores 32 membership bits in each array entry. Key \(k\) is stored in array entry \[ \left\lfloor \frac{k}{32} \right\rfloor \] and uses bit position \[ k \bmod 32. \] Bit masks and shift operations read, set, or clear that particular bit. The array therefore needs approximately \(\lceil U/32\rceil\) integers rather than one Boolean array entry for every possible key.

Some languages provide a bit-array or bit-set library that performs this packing automatically. We treat that low-level representation as an implementation detail and use the simpler present[key] notation above.

Library Implementations

Most programs should use a set implementation supplied by the language's standard library. The usual choice is between a hash-based set, which emphasizes fast membership and updates, and a sorted set, which maintains its keys in sorted order.

Language Hash-Based Set Sorted Set Other Useful Types
Java HashSet<E> provides expected \(O(1)\) membership, insertion, and removal. Its iteration order is unspecified. TreeSet<E> keeps keys sorted and provides \(O(\log n)\) membership, insertion, and removal. LinkedHashSet<E> preserves insertion order. BitSet represents nonnegative integer positions using a packed bit vector.
C++ std::unordered_set provides average \(O(1)\) membership, insertion, and removal. Its iteration order should not be treated as meaningful. std::set keeps keys sorted and provides \(O(\log n)\) membership, insertion, and removal. std::bitset<N> provides a fixed-size packed collection of bits, although its interface differs from that of a general-purpose set.
Python The built-in set type is hash based and supports membership, insertion, removal, iteration, and set-algebra operations. Python does not provide a general-purpose built-in set that automatically maintains its elements in sorted order. frozenset is an immutable hash-based set. When sorted output is needed, the elements can be sorted when they are processed.

Library implementations should normally be preferred in application code because they are tested, optimized, and integrated with the language's collection framework. Direct implementations remain useful for studying the Set ADT, comparing representations, or creating a specialized representation such as a bit vector.

Applications

Sets are useful whenever a program must track uniqueness, test membership, or compare collections without storing additional information for each key. Common applications include the following.

  • Duplicate detection: Insert each item into a set. If an insertion reports that the item was already present, then a duplicate has been found.
  • Removing duplicates: Add every item from a collection to a set, then iterate through the set to obtain the distinct items.
  • Visited tracking: Graph searches and maze-solving algorithms use a set to avoid processing the same vertex or position more than once.
  • Filtering: A set of allowed or blocked keys can determine whether each item in a collection should be kept, rejected, or processed.
  • Fast membership testing: One collection can be converted to a set so that items from another collection can be tested against it efficiently. For example, a program might test which submitted IDs appear in a set of valid IDs.
  • Permissions and capabilities: A user or process can have a set of permissions, roles, enabled features, or supported operations.
  • Comparing groups: Union, intersection, and difference can determine which items appear in either group, in both groups, or in only one group.
Example: Tracking Visited Vertices

During a graph search, the algorithm can store each vertex in a set when it is first visited. Before processing a neighboring vertex, the algorithm checks whether that vertex is already in the set. If it is, the algorithm can skip it; otherwise, the vertex is added and processed.

A set is appropriate because the algorithm needs only to know whether a vertex has already been visited. No additional value needs to be associated with the vertex, and storing each vertex at most once prevents repeated processing.

Example: Detecting Duplicates

Suppose a program reads a sequence of IDs and must determine whether any ID occurs more than once. As each ID is read, the program checks whether it is already in a set. If so, a duplicate has been found. Otherwise, the ID is added to the set before the next item is processed.

A set is appropriate because the only information that matters is whether each ID has appeared before. The program does not need to store how many times the ID has occurred; if that count were needed, a map from each ID to its frequency would be more appropriate.

Connections and Comparisons

Sets are closely related to several other abstract data types, but the distinctions among them determine what information is preserved and which operations are natural.

Structure What It Stores How It Differs from a Set
List Items in a sequence, possibly with duplicates A list preserves positions and may store the same value multiple times. A set stores only whether each distinct key is present.
Map Distinct keys with associated values A set stores keys only. A map is appropriate when each key must also have a count, label, record, distance, or other associated value.
Multiset Keys together with their numbers of occurrences A multiset allows repeated values and records their multiplicities. An ordinary set records only presence or absence.
Disjoint-set structure A partition of items into nonoverlapping groups A disjoint-set structure answers whether two items belong to the same group and supports merging groups. Despite the similar name, it is not a general-purpose Set ADT.

Sets and maps are especially closely connected. Many map implementations store distinct keys and already provide efficient key lookup. A set can therefore be implemented using a map in which each key is associated with the same unused marker value. The set contains a key exactly when the map contains that key. 

set contains key  <==>  markerMap contains key

The two ADTs nevertheless serve different purposes. A client that needs only membership should use a set, since the interface communicates that no associated values are needed. A client that needs information attached to each key should use a map.

A finite set can also be viewed as a membership predicate: for every possible key, the predicate answers either true or false. The bit-vector representation makes this connection explicit by storing one membership bit for every possible key in a fixed universe.

Variations and Extensions

The basic Set ADT requires only distinct keys and membership operations. Many libraries provide specialized variations that add ordering, immutability, multiplicities, or other guarantees.

  • Sorted sets: A sorted set maintains its keys in order and may support minimum, maximum, predecessor, successor, and range operations in addition to the basic Set operations.
  • Insertion-ordered sets: These sets preserve the order in which keys were first inserted. Duplicate insertions do not create new positions because each key still appears only once.
  • Immutable sets: An immutable set cannot be changed after it is created. Operations such as insertion and removal instead return new sets. Immutable sets are useful when values must be safely shared or used as keys in other data structures.
  • Persistent sets: A persistent set preserves earlier versions after an update. The old and new versions may share much of their internal structure rather than copying every key.
  • Multisets: A multiset extends the idea of a set by storing a multiplicity for each key. Adding an existing key increases its count rather than leaving the collection unchanged.
  • Identity sets: Some specialized sets distinguish objects by identity rather than by ordinary value equality. Two separate objects may therefore be treated as different keys even if their contents are equal.
  • Concurrent sets: A concurrent set allows multiple threads to perform operations safely. Its implementation must coordinate simultaneous membership tests and updates while preserving uniqueness.
  • Universe-specific sets: When the possible keys come from a small fixed collection, such as an enumeration, a specialized packed representation may use less space and support very fast operations.

These variations preserve the central idea that each ordinary set key is either present or absent, but they strengthen the interface or alter the update model to meet particular application needs.

Common Pitfalls

  • Allowing duplicate keys: An implementation must check whether a key is already present before storing it. Adding an existing key must not create another copy or increase the size.
  • Mishandling removal of a missing key: The interface should clearly specify whether removing an absent key returns false, leaves the set unchanged without reporting anything, or signals an error.
  • Using inconsistent equality rules: Membership, insertion, and removal must use the same definition of equality. In a hash-based set, equal keys must also have equal hash values. In a tree-based set, the ordering rule must agree with the equality rule.
  • Modifying stored keys: Changing a key after insertion can break later searches if the change affects its equality, hash value, or ordering. Keys stored in hash-based or tree-based sets should therefore remain unchanged in all properties used by the implementation.
  • Assuming an iteration order: Client code should not assume that iteration is sorted or follows insertion order unless the chosen implementation explicitly guarantees that behavior.
  • Using a set when multiplicity matters: A set records only whether a key is present, so it loses information about repeated occurrences. If frequencies matter, use a map from each key to its count or a multiset.
  • Choosing a bit vector for a sparse, large universe: A bit vector allocates space according to the range of possible keys rather than the number of keys actually stored. It may therefore waste substantial space when \(U\) is large and \(n\) is small.
  • Ignoring implementation guarantees: Hash-based, tree-based, sequential, and bit-vector sets provide different operation costs and ordering guarantees. Choosing an implementation without considering the required operations can lead to unnecessary time or space costs.
  • Using an out-of-range bit-vector key: A bit vector can represent only keys in its fixed universe. The implementation must reject or otherwise define the behavior for keys smaller than 0 or at least \(U\).

Summary

A set stores distinct keys and makes membership its central operation. The core Set ADT supports testing, adding, and removing keys, together with operations such as size, isEmpty, and clear. Adding an existing key does not create a duplicate, and removing an absent key normally leaves the set unchanged. Many implementations also support iteration and higher-level set-algebra operations such as union, intersection, difference, and subset testing.

The Set ADT does not prescribe a representation. Unsorted sequences are simple but require linear-time searches. Sorted arrays provide logarithmic membership but linear-time updates. Balanced search trees provide logarithmic membership and updates together with sorted traversal, while hash tables provide expected constant-time basic operations without a useful ordering guarantee. Bit vectors provide constant-time membership and updates for keys from a small fixed integer universe, but their space and traversal costs depend on the size of that universe rather than on the number of stored keys.

The appropriate representation depends on the required operations, ordering guarantees, key restrictions, and space constraints. In most application code, a standard-library set should be preferred. A set is the appropriate ADT when only uniqueness and membership matter; lists preserve positions and duplicates, maps associate values with keys, and multisets preserve occurrence counts.

Reading Comprehension Questions

  1. Cost of Sequential Insertion: In an unsorted sequential set, physically inserting a new key may take \(O(1)\) time. Why is the complete add(key) operation still \(O(n)\) in the worst case?
  2. Array Removal Choices: Describe the two removal methods presented for an unsorted array. What is the advantage and disadvantage of each method, and what is the worst-case time for each?
  3. Sorted-Array Tradeoff: A sorted array can locate a key or its insertion position in \(O(\log n)\) time. Why do add and remove still take \(O(n)\) time in the worst case?
  4. Set Operations in a BST: How are contains, add, and remove implemented using an ordinary balanced binary search tree? What additional capabilities does the tree representation provide?
  5. Intersection Construction: Describe how to construct \(A \cap B\) using iteration, contains, and add. Why should the algorithm iterate through the smaller input set?
  6. Representation-Specific Set Algebra: Why might the general intersection algorithm fail to be the fastest possible algorithm for a particular set representation? Give one example from the page.
  7. Universe Size versus Set Size: Suppose a bit-vector set contains only ten keys, but its possible keys range from 0 through one billion. Why can this representation still require a large amount of space and take a long time to iterate through?
  8. Logical and Physical Bit Arrays: The bit-vector pseudocode uses present[key] as though each array entry were one bit. Why might a Boolean array use more space than \(U\) bits, and how can an array of 32-bit unsigned integers store the bits more compactly?
  9. Consistent Key Rules: What consistency conditions must equality, hashing, and ordering satisfy in hash-based and tree-based sets? What can go wrong if a stored key is modified in a way that changes one of these properties?
  10. Choosing an Implementation: For each of the following situations, choose an unsorted sequence, sorted array, balanced search tree, hash table, or bit vector, and justify the choice:
    1. A small set used only a few times.
    2. A mostly static set requiring many membership tests.
    3. A frequently updated set that must be traversed in sorted order.
    4. A general-purpose set requiring fast membership but no ordering.
    5. A set of integers from a small fixed universe.
  1. Answer: Before inserting the key, the implementation must scan the existing keys to determine whether an equal key is already present. That duplicate check takes \(O(n)\) time in the worst case and dominates the constant-time physical insertion.
  2. Answer: The implementation can shift all later keys one position to the left, which preserves their relative order but may require \(O(n)\) work. If order need not be preserved, it can copy the final stored key into the removed key's position and reduce the used size. The second method takes \(O(1)\) time after the key has been located.
  3. Answer: Binary search finds the key or insertion position in \(O(\log n)\) time, but preserving sorted order may require shifting as many as \(n\) keys. Insertion shifts keys to the right, while removal shifts later keys to the left.
  4. Answer: contains uses BST search, add uses BST insertion, and remove uses BST deletion. A balanced tree keeps these operations at \(O(\log n)\) worst-case time and also supports sorted traversal, minimum and maximum keys, predecessors and successors, and range queries.
  5. Answer: Iterate through one input set. For each key, test whether the other set contains it and add it to the result when it does. Iterating through the smaller set minimizes the number of membership tests.
  6. Answer: The general algorithm uses only the Set ADT interface and does not take advantage of the internal representation. A bit vector, for example, can compute intersection by applying bitwise AND to corresponding packed words, thereby processing many membership positions at once.
  7. Answer: A bit vector reserves a position for every possible key, so its storage depends on \(U\), not on the ten keys actually present. Iteration may also need to inspect all \(U\) positions to determine which bits are 1.
  8. Answer: A language may store each Boolean value in a byte or a larger storage unit rather than in one bit. A packed representation divides the key \(k\) by 32 to select an unsigned integer and uses \(k \bmod 32\) to select one bit within that integer. Thus, each array entry represents 32 possible keys.
  9. Answer: In a hash-based set, equal keys must have equal hash values. In a tree-based set, the ordering rule must agree with equality. If a stored key is modified so that its equality, hash value, or ordering changes, later searches may look in a different location and fail to find the key.
  10. Answer:
    1. Use an unsorted sequence because it is simple and linear searches are acceptable for a small set.
    2. Use a sorted array because binary search provides \(O(\log n)\) membership and updates are infrequent.
    3. Use a balanced search tree because it supports \(O(\log n)\) updates and sorted traversal.
    4. Use a hash table because it provides expected \(O(1)\) membership and updates when no useful order is required.
    5. Use a bit vector because direct bit access provides constant-time membership and updates when the integer universe is small and fixed.
