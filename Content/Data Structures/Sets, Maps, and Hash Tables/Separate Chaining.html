Separate Chaining

Overview

Separate chaining, also called Chaining, Open Hashing (not to be confused with Open Addressing), or Closed Addressing, is a collision-resolution strategy for hash tables. Instead of requiring each table position to store at most one entry, each position refers to a bucket that can hold all entries whose keys have that home position.

To look up, insert, or remove a key, the table first computes the key's home position and then works only within the corresponding bucket. Thus, collisions do not require searching for another table position: colliding entries remain together in the same bucket.

A common implementation uses a linked list for each bucket, and that is the representation we will use on this page. Other data structures can also be used to represent a bucket.

Hash tables can be used to implement both sets and maps. A hash set stores keys, while a hash map stores key-value entries. Separate chaining works the same way in either case: entries whose keys have the same home position are stored together in the same bucket. To keep the discussion simple, we will focus primarily on sets and show only keys.

The essential invariant is that every entry is stored in the bucket selected by its key. The order of entries within a bucket is usually not important to the set or map being implemented.

Core Operations and Implementation

Lookup, insertion, and removal all begin by computing the key's home position. Separate chaining then performs the rest of the operation within that one bucket. Thus, the rest of the details depend on the data structure used to represent a bucket. In this section, we will demonstrate how to implement these operations when each bucket is a linked list and insertions are made at the tail of the list. Other bucket representations are possible, but the overall approach is similar.

Lookup

To look up a key, first compute its home position and follow the reference to the linked list stored at that bucket. Traverse the list from its head, comparing each stored key with the search key. The lookup succeeds as soon as a matching key is found. If the traversal reaches the end of the list, the key is not present. 

lookup(key):
    i = h(key)    // often key mod table.length
    current = table[i]

    while current != null:
        if current.key equals key:
            return true
        current = current.next

    return false

The comparison must use the actual keys, not just their home positions. Every key in this linked list has the same home position, but the keys themselves may be different. Lookup must therefore compare the search key with each stored key until it finds an equal key or reaches the end of the list.

Insert

To insert a key, first compute its home position and traverse the linked list in that bucket. If the key is already present, the set is unchanged. Otherwise, append a new node containing the key to the tail of the list. 

insert(key):
    i = h(key)    // often key mod table.length
    current = table[i]
    previous = null

    while current != null:
        if current.key equals key:
            return false
        previous = current
        current = current.next

    newNode = new Node(key)

    if previous == null:
        table[i] = newNode
    else:
        previous.next = newNode

    size = size + 1
    return true

The traversal serves two purposes. It determines whether the key is already present, and, if the key is absent, leaves previous pointing to the final node in the list. The new node can therefore be appended to the tail without another traversal. If the bucket is empty, previous remains null, so the new node becomes the head of the list.

For a hash map, the same traversal is used, but each node stores a key-value pair. If the key is found, its associated value is replaced rather than inserting a new node.

Remove

To remove a key, first compute its home position and traverse the linked list in that bucket. As the list is searched, keep track of both the current node and the node that precedes it. If the key is found, remove its node by changing the appropriate reference. If the traversal reaches the end of the list, the key is not present and the table is unchanged. 

remove(key):
    i = h(key)    // often key mod table.length
    current = table[i]
    previous = null

    while current != null:
        if current.key equals key:
            if previous == null:
                table[i] = current.next
            else:
                previous.next = current.next

            size = size - 1
            return true

        previous = current
        current = current.next

    return false

The case previous == null means that the matching node is the first node in the bucket, so the bucket reference must be changed to point to the next node. Otherwise, previous.next is changed to bypass the matching node.

Example: Removing from a Chain

Suppose the table has capacity 7 and uses \(h(k)=k \bmod 7\). Bucket 3 contains the chain [10, 17, 24]. To remove 17, the table first computes \(h(17)=3\), then searches bucket 3. When 17 is found, the reference from 10 is changed to point directly to 24. In the diagram below, we only show the one row of the table that is affected by the removal.

The node containing 17 is no longer part of the chain, but 24 remains reachable from the bucket. No other bucket is affected.

Because each bucket maintains its own linked list, removing a node affects only that bucket. The remaining nodes in the list stay reachable, and searches in every other bucket are unchanged. This makes deletion particularly straightforward with separate chaining.

Analysis

Suppose the table stores \(n\) entries in \(m\) buckets. The load factor is \[ \alpha=\frac{n}{m}. \] For separate chaining, \(\alpha\) is also the average number of entries per bucket. Because each bucket can store multiple entries, \(\alpha\) may be greater than 1.

Computing a key's home position takes constant time. The remaining work depends on the length of the selected bucket. If the hash function distributes entries uniformly, the expected bucket length is \(\alpha\). Thus lookup, insertion, and removal each take expected \(O(1+\alpha)\) time.

If the table is resized as needed so that \(\alpha\) remains bounded by a constant, these operations take expected \(O(1)\) time. In the worst case, however, all \(n\) entries may have the same home position, producing a single chain of length \(n\). Lookup, insertion, and removal then require \(O(n)\) time.

Operation Expected Cost Worst Case
Lookup \(O(1+\alpha)\) \(O(n)\)
Insert \(O(1+\alpha)\) \(O(n)\)
Remove \(O(1+\alpha)\) \(O(n)\)
Resize \(\Theta(n+m)\) \(\Theta(n+m)\)

As discussed on the Hash Tables page, increasing the table capacity requires the existing entries to be rehashed because their home positions may change. Resizing therefore requires scanning the old bucket array and processing every stored entry, taking \(\Theta(n+m)\) time. When \(m=\Theta(n)\), this is \(\Theta(n)\). With geometric growth, these occasional costs contribute only \(O(1)\) amortized resizing cost per insertion.

The bucket array uses \(O(m)\) space, while the \(n\) linked-list nodes use \(O(n)\) space. Thus the total space usage is \(O(n+m)\), which is \(O(n)\) when \(m=\Theta(n)\). Each node also stores a reference to the next node in its bucket.

Connections and Comparisons

Separate chaining combines two familiar ideas: hashing determines which bucket could contain a key, and a secondary data structure stores the entries assigned to that bucket. With linked-list buckets, a lookup therefore consists of a constant-time jump to one bucket followed by a linear search through only that bucket.

Compared with a Single Linked List

A set stored as one unsorted linked list may require examining all \(n\) entries during a lookup. Separate chaining divides those entries among \(m\) buckets. Under good hashing, a lookup examines only a bucket of expected length \(\alpha=n/m\), rather than the entire collection. The linked lists themselves have not become faster; hashing reduces the number of entries that must be searched.

Compared with Open Addressing

The other major collision-resolution strategy is open addressing, which will be discussed on the next page. Instead of storing a separate collection at each position, open addressing stores entries directly in the table array and searches other positions when collisions occur.

Feature Separate Chaining Open Addressing
Where colliding entries are stored Together in a bucket In other positions of the table array
Load factor above 1 Allowed Not possible
Deletion Remove the entry from its bucket Requires more care to preserve later searches
Extra per-entry storage Often needed for linked-list references Entries are stored directly in the array
Memory locality May be weaker with linked nodes Often better because entries remain in the array

Separate chaining is particularly attractive when deletion is an important operation. Removing an entry from a bucket is straightforward once the key is found, whereas deletion in open addressing requires extra care so that later searches are not disrupted. Chaining is also useful when temporarily allowing more entries than buckets is acceptable. Open addressing can be preferable when compact storage and memory locality are more important. Both strategies aim for expected constant-time operations when the hash function distributes keys well and the table is kept at an appropriate size.

Variations and Extensions

Separate chaining does not require linked lists. The essential requirement is only that each bucket can store and search the entries whose keys have that home position. Different bucket representations lead to different implementation and performance tradeoffs.

Alternative Bucket Representations

  • Linked lists: The classic representation and the one used on this page. Insertion and removal require only reference changes once the correct location has been found, but every node needs a next reference and nodes may be scattered throughout memory.
  • Dynamic arrays or small vectors: Entries in a bucket are stored contiguously, which can improve memory locality and make scanning short buckets efficient. Removing an entry may require shifting later entries, although the final entry can sometimes be moved into the vacated position when bucket order is irrelevant.
  • Balanced search trees: A very long bucket can be represented by a balanced tree rather than a linear structure, reducing search within that bucket from linear to logarithmic time. This requires an ordering rule for the keys and adds overhead that is usually unnecessary when buckets remain short.

Where to Insert in a Linked-List Bucket

New nodes can be inserted at either the head or the tail of a linked-list bucket. Head insertion takes constant time once the table knows that the key is not already present. On this page we insert at the tail instead. Because insertion must already traverse the bucket to check for a duplicate key, that traversal also identifies the final node, allowing the new node to be appended without another search.

The choice does not affect the set or map being represented, since bucket order is normally not part of the ADT. Tail insertion is convenient pedagogically because entries remain in insertion order within each bucket.

Resizing Policies

Implementations may also differ in how large they allow the load factor to become before resizing. A larger threshold uses fewer buckets but produces longer chains on average. A smaller threshold uses more space but keeps expected bucket lengths shorter. Regardless of the exact threshold, resizing requires rehashing the stored entries because changing the table capacity may change their home positions.

Handling Unusually Long Buckets

Some implementations can change the representation of an individual bucket when it becomes unusually long. For example, a bucket might begin as a linked list and later be converted to a balanced tree. This preserves the simplicity and low overhead of short buckets while providing better protection against an exceptionally long chain.

Common Pitfalls

  • Inserting before checking for an existing key: A set must not contain duplicate keys, and a map should update the value associated with an existing key rather than create a second entry with the same key.
  • Updating the size incorrectly: The size changes only when an entry is actually added or removed. Finding an existing key during insertion does not increase the size, and updating a value in a map does not change the number of entries.
  • Mishandling removal from the head of a bucket: Removing the first node of a singly linked bucket requires changing the bucket-array reference itself. Changing previous.next works only when there is a previous node.
  • Appending without first searching the bucket: Tail insertion is easy once the end of the list is known, but insertion must still search the bucket first to determine whether the key is already present. The traversal can both check for duplicates and locate the final node.
  • Comparing only home positions: Every key in a bucket already has the same home position. Lookup, insertion, and removal must compare the actual keys to determine whether a matching entry has been found.
  • Confusing average bucket length with every bucket length: A load factor of \(1\) means one entry per bucket on average. Some buckets may be empty while others contain several entries.
  • Assuming a bounded load factor guarantees short individual chains: Keeping \(\alpha\) small controls the average bucket length, but poor hashing can still place many entries in the same bucket. Good performance also depends on distributing keys well.
  • Resizing without rehashing the entries: Changing the table capacity may change a key's home position. Existing entries must therefore be assigned to buckets again rather than simply copying the old bucket references into a larger array.

Summary

Separate chaining resolves collisions by letting each hash-table position refer to a bucket that can hold multiple entries. To look up, insert, or remove a key, the table first computes the key's home position and then works only within that bucket. On this page, buckets were represented by singly linked lists.

Lookup searches the selected bucket for an equal key. Insertion must perform the same search to avoid duplicate keys in a set or to update an existing key in a map. Removal searches for the key and then changes the appropriate reference to remove its node. Removing the first node of a bucket is a special case because the bucket-array reference itself must change.

If a table stores \(n\) entries in \(m\) buckets, its load factor \(\alpha=n/m\) is also the average bucket length. Under uniform hashing, lookup, insertion, and removal take expected \(O(1+\alpha)\) time. If resizing keeps \(\alpha\) bounded, these operations take expected \(O(1)\) time, although the worst case remains \(O(n)\) when many keys are placed in the same bucket.

Linked lists are the classic bucket representation, but arrays, small vectors, balanced trees, and other structures can also be used. Separate chaining is particularly attractive when deletion is important because removing an entry from its bucket is straightforward. It also allows the load factor to exceed 1, although linked representations generally use additional memory and may have weaker memory locality than open addressing.
