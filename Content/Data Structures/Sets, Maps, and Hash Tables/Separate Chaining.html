Separate Chaining

Overview

Separate chaining is a collision-resolution strategy for hash tables. Instead of requiring each table position to store at most one entry, each position refers to a bucket that can hold all entries whose keys have that home position.

To look up, insert, or remove a key, the table first computes the key's home position and then works only within the corresponding bucket. Thus, collisions do not require searching for another table position: colliding entries remain together in the same bucket.

Buckets are classically implemented with linked lists, which is the representation used for most of this page. Other local collections can also be used. A chained hash set stores keys in its buckets, while a chained hash map stores key-value entries.

The essential invariant is that every entry is stored in the bucket selected by its key. The order of entries within a bucket is normally irrelevant to the set or map being implemented.

Example: Building Chains

Suppose the table has capacity 5 and uses \(h(k)=k\bmod 5\). Insert 12, 22, 7, 4, and 17 in that order.

Key Home Position Bucket After Insertion
122[12]
222[12, 22]
72[12, 22, 7]
44[4]
172[12, 22, 7, 17]

A lookup for 17 goes directly to bucket 2 and searches only that bucket. Notice that although the table stores five keys in five buckets, the entries are not evenly distributed: one bucket contains four keys and three buckets are empty.

Core Operations

Lookup, insertion, and removal all begin by computing the key's home position. Separate chaining then performs the rest of the operation within that one bucket.

Lookup

Lookup scans the selected bucket until it finds an equal key or reaches the end of the bucket. A map returns the associated value; a set reports whether the key is present. 

lookup(key):
    i = hash(key) mod table.length
    for each entry in table[i]:
        if entry.key equals key:
            return entry
    report missing key

The comparison must use the actual keys, not just their hash values. Different keys can collide and therefore appear in the same bucket.

Insert or Put

Before adding a new entry, the table searches the bucket to determine whether the key is already present. In a map, an existing key causes its value to be replaced. In a set, an existing key leaves the set unchanged. 

put(key, value):
    i = hash(key) mod table.length
    for each entry in table[i]:
        if entry.key equals key:
            entry.value = value
            return
    add (key, value) to table[i]
    size = size + 1

If the bucket is a linked list, a new entry can be added at the head in constant time. However, put must still search the bucket first to determine whether the key is already present.

Remove

Removal searches the selected bucket for an equal key and removes that entry if it is present. 

remove(key):
    i = hash(key) mod table.length
    search table[i] for key
    if found:
        remove that entry from the bucket
        size = size - 1

Unlike open addressing, separate chaining does not require tombstones. Removing one entry from a bucket does not break the search path used to find any other entry.

Implementation

Linked-List Representation

A standard chained hash map uses an array whose entries are references to linked lists. Each node stores a key, its associated value, and a reference to the next node in the same bucket. A set implementation can use the same structure without the value field.

In addition to the bucket array, the table normally stores the number of live entries. The array length is the table capacity \(m\), while the entry count is \(n\).

Linked-list insertion is simplest at the front of the bucket. Removal from a singly linked bucket must keep track of the previous node so that the matching node can be bypassed. Removing the first node is a boundary case because the bucket-array reference itself must change. If that node was the only entry, the bucket becomes empty.

Load Factor and Resizing

For a chained table, the load factor is \[ \alpha=\frac{n}{m}. \] Because a bucket can contain multiple entries, \(\alpha\) may be greater than 1. In fact, \(\alpha\) is also the average number of entries per bucket.

As \(\alpha\) grows, the buckets become longer on average, so operations require more work. Implementations therefore resize the bucket array when the load factor becomes too large. As discussed on the Hash Tables page, changing the capacity can change each key's home position, so existing entries must be rehashed. 

resize(newCapacity):
    oldBuckets = buckets
    buckets = array of newCapacity empty buckets

    for each bucket in oldBuckets:
        for each entry in bucket:
            i = hash(entry.key) mod newCapacity
            add entry to buckets[i]

During rehashing, the implementation already knows that every old entry is distinct. A private helper that places such an entry directly into its new bucket can avoid unnecessary duplicate checks and can prevent accidental recursive resizing.

Analysis

Computing the home position takes constant time. The remaining work depends on the length of the selected bucket. If the hash function distributes entries uniformly, the expected bucket length is \(\alpha\). Therefore lookup, put, and remove each take expected \(O(1+\alpha)\) time.

When resizing keeps \(\alpha\) bounded by a constant, these operations have expected \(O(1)\) time. In the worst case, however, all \(n\) entries can land in one bucket, making lookup, put, and remove \(O(n)\).

Operation Expected Cost Worst Case
Lookup\(O(1+\alpha)\)\(O(n)\)
Put\(O(1+\alpha)\)\(O(n)\)
Remove\(O(1+\alpha)\)\(O(n)\)
Resize\(\Theta(n+m)\)\(\Theta(n+m)\)
Iterate all entries\(\Theta(n+m)\)\(\Theta(n+m)\)

A resize must inspect the bucket array and rehash every stored entry. When the capacity is maintained as \(m=\Theta(n)\), this is \(\Theta(n)\). If the table grows geometrically, these occasional resizing costs are spread across many insertions, giving constant amortized resizing cost per insertion.

The table uses \(O(m)\) space for the bucket array and \(O(n)\) space for the stored entries, for \(O(n+m)\) total space. When \(m=\Theta(n)\), this simplifies to \(O(n)\). Linked-list buckets also require a next reference for each stored entry.

Applications

Separate chaining is a collision-resolution strategy rather than a separate abstract data type, so its applications are primarily applications of hash tables. It can be used to implement hash sets and hash maps whenever fast expected exact-key operations are more important than maintaining the keys in sorted order.

Chaining is especially natural when straightforward deletion is important or when the implementation should remain functional even if the number of stored entries temporarily exceeds the number of buckets. Examples include dictionaries, symbol tables, frequency tables, and other lookup structures built on maps or sets.

Variations and Tradeoffs

Linked lists are the classic bucket representation, but separate chaining only requires each bucket to hold a collection of entries.

  • Linked lists: Simple insertion and deletion, but each entry needs an additional reference and linked nodes may have poor cache locality.
  • Dynamic arrays or small vectors: Often provide better locality for short buckets, but deletion may require shifting entries or replacing the removed entry with another one.
  • Balanced trees: Can reduce the cost of searching an unusually long bucket, but add ordering requirements and substantially more overhead for the short buckets that good hashing normally produces.

Compared with open addressing, separate chaining makes deletion simpler and permits load factors above 1, but it normally uses additional storage for bucket or node references and may have weaker memory locality.

Common Pitfalls

  • Inserting before checking for an existing key: A set must not contain duplicate keys, and a map should update an existing entry rather than create a second one.
  • Updating the size incorrectly: Replacing the value associated with an existing key does not change the number of entries.
  • Mishandling the first node of a bucket: Removing the head of a singly linked chain requires changing the bucket-array reference itself.
  • Assuming head insertion makes put constant time: Adding a new node may be constant time, but the bucket still has to be searched first for an existing key.
  • Confusing average bucket length with every bucket length: A load factor of 1 means one entry per bucket on average, not exactly one entry in every bucket.
  • Resizing without redistributing entries: A new capacity can change home positions, so every stored entry must be assigned to a bucket again.

Summary

Separate chaining resolves collisions by letting each hash-table position refer to a bucket that can hold multiple entries. Every operation computes a home position and then searches only that bucket. With linked-list buckets, insertion and deletion are structurally simple, and deletion does not require tombstones.

The load factor \(\alpha=n/m\) is the average bucket length. Under uniform hashing, lookup, put, and remove take expected \(O(1+\alpha)\) time, which becomes expected \(O(1)\) when resizing keeps \(\alpha\) bounded. The worst case remains \(O(n)\) if many entries collect in one bucket.

In-Class Activities

  1. Build the Buckets: Use a table of capacity 5 with \(h(k)=k\bmod 5\). Insert 6, 11, 16, 2, 7, 21 in order. Draw the bucket array and linked lists after each insertion.
  2. Trace Successful and Unsuccessful Lookup: Using the table from the previous activity, list the entries examined when searching for 16, 21, and 12.
  3. Update Versus Insert: Treat the table as a map and assign values to the keys from the first activity. Execute put(16, newValue). Identify what changes and explain why the size does not.
  4. Linked-List Removal Cases: Starting with one bucket containing four linked nodes, choose keys so that the class can practice removing the first node, a middle node, the final node, and then the only remaining node. For each case, identify which references must change.
  5. Load Factor Is an Average: Construct two different chained tables with \(n=8\) and \(m=8\): one with entries spread as evenly as possible and one with all entries in a single bucket. Both have the same load factor. Compare the number of key comparisons required for several successful and unsuccessful searches.
  6. Rehash a Chained Table: Store 4, 9, 14, 19, 24, 29 in a table of capacity 5 using \(h(k)=k\bmod m\). Then resize to capacity 11 and redraw all buckets. Identify which old chains split among several new buckets.

Homework Problems

  2. Map Updates and Size: A chained map initially contains (8,A), (18,B), (28,C) in the same bucket. Execute put(18,D), put(38,E), and put(8,F) in that order. Show the bucket after each operation and give the map size after each step.
  3. Removal Cases: A singly linked bucket contains 41 -> 31 -> 21 -> 11. Show the bucket after removing 41, then 21, then 11, and finally 31. For each removal, identify which reference changes.
  4. Load Factor and Expected Cost: A chained table stores 120 entries in 40 buckets.
    1. Compute the load factor.
    2. Under uniform hashing, what is the expected bucket length?
    3. State the expected asymptotic cost of lookup in terms of \(\alpha\).
    4. If the table is resized to 160 buckets, recompute the load factor and expected bucket length.
  5. Same Load Factor, Different Behavior: Two tables both have \(n=m=20\). In the first, each bucket contains exactly one entry. In the second, all 20 entries are in one bucket.
    1. Compute the load factor of each table.
    2. Compare successful and unsuccessful lookup behavior.
    3. Explain why load factor alone does not guarantee good performance.
  6. Resize and Rehash: Keys 7, 17, 27, 37, 47, 57 are stored in a chained table using \(h(k)=k\bmod m\) with \(m=5\). Redraw the table after resizing to \(m=11\). Explain why copying the old linked lists to the same bucket indices would be incorrect.
  7. Compare Bucket Representations: Compare linked-list and dynamic-array buckets with respect to insertion of a new distinct key, removal, extra memory per entry, and cache locality. Assume bucket order is not part of the ADT.
  8. Implement Separate Chaining: Implement a chained hash set or map using an array of singly linked buckets. Include lookup, insertion or put, removal, size, and resizing. Test empty buckets, multiple keys in one bucket, duplicate or update behavior, removal from the beginning/middle/end of a chain, and successful lookup after a resize.
