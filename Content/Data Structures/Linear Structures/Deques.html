Deques

Overview

A deque, pronounced either "deck" or "D-Q", is a double-ended queue. It stores values in a specific order and allows insertion, removal, and inspection at both ends. The two ends are usually called the front and the back.

One way to understand a deque is as a restricted list. A list may allow access, insertion, and removal at arbitrary positions, but a deque only allows these operations at the two ends. Thus, if you already understand lists, a deque is conceptually simpler: it keeps the ordered sequence idea but removes the indexed operations.

A deque generalizes both stacks and queues. If a program only adds and removes at one end, the deque behaves like a stack. If a program adds at one end and removes from the other, the deque behaves like a queue. The extra flexibility is that both ends are available for both insertion and removal.

A deque is an abstract data type. The abstraction describes what operations are available, not how the values are stored. The essential operations are adding to either end, removing from either end, looking at either end, checking whether the deque is empty, and reporting its size.

There are four common implementation ideas for a deque. Each one supports the same logical operations, but the implementation details, operation costs, and memory tradeoffs are different.

  • Doubly linked list: Stores each value in a node with both next and prev links. The deque stores references to the front and back nodes. This makes adding, removing, and peeking at either end straightforward \(O(1)\) operations. The tradeoff is extra memory for two links per node.
  • Circular array: Stores the deque in a fixed-size array. The logical front may appear anywhere in the array, and values wrap around from the last physical cell back to the first physical cell. This supports \(O(1)\) operations at both ends when the array has room, but the implementation must carefully update indices using modular arithmetic.
  • Dynamic circular array: Uses the same wraparound idea as a circular array, but allocates a larger array and copies the values when the old array fills up. This removes the fixed-capacity limitation in ordinary use. A single resizing step costs \(O(n)\), but with geometric growth, a long sequence of additions has amortized \(O(1)\) cost per operation.
  • Block-based deque: Stores values across several fixed-size blocks rather than in one large array or one node per value. New blocks can be added near either end as the deque grows. This approach is more complex, but it can avoid some large copying costs while retaining better locality than a fully linked representation. Some library deques use this general idea.

We will study the first two implementations in detail: the doubly linked list and the circular array. The dynamic circular array and block-based deque are included as important variations, but their full implementation details are beyond the scope of this page.

Core Operations

A deque stores values in order, but unlike a general list, it does not normally support indexed access as a core operation. The emphasis is on efficient access to the two ends. The following table gives a compact set of core operations and common alternative names.

Operation Description Common Alternative Names
addFront(value) Add value so it becomes the front value in the deque. pushFront, offerFirst, addFirst, prepend
addBack(value) Add value so it becomes the back value in the deque. pushBack, offerLast, addLast, append
removeFront() Remove and return the front value. popFront, pollFirst, removeFirst
removeBack() Remove and return the back value. popBack, pollLast, removeLast
peekFront() Return the front value without removing it. front, first, getFirst, peekFirst
peekBack() Return the back value without removing it. back, last, getLast, peekLast
size() Return the number of values currently stored in the deque. length, count
isEmpty() Report whether the deque currently stores no values. empty, is_empty
clear() Remove all values from the deque. makeEmpty, removeAll, reset

General Policies

The operations peekFront(), peekBack(), removeFront(), and removeBack() require the deque to be nonempty. If the deque is empty, a real implementation should follow a documented policy, such as throwing an exception, returning a special value, or reporting failure without changing the deque.

Operations that add values may also require a capacity check. A linked implementation can usually grow until memory is exhausted. A fixed-size circular array has a fixed capacity, so addFront(value) and addBack(value) must report overflow or use another documented policy when the array is full. A dynamic circular array resizes instead of reporting overflow in ordinary use.

Implementation Options

The Deque ADT describes the operations a deque should support, but it does not specify how the values must be stored. This section studies two primary implementations: a doubly linked list and a circular array.

Implementation 1: Doubly Linked List

Basics

A doubly linked list deque stores each value in a node. Each node stores a value, a next reference to the following node, and a prev reference to the previous node. The deque stores references front and back, along with a size variable.

This representation fits the deque abstraction directly. The front reference gives direct access to the front end, the back reference gives direct access to the back end, and the two-way links make it possible to add or remove from either end without traversing the whole structure.

Visual Representation of a Doubly Linked Deque

The logical deque is [12, 4, 18, 7]. Because each node has both a next link and a prev link, the implementation can add or remove nodes at either end without traversing through the whole deque.

The main invariant is that front points to the first node, back points to the last node, and adjacent nodes agree through their next and prev references. If the deque is empty, then both front and back should be null, and size should be 0.

How the Operations Work

The implementation changes only a constant number of references for each end operation. The descriptions below assume that all preconditions have already been checked.

size, isEmpty, and clear
  • size() returns the value of the size variable.
  • isEmpty() checks whether size == 0.
  • clear() sets front and back to null and sets size to 0.
peekFront and peekBack
  • peekFront() returns front.value.
  • peekBack() returns back.value.
addFront
  • Create a new node storing the value.
  • Set the new node's next reference to the old front.
  • If the deque was nonempty, set the old front node's prev reference to the new node.
  • Update front so it points to the new node.
  • If the deque was empty, also update back so it points to the new node.
  • Increment size.
addBack
  • Create a new node storing the value.
  • Set the new node's prev reference to the old back.
  • If the deque was nonempty, set the old back node's next reference to the new node.
  • Update back so it points to the new node.
  • If the deque was empty, also update front so it points to the new node.
  • Increment size.
removeFront
  • Save front.value.
  • Move front to front.next.
  • If the deque is now empty, set back to null.
  • Otherwise, set the new front node's prev reference to null.
  • Decrement size and return the saved value.
removeBack
  • Save back.value.
  • Move back to back.prev.
  • If the deque is now empty, set front to null.
  • Otherwise, set the new back node's next reference to null.
  • Decrement size and return the saved value.

Doubly Linked Deque Pseudocode

The pseudocode assumes a node type with fields value, next, and prev. Empty-deque operations report an error and stop. 

isEmpty():
    return size == 0

size():
    return size

clear():
    front = null
    back = null
    size = 0

peekFront():
    if isEmpty():
        report empty-deque error and stop
    return front.value

peekBack():
    if isEmpty():
        report empty-deque error and stop
    return back.value

addFront(value):
    newNode = new Node(value)
    newNode.next = front
    newNode.prev = null
    if isEmpty():
        back = newNode
    else:
        front.prev = newNode
    front = newNode
    size = size + 1

addBack(value):
    newNode = new Node(value)
    newNode.prev = back
    newNode.next = null
    if isEmpty():
        front = newNode
    else:
        back.next = newNode
    back = newNode
    size = size + 1

removeFront():
    if isEmpty():
        report empty-deque error and stop
    value = front.value
    front = front.next
    size = size - 1
    if front == null:
        back = null
    else:
        front.prev = null
    return value

removeBack():
    if isEmpty():
        report empty-deque error and stop
    value = back.value
    back = back.prev
    size = size - 1
    if back == null:
        front = null
    else:
        back.next = null
    return value

Implementation Analysis

  • size(), isEmpty(): \(O(1)\). Each checks or returns a stored variable.
  • peekFront(), peekBack(): \(O(1)\). The implementation stores direct references to both ends.
  • addFront(value), addBack(value): \(O(1)\). Each creates one node and changes a constant number of references.
  • removeFront(), removeBack(): \(O(1)\). The next and prev references give direct access to the new end node, and only a few reference need to be updated.
  • clear(): \(O(1)\) if it only drops the references. In a language with manual memory management, freeing all nodes takes \(O(n)\).
Storage Used

A doubly linked deque uses \(O(n)\) space for \(n\) stored values. Each node has constant overhead for two references, next and prev. The deque object itself uses \(O(1)\) extra space for front, back, and size.

Implementation 2: Circular Array

Basics

A circular array deque stores the deque in a fixed-size backing array. The implementation keeps an integer front, which is the array index of the logical front value, and an integer size, which is the number of values stored. The back value is not necessarily stored at A[size - 1], because the logical order can wrap around the end of the physical array.

If the array has capacity c, then the logical value at deque position i is stored at array index (front + i) % c. In particular, the back value is stored at (front + size - 1) % c when the deque is nonempty.

Visual Representation of a Circular Array Deque

Here is a representation of the logical deque [12, 4, 18, 7], shown in a circular array where the values have wrapped around the end of the array. In logical order, the deque values are stored at array indices 5, 6, 0, 1, with the front at index 5 and the back at index 1. Indices 2, 3, 4 are currently unused.

The central invariant is that the deque values occupy size positions in circular order, starting at front. The logical order moves right through the array and sometimes wraps back to index 0 after the last cell. Positions not in this circular segment are unused capacity.

How the Operations Work

A circular array implementation stores a backing array A, a front index, and a size. The capacity is A.length, using Java-like notation. The descriptions below focus on the main steps of each operation, so they assume that all preconditions are satisfied and that the fixed-size array has room before an add operation. When an index moves past either end of the array, it wraps around using modular arithmetic.

Index Computations
  • The front value is stored at A[front].
  • If the deque is not empty, the back value is stored at A[(front + size - 1) % A.length].
  • If the array is not full, the first unused slot after the back is A[(front + size) % A.length].
  • The slot before the front is A[(front - 1 + A.length) % A.length].
size, isEmpty, and clear
  • size() returns the value of the size variable.
  • isEmpty() checks whether size == 0.
  • clear() sets front = 0 and size = 0. Some implementations also clear old references from the array.
peekFront and peekBack
  • peekFront() returns A[front].
  • peekBack() computes backIndex = (front + size - 1) % A.length and returns A[backIndex].
addFront and addBack
  • addFront(value) moves front one step backward in circular order, stores value there, and increments size.
  • addBack(value) stores value in the first unused slot after the current back and increments size.
removeFront and removeBack
  • removeFront() saves A[front], optionally clears that array cell, moves front one step forward in circular order, decrements size, and returns the saved value.
  • removeBack() computes the current back index, saves that value, optionally clears that array cell, decrements size, and returns the saved value.

Circular Array Deque Pseudocode

The pseudocode assumes a fixed-size backing array A, an integer front, and an integer size. Add operations report overflow and stop if the array is full. The helper backIndex() assumes the deque is not empty. 

isEmpty():
    return size == 0

isFull():
    return size == A.length

size():
    return size

clear():
    front = 0
    size = 0

backIndex():
    return (front + size - 1) % A.length

peekFront():
    if isEmpty():
        report empty-deque error and stop
    return A[front]

peekBack():
    if isEmpty():
        report empty-deque error and stop
    return A[backIndex()]

addFront(value):
    if isFull():
        report overflow and stop
    front = (front - 1 + A.length) % A.length
    A[front] = value
    size = size + 1

addBack(value):
    if isFull():
        report overflow and stop
    index = (front + size) % A.length
    A[index] = value
    size = size + 1

removeFront():
    if isEmpty():
        report empty-deque error and stop
    value = A[front]
    front = (front + 1) % A.length
    size = size - 1
    return value

removeBack():
    if isEmpty():
        report empty-deque error and stop
    index = backIndex()
    value = A[index]
    size = size - 1
    return value

In some implementations, removeFront() and removeBack() also clear the removed array cell, for example by assigning null. The value is no longer logically part of the deque once size changes, but clearing the old cell prevents the backing array from keeping an unnecessary reference to an object. This can help garbage collection and can also make debugging easier.

Implementation Analysis

  • size(), isEmpty(): \(O(1)\). Each checks or returns a stored variable.
  • peekFront(), peekBack(): \(O(1)\). Each performs a constant amount of index arithmetic and reads one array cell.
  • addFront(value), addBack(value): \(O(1)\). Each checks whether the array is full. If there is room, it writes one array cell and changes a constant number of variables; if not, it reports overflow.
  • removeFront(), removeBack(): \(O(1)\). Each reads one cell and updates a constant number of variables.
  • clear(): \(O(1)\) if it only resets front and size. It can be \(O(n)\) if old references are explicitly cleared.
Storage Used

A fixed-size circular array deque uses \(O(c)\) space, where \(c\) is the capacity of the backing array. If the deque currently stores \(n\) values, then \(c - n\) cells are unused capacity. The implementation uses \(O(1)\) extra space for variables such as front and size.

Implementation Cost Summary

Both primary implementations make all core deque operations constant time. The main differences are memory overhead, locality, resizing behavior, and implementation complexity.

Operation Doubly Linked List Fixed Circular Array Reason
size(), isEmpty() \(O(1)\) \(O(1)\) Both implementations store the current size or equivalent state.
peekFront(), peekBack() \(O(1)\) \(O(1)\) The linked version stores end references; the array version computes end indices directly.
addFront(value), addBack(value) \(O(1)\) \(O(1)\) The linked version relinks a constant number of references; the array version writes one circular position if space is available.
removeFront(), removeBack() \(O(1)\) \(O(1)\) Both remove from a known end without shifting or traversal.
clear() \(O(1)\) or \(O(n)\) \(O(1)\) or \(O(n)\) Constant time if references are discarded; linear time if nodes or cells are explicitly cleared.

A fixed circular array has a fixed capacity. An attempted addition to a full fixed-size array must fail or follow another documented policy. A dynamic circular array avoids this fixed limit by resizing, but an individual resize costs \(O(n)\), so additions are amortized \(O(1)\) rather than worst-case \(O(1)\).

Library Implementations

Many programming languages provide a deque or deque-like structure in their standard libraries. The operation names and implementation details vary, but the main idea is the same: the structure supports efficient insertion and removal at both the front and the back.

Language Common Structure Typical Representation Notes
Java ArrayDeque<E> Resizable circular array Usually the preferred general-purpose deque implementation in Java. It supports efficient operations at both ends and avoids the per-node overhead of a linked structure.
Java LinkedList<E> Doubly linked list Implements both List and Deque. It supports efficient end operations, but uses extra memory for node links and is usually less cache-friendly than an array-based deque.
C++ std::deque<T> Block-based deque Stores values in multiple fixed-size blocks rather than one single contiguous array. It supports efficient insertion and removal at both ends and also provides indexed access.
Python collections.deque Block-based deque Designed for fast appends and pops at both ends using methods such as append, appendleft, pop, and popleft.

These library structures show why implementation choice matters. A deque interface describes the operations, but the representation determines memory overhead, cache behavior, resizing behavior, and whether additional operations such as indexed access are efficient.

Applications

Deques are useful when a program needs ordered storage and both ends are active. They often appear in algorithms and systems where items may need to be added or removed from either end.

  • Implementing queues and stacks: A deque can implement queue-like or stack-like behavior by restricting which operations are used.
  • Breadth-first search variants: Some graph algorithms, such as 0-1 BFS, use a deque to add vertices to the front or back depending on edge cost.
  • Sliding-window algorithms: A monotonic deque can maintain useful candidates for window minimums or maximums.
  • Undo and redo buffers: A deque can store a bounded history where old states are dropped from one end while new states are added at the other.
  • Task scheduling: Work queues sometimes add urgent tasks to the front and ordinary tasks to the back.
  • Palindrome checking: Repeatedly compare and remove the front and back characters.
  • Recent-item tracking: A deque can help store a bounded list of recently seen items, with new items added at one end and old items removed from the other.

Comparisons and Tradeoffs

The deque ADT is narrower than the list ADT. A list emphasizes access by position and supports operations such as get(index), set(index, value), and insert(index, value). A deque removes the general indexed operations and emphasizes efficient access, insertion, and removal at the two ends.

Doubly Linked List vs. Circular Array

A doubly linked list grows one node at a time and does not need unused array capacity. It handles both ends symmetrically and avoids resizing. Its disadvantages are extra references in each node, scattered memory locations, and more reference updates during insertion and removal.

A circular array stores values in array cells, so it usually has better locality and lower per-value overhead. Its disadvantages are fixed capacity in the simplest version and more subtle index arithmetic. A dynamic circular array removes the fixed-capacity limitation but introduces occasional resizing.

Why Not a Singly Linked List?

A singly linked list with a tail pointer is not a good full deque implementation because removeBack() requires finding the node before the back node. With only forward links, that search takes \(O(n)\) time. Adding prev references gives the constant-time back removal expected from a deque implementation.

Choosing an Implementation

  • Use a doubly linked list when the deque should grow one node at a time, when worst-case constant-time end operations are important, and when extra link storage is acceptable.
  • Use a circular array when the maximum capacity is known or fixed, and compact storage and cache-friendly access matter.
  • Use a dynamic circular array when the deque size changes significantly and a fixed capacity is inconvenient. This keeps most operations constant time in the amortized sense, but occasional resizing takes \(O(n)\) time.
  • Use a block-based deque when a library needs growth at both ends without repeatedly copying one large array. This design is more complex, but it balances growth flexibility with better locality than a node-per-value linked representation.

Variations and Extensions

Dynamic Circular Array Deques

A dynamic circular array deque grows when the backing array becomes full. When resizing, the implementation allocates a larger array and copies the logical deque values into the new array in clean order, usually starting at index 0. Then it resets front = 0 and continues the operation that caused the resize.

If the capacity grows geometrically, such as by doubling, then a long sequence of additions has amortized \(O(1)\) time per addition. Individual additions can still take \(O(n)\) time when they trigger resizing.

Block-Based Deques

A block-based deque stores values in several fixed-size blocks rather than in one large array. The implementation keeps enough information to find the current front and back blocks and the positions within those blocks. It can grow by adding a block near either end, which avoids copying all stored values every time more room is needed.

Conceptual Representation of a Block-Based Deque

Here the logical deque is [12, 4, 18, 7, 9, 11, 13, 15, 20]. The values are stored across several fixed-size blocks rather than in one large array. The first and last blocks may be only partially filled, while the middle blocks can be completely full.

This approach is more complex than a simple circular array or doubly linked list, but it combines some advantages of both: better locality than one-node-per-value linked storage and less large-scale copying than a single dynamic array. Some library deque implementations use this general idea.

Bounded Deques

A bounded deque has a maximum capacity. It is often implemented using a fixed circular array. When the deque is full, an addition may fail, or the application may use a special policy such as removing a value from the opposite end before adding the new value. Some ring-buffer applications overwrite old values, but that behavior should be documented carefully because it changes the usual deque semantics.

Monotonic Deques

A monotonic deque is an algorithmic use of a deque in which the stored candidates are kept in increasing or decreasing order. This is useful in sliding-window minimum and maximum algorithms. It is not a new implementation, but a disciplined way to use the deque operations.

Common Pitfalls

Deque implementations are short, but the boundary cases are easy to mishandle.

  • Forgetting the empty-to-one transition: When adding to an empty doubly linked deque, both front and back must point to the new node. Updating only one end leaves the deque in an inconsistent state.
  • Forgetting the one-to-empty transition: When removing the only value from a doubly linked deque, both front and back must become null. Updating only the removed end leaves a stale reference at the other end.
  • Using negative remainders incorrectly: In a circular array, moving one step before index 0 should wrap to A.length - 1. The expression (front - 1) % A.length may be negative in some programming languages. The safer expression is (front - 1 + A.length) % A.length.
  • Making off-by-one errors at the back: If front stores the index of the first value and size stores the number of values, then the back value is at (front + size - 1) % A.length, not (front + size) % A.length. The expression (front + size) % A.length gives the first unused slot after the back.
  • Confusing size and capacity: In a circular array deque, size is the number of meaningful values, while capacity is the number of array cells. Empty and full states should be checked using size, not by comparing front and back indices alone.
  • Clearing the wrong slot: If removed values are references, an implementation may set the vacated array slot to null so old objects are not kept alive unnecessarily. The slot to clear is the old front position for removeFront() and the old back position for removeBack().
  • Confusing deques with lists: A deque is an ordered structure, but it does not normally support general indexed operations such as get(index), set(index, value), or insert(index, value). Adding these operations makes the structure behave more like a list and may make the performance story much less clear.

Summary

A deque is a double-ended queue. It stores values in order and supports insertion, removal, and inspection at both the front and the back. The core operations are addFront(value), addBack(value), removeFront(), removeBack(), peekFront(), peekBack(), size(), isEmpty(), and often clear().

Conceptually, a deque is a restricted ordered structure: unlike a general list, it does not emphasize indexed access, insertion, or removal. Instead, it focuses on efficient operations at the two ends. By restricting which operations are used, a deque can behave like a stack, a queue, or a more flexible two-ended structure.

The two primary implementations studied in detail are the doubly linked list and the circular array. A doubly linked list stores front and back references and uses bidirectional node links to support worst-case \(O(1)\) end operations. A circular array stores values in a backing array using a front index, a size, and wraparound index arithmetic. It also supports \(O(1)\) end operations when the fixed-size array has room.

Dynamic circular arrays, block-based deques, bounded deques, and monotonic deques extend or adapt these ideas for practical and algorithmic settings. Dynamic circular arrays resize when full and give amortized \(O(1)\) additions. Block-based deques store values across several fixed-size blocks. Bounded deques enforce a maximum capacity. Monotonic deques use deque operations in a disciplined way to maintain useful candidates for sliding-window problems.

Key Takeaways

  • A deque is an ordered collection with efficient access, insertion, and removal at both ends.
  • A deque can be used as a stack or queue by restricting which end operations are allowed.
  • The core deque abstraction does not include general indexed operations such as get(index) or insert(index, value).
  • A doubly linked list implementation stores front, back, size, and bidirectional node links.
  • A circular array implementation stores a backing array, front, and size, with values arranged in circular order.
  • Both primary implementations support the core deque operations in \(O(1)\) time, assuming the fixed circular array has room for additions.
  • Dynamic circular arrays remove the fixed-capacity limitation but make additions amortized \(O(1)\) rather than always worst-case \(O(1)\).
  • Block-based deques are more complex, but they help library implementations grow at both ends without repeatedly copying one large array.
  • Common deque applications include stack and queue behavior, 0-1 BFS, sliding-window algorithms, bounded histories, task scheduling, palindrome checking, and recent-item tracking.
  • Correct implementations must carefully handle empty deques, one-item deques, full arrays, back-index formulas, clearing removed references, and wraparound arithmetic.
