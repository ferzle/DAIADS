Stacks

Overview

A stack stores values so that the most recently added value is the first one removed. This rule is called last-in, first-out, or LIFO.

The active end of a stack is called the top. New values are pushed onto the top, and removals also happen from the top. Values below the top are still stored, but the stack interface does not allow the caller to reach into the middle or remove from the bottom.

This restriction is useful because many programs need to remember unfinished work in reverse order. Function calls, recursion, undo history, expression evaluation, depth-first search (in graphs), and backtracking all rely on stack behavior. A stack is an abstract data type, so the LIFO rule matters more than the particular storage representation. The same stack behavior can be implemented with an array, a linked list, or a library container.

When we want to represent a stack using text, we typically show the top of the stack at the right side of the list and the bottom at the left side. For example, the stack from the diagram above would be written as [14, 8, 31], with 31 at the top.

Core Operations

The following are the core operations of a stack ADT. The ones in bold are the essential LIFO operations. The exact method signatures and error-handling policies may vary, but the same basic operations are needed to maintain the LIFO abstraction.

Operation Description
push(value) Add value to the top of the stack. If the stack is full, the implementation must report overflow or use a documented full-stack policy.
pop() Remove and return the top value. If the stack is empty, the implementation must report underflow or use a documented empty-stack policy.
peek() Return the top value without removing it. It has the same empty-stack issue as pop().
isEmpty() Report whether the stack currently stores no values.
size() Return the number of values currently stored.
isFull() (Optional) For a bounded stack (i.e. one with fixed capacity), report whether the stack currently stores the maximum number of values.

As seen above, a bounded stack needs an overflow policy for push when it is full, as well as a method isFull() to check its status. Depending on the implementation, this might mean throwing an exception, returning a boolean, or otherwise signaling the overflow condition. On the other hand, a resizable stack can grow its backing storage instead, but even a resizable stack can run out of memory in a real program.

Here are a few more details about the essential operations of a stack.

Push

push makes a new value the top value. It does not disturb the relative order of the values already in the stack; it only places a new item above them. If the stack previously stored [4, 7], then push(9) updates the stack to [4, 7, 9].

The caller should not need to know where that new value is stored physically. An array stack might write into the next open array cell, while a linked stack might allocate a new head node. Both are still the same abstract operation. We will discuss both implementations in more detail later.

Pop

pop removes the current top and returns it to the caller. The operation changes the stack's state. Calling pop() on a stack with contents [4, 7, 9] returns 9 and leaves the stack with contents [4, 7].

Popping from an empty stack is called underflow. A clean stack implementation should define this case explicitly, usually by throwing an exception, returning an optional value (often a boolean), or otherwise reporting an error.

Peek

peek reads the top value without removing it. Calling peek() on [4, 7, 9] returns 9 and leaves the stack unchanged. Peeking at an empty stack should be dealt with in the same way as it was for pop.

peek is useful when the next decision depends on the top value but the value should remain available for later operations. Parentheses matching, for example, often peeks at the most recent unmatched opening delimiter before deciding whether a closing delimiter matches it.

Example Trace of Stack Operations

Below we can see what happens when we start with an empty stack that can hold up to 4 elements (a bounded stack) and perform the following sequence of operations. pop(), push(4), push(7), push(9), pop(), push(2), peek(), push(5), push(8), pop().

Operation Stack Afterward Return Value
pop() [] underflow
push(4) [4] none
push(7) [4, 7] none
push(9) [4, 7, 9] none
pop() [4, 7] 9
push(2) [4, 7, 2] none
peek() [4, 7, 2] 2

push(8) [4, 7, 2, 5] overflow

In the example, we specified return values of underflow and overflow. The most common ways of actually doing this are to return a boolean or throw an exception. In the former case, instead of having "none" as a return value, the calls to push would return true when the push succeeded and false when it failed. pop and peek are more difficult to handle with a boolean return because they also need to return a value when successful. If the stack is storing objects, one option is to return null on underflow, but that only works if null is not a valid stack value. Another option is to return a known invalid value, such as -1, but that only works if the stack is storing integers and -1 is not a valid value. The fallback is to throw an exception, which is more flexible but also more complex to use because the caller must handle the possibility of an exception.

Implementation Options

The stack ADT can be implemented using several representations. The best representation depends on what is most important in the context, such as compact storage, predictable fixed capacity versus dynamic resizing, or compatibility with a language library. The two standard implementations are an array-backed stack and a linked stack.

Implementation 1: Array-Backed Stack

Basics

An array-backed stack uses two pieces of data: an array A that stores the items and an integer variable top that records the index of the current top item. The bottom of the stack is stored at index 0, and the top of the stack is stored at index top.

The main invariant is that the logical stack consists exactly of the array entries A[0] through A[top]. Entries after top are unused capacity. The array may have room for more items, but those extra slots are not currently part of the stack. When the stack is empty, we use top = -1, so there are no valid stack entries.

For example, if the array has length \(5\) and top = 2, then the stack contains the three items in positions 0, 1, and 2. Positions 3 and 4 are unused.

Placing the top at the logical end of the used part of the array is deliberate. A push operation increments top and stores the new item in A[top]. A pop operation saves A[top], decrements top, and returns the saved value. Both operations affect only one array position, so no elements need to be shifted.

In contrast, if the top were stored at the front of an ordinary array, then pushing or popping would require moving the existing elements to keep the stack contiguous. That would make the main stack operations unnecessarily expensive.

A =
12 7 19
top = 2
0 1 2 3 4

Here the stack contains \(12\), \(7\), and \(19\), with \(19\) at the top. The next push would place a value in index \(3\), and a pop would remove the value at index \(2\) and update top to \(1\).

How the Operations Work

The implementation keeps the stack entries in the array A and uses top to store the index of the current top item. When the stack is empty, top = -1. When the stack is nonempty, the logical stack is A[0] through A[top].

isEmpty

isEmpty() checks whether top == -1. This works because top is supposed to store a valid array index whenever the stack has at least one item. Since array indices start at 0, the value -1 is not a valid index. We use it as a sentinel value meaning "there is no top item."

isFull

isFull() checks whether top == A.length - 1. This means the top item is already stored in the last valid array position, so there is no unused slot for another item. This operation is most relevant for a fixed-size array-backed stack. A resizable-array implementation may not expose isFull(), since it can grow the backing array when more space is needed.

Push

If top < A.length - 1, push first increments top and then writes the new value into A[top]. If top == A.length - 1, the backing array is full. In the fixed-size version shown here, push returns false to report that the new value could not be added.

Pop

pop first calls isEmpty(). If the stack is empty, pop reports underflow. Otherwise, A[top] is the value to remove. The operation saves that value, decrements top, and returns the saved value. In languages with references, clearing the old array slot can help garbage collection, but that clearing is not part of the abstract stack operation.

Peek

peek also first calls isEmpty(). If the stack is nonempty, it returns A[top] without changing top.

Size

If a separate size() method is provided, it returns top + 1. For example, when top = -1, the size is \(0\). When top = 2, the stack contains entries A[0], A[1], and A[2], so the size is \(3\).

Array-Based Stack Pseudocode

The following pseudocode assumes a fixed-size array A and an integer top. Since this version does not resize the array, push returns false when the stack is full. 

isEmpty():
    return top == -1

isFull():
    return top == A.length - 1

push(value):
    if isFull():
        return false
    top = top + 1
    A[top] = value
    return true

pop():
    if isEmpty():
        report underflow and stop
    value = A[top]
    top = top - 1
    return value

peek():
    if isEmpty():
        report underflow and stop
    return A[top]

size():
    return top + 1

Implementation Analysis

In the fixed-size array implementation, each operation uses the array A and the variable top. None of the operations shift elements, and this version does not resize the backing array. As a result, each basic stack operation takes constant time.

  • push: \(O(1)\). It checks whether the array is full, increments top, writes the new value into A[top], and returns a Boolean value indicating whether the push succeeded.
  • pop: \(O(1)\). It checks whether the stack is empty, saves A[top], decrements top, and returns the saved value.
  • peek: \(O(1)\). It checks whether the stack is empty and then returns A[top] without changing the stack.
  • isEmpty: \(O(1)\). It checks whether top == -1.
  • isFull: \(O(1)\). It checks whether top == A.length - 1. This operation is mainly relevant for fixed-size stacks.
  • size: \(O(1)\). It returns top + 1.
Storage used:

This implementation uses \(O(c)\) space, where \(c\) is the capacity of the backing array. If the stack currently contains \(n\) items, then \(n = top + 1\), and the array has \(c - n\) unused slots. In addition to the array, the implementation uses only \(O(1)\) space for variables such as top.

Tradeoffs

  • Array stacks are usually compact and cache-friendly because values are stored next to one another.
  • A bounded array stack has predictable capacity but must report overflow when full.
  • A bounded array stack may also waste space if the chosen capacity is much larger than the number of items actually stored.
  • A resizable array stack avoids a fixed capacity limit, but resizing requires allocating a larger array and copying all current values. Most pushes are still fast, but a push that triggers resizing takes longer and makes the implementation more complex.
  • The representation uses an array, but the stack interface should still restrict access to the top item. Allowing arbitrary insertions or deletions would no longer behave like a stack.

Implementation 2: Linked Stack

Basics

A linked stack stores each item in a separate node. Each node contains two pieces of data: the stored value and a reference to the next node below it in the stack. The stack itself keeps a reference called head, which points to the top node. If the stack is empty, then head == null.

This does not mean that we first build a general linked-list data structure and then use it as the stack. Instead, the stack implementation directly uses the idea of linked nodes. The only reference the stack needs is head, because all stack operations happen at the top.

The main invariant is that head points to the top node, and following next references visits the stack from top to bottom. The last node has next == null, marking the bottom of the stack.

For example, the stack written as [12, 7, 19] has 19 at the top. In a linked implementation, head points to the node storing 19, which points to the node storing 7, which points to the node storing 12.

Visual Representation of a Linked Stack

Here head points to the top node, which stores 19. A push would create a new node and make it the new head. A pop would remove the current head node and move head to the node storing 7.

How the Operations Work

The implementation keeps a reference head to the top node. We will also maintain an integer variable count so that size() can return the number of stored items in constant time. Note that a linked implementation does not need the isFull method since it can grow as needed until memory runs out.

isEmpty

isEmpty() checks whether head == null. This works because head is supposed to refer to the top node whenever the stack has at least one item. The value null means there is no top node.

Push

push creates a new node to store the new value. The new node's next reference is set to the old head, and then head is updated to refer to the new node. This makes the new value the top of the stack without moving any existing values. The operation also increments count to maintain the size variable.

Pop

pop first calls isEmpty(). If the stack is empty, pop reports underflow. Otherwise, head.value is the value to remove. The operation saves that value, updates head to head.next, decreases count, and returns the saved value.

Peek

peek also first calls isEmpty(). If the stack is nonempty, it returns head.value without changing head or any next references.

Size

If the implementation maintains count, then size() simply returns count. Without such a variable, computing the size would require following links and counting nodes, which would take \(O(n)\) time.

Linked Stack Pseudocode

The following pseudocode assumes a head reference and an integer count. An empty stack has head == null and count == 0. 

isEmpty():
    return head == null

push(value):
    node = new Node(value)
    node.next = head
    head = node
    count = count + 1

pop():
    if isEmpty():
        report underflow and stop
    value = head.value
    head = head.next
    count = count - 1
    return value

peek():
    if isEmpty():
        report underflow and stop
    return head.value

size():
    return count

Implementation Analysis

In the linked implementation, each operation works at the head of the node chain. No operation shifts values, scans the whole stack, or copies all stored items. As long as count is maintained, each basic stack operation takes constant time.

  • push: \(O(1)\). It creates one new node, sets one next reference, updates head, and increments count.
  • pop: \(O(1)\). It checks whether the stack is empty, saves head.value, moves head to head.next, decrements count, and returns the saved value.
  • peek: \(O(1)\). It checks whether the stack is empty and then returns head.value without changing the stack.
  • isEmpty: \(O(1)\). It checks whether head == null.
  • size: \(O(1)\) if the implementation maintains count. Without count, computing the size would take \(O(n)\) time because the nodes would need to be counted.
Storage used:

This implementation uses \(O(n)\) space for \(n\) stored items. Each item is stored in a node, and each node also stores at least one reference, next. In addition to the nodes, the stack uses \(O(1)\) space for variables such as head and count.

Tradeoffs

  • A linked stack grows one node at a time, so it does not need a fixed capacity.
  • A linked stack avoids resizing copies because pushing a value only creates one new node.
  • Each stored value has extra node overhead, including at least one reference.
  • Nodes are not necessarily stored next to one another in memory, so linked stacks are usually less cache-friendly than array stacks.
  • The stack only needs a head reference. A tail reference would point to the bottom, but stack operations do not use the bottom.
  • The implementation uses linked nodes, but the stack interface should still restrict access to the top item. Allowing arbitrary insertions or deletions would no longer behave like a stack.

Implementation Cost Summary

Both main implementations make the core stack operations constant time. The practical differences are capacity limits, memory layout, and per-element overhead.

Operation Fixed-Size Array Stack Linked Stack Notes
push \(O(1)\) \(O(1)\) The fixed-size array version must report overflow when full; the linked version creates a new node.
pop \(O(1)\) \(O(1)\) Both remove from the top.
peek \(O(1)\) \(O(1)\) Both read the top without removing it.
isEmpty \(O(1)\) \(O(1)\) The array version checks top == -1; the linked version checks head == null.
size \(O(1)\) \(O(1)\) The array version returns top + 1. The linked version is \(O(1)\) only if it maintains a count field.
search \(O(n)\) \(O(n)\) Search is not a core stack operation.
Storage \(O(c)\), where \(c\) is the array capacity \(O(n)\), one node per stored item If the array stack stores \(n\) items, it has \(c - n\) unused slots. The linked stack avoids unused array capacity but stores an extra next reference in each node.

A stack's asymptotic operation costs are simple, but implementation details still matter. A fixed-size array stack is compact and usually cache-friendly, but it has a capacity limit. A linked stack grows one node at a time and avoids unused array capacity, but each pushed value requires a node allocation and an extra reference.

Library Implementations

In everyday programming, it is usually better to use a standard library structure than to write a new stack from scratch. Library implementations are tested, efficient, and familiar to other programmers. In a data structures course, however, implementing stacks by hand is still valuable because it clarifies the ADT, boundary cases, and representation tradeoffs.

Here are the obvious first choices for each language:

Language Common Stack Choice Push Pop Peek Notes
Java ArrayDeque<E> push(value) pop() peek() Usually preferred for stack behavior in modern Java. It supports efficient insertion and removal at both ends and avoids the older design of Stack.
C++ std::stack<T> push(value) pop() top() A container adapter that exposes stack operations while hiding most operations of the underlying container. Notice that pop() removes the top value but does not return it; use top() first if the value is needed.
Python list append(value) pop() stack[-1] Python lists work well as array-backed stacks when using the right end as the top. Avoid pushing or popping at the front of the list, since that requires shifting elements.

Java also has an older class named Stack, but modern Java code usually uses ArrayDeque for stack-like behavior. If the goal is to implement a resizable array-backed stack by hand, ArrayList<E> is another useful option: add(value) can act like push, remove(size - 1) can act like pop, and get(size - 1) can act like peek.

In C++, std::stack is not a separate storage structure by itself. It is a container adapter, meaning it gives a stack interface on top of another container, commonly std::deque. This is useful when the program should expose only stack operations, not random access or iteration through the stored values.

In Python, a plain list is the usual choice for basic stack behavior. For some queue-like operations, Python also provides collections.deque, but for stack operations at the end, list.append and list.pop are simple and efficient.

The main lesson is that the library type does not have to be named Stack to be used as a stack. What matters is whether the program uses it through the stack discipline: add at the top, remove from the top, and avoid operations that break the LIFO abstraction.

Applications

Stacks appear whenever the newest unfinished item should be handled next. The structure is small, but the LIFO rule fits many programming and algorithmic situations. In each application below, the key idea is that the most recently opened, started, or postponed item is the first one that should be closed, finished, or resumed.

  • Function calls and recursion: Programming languages use a call stack to remember active function calls.
  • Depth-first search and backtracking: A stack stores the most recently discovered unfinished state.
  • Expression processing and nested-structure validation: Stacks help with balanced-symbol checking, postfix evaluation, parsing nested expressions, and checking whether delimiters, tags, or scopes are properly nested.
  • Undo and redo history: Editors use stacks to remember actions that can be reversed or restored.
  • Explicit recursion simulation: Recursive algorithms can often be rewritten with an explicit stack of pending work.
  • Free lists and resource pools: Some systems keep reusable objects in a stack-like structure for simple allocation and deallocation.
  • Monotonic scans: A monotonic stack stores candidates in increasing or decreasing order while scanning an array.

Example 1: Checking Balanced Delimiters

A common stack application is checking whether parentheses, brackets, and braces are properly nested. For example, the string [{()}()] is balanced, but [{)] is not. The reason a stack is appropriate is that the next closing delimiter must match the most recent unmatched opening delimiter.

The algorithm scans the string from left to right. When it sees an opening delimiter such as (, [, or {, it pushes that delimiter onto the stack. When it sees a closing delimiter, it checks the top of the stack. If the stack is empty, there is no opening delimiter to match the closing one. If the top delimiter is the wrong type, the nesting is incorrect. Otherwise, the matching opening delimiter is popped. At the end, if the stack is empty, the expression is balanced, and if the stack is not empty, there are unmatched opening delimiters and the expression is not balanced.

Here is the algorithm:

isBalanced(text):
    create an empty stack S

    for each character ch in text:
        if ch is one of '(', '[', '{':
            S.push(ch)
        else if ch is one of ')', ']', '}':
            if S.isEmpty():
                return false
            other = S.pop()
            if other and ch are not a matching pair:
                return false

    return S.isEmpty()

For example, consider [{()}]. The scan pushes [, then {, then (. When it reaches ), the top of the stack is (, so they match and ( is popped. Then } matches {, and ] matches [. The stack is empty at the end, so the expression is balanced.

Character Action Stack Afterward
[ Push opening delimiter [
{ Push opening delimiter [, {
( Push opening delimiter [, {, (
) Matches (; pop [, {
} Matches {; pop [
] Matches [; pop empty

The string [{)] fails because when the algorithm reaches ), the most recent unmatched opening delimiter is {, not (. This is exactly the kind of "most recent unfinished item" rule that stacks are designed to enforce.

Example 2: Function Calls and Recursion

When one function calls another, the computer must remember where to return after the called function finishes. It also needs to remember local variables and other information for each unfinished call. This information is stored in a stack-like structure called the call stack.

Recursion relies on this behavior. If a function calls itself several times, each unfinished call gets its own stack frame. The most recent call finishes first, then control returns to the previous call, and so on. This is why deeply recursive code can run out of stack space: each active call uses one more frame.

Example 3: Backtracking

Backtracking algorithms explore possible choices until they either find a solution or reach a dead end. If a choice leads to a dead end, the algorithm backs up and tries another choice.

Recursion is a common way to implement backtracking, but the same idea can be written with an explicit stack. Each stack item stores a partially completed state, such as a partial puzzle solution, a partial string, or a partial selection of items.

A stack can store choices that still need to be explored. The following pseudocode shows the general pattern for iterative backtracking: 

backtrack(start):
    create an empty stack S
    S.push(start)

    while not S.isEmpty():
        state = S.pop()

        if state is a complete solution:
            process state
        else:
            for each valid next choice from state:
                S.push(state with that choice added)

The stack stores unfinished states. Each time the algorithm pops a state, it either processes it as a complete solution or pushes larger states that represent possible next steps. Because a stack removes the most recently pushed state first, the search follows one chain of choices deeply before returning to earlier alternatives.

Example 4: Undo and Redo

Many editors use stacks to support undo and redo. When the user makes an edit, the editor pushes enough information to reverse that edit onto an undo stack. When the user chooses undo, the most recent edit is popped and reversed. That reversed action can then be pushed onto a redo stack.

If the user makes a new edit after undoing, the redo stack is usually cleared. The old redo history represented a future path that no longer matches the document's current state.

Example 5: Postfix Expression Evaluation

Stacks are useful for evaluating postfix expressions, where the operator comes after its operands. For example, the infix expression (3 + 4) * 5 can be written in postfix form as 3 4 + 5 *.

The evaluator scans tokens from left to right. When it sees a number, it pushes the number. When it sees an operator, it pops the needed operands, applies the operator, and pushes the result. It is important that the operands are popped in the correct order. For a binary operator, the first popped value is the right operand, and the second popped value is the left operand. 

evaluatePostfix(tokens):
    create an empty stack S

    for each token in tokens:
        if token is a number:
            S.push(token)
        else:
            right = S.pop()
            left = S.pop()
            S.push(left operator right)

    return S.pop()

For 3 4 + 5 *, the evaluator pushes numbers as they are encountered. When it reaches an operator, it pops the right operand first, then the left operand, applies the operator, and pushes the result.

Token Action Stack Afterward
3 Push 3 [3]
4 Push 4 [3, 4]
+ Pop 4 as the right operand, pop 3 as the left operand, compute 3 + 4 = 7, then push 7 [7]
5 Push 5 [7, 5]
* Pop 5 as the right operand, pop 7 as the left operand, compute 7 * 5 = 35, then push 35 [35]

Operand order matters for noncommutative operations such as subtraction and division. The first value popped is the right operand, and the second value popped is the left operand. For example, in 10 3 - 4 *, the operator - should compute 10 - 3, not 3 - 10.

The evaluator first pushes 10 and 3. When it reaches -, it pops 3 as the right operand and 10 as the left operand, then computes 10 - 3 = 7 and pushes 7. It then pushes 4. Finally, * pops 4 as the right operand and 7 as the left operand, computes 7 * 4 = 28, and pushes 28.

If the operands were reversed for subtraction, the evaluator would compute 3 - 10 = -7 instead. That would leave -7 on the stack before the final multiplication, producing the incorrect result -28.

Connections and Comparisons

A stack is intentionally limited. It does not provide arbitrary access to its contents, and it does not allow removals from the middle or bottom. That smaller interface is a strength when the problem naturally uses reverse-order processing, but it is the wrong choice when the program needs general sequence operations.

  • Stack vs. general list: A list usually allows access, insertion, and deletion at many positions. A stack exposes only top-based operations such as push, pop, and peek. This restriction makes stack-based algorithms easier to reason about because values leave in exactly the reverse of the order they entered.
  • Stack vs. queue: A stack removes the newest item first, while a queue removes the oldest item first. Use a stack when the most recent unfinished task should be handled next, such as in undo history, nested delimiter checking, or backtracking. Use a queue when arrival order matters, such as in scheduling, buffering, or breadth-first processing.
  • Stack ADT vs. backing structure: The stack ADT describes the allowed behavior, not the storage layout. An array, linked nodes, or a library container can all be used to implement a stack. The backing structure may support extra operations, but exposing those operations weakens the stack abstraction.
  • Array-backed stack vs. linked stack: An array-backed stack is compact and usually cache-friendly because values are stored next to one another. A linked stack grows one node at a time and avoids fixed unused capacity, but each value requires a node and at least one extra reference.
  • Bounded vs. dynamically growing stack: A bounded stack has a fixed capacity and must define what happens when push is called on a full stack. A dynamically growing stack is easier to use because it can allocate more storage, but it still has practical memory limits and may occasionally do more work to grow.
  • Implicit vs. explicit stack: Recursive code uses the language runtime's implicit call stack. An explicit stack is a stack object created and controlled by the programmer. The two approaches often represent the same pattern of unfinished work, but an explicit stack gives the programmer more control over storage, order, and stopping conditions.
  • Stack vs. recursion: Recursion is a programming technique, while a stack is a data structure. However, recursive algorithms often work because the call stack stores unfinished function calls. Many recursive algorithms can be rewritten iteratively by storing the unfinished work in an explicit stack.

A stack is useful not merely because it can store items, but because it controls how those items are accessed. When a problem should only use the most recently added item, the stack restriction is helpful: it prevents irrelevant choices and matches the structure of the task. When the program needs access to older items directly, a different data structure is probably a better fit.

Variations and Extensions

Many useful structures keep the basic LIFO rule but add a constraint, extra operation, or specialized interpretation. Some variations are implementation choices, while others are algorithmic patterns that use stack behavior in a particular way.

  • Bounded stack: A bounded stack has a fixed capacity and must define what happens when push is called while the stack is full. This is common in embedded systems, low-level programming, and assignments where the memory limit is explicit. The array-backed stack we discussed is a simple example of a bounded stack.
  • Resizable stack: A resizable stack grows its backing storage when it fills. The most obvious example of this is the linked stack that we discussed earlier, since it grows one node at a time. For a resizable array-backed stack, resizing usually involves creating a new array with larger capacity and copying the old values into it. Most pushes take \(O(1)\) time, while a push that triggers resizing takes \(O(n)\) time; with geometric growth, the amortized cost of push is still \(O(1)\).
  • Min stack or max stack: A min stack supports returning the current minimum in \(O(1)\), and a max stack similarly supports returning the current maximum. A common implementation stores a second stack that tracks the running minimum or maximum as values are pushed and popped.
  • Call stack: A call stack stores activation records for function calls, including return locations, local variables, and other state needed to resume unfinished calls. The LIFO rule matches function execution: the most recently called function must finish before control returns to the function that called it.
  • Two-stack queue: Two stacks can implement FIFO queue behavior by moving items between an input stack and an output stack. This is a useful example of composing ADTs: each individual structure is still a stack, but together they provide queue behavior.
  • Monotonic stack: A monotonic stack keeps candidates in increasing or decreasing order while scanning a sequence. It is commonly used for next-greater-element, stock-span, and histogram-area problems, where each item can be pushed once and popped at most once.
  • Persistent stack: A persistent stack preserves old versions after updates. Instead of destroying the previous stack when a value is pushed or popped, the implementation can share unchanged nodes between versions. This idea is common in functional programming and is easiest to implement with linked nodes.

Common Pitfalls

Most stack mistakes come from breaking the LIFO abstraction, mishandling boundary cases, or confusing the stack ADT with the details of one particular implementation.

  • Ignoring underflow: pop and peek need defined behavior when the stack is empty. The implementation might throw an exception, return a special value, or report failure in some other documented way. What it should not do is return an arbitrary value or access invalid memory.
  • Ignoring overflow: A bounded stack also needs defined behavior when push is called on a full stack. The implementation might return false, throw an exception, or report overflow in another documented way. Silently dropping the new value is usually a poor choice.
  • Choosing the wrong array end: In an array-backed stack, the top should usually be the logical end of the used portion of the array. Using the front of an ordinary array as the top causes unnecessary shifts on every push or pop, resulting in slower performance.
  • Forgetting to update the top reference or index: Array stacks must update top consistently, and linked stacks must update head consistently. Off-by-one errors with top are common: for example, writing to A[top] before incrementing top may overwrite the old top item.
  • Returning before saving the value: A pop operation must save the top value before changing the structure in a way that makes the value inaccessible. In a linked stack, for example, the value in head.value should be saved before head is moved to head.next.
  • Confusing LIFO and FIFO: A stack and a queue can contain the same values but produce different removal orders. Use a stack when the newest unfinished item should be handled next. Use a queue when the oldest waiting item should be handled next.
  • Exposing too many operations: If client code can search inside the stack, insert into the middle, or remove from the bottom, then it is no longer using a clean stack abstraction. The backing structure may support extra operations, but the stack interface should restrict access to the top.
  • Assuming library names match ADT names: A useful stack implementation does not always have the word Stack in its name. For example, Java programmers often use ArrayDeque, and Python programmers often use a list with append and pop.
  • Forgetting call-stack limits: Recursive code uses stack space even when no explicit stack object appears in the program. Very deep recursion can overflow the language runtime's call stack.

Summary

A stack stores items so that the most recently added item is the first one removed. This LIFO rule makes stacks useful for nested structures, undo history, backtracking, recursion, expression processing, and other situations where the newest unfinished item should be handled next.

The core stack operations are push, pop, and peek. Most implementations also provide isEmpty and size. A bounded implementation may also provide isFull or some other way to detect overflow.

An array-backed stack stores values in an array and uses a variable such as top to record the index of the current top item. It is compact and usually cache-friendly, but a fixed-size version has a capacity limit. A linked stack stores values in nodes and uses a head reference for the top node. It grows one node at a time, but each value requires extra reference storage.

The main design question is whether the program should access only the top item—more precisely, the last item added. If that restriction matches the problem, a stack is often the right abstraction. If the program needs arbitrary access, searching, or removals from the middle, a different data structure is probably more appropriate.

    Note: The purpose of the sentinel node is to make the front of the linked structure behave more uniformly. In an ordinary linked stack, pushing onto an empty stack and popping the final node require special attention because head changes between null and a real node. With a sentinel, the stack always has one node present, and the top real node is always found at sentinel.next. This can make the code easier to reason about, even though it uses one extra node. Although the sentinel node does not simplify the implementation of a stack, it is a common technique for simplifying other linked data structures such as general linked lists, so practicing using it is worthwile.
