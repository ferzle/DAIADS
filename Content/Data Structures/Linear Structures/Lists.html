Lists

Overview

A list stores values in a specific order. Unlike a stack or queue, a list is not restricted to one active end or one removal rule. Instead, each value has a position, usually numbered from 0 through n - 1, where n is the number of values currently stored. The position of a value is called its index.

For example, the list [12, 4, 18, 7] has size 4. The value at index 0 is 12, the value at index 1 is 4, the value at index 2 is 18, and the value at index 3 is 7. The list order is part of the abstraction: changing the order changes the list.

A list is an abstract data type. The abstraction describes what operations are available, not how the values are stored. A program using a list may ask for the value at an index, replace a value, append a new value at the end, insert a value into the middle, or remove a value from a position. The implementation decides how to carry out those operations.

This page compares two common implementations of the same list idea. An array-based list stores the values in contiguous array positions. This makes indexed access fast, because the implementation can jump directly to position i. The tradeoff is that inserting or removing near the front or middle requires shifting values to preserve the list order.

A singly linked list with a tail pointer stores each value in a node. Each node points to the next node, the list stores a head reference to the first node, and the tail reference points to the last node. The tail reference makes appending at the end constant time, but indexed access is slower because the implementation must follow links from the head until it reaches the requested position.

The important point is that both representations store the same logical list. The operations should have the same meaning for the user of the list, even though the implementation details and operation costs are different. This is the central distinction between an abstract data type and a data-structure implementation.

Core Operations

A list stores values in a definite order. Unlike a stack or queue, a list allows access by position. If a list has \(n\) values, its valid indices are 0 through n - 1.

Also unlike stacks and queues, there is no definitive list of core operations. Different languages and libraries provide different operations, and the same operation may have different names in different contexts. The operations described below are a common set of core operations that cover the main ideas of list manipulation. The table below gives the operation names and descriptions, along with common alternative names.

The most important naming convention in this chapter is the distinction between remove(index) and delete(value). The operation remove(index) removes by position, while delete(value) removes the first matching value. Some libraries overload one name for both ideas, but keeping the names separate helps avoid ambiguity.

Operation Description Common Alternative Names

addLast(value) Add value so it becomes the last value in the list. append, pushBack, insertLast, add

removeLast() Remove and return the last value in the list. popBack, deleteLast, removeTail
first() Return the first value without removing it. front, getFirst, peekFirst, head
last() Return the last value without removing it. back, getLast, peekLast, tail
get(index) Return the value at position index without changing the list. at, getAt, array-style notation such as A[index]

isEmpty() Report whether the list currently stores no values. empty, is_empty
clear() Remove all values from the list, leaving an empty list. makeEmpty, removeAll, reset

General Policies

Several operations require either a valid position or a nonempty list. The operations first(), last(), removeFirst(), and removeLast() require the list to contain at least one value. If the list is empty, a real implementation should handle the case with a documented policy, such as throwing an exception, returning a special value, or reporting failure without changing the list.

The indexed operations also need bounds checks. For get(index), set(index, value), and remove(index), the valid indices are 0 through size() - 1. For insert(index, value), the valid insertion positions are 0 through size(), since inserting at size() adds the new value after the current last value.

If a searched value appears more than once, this chapter uses the first occurrence unless otherwise stated. Thus indexOf(value) returns the index of the first matching value, or -1 if there is no match, and delete(value) deletes the first matching value.

Operation Categories

The operations above can be grouped by what they ask the list to do. End operations work with the first or last value. Indexed operations work with a position. Search operations look for a value. Status operations report or reset the state of the list.

End Operations

End operations are useful because stacks, queues, and deques can all be described using restricted combinations of list operations. A stack uses one end, a queue uses one end for insertion and the other end for removal, and a deque allows insertion and removal at both ends.

Indexed Operations

Indexed operations emphasize one of the main differences between the two implementations studied on this page. An array-based list can jump directly to an index, while a linked list usually has to traverse from the head to reach the same position.

Search and Deletion by Value

Search operations look for a value rather than going directly to a known index. Unless the list is stored in some special searchable form, these operations usually scan values from the beginning until the value is found or the end is reached.

Status and Utility Operations

Status and utility operations keep the rest of the interface consistent. For example, after clear(), size() should return 0, isEmpty() should return true, and end operations should follow the implementation's documented policy for an empty list.

Example Trace of List Operations

Start with an empty list and perform the following sequence of operations: addLast(12), addLast(4), addLast(18), insert(1, 7), set(2, 9), get(1), delete(9), remove(0), addFirst(5), last().

Implementation Options

The List ADT describes the operations a list should support, but it does not specify how the values must be stored. This section studies two common implementations: an array-based list and a singly linked list with a tail reference. Both represent the same kind of ordered sequence, but they make different operations efficient.

The array-based implementation stores the list in consecutive positions of a backing array, which makes indexed access fast but can require shifting values during insertion and removal. The linked implementation stores values in nodes connected by references, which makes some end operations efficient but requires traversal to reach a general index. Comparing these two designs shows why choosing a data structure depends on the operations a program performs most often.

Implementation 1: Array-Based List

Basics

An array-based list stores the logical list in a backing array. In the fixed-size version presented here, the backing array has a maximum capacity that does not change. The implementation keeps an integer size, which records the number of meaningful values currently in the list. The list values occupy positions A[0] through A[size - 1]. Positions from A[size] through A[A.length - 1] are unused storage.

For example, the logical list [12, 4, 18, 7] might be stored in an array with six total slots. The first four cells store the list values. The remaining two cells are unused capacity. They are available for future additions or insertions, but they are not part of the logical list.

Visual Representation of an Array-Based List

The unused cells are part of the array, but they are not part of the logical list. A call to size() returns 4, not 6. Since this version uses a fixed-size array, future additions or insertions can use the two unused cells, but an addition to a full array must report overflow or use some other documented full-list policy.

The central invariant is that the logical list is stored contiguously starting at index 0. This invariant makes indexed access simple: the value at list index i is stored directly in A[i]. The cost is that insertions and removals in the front or middle must shift values to keep the list contiguous.

Many real array-based lists are dynamic arrays rather than fixed-size arrays. We will briefly discuss how the operations differ for a dynamic array after we cover the fixed-size version.

How the Operations Work

An array-based list implementation must store the backing array A and the current size of the logical list. It may also store the capacity of the array, if the given programming language does not provide the capacity as part of the array object.

Operations that have an index parameter (e.g., get, set, insert, remove), must first check that the index is valid (i.e., between 0 and size - 1). Other operations need to check that the list is not empty before they can proceed (e.g. first, last, removeFirst, removeLast). Finally, operations that add values must check whether the backing array is full before they can proceed. In these cases, the implementation should follow its documented policy for invalid input, such as throwing an exception, returning a special value, or reporting failure without changing the list. The descriptions below assume that all preconditions are satisfied and describe the main steps of the operation without mentioning error handling or bounds checks.

size, isEmpty, and clear

  • size() returns the value of the size variable.
  • isEmpty() checks whether size == 0.
  • clear() sets size to 0, which logically empties the list. To be safe, some implementations also set the now-unused cells to a default value, such as 0 or null, to avoid leaving old values in the array.

first and last

  • first() returns A[0]
  • last() returns A[size - 1].

get and set

  • get(index) returns A[index]
  • set(index, value) replaces A[index] with value.

addLast

  • addLast(value) places the new value in the first unused position, A[size], and then increments size.

addFirst and insert

  • insert(index, value) shifts values at positions index through size - 1 one position to the right, writes the new value into A[index], and increments size.
  • addFirst(value) is the same as insert(0, value).

When inserting into an array-based list, values are shifted one position to the right to make room for the new value. This shift must start at the last used position and move backward toward the insertion position. For example, to insert at index 2, copy A[size - 1] to A[size], then copy A[size - 2] to A[size - 1], and continue until A[2] has been copied to A[3]. If the shift started at index 2, then A[3] would be overwritten before its old value was moved.

removeFirst, removeLast, and remove

  • removeLast() removes and returns A[size - 1], then decrements size. No shifting is needed.
  • remove(index) saves the value at A[index], shifts later values one position left, decrements size, and returns the saved value.
  • removeFirst() is the same as remove(0).

Similar to the shifting operation for insertion, the removal operation must proceed from left to right when shifting elements to the left. Note that this is the opposite direction from the shift for insertion, which must proceed from right to left.

contains, indexOf, and delete

Search operations scan the array from left to right through the logical portion of the list. They maintain an index variable that starts at 0 and increments until a match is found or the end of the list is reached. At each step the implementation checks whether the current value matches the search value. The main difference between the operations is what they do when a match is found.

  • indexOf(value) returns the first index whose value matches, or -1 if no match is found.
  • contains(value) can be implemented by checking whether indexOf(value) != -1.
  • delete(value) can be implemented by calling indexOf(value) to find the index of the first match, then calling remove(index) to remove it if a match is found.

Dynamic Arrays

If implemented as a dynamic array that resizes when full, the implementations of addFirst(value), addLast(value), and insert(index, value) changes slightly to accommodate the possibility of a full backing array. When the backing array is full, a larger backing array is allocated, the current values are copied into it, and then the original operation is continued. This resizing step takes \(O(n)\) time, but if the capacity grows geometrically, such as by doubling, a long sequence of calls to these operations has amortized \(O(1)\) time per addition.

Array-Based List Pseudocode

The descriptions above focused on the main idea of each operation and did not show every error-handling detail. The pseudocode below is more explicit: it includes checks for invalid indices, empty-list operations, and attempts to add to a full fixed-size array.

The pseudocode assumes a fixed-size backing array A and an integer size. The array length A.length is the capacity of the list. This notation is Java-like: in other languages, the capacity may be stored in a separate variable.

Since this version does not resize the array, an operation that adds a value to a full array reports overflow and stops. Other invalid operations also report an error and stop, including invalid indices and attempts to access or remove from an empty list. Depending on the language and design choices, a real implementation might throw an exception, return a special value, or report failure without changing the list.

Search operations use a different convention because an unsuccessful search is not an error. The operation indexOf(value) returns -1 when the value is absent, and delete(value) returns false when no value is deleted. 

isEmpty():
    return size == 0

size():
    return size

clear():
    size = 0

first():
    if isEmpty():
        report empty-list error and stop
    return A[0]

last():
    if isEmpty():
        report empty-list error and stop
    return A[size - 1]

get(index):
    if index < 0 or index >= size:
        report invalid index and stop
    return A[index]

set(index, value):
    if index < 0 or index >= size:
        report invalid index and stop
    A[index] = value

addLast(value):
    if size == A.length:
        report overflow and stop
    A[size] = value
    size = size + 1

addFirst(value):
    insert(0, value)

insert(index, value):
    if index < 0 or index > size:
        report invalid index and stop
    if size == A.length:
        report overflow and stop
    for j = size down to index + 1:
        A[j] = A[j - 1]
    A[index] = value
    size = size + 1

removeLast():
    if isEmpty():
        report empty-list error and stop
    value = A[size - 1]
    size = size - 1
    return value

removeFirst():
    return remove(0)

remove(index):
    if index < 0 or index >= size:
        report invalid index and stop
    value = A[index]
    for j = index to size - 2:
        A[j] = A[j + 1]
    size = size - 1
    return value

indexOf(value):
    for i = 0 to size - 1:
        if A[i] == value:
            return i
    return -1

contains(value):
    return indexOf(value) != -1

delete(value):
    index = indexOf(value)
    if index == -1:
        return false
    remove(index)
    return true

Implementation Analysis

The running times below come from two facts about the representation: an array can access a known index directly, but keeping the list contiguous may require shifting values after an insertion or removal.

  • size(), isEmpty(): \(O(1)\). Each checks or returns a stored variable.
  • first(), last(): \(O(1)\). Each reads one array cell after checking that the list is nonempty.
  • get(index), set(index, value): \(O(1)\). After a bounds check, the implementation accesses A[index] directly.
  • addLast(value): \(O(1)\). It checks whether the array is full, writes the value into A[size], and increments size.
  • addFirst(value): \(O(n)\), because all existing values must shift one position right.
  • insert(index, value): \(O(n)\) in the worst case. Inserting near the front shifts many values. Inserting at the end shifts none, but the operation must still check whether the fixed-size array has room.
  • removeLast(): \(O(1)\). It removes the final logical value without shifting.
  • removeFirst(): \(O(n)\), because all remaining values shift one position left.
  • remove(index): \(O(n)\) in the worst case. Removing near the front shifts many later values.
  • indexOf(value), contains(value): \(O(n)\) in the worst case, because the value may be absent or appear only at the end.
  • delete(value): \(O(n)\) in the worst case. It may scan the whole list and, if it finds the value, shift later values left.
  • clear(): \(O(1)\) if it only sets size = 0. It can be \(O(n)\) if the implementation also clears old references from the backing array.
Storage Used

A fixed-size array-based list uses \(O(c)\) space, where \(c\) is the capacity of the backing array. If the list stores \(n\) values, then \(c - n\) array cells are unused capacity. In addition to the array, the implementation uses \(O(1)\) extra space for variables such as size and loop indices.

Dynamic Array Note

In a dynamic array implementation, addFirst(value), addLast(value), and insert(index, value) can resize the backing array when it is full. A resize takes \(O(n)\) time because the current values must be copied. If capacity grows geometrically, repeated calls to addLast(value) have amortized \(O(1)\) time per addition. However, addFirst(value) and general insert(index, value) are still \(O(n)\) in the worst case because they may need to shift values.

Tradeoffs

  • Array-based lists provide fast indexed access. The value at index i is stored directly in A[i].
  • In a fixed-size array, the capacity is known in advance, so the implementation is simple and memory use is predictable.
  • A fixed-size array can overflow. If the array is full, operations such as addFirst(value), addLast(value), and insert(index, value) cannot add another value unless the implementation uses a different policy.
  • Insertions and removals near the front or middle are expensive because values must shift to keep the list contiguous.
  • The backing array may contain unused capacity, so the implementation can use more space than the logical list size alone requires.
  • Array-based lists are usually cache-friendly because values are stored in adjacent array cells.
  • A dynamic array version avoids the fixed capacity limit in ordinary use by allocating a larger array when needed, but resizing adds occasional \(O(n)\) copying work.
  • This representation is a strong default when a program frequently uses indexing, scanning, or adding at the end.

Implementation 2: Singly Linked List with Tail

Basics

A singly linked list stores each value in a separate node. Each node stores a value and a next reference to the following node. The list itself stores a head reference to the first node. In this implementation, it also stores a tail reference to the last node and a size variable.

The tail reference is what makes this version different from the simplest singly linked list, which stores only head. With tail, addLast(value) can attach a new node directly after the current last node. Without tail, adding at the end would require traversing the whole list to find the last node.

In the logical list [12, 4, 18, 7], the values can be represented as a chain of four nodes. The head reference points to the node storing 12, and the tail reference points to the node storing 7. The final node's next reference is null.

Visual Representation of a Singly Linked List with Tail

The logical order is determined by the links, not by adjacent memory locations. Following next references from head visits the values in list order.

The main invariant is that head points to the first node, tail points to the last node, and following next references from head visits all nodes in order and then reaches null. If the list is empty, then both head and tail should be null, and size should be 0.

How the Operations Work

A singly linked list with tail stores references head and tail, along with an integer size. The head reference gives direct access to the first node. The tail reference gives direct access to the last node.

Operations that have an index parameter (e.g., get, set, insert, remove) must first check that the index is valid. Other operations need to check that the list is not empty before they can proceed (e.g., first, last, removeFirst, removeLast). In these cases, the implementation should follow its documented policy for invalid input, such as throwing an exception, returning a special value, or reporting failure without changing the list. The descriptions below assume that all preconditions are satisfied and describe the main steps of the operation without mentioning error handling or bounds checks.

size, isEmpty, and clear

  • size() returns the value of the size variable.
  • isEmpty() checks whether size == 0, or equivalently whether head == null.
  • clear() sets head and tail to null and sets size to 0.

first and last

  • first() returns head.value.
  • last() returns tail.value.

get and set

A singly linked list cannot jump directly to index i. To reach a position, the implementation starts at head and repeatedly follows next references. After following one next reference, it reaches index 1; after following two, it reaches index 2; and so on. In general, reaching index index requires following next references index times.

  • get(index) traverses to the node at position index and returns that node's value.
  • set(index, value) traverses to the node at position index and replaces that node's value with value.

addFirst

  • addFirst(value) creates a new node whose next reference points to the old head.
  • Then head is updated to point to the new node.
  • If the list was empty, the new node is both the first and last node, so tail must also point to it.
  • Finally, size is incremented.

addLast

  • addLast(value) creates a new node whose next reference is null.
  • If the list is empty, both head and tail point to the new node.
  • Otherwise, attach the new node after the old tail by setting tail.next = newNode, then update tail so it points to newNode.
  • Finally, size is incremented.

This is the operation that most clearly benefits from storing a tail reference. Without tail, the implementation would have to traverse from head to find the last node before adding the new one.

insert

  • If index == 0, insert(index, value) calls addFirst(value). This handles the special case where the head reference must move to the new node.
  • If index == size, insert(index, value) calls addLast(value). This handles the special case where the tail reference must move to the new node.
  • Otherwise, the implementation traverses to the node at position index - 1, which is the node before the insertion position.
  • It then creates a new node, makes the new node point to the old successor, makes the previous node point to the new node, and increments size.

The order of reference updates matters. The new node should first point to the old successor. Then the previous node can point to the new node. Reversing those steps can lose access to the rest of the list.

removeFirst

  • removeFirst() saves head.value, moves head to head.next, decrements size, and returns the saved value.
  • If the removed node was the only node, the list becomes empty, so tail must also be set to null.

removeLast

removeLast() is more expensive in a singly linked list. Even though tail points to the last node, the implementation also needs the node before tail so it can change that node's next reference to null. Since nodes only point forward, the implementation must traverse from head to find the predecessor of tail.

  • If the list has only one node, removeLast() can call removeFirst().
  • Otherwise, it traverses to the node before tail, saves tail.value, sets that predecessor's next reference to null, updates tail to the predecessor, decrements size, and returns the saved value.

remove

  • If index == 0, remove(index) calls removeFirst(). This handles the special case where the head reference must move.
  • Otherwise, the implementation traverses to the node at position index - 1, which is the node before the one being removed.
  • It then saves the removed value, bypasses the node after the predecessor, updates tail if the removed node was the last node, decrements size, and returns the removed value.

contains, indexOf, and delete

Search operations traverse from head toward the end of the list. They maintain a current node reference and, depending on the operation, may also maintain an index counter or a previous node reference. At each step, the implementation checks whether the current node stores the search value.

  • indexOf(value) returns the first index whose node stores value, or -1 if no match is found. This operation maintains an index counter while it traverses the list.
  • contains(value) can be implemented by checking whether indexOf(value) != -1.
  • delete(value) searches for the first node storing value and removes it if it exists. This operation maintains references to both the current node and the previous node, since the previous node's next reference must change when the current node is removed. It must also handle the boundary cases where the node to delete is the first or last node.

Linked List Pseudocode

The following pseudocode assumes a node type with two fields: value, which stores the node's data, and next, which refers to the following node. The list itself stores three variables: head, tail, and size.

The implementation includes a helper operation nodeAt(index) that returns a reference to the node at a given index. It assumes that the index is valid, so the caller must check the index before calling nodeAt(index).

Invalid operations report an error and stop. This includes invalid indices and attempts to access or remove from an empty list. Search operations use the same convention as before: indexOf(value) returns -1 when the value is absent, and delete(value) returns false when no value is deleted. 

isEmpty():
    return size == 0

size():
    return size

clear():
    head = null
    tail = null
    size = 0

first():
    if isEmpty():
        report empty-list error and stop
    return head.value

last():
    if isEmpty():
        report empty-list error and stop
    return tail.value

addFirst(value):
    newNode = new Node(value)
    newNode.next = head
    head = newNode
    if tail == null:
        tail = newNode
    size = size + 1

addLast(value):
    newNode = new Node(value)
    if isEmpty():
        head = newNode
        tail = newNode
    else:
        tail.next = newNode
        tail = newNode
    size = size + 1

nodeAt(index):
    cur = head
    for i = 0 to index - 1:
        cur = cur.next
    return cur

get(index):
    if index < 0 or index >= size:
        report invalid index and stop
    return nodeAt(index).value

set(index, value):
    if index < 0 or index >= size:
        report invalid index and stop
    nodeAt(index).value = value

insert(index, value):
    if index < 0 or index > size:
        report invalid index and stop
    if index == 0:
        addFirst(value)
    else if index == size:
        addLast(value)
    else:
        prev = nodeAt(index - 1)
        newNode = new Node(value)
        newNode.next = prev.next
        prev.next = newNode
        size = size + 1

removeFirst():
    if isEmpty():
        report empty-list error and stop
    value = head.value
    head = head.next
    size = size - 1
    if head == null:
        tail = null
    return value

removeLast():
    if isEmpty():
        report empty-list error and stop
    if size == 1:
        return removeFirst()
    prev = nodeAt(size - 2)
    value = tail.value
    prev.next = null
    tail = prev
    size = size - 1
    return value

remove(index):
    if index < 0 or index >= size:
        report invalid index and stop
    if index == 0:
        return removeFirst()
    prev = nodeAt(index - 1)
    oldNode = prev.next
    value = oldNode.value
    prev.next = oldNode.next
    if oldNode == tail:
        tail = prev
    size = size - 1
    return value

indexOf(value):
    cur = head
    index = 0
    while cur != null:
        if cur.value == value:
            return index
        cur = cur.next
        index = index + 1
    return -1

contains(value):
    return indexOf(value) != -1

delete(value):
    if isEmpty():
        return false
    if head.value == value:
        removeFirst()
        return true

    prev = head
    cur = head.next
    while cur != null:
        if cur.value == value:
            prev.next = cur.next
            if cur == tail:
                tail = prev
            size = size - 1
            return true
        prev = cur
        cur = cur.next
    return false

The clear() operation above simply disconnects the list by setting head and tail to null. In a language with garbage collection, the unreachable nodes can be reclaimed automatically. In a language with manual memory management, the implementation should first traverse the list and free each node.

Implementation Analysis

The running times below come from two facts about the representation: the list has direct references to the first and last nodes, but reaching a general position requires following next references from head.

  • size(), isEmpty(): \(O(1)\). Each checks or returns a stored variable.
  • first(), last(): \(O(1)\). The implementation stores direct references to both the first and last nodes.
  • addFirst(value): \(O(1)\). It creates one node and changes a constant number of references.
  • addLast(value): \(O(1)\). The tail reference lets the implementation attach a new node at the end without traversal.
  • get(index), set(index, value): \(O(n)\) in the worst case, because reaching index index may require following many links from head. More precisely, these operations are \(O(i)\) when index == i, so they are \(O(n)\) in the worst case when index is near the end of the list.
  • insert(index, value): \(O(n)\) in the worst case. Inserting at the front is \(O(1)\) by calling addFirst(value), and inserting at the back is \(O(1)\) by calling addLast(value). Inserting at a general index requires traversal to the predecessor. As with the get and set operations, the time complexity is \(O(i)\) when index == i, so it is \(O(n)\) in the worst case when index is near the end of the list.
  • removeFirst(): \(O(1)\). It moves head to the next node and possibly clears tail.
  • removeLast(): \(O(n)\). The implementation must find the node before tail, which requires traversing the entire list. This is one of the main disadvantages of a singly-linked list implementation. This would improve to \(O(1)\) if we used a doubly-linked list.
  • remove(index): \(O(n)\) in the worst case. Removing the first value is \(O(1)\), but removing at a general index requires traversal to the predecessor. Again, the time complexity is more precisely \(O(i)\) when index == i, so it is \(O(n)\) in the worst case when index is near the end of the list.
  • indexOf(value), contains(value): \(O(n)\) in the worst case, because the value may be absent or stored only at the last node.
  • delete(value): \(O(n)\) in the worst case. It may have to search the whole list before deleting, or before determining that the value is absent.
  • clear(): \(O(1)\) if it only sets head = null, tail = null, and size = 0. In a language with manual memory management, freeing all nodes would take \(O(n)\).
Storage Used

A linked list uses \(O(n)\) space for \(n\) stored values. Each value is stored inside a node which store both the value and a reference to the next node, so each stored value has \(O(1)\) overhead for the node structure. The list itself stores \(O(1)\) extra information: head, tail, and size.

Tradeoffs

  • A linked list allocates storage one node at a time, so it does not reserve extra unused slots the way an array-based list often does.
  • addFirst(), addLast(), removeFirst(), first(), and last() are constant-time operations.
  • removeLast() is still linear time because a singly linked list cannot move backward from tail to the previous node. A doubly linked list can make this operation constant time, but it requires an additional reference in each node and slightly more complex insertion and removal code.
  • Indexed access is slow compared with an array-based list because the implementation must follow links to reach a position.
  • Insertion or removal at a known node can be efficient, but the List ADT operations are index-based, so finding the right node is often part of the cost.
  • Each node has reference overhead, so a linked list usually uses more memory per stored value than an array-based list.
  • Linked nodes may be scattered in memory, making traversal less cache-friendly than scanning an array.
  • This representation is most useful when a program frequently updates the front, adds or reads at the back, and does not rely heavily on indexed access.

Implementation Cost Summary

The two implementations represent the same List ADT, but they make different operations efficient. The fixed-size array-based list is strongest when the program needs indexed access, indexed updates, or adding at the end when space is available. The singly linked list with tail is strongest for operations at the front and for adding at or reading from the end.

Applications

Lists are one of the most common ways to store a collection of values when the order matters. They are more flexible than stacks and queues because they support access by position, not just access at one or two restricted ends. The best implementation depends on how the list is used.

  • General-purpose ordered collections: Lists are used whenever a program needs to keep values in a meaningful order, such as names in a roster, assignments in a gradebook, songs in a playlist, or messages in a conversation.
  • Indexed data: Array-based lists are useful when positions matter and the program frequently calls operations such as get(index) and set(index, value). Many tables, dynamic programming arrays, and simulation states rely on efficient indexed access.
  • Accumulating results: A dynamic array is often used to collect results when the final number of values is not known ahead of time. The program can repeatedly call addLast(value) and allow the list to grow as needed.
  • Stacks, queues, and deques: These structures can be implemented using a restricted set of list operations. For example, a stack can use one end of a list, a queue can add at one end and remove at the other, and a deque can allow additions and removals at both ends.
  • Graph representations: Many graph algorithms represent a graph using adjacency lists. Each vertex stores a list of its neighbors. Depending on the application, these neighbor lists might be array-based, linked-based, or implemented by a library container.
  • Local insertion and deletion: Linked lists are useful when a program already has a reference to the relevant location and needs to insert or remove nearby nodes. This appears in some low-level data structures, memory-management systems, and iterator-based container operations.
  • Maintaining changing sequences: Lists are useful when the order changes over time, such as editing a sequence of tasks, maintaining a list of active events in a simulation, or storing a mutable collection of objects in a game or interface.

These applications do not all favor the same representation. Applications that rely heavily on indexing usually favor array-based lists, while applications that work near known nodes or update the front frequently may benefit from linked storage. Choosing a list implementation means matching the representation to the operations the application performs most often.

Comparisons and Tradeoffs

The List ADT describes what operations are available, but the implementation determines which operations are efficient. The fixed-size array-based list and the singly linked list with tail both store the same kind of logical sequence, but they organize the data in very different ways.

Indexing vs. Traversal

The biggest advantage of an array-based list is direct indexed access. Once an index is checked, get(index) and set(index, value) can go directly to A[index]. A linked list cannot do this because the location of the \(i\)th value is not computed from the index. The implementation must start at head and follow next references until it reaches the desired node.

Shifting vs. Relinking

Array-based lists keep all logical values in consecutive array positions. This makes indexing fast, but it means that insertion or removal near the front may require many values to shift. Linked lists avoid shifting values. Once the relevant node or predecessor is known, an insertion or removal changes only a few references. However, if the operation is specified by index or by value, the linked list may still spend linear time finding the correct location.

Front and Back Operations

The two implementations behave differently at the ends of the list. In a singly linked list with a tail reference, addFirst(value), removeFirst(), first(), addLast(value), and last() are all constant-time operations. The exception is removeLast(), which is linear time because a singly linked list cannot move backward from tail to the previous node.

In an array-based list, last(), removeLast(), and addLast(value) are efficient when there is available capacity. But addFirst(value) and removeFirst() are expensive because they require shifting existing values.

Memory Use

A fixed-size array-based list reserves a fixed number of array cells. Some of those cells may be unused if the logical list is smaller than the array capacity. A linked list does not reserve unused array slots, but each node stores an extra next reference in addition to the value.

Practical Performance

Even when two operations have the same Big-O running time, their practical performance can differ. Array-based lists are usually cache-friendly because neighboring values are stored near each other in memory. Linked lists may scatter nodes throughout memory, so traversal can be slower in practice even when the asymptotic cost is the same.

Choosing an Implementation

An array-based list is usually the better default when a program frequently uses indexing, scanning, or adding at the end when capacity is available. A linked list is more appropriate when the program frequently updates the front of the list or already has references to the nodes where insertions and deletions should occur. The important lesson is not that one representation is always better, but that the right representation depends on the operations the program performs most often.

Variations and Extensions

The two implementations in this chapter are not the only ways to represent a list. They are useful baseline designs because they show the main tradeoff between direct indexing and linked traversal. Many real data structures adjust these ideas to improve particular operations or support additional behavior.

Dynamic Array Lists

The array-based implementation in this chapter uses a fixed-size backing array. A dynamic array version can grow when it runs out of room. When the backing array is full, the implementation allocates a larger array, copies the current values into it, and then continues the operation that needed more space.

Dynamic arrays usually grow geometrically, such as by doubling the capacity. This means that an individual addition can occasionally take \(O(n)\) time because of copying, but a long sequence of additions at the end has amortized \(O(1)\) time per addition. Some implementations also shrink the backing array when the list becomes much smaller than its capacity. Shrinking can save memory, but it must be done carefully so that repeated additions and removals do not cause repeated resizing.

Doubly Linked Lists

A doubly linked list gives each node two links: next and prev. The next link points toward the following node, and the prev link points toward the previous node. This extra link allows movement in both directions and makes it possible to remove a known node without first finding its predecessor.

Doubly linked lists also make removeLast() efficient when the list stores a tail reference, because the implementation can move backward from the tail to the previous node. The tradeoff is extra memory per node and more reference updates during insertion and deletion.

Circular Linked Lists

In a circular linked list, the final node points back to the first node instead of pointing to null. This can be useful for round-robin scheduling, repeated cycling through values, or structures where there is no natural end. Circular lists require careful stopping conditions during traversal, since following links never reaches null.

Sentinel Nodes

A sentinel node is a special dummy node that does not store a real list value. Sentinels can simplify boundary cases by ensuring that there is always a node before the first real value or after the last real value. This can make insertion and deletion code more uniform, but it adds an extra concept that the implementation must keep separate from the actual data.

Sorted Lists

A sorted list keeps its values in increasing or decreasing order. Instead of inserting a new value at an arbitrary position, the implementation searches for the correct position and inserts the value there. Searching for a value can stop early once the scan passes the position where the value would have appeared, but insertion may still require shifting values in an array-based list or traversing links in a linked list.

Unrolled Linked Lists

An unrolled linked list stores several values in each node instead of storing only one value per node. This reduces the number of links and can improve cache behavior while still allowing linked-style growth. The tradeoff is that insertion and deletion inside a node may require shifting values within that node.

Skip Lists

A skip list augments a sorted linked structure with extra forward links that skip over many values. These extra links make search, insertion, and deletion much faster on average than scanning a basic linked list. Skip lists are more advanced than the list implementations in this chapter, but they show how adding structure can improve search performance.

These variations reinforce the main theme of the chapter: a list is an abstract sequence, while an implementation is a particular set of choices about storage, access, and update costs. Different choices are useful for different workloads.

Common Pitfalls

List implementations are conceptually simple, but many errors come from boundary cases and from confusing the abstract list with its underlying representation. The following pitfalls are especially common when implementing fixed-size array-based lists or singly linked lists with tail.

Confusing Size and Capacity

In an array-based list, size is the number of meaningful values in the list, while capacity is the number of allocated array cells. Operations such as get(index), set(index, value), and remove(index) should check indices against size, not against the array's capacity. An unused array cell is not part of the list.

Using the Wrong Bounds for Insert

The operation insert(index, value) has slightly different bounds than get(index), set(index, value), and remove(index). For get, set, and remove, the valid indices are 0 through size - 1. For insert, the valid positions are 0 through size. Inserting at size means adding after the current last value.

Shifting in the Wrong Direction

In an array-based list, inserting requires shifting values to the right before writing the new value. That shift must proceed from right to left so that values are not overwritten before being copied. Removing shifts values left, so that shift proceeds from left to right.

Forgetting to Check Capacity Before Adding

A fixed-size array-based list must check that there is room before adding a new value. This matters for addFirst(value), addLast(value), and insert(index, value). If the array is already full, the operation should report overflow or follow some other documented full-list policy. Without this check, the implementation may try to write outside the bounds of the array.

Leaving Stale References in an Array

After removing an element from an array-based list, the old last logical position is no longer part of the list. In languages with garbage collection, it is often useful to set that array cell to null when the stored values are references. This prevents the array from accidentally keeping an object alive after it has been removed from the list.

Losing Part of a Linked List

In a linked list, the order of reference updates matters. When inserting a node after another node, the new node should first point to the old successor. Then the previous node can point to the new node. If the old link is overwritten too early, the rest of the list can become unreachable.

Forgetting to Update Tail

A singly linked list with a tail reference must keep tail consistent with the actual last node. If an operation adds to an empty list, both head and tail should point to the new node. If an operation removes the last remaining node, both should become null. If an operation removes the current tail, tail must move to the previous node.

Assuming Tail Makes Every Back Operation Constant Time

A tail reference makes last() and addLast(value) constant time, but it does not make removeLast() constant time in a singly linked list. To remove the last node, the implementation must also find the node before it. Since nodes only point forward, that search starts at head and takes linear time in the worst case.

Confusing Removal by Position and Removal by Value

In this chapter, remove(index) removes by position, while delete(value) removes the first matching value. Mixing these up can produce subtle errors, especially when the list stores integers. For example, remove(3) means remove the value at index 3, not remove the value 3. What is worse is in that in languages that allow overloading, same method name can be used for both operations. For instance, in Java, remove(int index) removes by position, while remove(Object value) removes by value. So what does remove(3) do on an array of Integers? I will leave it as an exercise for the reader to find out.

Ignoring Empty-List Cases

Operations such as first(), last(), removeFirst(), and removeLast() require the list to contain at least one value. A complete implementation should define what happens when these operations are called on an empty list, rather than accidentally reading invalid array positions or dereferencing null.

Summary

A list is an ordered collection of values with positions. Unlike a stack or queue, a list allows operations that refer directly to an index, such as get(index), set(index, value), insert(index, value), and remove(index). Lists also support operations at the ends, search operations, and utility operations such as size(), isEmpty(), and clear().

The same List ADT can be implemented in different ways. A fixed-size array-based list stores values in consecutive positions of a backing array. This makes indexed access and update fast, but insertions and removals near the front or middle may require shifting many values. A singly linked list with a tail reference stores values in nodes connected by next references. This makes several end operations efficient, but indexed access requires traversal.

Key Takeaways

  • A list stores values in order and identifies them by position.
  • remove(index) removes by position; delete(value) removes the first matching value. At least in our presentation. Be careful to know which version is meant when you come across it in other contexts.
  • Fixed-size array-based lists provide \(O(1)\) indexed access and \(O(1)\) addition at the end when space is available.
  • Array-based insertions and removals can take \(O(n)\) time because values may need to shift.
  • Singly linked lists with a tail pointer support efficient front operations and efficient addition at the back.
  • removeLast() is still \(O(n)\) for a singly linked list because the previous node must be found.
  • Linked lists require traversal for indexed access, indexed update, search, and most middle operations.
  • Implementation details such as capacity checks, bounds checks, reference updates, and empty-list cases are essential for correctness.

    • resize(newCapacity): Add this helper method to allocate a larger backing array, copy the logical values A[0] through A[count - 1], and replace the old array.
    • ensureCapacity(): Add this helper method to check if the backing array is full, and if so, call resize(2 * A.length).
    • addLast(value): call ensureCapacity(), then append as before.
    • addFirst(value): call ensureCapacity(), then shift right and insert as before.
    • insert(index, value): check the index, call ensureCapacity(), then shift right and insert as before.

    All other requirements from the fixed-size array activity still apply: the logical list occupies A[0] through A[count - 1], invalid indexed operations should fail without changing the list, and size() should return count in \(O(1)\) time.

    Challenge: After removals, shrink the backing array when the list becomes sparse. One reasonable policy is to shrink when count <= A.length / 4, cutting the capacity in half. Do not shrink below a fixed minimum capacity, such as the initial capacity.

    The challenge version should add one helper and update the removal operations:

    • shrinkIfNeeded(): if the list is sparse enough, such as count <= A.length / 4, shrink the backing array while preserving the logical values.
    • removeFirst(), removeLast(), and remove(index): after every successful removal, call shrinkIfNeeded().
    • delete(value): call shrinkIfNeeded() only if the value was found and deleted. If the value is not present, the list should not change.

    Be careful not to shrink too aggressively. If the array shrinks whenever count == A.length / 2, then a sequence of alternating additions and removals can cause repeated resizing. Waiting until the array is at most one-quarter full gives the implementation some buffer.
