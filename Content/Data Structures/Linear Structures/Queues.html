Queues

Overview

A queue stores values so that the earliest added value is the first one removed. This rule is called first-in, first-out, or FIFO.

A queue has two active ends. New values enter at the back, and removals happen at the front. Values in the middle are waiting in order, but the queue interface does not allow the caller to remove an arbitrary middle value or skip ahead to a later arrival.

This restriction is useful because many programs need fairness by arrival order. Waiting lines, print jobs, network buffers, task schedulers, and producer-consumer systems all use queue behavior. Later in the course, queues will also appear in algorithms such as level-order tree traversal and breadth-first search in graphs. A queue is an abstract data type, so the FIFO rule matters more than the particular storage representation. The same queue behavior can be implemented with linked nodes, an ordinary array, a circular array, or a library container.

When we represent a queue using text, we usually show the front on the left and the back on the right. For example, the queue from the diagram above is written as [14, 8, 31], with 14 at the front and 31 at the back.

Core Operations

The following are the core operations of a queue ADT. The ones in bold are the essential FIFO operations. Exact method names and error-handling policies vary by language and implementation, but the same basic operations are needed to maintain the queue abstraction.

Operation Description
enqueue(value)   Add value to the back of the queue. If the queue is full, the implementation must report overflow or use a documented full-queue policy.
dequeue() Remove and return the front value. If the queue is empty, the implementation must report underflow or use a documented empty-queue policy.
front() Return the front value without removing it. Some libraries call this operation peek().
isEmpty() Report whether the queue currently stores no values.
size() Return the number of values currently stored.
isFull() (Optional) For a bounded queue, report whether the queue currently stores the maximum number of values.

A bounded queue needs an overflow policy for enqueue when it is full. It might return false, throw an exception, block until space is available, overwrite an old value, or reject the operation in some other documented way. A resizable queue can grow its backing storage instead, but it can still run out of memory in a real program. Similarly, dequeue and front need a defined underflow policy for the empty-queue case.

Enqueue

enqueue makes a new value the back value. It does not disturb the relative order of the values already waiting. If the queue previously stored [4, 7], then enqueue(9) updates the queue to [4, 7, 9].

Dequeue

dequeue removes the current front and returns it to the caller. Calling dequeue() on a queue with contents [4, 7, 9] returns 4 and leaves the queue with contents [7, 9].

Dequeuing from an empty queue is called underflow. A clean queue implementation should define this case explicitly rather than accessing invalid memory or returning an arbitrary value.

Front

front reads the front value without removing it. Calling front() on [4, 7, 9] returns 4 and leaves the queue unchanged. It has the same empty-queue issue as dequeue().

Example Trace of Queue Operations

Below we start with an empty bounded queue that can hold up to four elements and perform the following sequence of operations: dequeue(), enqueue(4), enqueue(7), enqueue(9), dequeue(), enqueue(2), front(), enqueue(5), enqueue(8), dequeue().

Operation Queue Afterward Return Value
dequeue() [] underflow
enqueue(4) [4] none
enqueue(7) [4, 7] none
enqueue(9) [4, 7, 9] none
dequeue() [7, 9] 4
enqueue(2) [7, 9, 2] none
front() [7, 9, 2] 7
enqueue(5) [7, 9, 2, 5] none
enqueue(8) [7, 9, 2, 5] overflow
dequeue() [9, 2, 5] 7

In the example, we specified return values of underflow and overflow. The most common ways of actually doing this are to return a boolean or throw an exception. In the former case, instead of having "none" as a return value, the calls to enqueue would return true when the enqueue succeeded and false when it failed. dequeue and front are more difficult to handle with a boolean return because they also need to return a value when successful. If the queue is storing objects, one option is to return null on underflow, but that only works if null is not a valid queue value. Another option is to return a known invalid value, such as -1, but that only works if the queue is storing integers and -1 is not a valid value. The fallback is to throw an exception, which is more flexible but also more complex to use because the caller must handle the possibility of an exception.

Implementation Options

The queue ADT can be implemented using several representations. This page develops a linked queue and an ordinary array queue in detail, then outlines the circular array queue. The circular array version is often the efficient array-based implementation used in practice, but the simpler ordinary array version is useful for seeing exactly where the shifting cost comes from.

Implementation 1: Linked Queue

Basics

A linked queue stores each item in a separate node. Each node contains a stored value and a reference to the next node behind it in the queue. The queue itself keeps two references: head, which points to the front node, and tail, which points to the back node.

The tail reference is the important addition compared with a simple singly linked list that stores only a head reference. Without tail, adding at the back would require walking from the front to the last node every time, taking \(O(n)\) time. With tail, enqueue can link the new node after the old tail and update tail in constant time.

The main invariant is that head points to the front node, tail points to the back node, and following next references from head visits the queue from front to back. If the queue is empty, then both head == null and tail == null.

Visual Representation of a Linked Queue

Here head points to the front node, which stores 12, and tail points to the back node, which stores 19. An enqueue adds a new node after 19 and moves tail. A dequeue removes 12 and moves head to the node storing 7.

How the Operations Work

The implementation keeps references head and tail. We also maintain an integer variable count so that size() can return the number of stored items in constant time. A linked queue does not normally provide isFull(), because it can create new nodes until memory is exhausted.

isEmpty

isEmpty() checks whether head == null. In a correct empty linked queue, tail is also null.

Enqueue

enqueue creates a new node whose next reference is null. If the queue is empty, the new node is both the front and the back, so both head and tail point to it. Otherwise, the old tail.next is set to the new node, and then tail is updated to the new node. The operation also increments count.

Dequeue

dequeue first checks whether the queue is empty. If not, head.value is the value to remove. The operation saves that value, updates head to head.next, decrements count, and returns the saved value. If the removed node was the only node, then head becomes null, so the implementation must also set tail = null. Forgetting this step leaves tail pointing to a node that is no longer in the queue.

Front

front checks whether the queue is empty. If the queue is nonempty, it returns head.value without changing head, tail, or any links.

Size

If the implementation maintains count, then size() returns count. Without such a variable, computing the size would require following links and counting nodes, which would take \(O(n)\) time.

Linked Queue Pseudocode

The following pseudocode assumes we have head, tail, and count variables defined in the appropriate scope. 

isEmpty():
    return head == null

enqueue(value):
    newNode = new Node(value)
    if isEmpty():
        head = newNode
        tail = newNode
    else:
        tail.next = newNode
        tail = newNode
    count = count + 1

dequeue():
    if isEmpty():
        report underflow and stop
    value = head.value
    head = head.next
    count = count - 1
    if head == null:
        tail = null
    return value

front():
    if isEmpty():
        report underflow and stop
    return head.value

size():
    return count

Implementation Analysis

In the linked implementation, each core operation changes only a constant number of references. No operation shifts values, scans the whole queue, or copies all stored items. As long as count is maintained, each basic queue operation takes constant time.

  • enqueue: \(O(1)\). It creates one node, possibly sets head, updates tail.next and tail, and increments count.
  • dequeue: \(O(1)\). It checks for underflow, saves head.value, moves head, possibly clears tail, decrements count, and returns the saved value.
  • front: \(O(1)\). It checks for underflow and returns head.value.
  • isEmpty: \(O(1)\). It checks whether head == null.
  • size: \(O(1)\) if the implementation maintains count. Without count, computing the size would take \(O(n)\).
Storage used:

This implementation uses \(O(n)\) space for \(n\) stored items. Each item is stored in a node, and each node stores at least one reference, next. In addition to the nodes, the queue uses \(O(1)\) space for variables such as head, tail, and count.

Tradeoffs

  • A linked queue grows one node at a time, so it does not need a fixed capacity.
  • The tail reference is essential for constant-time enqueue at the back.
  • Each stored value has node overhead, including at least one reference.
  • Nodes are not necessarily stored next to one another in memory, so linked queues are usually less cache-friendly than array queues.
  • The empty and one-element cases require care because both head and tail must remain consistent.

Implementation 2: Array Queue

Basics

The simplest array queue stores the front value at index 0, the next value at index 1, and so on. It uses an array A and an integer count that stores the number of values currently in the queue. The logical queue consists exactly of A[0] through A[count - 1].

In this representation, enqueue is simple: if there is room, store the new value in A[count] and increment count. The front value is always A[0]. The cost appears when the queue removes the front. After dequeue removes A[0], every remaining item must shift one position left so that the new front is again at index 0.

This implementation is easy to understand and useful for comparison, but it is not the preferred array implementation for a queue with many dequeues. The circular array implementation outlined later avoids the shifting by moving an index instead of moving all values.

Visual Representation of an Ordinary Array Queue

A =
12 7 19
count = 3
0 1 2 3 4 5

Here the queue contains [12, 7, 19], with 12 at the front and 19 at the back. The next enqueue would store a value in index 3. A dequeue would remove 12, shift 7 into index 0, shift 19 into index 1, and update count to 2.

How the Operations Work

The implementation keeps queue entries in A[0] through A[count - 1]. Positions from count through A.length - 1 are unused capacity.

isEmpty

isEmpty() checks whether count == 0.

isFull

isFull() checks whether count == A.length. This operation is relevant for a fixed-size array queue (which is what we are discussing here). A resizable array queue may not expose isFull(), since it can grow the backing array when more space is needed.

Enqueue

If count < A.length, enqueue stores the new value in A[count], increments count, and reports success. If count == A.length, the fixed-size version shown here returns false to report overflow.

Dequeue

dequeue first checks whether the queue is empty. If it is not empty, the value to remove is A[0]. The operation saves that value, shifts each remaining item one position left, decrements count, and returns the saved value. Clearing the old last slot can help garbage collection in languages with references, but it is not part of the abstract queue operation.

Front

front checks whether the queue is empty. If not, it returns A[0] without shifting or changing count. If the queue is empty, it reports underflow or uses some other defined policy.

Size

size() returns count, the number of stored items. This is not the same as the capacity of the queue, which is the length of the backing array.

Array Queue Pseudocode

The following pseudocode assumes a fixed-size array A and an integer count. Since this version does not resize the array, enqueue returns false when the queue is full. 

isEmpty():
    return count == 0

isFull():
    return count == A.length

enqueue(value):
    if isFull():
        return false
    A[count] = value
    count = count + 1
    return true

dequeue():
    if isEmpty():
        report underflow and stop
    value = A[0]
    for i = 1 to count - 1:
        A[i - 1] = A[i]
    count = count - 1
    return value

front():
    if isEmpty():
        report underflow and stop
    return A[0]

size():
    return count

Implementation Analysis

In the ordinary array implementation, enqueue, front, isEmpty, isFull, and size are constant-time operations. The costly operation is dequeue, because it shifts all remaining values left.

  • enqueue: \(O(1)\). It checks whether the array is full, writes into A[count], increments count, and returns a Boolean value.
  • dequeue: \(O(n)\) in the worst case for a queue with \(n\) items. It removes the front value and shifts the remaining \(n - 1\) values left.
  • front: \(O(1)\). It checks whether the queue is empty and returns A[0].
  • isEmpty: \(O(1)\). It checks whether count == 0.
  • isFull: \(O(1)\). It checks whether count == A.length.
  • size: \(O(1)\). It returns count.
Storage used:

This implementation uses \(O(c)\) space, where \(c\) is the capacity of the backing array. If the queue currently contains \(n\) items, then the array has \(c - n\) unused slots. In addition to the array, the implementation uses \(O(1)\) space for variables such as count and loop indices.

Tradeoffs

  • The ordinary array queue is simple and keeps the logical queue starting at index 0.
  • enqueue and front are constant time.
  • dequeue is expensive because it shifts all remaining elements.
  • A bounded version has predictable capacity but must report overflow when full.
  • A circular array queue keeps the array representation but avoids the shifting cost.

Implementation 3: Circular Array Queue

Basics

A circular array queue is the standard way to make an efficient array-backed queue. The ordinary array version keeps the logical queue in positions A[0] through A[count - 1], so at least one operation must shift values. The circular version stops insisting that the queue begin at index 0. Instead, it stores a frontIndex and a count.

The frontIndex tells where the current front value is stored, and count tells how many values are currently in the queue. The next enqueue position is computed as (frontIndex + count) % A.length. When an index reaches the physical end of the array, it wraps back to index 0 using modulo arithmetic.

Notice that count has a slightly different role than it had in the ordinary array implementation. In the ordinary version, count also identified the next open position because the queue always started at A[0]. In the circular version, count still records the number of stored values, but the next open position must be computed from both frontIndex and count.

Visual Representation of a Circular Array Queue

A =
28 9 14 22 31
frontIndex = 2, count = 5
A =
0 1 2 3 4 5
frontIndex = 2, count = 5

Here frontIndex = 2, so the front value is 9. Since count = 5, the logical queue contains five values: [9, 14, 22, 31, 28]. The order wraps around from index 5 back to index 0.

The next enqueue position is (frontIndex + count) % A.length = (2 + 5) % 6 = 1, so the next value would be stored at index 1.

How the Operations Work

This outline uses a fixed-size backing array A, an integer frontIndex, and an integer count. An empty queue has count == 0. The value of frontIndex is meaningful when the queue is nonempty; many implementations simply leave it at 0 when the queue is empty.

isEmpty

isEmpty() checks whether count == 0. This is independent of the value of frontIndex.

isFull

For a bounded circular array queue, isFull() checks whether count == A.length. If the queue is full, every array slot is part of the logical queue, even though the logical order may wrap around the physical end of the array.

Enqueue

To enqueue a value, first check whether the queue is full. If it is not full, compute the insertion position as (frontIndex + count) % A.length. Store the new value in that position and then increment count. No existing values are shifted.

The two examples below show an enqueue operation on a queue that has values [9, 14, 22]. The difference is that in the second one the values have wrapped around the end of the array. In both cases, the new value 8 is stored properly as the last element of the logical queue, but in different physical positions in the array. After the enqueue, the logical queue is [12, 7, 19, 8] in both cases.

Dequeue

To dequeue, first check whether the queue is empty. If it is not empty, save A[frontIndex], because that is the front value. Then advance frontIndex to (frontIndex + 1) % A.length, decrement count, and return the saved value. The old array slot may be cleared or simply ignored.

The two examples below show a dequeue operation on a queue that has values [12, 7, 19, 8]. In both cases, the front value 12 is removed and returned, but from a different physical position in the array. In addition, frontIndex wraps around to 0 in the second example since it was at the end of the array. After the dequeue, the logical queue is [7, 19, 8] in both cases.

Front

front() checks whether the queue is empty. If it is nonempty, it returns A[frontIndex] without changing frontIndex, count, or any array entries.

Size

size() returns count. As with the ordinary array implementation, this is the number of stored items, not the capacity of the queue.

Circular Array Queue Pseudocode

The following pseudocode assumes a fixed-size array A, an integer frontIndex, and an integer count. The enqueue operation returns false if the queue is full. The dequeue and front operations report underflow if the queue is empty. 

isEmpty():
    return count == 0

isFull():
    return count == A.length

enqueue(value):
    if isFull():
        return false

    backIndex = (frontIndex + count) % A.length
    A[backIndex] = value
    count = count + 1
    return true

dequeue():
    if isEmpty():
        report underflow and stop

    value = A[frontIndex]
    A[frontIndex] = empty // optional, for garbage collection
    frontIndex = (frontIndex + 1) % A.length
    count = count - 1
    return value

front():
    if isEmpty():
        report underflow and stop

    return A[frontIndex]

size():
    return count

Implementation Analysis

In the bounded circular array implementation, every operation uses only a constant number of arithmetic operations, comparisons, array accesses, and assignments. No operation shifts the stored values.

  • enqueue: \(O(1)\). It checks whether the queue is full, computes the next insertion position with modulo arithmetic, stores the new value, and increments count.
  • dequeue: \(O(1)\). It checks whether the queue is empty, saves the front value, advances frontIndex, decrements count, and returns the saved value.
  • front: \(O(1)\). It checks whether the queue is empty and then returns A[frontIndex].
  • isEmpty: \(O(1)\). It checks whether count == 0.
  • isFull: \(O(1)\). It checks whether count == A.length.
  • size: \(O(1)\). It returns count.
Storage used:

The implementation uses \(O(c)\) space, where \(c\) is the capacity of the backing array. If the queue currently contains \(n\) values, then \(n = count\), and the array has \(c - n\) unused slots. In addition to the array, the implementation uses only \(O(1)\) extra space for variables such as frontIndex and count.

Tradeoffs and Variants

  • A circular array queue avoids the \(O(n)\) shifting cost of the ordinary array queue, so both enqueue and dequeue take \(O(1)\) time.
  • The representation is compact and usually cache-friendly because the values are stored in one array.
  • The implementation is more subtle than the ordinary array version because the logical order of the queue may wrap around the physical end of the array.
  • A bounded circular array queue has a fixed capacity and must define what happens when enqueue is called on a full queue.
  • A resizable circular array queue can grow when full, but resizing is more complicated than in an ordinary array queue. The implementation usually copies the logical queue into a new array starting at index 0, then resets frontIndex to 0.
  • Some implementations store both frontIndex and a separate backIndex. This can save a small calculation during enqueue, but it is redundant when frontIndex and count are already available. It also adds another field that must be updated correctly.
  • Some two-index implementations do not store count. In that design, frontIndex == backIndex can be ambiguous: it might mean the queue is empty or full. One common fix is to leave one array slot unused. Then the queue is full when advancing the back index would make it equal to the front index. This removes the ambiguity, but an array of length \(c\) can store only \(c - 1\) values.
  • Another alternative is to store a Boolean flag such as isFull along with the two indices. This allows all array slots to be used, but the flag must be updated carefully after every enqueue and dequeue.
  • All of these variations of a circular array queue ensure that the queue operations maintain their time complexity guarantees, and no one of them is clearly superior to the others. When choosing one to implement, use the one that makes the most sense to you so you can be sure that you implement it correctly.

Implementation Cost Summary

The three implementations differ mostly in how they handle the two ends of the queue. A linked queue keeps direct references to both ends. An ordinary array queue keeps the front fixed at index 0, which makes dequeue expensive. A circular array queue uses an array more cleverly to keep both ends accessible without shifting values. The following table summarizes the costs of the core queue operations for each implementation.

For a queue implementation intended for regular use, both enqueue and dequeue should be constant-time operations. The ordinary array queue does not meet that goal because each dequeue may shift many values. It is useful as a stepping stone because it shows why the circular array queue is needed.

Between the linked queue and the circular array queue, the better choice depends on context. A linked queue grows naturally and avoids unused capacity, but each value requires a node and an extra reference. A circular array queue is usually more compact and cache-friendly, but a bounded version needs a full-queue policy, and a resizable version needs careful copying when the array grows.

Library Implementations

In everyday programming, it is usually better to use a standard library structure than to write a new queue from scratch. Library implementations are tested, efficient, and familiar to other programmers. In a data structures course, implementing queues by hand is still valuable because it clarifies the ADT, boundary cases, and representation tradeoffs.

The main lesson is that the library type does not have to be named Queue to be used as a queue. What matters is whether the program uses it through FIFO discipline: add at the back, remove from the front, and avoid operations that break the queue abstraction. In addition, not all library implementations are equally efficient for queue behavior. For example, like an array in other languages, a Python list is not a good choice for a queue because removing from the front is \(O(n)\). The Python collections.deque is designed for efficient operations at both ends, so it is a better choice for a queue in Python.

Applications

Queues appear whenever older waiting items should usually be handled before newer waiting items. In each application below, the important idea is that the structure preserves arrival order. The queue does not merely store items; it controls the order in which waiting work is handled.

  • Task scheduling: Print queues, job queues, and simple first-come-first-served schedulers use FIFO order when fairness by arrival time is desired.
  • Producer-consumer buffers: One part of a program enqueues work, data, or messages, while another part dequeues and processes them later.
  • Service-line simulations: Queues model customers, packets, orders, or requests waiting for service. Such simulations can estimate waiting time, queue length, and throughput.
  • Message passing: Programs often use queues to decouple senders from receivers. Senders can add messages without requiring the receiver to handle them immediately.
  • Sliding windows: A queue can store the active items in a window where new values enter at the back and old values leave from the front.
  • Streaming data: A queue can hold incoming data temporarily when data arrives faster than it can be processed.
  • Level-order tree traversal: A queue stores tree nodes whose children still need to be visited. This lets the traversal process one level before moving to the next.
  • Breadth-first search (in graphs): A queue stores discovered but unprocessed vertices so that BFS explores a graph layer by layer.

Example 1: Printer Queue

A printer queue stores documents waiting to be printed. When a document arrives, it is enqueued at the back. When the printer becomes available, the job at the front is dequeued and printed. This preserves arrival order: older waiting jobs print before newer waiting jobs.

The following pseudocode processes a sequence of events. Each event is either a new print job arriving or the printer becoming ready for the next job. 

processPrinterEvents(events):
    create an empty queue Q

    for each event in events:
        if event is a new print job:
            Q.enqueue(event.job)

        else if event means printer is ready:
            if Q.isEmpty():
                report "printer is idle"
            else:
                nextJob = Q.dequeue()
                print nextJob

Suppose the events are: 

arrive(Essay), arrive(Lab), printerReady(), arrive(Schedule),
printerReady(), arrive(Poster), printerReady(), printerReady(), printerReady()

Then the program will process the events in order, and the queue will evolve as shown in the following table.

Step Event Action Queue Afterward Printed Job
1 arrive(Essay) Enqueue Essay [Essay] none
2 arrive(Lab) Enqueue Lab [Essay, Lab] none
3 printerReady() Dequeue the front job [Lab] Essay
4 arrive(Schedule) Enqueue Schedule [Lab, Schedule] none
5 printerReady() Dequeue the front job [Schedule] Lab
6 arrive(Poster) Enqueue Poster [Schedule, Poster] none
7 printerReady() Dequeue the front job [Poster] Schedule
8 printerReady() Dequeue the front job [] Poster
9 printerReady() The queue is empty [] idle

The queue matters because the printer never needs to search for the next job. It always removes the front job. New arrivals are placed at the back and wait their turn.

Example 2: Producer-Consumer Buffer

A producer-consumer system has one part of a program producing work and another part consuming it. For example, one process might read requests from a network connection while another process handles those requests. A queue lets the producer add work quickly and lets the consumer process that work in arrival order. 

producer(items):
    for each item in items:
        Q.enqueue(item)

consumer():
    while not Q.isEmpty():
        item = Q.dequeue()
        process item

In a bounded queue, the producer may need to stop, wait, or reject new work when the queue is full. This prevents the program from using unlimited memory if work arrives faster than it can be processed.

Example 3: Hot Potato

A simple elimination game illustrates rotation through a queue. Put the players in a queue. Given a number of passes, each round consists of repeating the following two-step action exactly passes times: dequeue the front player, then immediately enqueue that same player at the back. After those rotations are complete, dequeue the front player one more time and eliminate them. Repeat until only one player remains, and that player is the winner. 

hotPotato(players, passes):
    create queue Q containing players in order

    while Q.size() > 1:
        repeat passes times:
            Q.enqueue(Q.dequeue())

        eliminated = Q.dequeue()
        report eliminated

    return Q.dequeue()

This example uses the queue in two ways. Moving a player from the front to the back simulates passing the potato, while removing the front player after the passes simulates elimination.

Example 4: Sliding Window Average

Suppose a program receives a stream of numbers and wants the average of the most recent \(k\) values. A queue stores the current window. Each new value is enqueued, and when the window becomes too large, the oldest value is dequeued. 

slidingAverage(stream, k):
    create an empty queue Q
    sum = 0

    for each value in stream:
        Q.enqueue(value)
        sum = sum + value

        if Q.size() > k:
            old = Q.dequeue()
            sum = sum - old

        report sum / Q.size()

The queue is appropriate because the value that leaves the window is always the oldest value still stored. Maintaining the running sum avoids recomputing the entire window average after each new item.

Connections and Comparisons

A queue has an intentionally limited interface. It allows insertion at the back and removal from the front, but it does not provide arbitrary access to the middle. This smaller interface is useful when the problem should preserve arrival order. The comparisons below separate the queue ADT from related data structures and from particular queue implementations.

  • Queue vs. stack: A queue removes the oldest stored item first, while a stack removes the newest stored item first. Use a queue when waiting order should be preserved. Use a stack when the most recent unfinished item should be handled next.
  • Queue vs. general list: A general list may allow access, insertion, and deletion at many positions. A queue exposes a smaller interface: add at the back, remove from the front, and inspect the front. This restriction makes the intended FIFO behavior clear.
  • Queue vs. deque: A deque, or double-ended queue, allows insertion and removal at both ends. A queue can be viewed as a restricted deque that only enqueues at the back and dequeues from the front.
  • Queue vs. priority queue: A FIFO queue removes the item that has been waiting the longest. A priority queue removes the item with highest priority, even if that item arrived later. Despite the similar name, a priority queue is a different abstract data type.
  • Linked queue vs. linked stack: A linked stack needs only one reference to the top because both push and pop happen at the same end. A linked queue needs both head and tail references because dequeue happens at the front while enqueue happens at the back.
  • Ordinary array queue vs. circular array queue: An ordinary array queue keeps the front fixed at index 0, so dequeue requires shifting values left. A circular array queue lets the front index move and wrap around, so it avoids shifting.
  • Bounded vs. dynamically growing queue: A bounded queue has a fixed capacity and must define what happens when it is full. A dynamically growing queue can allocate more storage, but it still has practical memory limits and occasionally needs extra work to resize.

The main design question is whether FIFO order is the rule the program needs. If so, a queue communicates that rule directly. If the program needs random access, priority-based removal, or insertion and removal at both ends, then a different abstraction may be more appropriate.

Variations and Extensions

Many structures preserve the basic queue idea of waiting items, but change one of the rules. Some variations change the storage policy, some change what happens when the queue is empty or full, and some change which item is removed next.

  • Bounded queue: A bounded queue has a fixed capacity. When it is full, enqueue must follow a documented policy: reject the new item, block until space is available, overwrite an old item, or report overflow. Bounded queues are common in buffers, embedded systems, simulations, and producer-consumer settings.
  • Resizable queue: A resizable queue grows its backing storage when it becomes full. A linked queue grows one node at a time. A resizable circular array queue usually allocates a larger array and copies the logical queue into the new array in front-to-back order.
  • Circular queue: A circular queue is an array-based implementation pattern where indices wrap around the physical end of the array. It is not a different ADT from a queue; it is a way to implement the same FIFO behavior without shifting values after each dequeue.
  • Deque: A deque, or double-ended queue, supports insertion and removal at both the front and the back. A stack and a queue can both be viewed as restricted versions of a deque.
  • Priority queue: A priority queue removes the highest-priority item rather than the oldest item. Despite the name, it is not a FIFO queue. It is a different ADT, often implemented with a heap.
  • Blocking queue: A blocking queue is used in concurrent programs. If a consumer tries to dequeue from an empty queue, it waits until an item is available. If a producer tries to enqueue into a full bounded queue, it waits until space is available.
  • Monotonic queue: A monotonic queue keeps candidates in increasing or decreasing order while scanning a sequence. It is often used for sliding-window minimum and maximum problems. This is more specialized than an ordinary FIFO queue because it may remove items from the back when they can no longer be useful.

The important distinction is whether the structure still obeys ordinary FIFO behavior. Bounded, resizable, and circular queues are implementation or capacity variations of the same queue ADT. Deques, priority queues, blocking queues, and monotonic queues change or extend the behavior enough that they should be treated as related but distinct structures.

Common Pitfalls

Most queue mistakes come from breaking FIFO behavior, mishandling empty or full queues, or updating one piece of representation state while forgetting another. The details differ between linked and array implementations, but the underlying issue is usually the same: the front, back, and size information must stay consistent after every operation.

  • Ignoring underflow: dequeue and front need defined behavior when the queue is empty. A clean implementation might throw an exception, return a special value, or report failure in some documented way. It should not read from an invalid array position or follow a null reference.
  • Ignoring overflow: A bounded queue needs defined behavior when enqueue is called on a full queue. It might reject the new item, return false, throw an exception, block until space is available, or resize if the implementation supports resizing.
  • Breaking FIFO order: A queue should remove the oldest waiting item. Removing from the back, removing from the middle, or letting new values jump ahead changes the abstraction into something other than an ordinary FIFO queue.
  • Forgetting the tail pointer: A linked queue without a tail reference usually has slow enqueue operations, because adding at the back requires scanning from the front to the final node.
  • Leaving a stale tail: When the final node is dequeued from a linked queue, both head and tail must become null. If tail still points to the removed node, later operations may use stale state.
  • Updating fields in the wrong order: In a linked queue, dequeue should save the front value before moving head. In a circular array queue, enqueue should compute the insertion position before increasing count. Small ordering mistakes can lose values or write into the wrong slot.
  • Shifting after every dequeue without noticing the cost: In an ordinary array queue, shifting values left after each dequeue makes that operation \(O(n)\). This may be acceptable for small examples, but it is not an efficient array-based queue implementation.
  • Off-by-one wrap-around errors: Circular queues require consistent modulo arithmetic whenever an index advances. For example, advancing frontIndex should use (frontIndex + 1) % A.length, not simply frontIndex + 1.
  • Confusing the current back with the next insertion position: In a circular array queue, the current back value and the next open slot are not the same thing. In the frontIndex and count version, the next insertion position is (frontIndex + count) % A.length.
  • Ambiguous empty and full states: Some circular queue designs use two indices and no count. In those designs, frontIndex == backIndex can mean either empty or full unless the implementation adds another rule, such as leaving one array slot unused or keeping a separate full flag.
  • Forgetting to preserve logical order during resizing: A resizable circular array queue may have its logical queue wrapped around the physical end of the array. When resizing, the values should be copied into the new array in front-to-back order, not ordered according to their current array indices. After resizing, the new array should have the front at index 0.
  • Using FIFO when priority matters: If urgent items should go first, an ordinary queue may be the wrong structure. A priority queue or multiple queues may be more appropriate.

Summary

A queue stores items so that the first item added is the first item removed. This first-in, first-out rule makes queues useful for waiting lines, print jobs, scheduling, buffering, producer-consumer systems, simulations, and other situations where arrival order matters.

The core queue operations are enqueue, dequeue, and front. enqueue adds a value at the back, dequeue removes and returns the front value, and front returns the front value without removing it. Most implementations also provide isEmpty and size. A bounded implementation may also provide isFull or another way to detect overflow.

A linked queue stores values in nodes and uses both head and tail references. The head reference gives direct access to the front, and the tail reference makes enqueue at the back constant time. When the final node is removed, both references must be updated to represent the empty queue.

An ordinary array queue is simple: it keeps the front at A[0] and stores the queue in positions A[0] through A[count - 1]. However, this makes dequeue expensive because the remaining values must shift left. Reversing the ends only moves the shifting cost to enqueue.

A circular array queue keeps the compact array representation but avoids shifting. It stores a moving frontIndex and a count, computes the next enqueue position using modulo arithmetic, and lets the logical queue wrap around the physical end of the array. This makes both enqueue and dequeue constant time in a bounded implementation.
