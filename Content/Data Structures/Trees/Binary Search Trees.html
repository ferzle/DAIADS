Binary Search Trees

Overview

A binary search tree, or BST, stores comparable values in a binary tree according to the following rule: at every node, all values in the left subtree are smaller than the value at the node, and all values in the right subtree are larger. We call this ordering rule the search tree property.

The ordering gives us a clear path when looking for a value. After comparing the target with the value at the current node, we continue in the left subtree if the target is smaller and in the right subtree if it is larger. The same comparisons guide insertion and removal. In an ordinary binary tree, there is no relationship between a node's value and the values below it, so searching may require examining the entire tree.

Binary Search Tree and Ordinary Binary Tree

The trees have the same shape, but only the tree on the left is a binary search tree. The tree on the right violates the search tree property in several places. For instance, the value \(70\) appears in the left subtree of \(50\), and the value \(30\) appears in the right subtree of \(50\). Can you find the other two violations?

Recall that an inorder traversal visits the left subtree, then the node itself, and then the right subtree. Each node is therefore visited in between its two subtrees. By the definition of a BST, every value in the left subtree is smaller than the value at the current node, and every value in the right subtree is larger. Because the left and right subtrees are themselves binary search trees, an inorder traversal lists the values in the left subtree in increasing order, then visits the current node, and then lists the values in the right subtree in increasing order. These three parts combine into a single increasing sequence. Thus, for a binary search tree, an inorder traversal literally lists the entries in order.

Every binary search tree is a binary tree, but not every binary tree is a binary search tree. A basic BST controls where values are placed but does not control the overall shape of the tree. Depending on the order in which values are inserted, the tree may be short and well distributed or may become a long chain. Later pages will introduce self-balancing search trees, which use additional rules to prevent the tree from becoming too tall.

On this page, we treat a binary search tree as an implementation of an ordered set: it stores distinct values and supports operations such as search, insertion, removal, minimum, maximum, predecessor, and successor. Duplicate values are not inserted. Other BST implementations may store a count with each value or use a consistent rule for placing duplicates, but those choices add details that are not needed for the basic operations considered here.

Core Operations and Implementation

Core Operations

As we have previously seen, a binary tree can be represented either in an array or with linked nodes. Although the array representation is useful for complete or nearly complete trees, it is not normally used for binary search trees. The shape of a BST depends on the order in which keys are inserted, so the tree may be sparse or highly unbalanced. In an array, this can leave many unused positions and may require an impractically large index range. Linked nodes store only the nodes that are actually present and adapt naturally as insertions and removals change the shape of the tree. Array representations become even more unwieldy for balanced search trees, where rotations and other restructuring operations repeatedly change the relationships among nodes. For these reasons, linked nodes are the standard representation for BSTs, and we discuss each operation together with its linked implementation.

A binary search tree supports operations for locating, adding, and removing keys. The three essential operations are shown in bold below. Because the keys are stored in order, a BST also supports useful queries involving the smallest, largest, next smaller, and next larger keys. Most implementations additionally provide basic container operations such as isEmpty() and size().

Operation Description
search(key) Find and return the entry with the given key, or report that the key is not present.
insert(key) Add the key in a position that preserves the search tree property, assuming it is not already present.
remove(key) Remove the entry with the given key, if it is present, while preserving the search tree property.
minimum() Return the smallest key in the tree, or report that no such key exists when the tree is empty.
maximum() Return the largest key in the tree, or report that no such key exists when the tree is empty.
predecessor(node) Return the node containing the largest key smaller than node.key, when such a node exists.
successor(node) Return the node containing the smallest key larger than node.key, when such a node exists.
isEmpty() Report whether the tree contains no keys.
size() Return the number of keys currently stored. This can be done in constant time if the implementation maintains a count as keys are inserted and removed.

The pseudocode below uses a linked-node representation. Each node stores a key and references named left, right, and parent. The tree stores a root reference and an integer size. An empty reference is written as null. An empty tree has root == null and size == 0; in a nonempty tree, the root's parent reference is null.

Parent references are not required for search or insertion, but they make predecessor, successor, and removal especially clear. The implementation stores distinct keys only, so an attempt to insert a duplicate leaves the tree unchanged. Operations that search for a key or a related key report failure when the requested result does not exist.

Search

Searching begins at the root. If the target key equals the key at the current node, the search succeeds. If the target is smaller, the search continues in the left subtree; if the target is larger, it continues in the right subtree. Each comparison therefore determines which child to follow.

The search continues along a single downward path. If it reaches an empty child reference, the key is not in the tree. For example, when searching for \(34\) in the tree below, the search moves left from \(50\), right from \(25\), left from \(37\), and right from \(31\). Since \(31\) has no right child, the search ends and we conclude that \(34\) is not stored in the tree.

The implementation keeps a reference to the current node and follows exactly one child after each comparison. Returning the node rather than only a Boolean value allows other operations to use the node and its links after the search succeeds. 

search(key):
    current = root

    while current != null:
        if key == current.key:
            return current
        if key < current.key:
            current = current.left
        else:
            current = current.right

    return null

Insertion

Insertion begins by following the same comparisons used during a search. Starting at the root, the algorithm moves to the left child when the new key is smaller than the current key and to the right child when the new key is larger. If the new key equals a key already in the tree, the duplicate policy used on this page leaves the tree unchanged.

The return value of insertion varies among implementations. Some return true or false to indicate whether a new key was inserted. Our implementation returns the node containing the key: the existing node if the key was already present, or the newly created node otherwise.

If the key is not already present, the comparisons eventually lead to an empty child position. A new node containing the key is attached at that position. Since the new node has no children, every newly inserted node begins as a leaf. If the tree was initially empty, the new node instead becomes the root.

The implementation keeps track of both the current node and its parent while searching for the key. If the search reaches null, the parent is the node beneath which the new node must be attached. Comparing the new key with the parent's key determines whether it becomes the left or right child. If the key is already present, the existing node is returned and the tree is not changed. 

insert(key):
    parent = null
    current = root

    while current != null:
        parent = current

        if key == current.key:
            return current
        if key < current.key:
            current = current.left
        else:
            current = current.right

    newNode = new Node(key)
    newNode.parent = parent

    if parent == null:
        root = newNode
    else if key < parent.key:
        parent.left = newNode
    else:
        parent.right = newNode

    size = size + 1
    return newNode

Minimum and Maximum

The search tree property makes the smallest and largest keys easy to locate. In any nonempty subtree, a node's left child has a smaller key than the node. Thus, as long as a left child exists, the minimum must be found farther to the left. When a node has no left child, no smaller key remains in that subtree, so that node contains the minimum key.

The maximum is found symmetrically. As long as the current node has a right child, the subtree contains a larger key. The first node reached with no right child therefore contains the maximum key.

The public operations minimum() and maximum() begin at root, but the helper algorithms below accept the root of any subtree. Thus, minimum(root) and maximum(root) find the extreme nodes in the full tree, while passing another node finds the minimum or maximum within that node's subtree. This flexibility is useful when finding predecessors, successors, and replacement keys during removal. If the given subtree is empty, the algorithm returns null. 

minimum(node):
    if node == null:
        return null

    current = node

    while current.left != null:
        current = current.left

    return current

maximum(node):
    if node == null:
        return null

    current = node

    while current.right != null:
        current = current.right

    return current

Now that we have seen the simplest BST operations, we can turn to the more challenging ones: predecessor, successor, and removal.

Successor and Predecessor

The successor of a node is the node containing the smallest key larger than its key. Similarly, the predecessor is the node containing the largest key smaller than its key. In an inorder traversal, these are the nodes visited immediately after and immediately before the given node.

We will develop the successor operation here. The predecessor operation is symmetric and will be left as an activity. The algorithm assumes that the given node is already in the tree.

There are two cases. If the node has a right subtree, its successor is the minimum node in that subtree. Every key in the right subtree is larger than the node's key, and the minimum operation finds the smallest of those larger keys.

If the node has no right subtree, the successor must be one of its ancestors. The algorithm follows parent references upward while the current node is a right child. In each such step, the parent has a smaller key and therefore cannot be the successor. The first time the algorithm reaches a node that is a left child of its parent, that parent is the next larger key. If the algorithm moves above the root, the original node was the largest node in the tree and has no successor.

The implementation of successor first checks the right-subtree case. If there is no right subtree, current and parent move upward together until current is a left child or there is no parent. The algorithm returns the node it finds, or null if the given node has no successor. 

successor(node):
    if node.right != null:
        return minimum(node.right)

    current = node
    parent = current.parent

    while parent != null and current == parent.right:
        current = parent
        parent = parent.parent

    return parent

Finding a predecessor uses the same idea with left and right reversed: first look for the maximum node in the left subtree, and otherwise move upward through ancestors. We will develop that algorithm in the activities.

Removal

Removal begins by searching for the key. If the key is not present, the tree is unchanged and the operation returns false. If the key is found, the node containing it must be taken out of the tree without losing any of its descendants or violating the search tree property. How this is done depends on whether the node has zero, one, or two children. After a successful removal, the operation decreases size and returns true.

  • No children: A leaf has no subtrees that need to be preserved. It can therefore be disconnected from its parent. If the leaf is the root, the tree becomes empty.
  • One child: The node is replaced by its only child. The removed node's parent is connected directly to that child, and the child's parent reference is updated. If the removed node is the root, its child becomes the new root.
  • Two children: The node cannot be removed directly without disconnecting one of its subtrees. Instead, its key is replaced by the key of its successor, which is the minimum node in its right subtree. The successor is then removed from its original position.

The two-child case works because the successor contains the smallest key larger than the key being removed. Replacing the original key with the successor's key therefore preserves the ordering between the node's left and right subtrees.

Since the successor is the minimum node in the right subtree, it cannot have a left child. It may have a right child, but this means that removing the successor reduces to the simpler case of removing a node with at most one child.

Each removal case requires changing the link from the removed node's parent to the node or subtree that will take its place. The parent reference of that replacement must also be updated. Rather than repeat these link changes in several places, the implementation uses a helper named replaceSubtree. replaceSubtree(oldRoot, newRoot) replaces the subtree rooted at oldRoot with the subtree rooted at newRoot. It changes the appropriate child reference in oldRoot's parent and, when newRoot is not null, updates its parent reference. The helper also handles the special case in which oldRoot is the root of the entire tree.

The remove algorithm first handles nodes with at most one child. If the node has no left child, it is replaced by its right subtree, which may be null. Otherwise, if it has no right child, it is replaced by its left subtree.

If the node has two children, the algorithm finds its successor, which is the minimum node in its right subtree. It copies the successor's key into the node being removed and then removes the successor from its original position. Because the successor is the minimum node in that subtree, it has no left child. Removing it therefore reduces to one of the simpler cases already handled above. 

replaceSubtree(oldRoot, newRoot):
    if oldRoot.parent == null:
        root = newRoot
    else if oldRoot == oldRoot.parent.left:
        oldRoot.parent.left = newRoot
    else:
        oldRoot.parent.right = newRoot

    if newRoot != null:
        newRoot.parent = oldRoot.parent


remove(key):
    node = search(key)

    if node == null:
        return false

    if node.left != null and node.right != null:
        successor = minimum(node.right)
        node.key = successor.key
        node = successor

    if node.left != null:
        replaceSubtree(node, node.left)
    else:
        replaceSubtree(node, node.right)

    size = size - 1
    return true

Analysis

Let \(h\) be the height of the tree, measured as the number of edges on the longest path from the root to a leaf. Each comparison during search or insertion moves down one level of the tree, so these operations visit at most \(h + 1\) nodes and take \(O(h)\) time.

Finding a minimum or maximum also follows a single downward path, repeatedly moving left or right. Finding a successor or predecessor may move down through a subtree or upward through parent references, but it still traverses at most \(O(h)\) edges. Removal first searches for the key and may then locate a successor and remove a node with at most one child. Although this can involve more than one path, only a constant number of paths are followed, so removal also takes \(O(h)\) time.

The value of \(h\) depends on the shape of the tree. In a balanced tree, \(h = \Theta(\log n)\), so all of these operations take \(O(\log n)\) time. However, a plain BST does not guarantee balance. For example, inserting keys in increasing order produces a degenerate tree with height \(n - 1\), causing the same operations to take \(O(n)\) time in the worst case.

If distinct keys are inserted in random order, the expected height of the BST is \(\Theta(\log n)\), and the expected running time of the operations is therefore \(O(\log n)\). This is an expected result, not a worst-case guarantee. The self-balancing search trees introduced later maintain logarithmic height even for unfavorable insertion orders.

The nodes occupy \(\Theta(n)\) total space. Storing a parent reference adds one reference to each node but does not change this asymptotic bound. The iterative algorithms presented on this page use \(O(1)\) additional working space. Recursive versions would use \(O(h)\) additional space for the recursion stack.

Applications

Binary search trees are useful when a collection changes over time and its keys must remain ordered. Unlike a sorted array, a BST can insert and remove keys without shifting many other entries. Unlike a hash table, it can efficiently answer questions that depend on the ordering of the keys.

  • Ordered sets and maps: A BST can store a changing set of distinct keys or associate each key with a value. Search, insertion, and removal support updates, while an inorder traversal reports the entries in sorted order.
  • Predecessor and successor queries: Applications can quickly locate the stored key immediately before or after a given key. For example, a scheduling system can find the events immediately before and after a particular time.
  • Range queries: A BST can report all keys between two bounds without examining too many keys that lie outside the range. This is useful for retrieving records with dates, prices, scores, or other ordered values in a specified interval.
  • Symbol tables and indexes: Compilers, databases, and other systems use ordered search structures to associate names or keys with stored information while supporting both updates and ordered queries.

In practice, these applications usually use a self-balancing BST rather than a plain BST. Balanced trees preserve the same ordering and operations while guaranteeing that the tree remains short enough for efficient searches and updates.

Connections and Comparisons

Binary search trees combine hierarchical structure with sorted order. Comparing them with other data structures helps clarify both when a BST is especially useful and when another structure may provide better support for the operations that matter most in a given situation.

  • Ordinary binary trees: A binary search tree is a binary tree with an additional ordering rule. In an ordinary binary tree, the position of a key provides no information about where other keys are stored, so searching may require visiting every node. In a BST, each comparison determines which subtree can still contain the target.
  • Sorted arrays: A sorted array supports binary search in \(O(\log n)\) time and uses memory efficiently. However, inserting or removing an entry may require shifting \(O(n)\) entries. A BST does not require entries to be shifted; its search, insertion, and removal operations instead take \(O(h)\) time, where \(h\) is the height of the tree.
  • Ordered linked lists: An ordered linked list also keeps its keys in sorted order, but searching for a position takes \(O(n)\) time because nodes must be examined sequentially. Once the position is known, insertion or removal requires only a few link changes. A well-shaped BST improves the search for that position to \(O(\log n)\).
  • Hash tables: A hash table typically provides faster expected time for searching, inserting, and removing a key when only exact-key operations are needed. However, hash tables do not maintain their keys in sorted order. BSTs naturally support minimum, maximum, predecessor, successor, inorder traversal, and range queries.
  • Balanced search trees: A plain BST does not control its shape and can become a chain with height \(n - 1\). AVL trees, red-black trees, and other self-balancing BSTs preserve the same search tree property while using additional rules and restructuring operations to guarantee height \(O(\log n)\).
  • Inorder traversal: An inorder traversal visits the keys of a BST in increasing order. This connects the tree structure to sorting and allows all stored keys to be reported in \(\Theta(n)\) time without performing a separate sorting step.
  • Heaps: A heap also stores keys in a binary tree, but its ordering rule is weaker. In a min-heap, each node is no larger than its children, but there is no ordering relationship between the left and right subtrees. This makes finding the minimum especially efficient, but searching for an arbitrary key, finding a predecessor or successor, and reporting all keys in sorted order are not as natural as they are in a BST.

Variations and Extensions

Binary search trees can be adapted in several ways depending on what information must be stored, which operations must be supported, and whether the tree must guarantee good performance.

  • Key-value trees: Instead of storing only keys, each node can associate a key with a value. This produces an ordered map rather than an ordered set.
  • Duplicate-key policies: An implementation may reject duplicate keys, replace the value associated with an existing key, store a count or collection of items associated with the key, or use a consistent rule for placing repeated keys.
  • Parent references: Some implementations store a parent reference in every node, as we have done here. Others omit it and instead retain ancestor information during an operation or use recursion.
  • Augmented BSTs: Nodes can store additional information about their subtrees, such as the number of nodes, a sum of values, or interval endpoints. These additions can support operations such as rank queries, selection by position, range sums, and interval searches.
  • Self-balancing BSTs: AVL trees, red-black trees, and related structures preserve the binary search tree property while using rotations and additional balance information to keep the height \(O(\log n)\).
  • Randomized BSTs: Structures such as treaps use randomness to reduce the likelihood of highly unbalanced trees and provide good expected performance.
  • Multiway search trees: 2-3 trees and B-trees extend the ordered search-tree idea by allowing a node to contain more than one key and to have more than two children. They are therefore more distant relatives of BSTs than AVL or red-black trees, since they are not binary trees. Their broader nodes can keep the tree very short, which is especially important for data stored on disks or other external storage.

Common Pitfalls

Binary search tree algorithms are often short, but small mistakes in the ordering logic or link updates can corrupt the tree or produce incorrect results.

  • Checking only immediate children: The search tree property applies to entire subtrees, not just to a node and its children. Every key in the left subtree must be smaller than the node's key, and every key in the right subtree must be larger.
  • Losing a subtree: During insertion or removal, changing a child reference before saving the subtree currently attached there can make part of the tree unreachable.
  • Forgetting parent references: Whenever a node is attached in a new position, its parent reference must also be updated. The root is the one exception: its parent must remain null.
  • Ignoring special root cases: Inserting into an empty tree or removing the root may require changing the tree's root reference rather than a left or right child reference.
  • Mishandling duplicate keys: The implementation must use a clear duplicate policy. On this page, inserting a key already in the tree leaves the tree unchanged.
  • Assuming the tree remains balanced: A plain BST can become highly unbalanced, even if it begins with a balanced shape. Its height, and therefore its performance, depends on the order in which keys are inserted and removed. To guarantee that the height remains \(O(\log n)\), the implementation must use a self-balancing strategy, such as an AVL tree or a red-black tree.
  • Confusing a successor with a right child: A node's successor is the next node in sorted order. If the node has a right subtree, the successor is the minimum node in that subtree, which is not necessarily the immediate right child.
  • Copying a successor key without removing the successor: In the two-child removal case, copying the successor's key creates a duplicate unless the original successor node is also removed from its old position.
  • Updating size incorrectly: The size should change only when a new node is inserted or an existing node is removed. An unsuccessful search, duplicate insertion, or unsuccessful removal must not change it.

Summary

A binary search tree stores keys according to the search tree property: every key in a node's left subtree is smaller than the node's key, and every key in its right subtree is larger. This ordering allows search, insertion, removal, minimum, maximum, predecessor, and successor operations to follow paths through the tree rather than examining every node. An inorder traversal visits the keys in increasing order.

BSTs are normally implemented using linked nodes because their shape changes as keys are inserted and removed. In the implementation on this page, each node stores left, right, and parent references, and the tree maintains references to its root and its current size. Parent references simplify upward-moving operations such as successor, predecessor, and removal.

Search and insertion follow comparisons downward from the root. Minimum and maximum follow left or right references as far as possible. Successor and predecessor may search within a subtree or move upward through ancestors. Removal has separate cases for nodes with zero, one, or two children; in the two-child case, the node's key can be replaced by its successor's key before the successor is removed from its original position.

The running time of these operations is \(O(h)\), where \(h\) is the height of the tree. A well-shaped tree has height \(\Theta(\log n)\), but a plain BST can become degenerate and have height \(n - 1\), producing \(O(n)\) worst-case operations. Self-balancing search trees such as AVL and red-black trees preserve the BST ordering while guaranteeing logarithmic height.
