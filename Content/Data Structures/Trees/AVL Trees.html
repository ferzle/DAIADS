AVL Trees

Overview

Prerequisites: This page assumes familiarity with Binary Search Trees and the single and double rotations introduced on the Balanced Search Trees page.

An AVL tree is a binary search tree that automatically keeps its height under control. It preserves the ordinary BST ordering rule, so search still decides between the left and right subtree by comparing keys. In addition, the left and right subtrees at every node must have heights that differ by at most one.

That local rule prevents a long chain from forming. After an insertion or removal, an AVL tree walks back toward the root, updates height information, and uses a small rotation when it finds an imbalance. A rotation changes local parent-child relationships without changing the sorted order of the keys. The result is a worst-case height of \(O(\log n)\), rather than the \(O(n)\) height possible in an ordinary BST.

Same ordered-set behavior

Search, minimum, maximum, predecessor, successor, traversal, and range queries mean exactly what they mean in a BST.

One extra invariant

At every node, the heights of the two child subtrees differ by no more than one.

Local update repair

Insertion and removal may update heights and rotate a small subtree; the rest of the ordering remains intact.

Both trees satisfy BST ordering. Only the left tree also satisfies the AVL height rule at every node.

This page treats an AVL tree as an ordered set of distinct keys. A map stores a value with each key; a multiset can store a count. Neither extension changes the balancing mechanism.

The AVL Balance Condition

Height and Balance Factor

We use the same height convention as the Binary Trees page: an empty subtree has height \(-1\), a leaf has height \(0\), and a nonleaf has one plus the larger child height. For a node \(v\), define

\[ \operatorname{balanceFactor}(v)=\operatorname{height}(v.left)-\operatorname{height}(v.right). \]

A positive balance factor means the node leans left; a negative factor means it leans right. A node is AVL-balanced exactly when its factor is \(-1\), \(0\), or \(1\). The following table is a set of examples, not an exhaustive list of height combinations. The actual rule is simply \(|BF(v)|\leq 1\): the two child heights may be any nonnegative values (or \(-1\) for an empty child) as long as their difference is at most one.

Representative balance-factor calculations
Left heightRight heightBalance factorWhat this example shows
21\(1\)Balanced; left subtree is one level taller.
22\(0\)Balanced; child heights are equal.
12\(-1\)Balanced; right subtree is one level taller.
20\(2\)Not balanced; a repair is required after an update.
Sign conventions vary. Some books compute right height minus left height. That convention is valid too, but it reverses every sign and case test. Always identify the definition before reading rotation code.

What an AVL node stores

In the representation used on this page, every node stores its key, left child, right child, optional parent, and one integer height. A new leaf initializes height = 0. The tree object separately stores root and size. Balance factor does not need its own field because it can be calculated from the two child heights in constant time. 

class Node:
    key
    left = null
    right = null
    parent = null       // optional if recursion reconnects subtrees
    height = 0          // a newly created node is a leaf

Without stored heights, finding a node's balance factor could require traversing both of its subtrees. With stored heights, updateHeight(node) and balanceFactor(node) each take \(O(1)\) time. Only nodes on the update path and nodes touched by rotations can have stale heights, so an insertion or removal never needs to recompute every height in the tree.

Recognizing AVL Trees

A tree is an AVL tree only if it satisfies two independent requirements: it is a binary search tree, and every node satisfies the AVL balance condition. Checking only whether the root looks balanced is not enough.

Example: Which Trees Are AVL Trees?

Tree A is AVL. Tree B has a balanced shape but fails BST ordering. Tree C is a BST and its root is balanced, but the lower violation at 20 makes the whole tree non-AVL.

Why AVL Trees Stay Short

To make an AVL tree of a fixed height as sparse as possible, make one child as short as the rule permits. If the whole tree has height \(h\), its taller child must have height \(h-1\), and the other child can have height \(h-2\). Let \(N(h)\) be the minimum number of nodes in an AVL tree of height \(h\). Then

\[ N(-1)=0,\qquad N(0)=1,\qquad N(h)=1+N(h-1)+N(h-2). \]
\(h\)−1012345
\(N(h)\)012471220

In fact, \(N(h)=F_{h+3}-1\), where \(F_k\) is the \(k\)-th Fibonacci number with \(F_0=0\) and \(F_1=1\). Since \(F_k\geq\varphi^{k-2}\) for \(k\geq2\), where \(\varphi=(1+\sqrt5)/2\), an AVL tree with \(n\) nodes satisfies

\[ n+1\geq\varphi^{h+1} \quad\Longrightarrow\quad h\leq\log_\varphi(n+1)-1 \approx 1.4405\log_2(n+1)-1. \]

Theorem: An AVL tree with \(n\) nodes has height \(O(\log n)\).

The explicit inequality gives more information than the asymptotic notation: under this page's convention that a leaf has height 0, the height is at most approximately \(1.4405\log_2(n+1)-1\). The bound is an upper bound on the worst legal AVL shape, not a claim that every AVL tree reaches that height. A perfectly balanced tree is shorter, with height close to \(\log_2(n+1)-1\).

For example, \(n=1{,}000\) gives \(h\leq13.36\), so the integer height is at most 13 by this bound. A plain BST containing the same 1,000 keys could have height 999. The strict local balance rule is therefore strong enough to give a useful numerical guarantee, not merely an abstract logarithmic classification.

Core Operations and Implementation

Core Operations

An AVL tree presents the same public interface as an ordinary BST. Clients do not need to know whether an update caused a rotation.

OperationRelationship to the BST Version
search, minimum, maximumUnchanged; AVL balance does not alter key ordering.
predecessor, successor, traversal, range queryUnchanged; these operations use BST relationships.
isEmpty, sizeUnchanged; these read tree-level state and do not inspect balance.
insertPerform BST insertion, then update heights and repair the first unbalanced ancestor.
removePerform BST removal, then update heights and repair every imbalance encountered toward the root.

A typical node stores key, left, right, an optional parent reference, and height. The tree stores root and size. Parent links allow iterative upward repair; recursive code can instead return each repaired subtree root to its caller.

Internal helpers

The table below is not introducing a completely new collection of algorithms. It organizes operations that have already appeared on this page or on the prerequisite BST and rotation pages into a possible implementation interface. The names are suggestions; the important part is keeping ordinary BST structure changes separate from AVL height repair.

Helper groupConnection to the discussion
height, updateHeight, balanceFactor These are the constant-time metadata operations defined in “Height and Balance Factor” and written as pseudocode in the next subsection.
rotateLeft, rotateRight, and replaceSubtree The first two are the single rotations from the Balanced Search Trees page. replaceSubtree is the small link-management helper they can use to reconnect the new local root to its former parent.
rotateLeftRight, rotateRightLeft (optional wrappers) Each wrapper performs two single rotations. Keeping them as wrappers makes the intermediate state explicit: left-right means left at the child and then right at the unbalanced node; right-left is symmetric.
bstInsert, bstRemove These are the ordinary BST insert and remove procedures already studied, renamed here to emphasize that they perform only the structural BST phase and do not repair AVL balance.
rebalance, fixAfterInsert, fixAfterRemove These are the AVL-specific helpers developed below. rebalance repairs one local subtree; the two fix-up methods decide how far to continue toward the root.

Public methods such as insert remain short coordinators: call the BST-phase helper, update size once if the set changed, and then call the appropriate AVL fix-up helper. Search and ordered-query helpers are unchanged from the BST page, so they are not repeated in this AVL-specific table. A structural validator is valuable while testing an implementation, but it is development support rather than part of the operation itself.

Maintaining Heights

Stored heights make a balance check constant-time. They must be derived from current child links, never adjusted by guesswork.

height(node):
    if node == null:
        return -1
    return node.height

updateHeight(node):
    node.height = 1 + max(height(node.left), height(node.right))

balanceFactor(node):
    return height(node.left) - height(node.right)

Work upward because a parent's height depends on its children. After a rotation, update the node that moved down first, then the node that moved up. The new local root's formula may depend on the first result.

Local information is enough. If both child heights are correct, one call to updateHeight makes the parent's height correct. This bottom-up dependency is why insertion and removal repair follows the search path in reverse.

Choosing a Rotation

Let \(z\) be the first unbalanced node encountered while moving upward. Its balance factor is \(+2\) or \(-2\). Let \(y\) be its taller child. The ordered pair \((BF(z),BF(y))\) determines the repair. This numeric form is more precise than names such as “left-heavy,” and it is the form an implementation can test directly.

What the case names mean: LL, LR, RR, and RL are standard AVL abbreviations for the two directions along the heavy path beginning at \(z\). They do not name the rotation that will be performed. An LL shape is repaired by a right rotation, and an RR shape is repaired by a left rotation. LR and RL name bent shapes and require two rotations.
Complete AVL rotation-selection rules using \(BF(v)=height(v.left)-height(v.right)\)
\(BF(z)\)\(BF(y)\)CaseRepair
\(+2\)\(+1\) during insertion; \(+1\) or \(0\) during removalLeft-left (LL)Rotate right at \(z\).
\(+2\)\(-1\)Left-right (LR)Rotate left at \(y=z.left\), then right at \(z\).
\(-2\)\(-1\) during insertion; \(-1\) or \(0\) during removalRight-right (RR)Rotate left at \(z\).
\(-2\)\(+1\)Right-left (RL)Rotate right at \(y=z.right\), then left at \(z\).

During insertion, the newly lengthened path makes the heavy child lean in one direction, so its factor at the first violation is \(+1\) or \(-1\), never 0. During removal, the sibling subtree may become too short while the heavy child remains perfectly balanced. That is why the numeric pairs \((+2,0)\) and \((-2,0)\) occur only in removal and use a single rotation.

LL: \((+2,+1)\) — rotate right

The heavy path goes left from 30 and left again from 20. One right rotation promotes 20.

RR: \((-2,-1)\) — rotate left

The heavy path goes right twice. One left rotation promotes 20.

LR: \((+2,-1)\) — left, then right

Rotate left at 10 to make an LL shape, then rotate right at 30. The middle key becomes the local root.

RL: \((-2,+1)\) — right, then left

Rotate right at 30 to make an RR shape, then rotate left at 10.

A double rotation is not an indivisible action. In a left-right repair, the first rotation converts the bent shape into a left-left shape; the second resolves that straight shape. Right-left repair is symmetric. Seeing the intermediate tree is useful for understanding which middle subtree is transferred, so the demo on this page records the two rotations as separate steps.

An implementation may give those two-call sequences names, but the wrappers should not hide what happens: 

rotateLeftRight(z):
    rotateLeft(z.left)
    return rotateRight(z)

rotateRightLeft(z):
    rotateRight(z.right)
    return rotateLeft(z)

The main rebalance pseudocode below spells out the two calls directly so the numeric case test and the order of the single rotations remain visible. 

rebalance(node):
    updateHeight(node)

    if balanceFactor(node) == 2:
        if balanceFactor(node.left) < 0:
            node.left = rotateLeft(node.left)       // first LR step
        return rotateRight(node)                    // second LR step, or LL repair

    if balanceFactor(node) == -2:
        if balanceFactor(node.right) > 0:
            node.right = rotateRight(node.right)    // first RL step
        return rotateLeft(node)                     // second RL step, or RR repair

    return node
Removal includes a child balance factor of zero. A left-heavy node with a balanced left child still uses a single right rotation; a right-heavy node with a balanced right child uses a single left rotation. Choosing from subtree factors handles insertion and removal correctly.

Search and Ordered Queries

Search, minimum, maximum, predecessor, successor, inorder traversal, and range queries use the ordinary BST algorithms. Rotations preserve inorder order, so no AVL-specific search case exists. The improvement is the height guarantee: a single root-to-leaf walk is \(O(\log n)\) in the worst case.

Insertion

Treat insertion as two phases. bstInsert performs the familiar search and attaches a height-0 leaf without doing any rotations. If a new node was created, fixAfterInsert walks back over that search path. This separation keeps BST placement and AVL maintenance independently understandable and testable.

  1. Search for the key. If it is already present, leave the set unchanged.
  2. Attach a new leaf exactly as in a BST.
  3. Move upward from the new leaf's parent, updating each height.
  4. If a node is unbalanced, perform the appropriate single or double rotation.
  5. Reconnect the returned local root to its former parent or make it the tree root.
Worked example: inserting 25 creates a left-right case

Start with keys 30, 10, and 40, then insert 20 and 25. The new key follows the BST path \(30\to10\to20\). Node 30 becomes left-heavy, while its left child 10 is right-heavy.

The intermediate tree is still unbalanced, but it has become a left-left shape. The second rotation promotes 20 and restores balance while preserving the inorder sequence \(10,20,25,30,40\).

insert(key):
    newLeaf = bstInsert(key)
    if newLeaf == null:                 // key was already present
        return false

    size = size + 1
    fixAfterInsert(newLeaf)
    return true

fixAfterInsert(newLeaf):
    node = newLeaf.parent

    while node != null:
        repairedRoot = rebalance(node)  // also updates node.height

        if repairedRoot != node:        // one or two rotations occurred
            return                     // no higher insertion repair is needed

        node = node.parent
How far does insertion fix-up continue? It must keep moving upward while nodes remain balanced because the new leaf may have increased the height seen by the next ancestor. It stops when it reaches the root or when it performs the first repair. Immediately before insertion, the repaired subtree had height \(h\). Insertion temporarily raised it to \(h+1\), and the rotation restores it to \(h\). Higher ancestors therefore see the same child height they saw before insertion and cannot become newly unbalanced. An optimized implementation may also stop early when updating a node does not change its height.

Removal

Removal begins with the three ordinary BST cases. A leaf is detached. A node with one child is replaced by that child. A node with two children exchanges its key-value entry with its inorder successor (or predecessor), after which the successor is physically removed from a position with at most one child.

As with insertion, separate the ordinary BST phase from the AVL phase. bstRemove returns both whether it succeeded and the parent of the position that physically lost a node. fixAfterRemove begins there. Unlike insertion fix-up, it continues after a rotation because the repaired subtree may be shorter than it was before removal. 

remove(key):
    (removed, repairStart) = bstRemove(key)
    if not removed:
        return false

    size = size - 1
    fixAfterRemove(repairStart)
    return true

fixAfterRemove(node):
    while node != null:
        repairedRoot = rebalance(node)
        node = repairedRoot.parent        // continue above the repaired subtree
Track the physical removal site. When removing a two-child node, copying the successor key does not change the original node's child structure. Height repair starts where the successor node was detached, not where the requested key was first found.
Example: one removal can cause two repairs

Consider a root 100 whose left subtree is rooted at 50 and has height 3. Node 50 has children 30 and 70; node 30 has children 20 and 40; node 20 has left child 10; and node 70 has children 60 and 80. The right subtree of 100 is rooted at 150 and has height 2: 150 has left child 140, right child 160, and 140 has left child 135. Thus \(BF(50)=1\) and \(BF(100)=1\), and every node is initially AVL-balanced.

  1. Remove 160. Node 150 changes from balanced to \(BF(150)=2\), with \(BF(140)=1\). A right rotation at 150 repairs that subtree and lowers its height from 2 to 1.
  2. Root 100 now sees child heights 3 and 1, so \(BF(100)=2\). A second right rotation, this time at 100, is required.

The first rotation repaired every node in the right subtree, but its height decrease was visible to an ancestor outside that subtree. This is the reason the removal loop resumes at repairedRoot.parent rather than returning after one rotation.

Analysis

OperationWorst-case timeReason
Search, minimum, maximum, predecessor, successor\(O(\log n)\)Each follows at most one path in a logarithmic-height tree.
Single or double rotation\(O(1)\)Only a fixed number of links and height fields change.
Insertion\(O(\log n)\)BST search and upward height updates dominate; at most one single or double repair occurs.
Removal\(O(\log n)\)There are \(O(\log n)\) ancestors; each may require only constant work.
Full traversal\(\Theta(n)\)Every stored node is visited once.

The nodes occupy \(\Theta(n)\) space, including one height or balance field per node. An iterative implementation with parent links uses \(O(1)\) auxiliary working space. A recursive implementation, or one that records an ancestor stack, uses \(O(\log n)\) auxiliary space because the tree height is logarithmic.

Applications

AVL trees are useful for in-memory ordered sets and maps when worst-case guarantees matter and lookup operations are frequent. Unlike a hash table, an AVL tree supports predecessor, successor, sorted traversal, and range reporting directly. Its relatively strict balance also makes its search paths short.

  • Ordered indexes: maintain records by a comparable key while supporting neighbors and ranges.
  • Lookup-heavy dictionaries: provide predictable searches when keys are inserted in an uncontrolled order.
  • Augmented search trees: store subtree sizes, interval endpoints, or aggregates to support rank, selection, overlap, or range queries.

AVL trees are usually an in-memory structure. Storage systems often prefer multiway B-trees because one disk or cache-line access can examine many keys at once.

The AVL height recurrence is also a concrete algorithmic appearance of Fibonacci growth: restricting how slowly a tree can gain nodes restricts how quickly its height can grow.

Variations and Extensions

  • Store height or balance factor: stored height makes formulas direct; a carefully maintained balance factor can use a smaller field.
  • Parent links or returned subtree roots: iterative code often uses parents, while recursive code reconnects the root returned by each call.
  • Maps and duplicate policies: store values with keys, or store a multiplicity count. Sending equal keys consistently to one side alone can interfere with the intended height bound.
  • Augmentation: recompute metadata such as subtree size or range aggregate in the same bottom-up order used for heights, including after rotations.
  • Persistent AVL trees: copy the nodes along an update path and reuse unchanged subtrees to preserve earlier versions.

Common Pitfalls

  • Checking only the root: BST order and the AVL height condition must hold at every node.
  • Mixing height conventions: if an empty subtree has height \(-1\), a leaf has height \(0\). Every formula and initialization must agree.
  • Reversing the balance-factor sign: either subtraction order works, but its rotation tests are different.
  • Updating heights top-down: a parent cannot receive its final height until both child heights are current.
  • Updating rotated nodes in the wrong order: recompute the node moved downward before the node moved upward.
  • Choosing removal cases from the removed key: use current balance factors; the key is no longer a reliable guide and a heavy child can be balanced.
  • Stopping after one removal repair: removal can shorten the repaired subtree and trigger another violation above it.
  • Losing the transferred middle subtree: a rotation must preserve all child subtrees and reconnect the new local root to its former parent.

Summary

An AVL tree is a binary search tree that stores enough height information to enforce a local balance rule at every node. With \(BF(v)=height(v.left)-height(v.right)\), every completed operation must leave each balance factor in \(\{-1,0,1\}\). A node's stored height is recomputed in constant time from its two children, so only the update path and rotated nodes need attention.

When a factor reaches \(+2\) or \(-2\), the factor of the heavy child distinguishes LL, RR, LR, and RL. Straight cases use one rotation; bent cases use two single rotations and have a meaningful intermediate state. Insertion walks upward until it reaches the root or repairs its first imbalance, then stops because that subtree returns to its old height. Removal must continue toward the root because a repaired subtree may remain shorter and unbalance another ancestor.

The minimum-node recurrence follows Fibonacci growth, giving \(h\leq\log_\varphi(n+1)-1\approx1.4405\log_2(n+1)-1\). Consequently, search, insertion, and removal all take \(O(\log n)\) worst-case time while rotations themselves take \(O(1)\). AVL trees therefore implement ordered sets and maps with predictable search paths, at the cost of one metadata field per node and additional update logic.

  1. Audit an AVL Tree: Draw the BST with root 40; children 20 and 60; grandchildren 10, 30, 50, and 70; and node 5 as the left child of 10.
    1. Label every null subtree with height \(-1\), then compute all node heights bottom-up.
    2. Write the balance factor beside every node and verify the BST ranges separately.
    3. Predict which stored heights change if 5 is removed.
    4. Predict which stored heights change if 2 is inserted instead. Does a rotation occur?
  2. Classify Counterexamples: In small groups, draw three trees: a valid AVL tree, a height-balanced binary tree that is not a BST, and a BST whose root is balanced but a descendant is not.
    1. Exchange drawings with another group without identifying the categories.
    2. For each drawing, check key ranges and balance factors independently.
    3. Identify every violation rather than stopping after the first.
    4. Propose one smallest change that would make each invalid tree valid.
  3. Act Out the Four Numeric Cases: Use cards labeled 10, 20, and 30. Construct the pre-rotation trees produced by the sequences \(30,20,10\), \(10,20,30\), \(30,10,20\), and \(10,30,20\).
    1. For each tree, identify \(z\), its heavy child \(y\), and the pair \((BF(z),BF(y))\).
    2. Name the case only after writing the numeric pair.
    3. Move the cards through each individual rotation, pausing between the two LR/RL steps.
    4. Verify that the inorder sequence remains 10, 20, 30 after every single rotation.
  4. Trace Insertion Fix-Up: Insert \[50,30,70,20,40,60,80,10,5\] into an empty AVL tree.
    1. Draw the ordinary BST insertion path for each key before doing height work.
    2. List the nodes visited by fixAfterInsert in order.
    3. At the first violation, record the numeric balance-factor pair and rotation.
    4. Use subtree heights to justify why fix-up stops at that point.
  5. Debug a Rotation: A right-rotation implementation changes all pointers correctly but updates the promoted node before the node that moved downward.
    1. Use keys 30, 20, and 10 to calculate the stale value the promoted node reads.
    2. Explain how the wrong height can cause a later balance-factor test to choose the wrong case.
    3. Write the correct two-line height-update order.
    4. Add a fourth key and describe a test that exposes the defect.
  6. Insertion versus Removal Fix-Up: Divide into two teams. One team explains why insertion stops after one repair; the other explains why removal may continue.
    1. Use \(h\) for the affected subtree's height before the operation.
    2. State its height immediately before and after the first repair.
    3. Identify exactly what the parent of the repaired subtree observes.
    4. Challenge the other team's explanation with a counterexample attempt.
  7. Compare Plain BST and AVL Behavior: Insert keys 1 through 15 in increasing order into both structures.
    1. Record the height after each insertion.
    2. For the AVL tree, record every numeric case and rotation.
    3. Compare searches for 1, 8, and 15 in the final trees.
    4. Explain what extra update work buys the worst-case search guarantee.
