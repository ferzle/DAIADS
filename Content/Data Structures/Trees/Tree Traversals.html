Tree Traversals

Overview

A tree traversal is a systematic method for processing the nodes of a tree in a specified order. To visit a node means to perform the operation associated with the traversal, such as displaying the node's value, adding it to a collection, evaluating an expression, or using it in a computation. The operation depends on the application; the traversal determines when that operation is performed at each node.

It is important to distinguish visiting a node from merely reaching or returning to it during the traversal. In a recursive depth-first traversal, a call on a nonempty node has three important moments:

  1. when the call first reaches the node, before traversing its left subtree;
  2. when control returns from the left subtree, before traversing the right subtree;
  3. when control returns from the right subtree, just before the call finishes.

Thus, the traversal process may be at the same node several times, but the node is normally visited only once. Preorder, inorder, and postorder differ in which of these three moments is chosen as the visit:

  • Preorder: visit the node when it is first reached, before traversing either subtree.
  • Inorder: visit the node after traversing the left subtree but before traversing the right subtree.
  • Postorder: visit the node after traversing both subtrees, just before the recursive call returns.

These are called depth-first traversals because each one continues downward through a subtree before moving to another part of the tree. They traverse the same nodes but may visit them in different orders.

A fourth common traversal is level-order traversal. Rather than following one branch downward, level order visits nodes by increasing depth: first the root, then the nodes at depth \(1\), then the nodes at depth \(2\), and so on. It is therefore a breadth-first traversal and is implemented using a queue.

A traversal may begin at the root of an entire tree or at the root of any subtree. In either case, the same algorithm visits every node in the selected tree or subtree exactly once in the specified order.

This page develops the recursive preorder, inorder, and postorder algorithms, followed by the queue-based level-order algorithm. We will compare their visit orders, analyze their running time and extra space, and examine applications in which each order is useful.

Depth-First Traversals

Introduction

A depth-first traversal follows a branch downward into a subtree before returning to explore another part of the tree. The recursive structure of a binary tree makes this approach natural: starting at a node, we recursively traverse its left subtree and its right subtree.

As discussed in the overview, a recursive call has three possible moments at which it can visit the current node:

  1. when the call first reaches the node;
  2. after the left subtree has been traversed;
  3. after both subtrees have been traversed.

Preorder, inorder, and postorder traversal use the same recursive structure. They differ only in which of these three moments is chosen for the visit. We will apply all three traversals to the following binary tree.

Example 1: A Binary Tree for Comparing Traversals

As we will see shortly, the three depth-first traversal algorithms are nearly identical. They use the same base case and make the same recursive calls on the left and right subtrees. The only difference is the position of the visit(node) operation: before both recursive calls for preorder, between them for inorder, and after both of them for postorder.

Preorder Traversal

In a preorder traversal, the current node is visited when the recursive call first reaches it. The left subtree is then traversed, followed by the right subtree. The order is therefore:

  1. visit the root;
  2. traverse the left subtree in preorder;
  3. traverse the right subtree in preorder.
preorder(node):
  if node = null:
      return

  visit(node)
  preorder(node.left)
  preorder(node.right)

The recursive calls do not merely visit the roots of the two subtrees. Each call performs a complete preorder traversal of its entire subtree before the algorithm continues.

Preorder is useful when a parent must be processed before its descendants. For example, prefix expressions use preorder, and a preorder traversal with markers for empty child positions can record the structure of a binary tree.

Inorder Traversal

In an inorder traversal, the left subtree is traversed before the current node is visited. The right subtree is traversed afterward. The order is:

  1. traverse the left subtree in inorder;
  2. visit the root;
  3. traverse the right subtree in inorder.
inorder(node):
  if node = null:
      return

  inorder(node.left)
  visit(node)
  inorder(node.right)

Unlike preorder and postorder, inorder depends specifically on the two distinct child positions of a binary tree. The visit occurs between the traversals of the left and right subtrees. There is no single corresponding inorder traversal for a general tree whose nodes may have any number of children.

Inorder traversal is particularly important for binary search trees. Because of the ordering rule used by a binary search tree, an inorder traversal visits its stored values in sorted order.

Postorder Traversal

In a postorder traversal, the current node is visited only after both of its subtrees have been traversed. The order is:

  1. traverse the left subtree in postorder;
  2. traverse the right subtree in postorder;
  3. visit the root.
postorder(node):
  if node = null:
      return

  postorder(node.left)
  postorder(node.right)
  visit(node)

Postorder is useful when a node must be processed after its descendants. For example, it can be used to delete a linked binary tree safely, evaluate a postfix expression tree, or combine information computed for two subtrees. The structural algorithms from the Binary Trees page have a postorder-like structure because they compute results for both subtrees before returning the result for the current node.

Analysis

Preorder, inorder, and postorder make exactly the same recursive calls. They differ only in the placement of the visit(node) operation. Assuming that visiting a node takes constant time, all three traversals therefore have the same asymptotic running time and recursive-stack space.

Running Time

Let \(R(n)\) denote the running time on a binary tree with \(n\) nodes. If the left and right subtrees contain \(n_L\) and \(n_R\) nodes, respectively, then \[ n_L+n_R=n-1 \] and \[ R(n)=R(n_L)+R(n_R)+\Theta(1), \qquad R(0)=\Theta(1). \]

Unfortunately, as is the case with many tree-related algorithms, the resulting recurrence relation is of little use in helping determine the running time of trees in general. Instead we have to logically think through what the algorithm is doing in order to analyze it.

Notice that each non-null node produces exactly one recursive call. During that call, control may be at the node at three significant moments:

  1. when the call first begins;
  2. when control returns from the left subtree;
  3. when control returns from the right subtree.

Thus, the recursive process may return to the same node more than once, but these moments represent only a constant amount of work per node. Exactly one of the three moments is chosen as the visit, depending on whether the traversal is preorder, inorder, or postorder.

Since there are \(n\) non-null nodes and only constant work is performed during the call for each one, the work associated with non-null nodes is \(\Theta(n)\).

The algorithms also make recursive calls on null child references. A binary tree with \(n\) nodes has \(2n\) child positions. Since \(n-1\) of those positions contain the edges leading to non-root nodes, the remaining \[ 2n-(n-1)=n+1 \] positions are null. Thus, there are \(n+1\) constant-time calls on null references.

Combining the \(n\) calls on nodes with the \(n+1\) calls on null references, each traversal performs only a linear number of calls and a constant amount of work in each one. Therefore, preorder, inorder, and postorder each have running time \[ \Theta(n). \]

Recursive Stack Space

At any moment, the active recursive calls correspond to a single downward path in the tree. Although control may later return to an earlier node, that return resumes an existing call rather than creating another copy of it.

A tree of height \(h\) has at most \(h+1\) nodes on a root-to-leaf path. There may also be one active call on a null child, but this adds only a constant. Therefore, each recursive depth-first traversal uses \[ \Theta(h+1) \] extra stack space.

For a complete binary tree, \(h=\Theta(\log n)\), so the stack uses \(\Theta(\log n)\) extra space. For a degenerate binary tree, \(h=n-1\), so the stack uses \(\Theta(n)\) extra space.

Level-Order Traversal

The depth-first traversals follow a branch downward before moving to another part of the tree. A level-order traversal instead visits nodes in order of increasing depth. It visits the root first, then all nodes at depth \(1\), then all nodes at depth \(2\), and so on. Within each depth, nodes are visited from left to right.

Level order is therefore a breadth-first traversal. Instead of using recursion, it uses a queue to keep track of nodes that have been discovered but not yet processed.

Algorithm

The root is first placed in an empty queue. The algorithm repeatedly removes the node at the front of the queue, visits it, and adds its non-null children to the back of the queue. The left child is added before the right child so that nodes at the same depth are visited from left to right.

More precisely, level-order traversal proceeds as follows:

  1. If the tree is empty, stop.
  2. Place the root in an empty queue.
  3. Remove the node at the front of the queue.
  4. Visit that node.
  5. Add its left child to the queue if it exists.
  6. Add its right child to the queue if it exists.
  7. Repeat Steps 3-6 until the queue is empty.

This leads to the following pseudocode:

levelOrder(root):
  if root = null:
      return

  create an empty queue
  enqueue root

  while queue is not empty:
      node = dequeue
      visit(node)

      if node.left != null:
          enqueue node.left

      if node.right != null:
          enqueue node.right

The queue processes nodes in first-in, first-out order. Since children are added to the back of the queue, every node already waiting at the current depth is processed before any newly added node at the next depth.

The queue is what preserves this ordering. Nodes are processed in the order in which they were added, so nodes already waiting at one depth remain ahead of their children at the next depth.

Array-Based Level Order

If a binary tree is stored using the array representation described previously, processing its occupied array positions in increasing index order produces the same order as a level-order traversal. The indices assign positions one depth at a time from left to right, which is precisely the order in which level-order traversal visits the nodes.

For a complete binary tree, all occupied positions are consecutive, so level-order traversal is obtained simply by processing the array from beginning to end. For a tree whose array representation contains gaps, the empty positions must be skipped; processing the nonempty positions in increasing index order still produces the level-order sequence.

Analysis

Queue-Based Algorithm

Each node is added to the queue exactly once and removed from the queue exactly once. When a node is removed, the algorithm visits it and checks its two child references. Assuming that enqueue, dequeue, and the visit operation take constant time, the work performed for each node is \(\Theta(1)\).

Since the tree contains \(n\) nodes, the total running time is \(\Theta(n)\). This bound does not depend on the shape of the tree.

The extra space depends on the number of nodes waiting in the queue. Let \(w\) denote the width of the tree, meaning the largest number of nodes at any single depth.

While one depth is being processed, the queue may contain some remaining nodes from that depth together with children from the next depth. Since neither depth contains more than \(w\) nodes, the queue contains \(O(w)\) nodes. At the beginning of the widest depth, it contains all \(w\) nodes at that depth. Therefore, the queue uses \(\Theta(w)\) extra space.

For a complete binary tree, the final depth may contain \(\Theta(n)\) nodes, so the queue may require \(\Theta(n)\) extra space. For a degenerate binary tree, each depth contains only one node, so the queue contains at most one node and uses \(\Theta(1)\) extra space.

Array-Based Algorithm

Suppose the array representation has length \(m\), including any empty positions. Scanning the array from beginning to end takes \(\Theta(m)\) time because every array position must be examined, whether or not it contains a node.

For a complete binary tree with \(n\) nodes, all occupied positions are consecutive, so \(m=n\) and the scan takes \(\Theta(n)\) time. For a sparse tree, however, \(m\) may be much larger than \(n\). Scanning the entire array may therefore take much more than \(\Theta(n)\) time.

Apart from the array that already stores the tree, the scan requires only \(\Theta(1)\) extra space. Thus, the array-based method can use less additional space than the queue-based method, but it is efficient only when the tree is stored compactly.

Remark

The output sequence shown in the animation requires \(\Theta(n)\) space because it stores every visited value. This space is not required by either traversal method. In many applications, the visit operation processes each value immediately without saving the complete traversal order.

Comparing the Traversals

The four traversals visit the same set of nodes, but they visit them in different orders. Preorder, inorder, and postorder are depth-first traversals: each completely traverses one subtree before moving to another. Level order is breadth-first: it visits all nodes at one depth before proceeding to the next.

The appropriate traversal depends primarily on when a node should be processed relative to its parent, its children, and the other nodes at the same depth.

Inorder \(D,\ B,\ H,\ E,\ A,\ F,\ C,\ G\) Every node is visited after its entire left subtree and before its entire right subtree.
Postorder \(D,\ H,\ E,\ B,\ F,\ G,\ C,\ A\) Every node is visited after all of its descendants.

Preorder, inorder, and postorder make exactly the same recursive calls. Moving the visit(node) operation changes the visit sequence without changing which calls are made: 

preorder:   visit, left,  right
inorder:    left,  visit, right
postorder:  left,  right, visit

Level order is structurally different. It does not finish one subtree before beginning another. Instead, its queue preserves the order in which nodes are discovered and causes all nodes at one depth to be visited before nodes at the next depth.

Choosing a Traversal

  • Use preorder when a node must be processed before its descendants.
  • Use inorder when a binary tree must be processed between its left and right subtrees.
  • Use postorder when a node must be processed after its descendants.
  • Use level order when nodes must be processed by increasing depth.

Applications

The most appropriate traversal depends on when each node should be processed relative to its parent, its descendants, and the other nodes at the same depth. The following table summarizes several common applications.

Common Applications

Traversal When It Is Useful Common Applications
Preorder A node must be processed before any of its descendants.
  • producing prefix notation from an expression tree;
  • copying or serializing a tree from the root downward;
  • processing directory or organizational structures before their contents.
Inorder A node must be processed between its left and right subtrees.
  • listing the values of a binary search tree in sorted order;
  • producing infix notation from an expression tree;
  • processing the left and right portions of a binary structure around a central value.
Postorder A node must be processed only after all of its descendants.
  • producing postfix notation or evaluating an expression tree;
  • deleting a linked binary tree safely;
  • computing properties such as subtree size or height from child results.
Level order Nodes must be processed in order of increasing depth.
  • finding a shallowest node that satisfies a condition;
  • displaying or processing a tree one depth at a time;
  • constructing level-based layouts or summaries of a tree.

These applications are not exclusive. The same tree may be traversed in several different ways depending on the task being performed. For example, an expression tree can be written in prefix, infix, or postfix notation by changing only the traversal order.

Detailed Example: Expression Trees

Introduction

An expression tree represents an arithmetic expression using a binary tree. Each leaf stores an operand, such as a number or variable, and each internal node stores a binary operator. The left and right subtrees of an operator represent its left and right operands.

The position of an operator relative to its operands determines the notation used to write the expression:

  • In prefix notation, the operator appears before its operands.
  • In infix notation, the operator appears between its operands.
  • In postfix notation, the operator appears after its operands.

These three placements correspond directly to preorder, inorder, and postorder traversal.

Example 7: Three Notations from One Expression Tree

The root stores multiplication. Its left subtree represents \(a+b\), and its right subtree represents \(c-d\). The complete expression represented by the tree is therefore \[ (a+b)(c-d). \]

Traversing the same tree in three different depth-first orders places each operator before, between, or after the expressions represented by its subtrees.

FOO
Traversal Notation Result
Preorder Prefix * + a b - c d
Inorder Infix a + b * c - d
Postorder Postfix a b + c d - *

The prefix and postfix results preserve the structure of the expression without parentheses. However, the direct inorder result does not, so parentheses must be added to recover the grouping represented by the tree. We will discuss this in more detail below.

People generally find infix notation easiest to read because it is the notation normally used in mathematics and programming languages. Prefix and postfix notation may initially look less familiar, but they have an important advantage: the order of operations can be determined directly from the placement of the operators. When every operator has a known number of operands, parentheses and precedence rules are not needed to recover the structure of the expression.

Preorder and Prefix Notation

A preorder traversal visits each operator before traversing the subtrees that represent its operands. It therefore places every operator before its operands, producing prefix notation.

For the expression tree above, preorder produces \[ *,\ +,\ a,\ b,\ -,\ c,\ d, \] or * + a b - c d.

Prefix notation does not require parentheses to preserve the structure of this expression. The first symbol, *, indicates that the complete expression is a multiplication. Its first operand is the prefix expression + a b, and its second operand is the prefix expression - c d.

This makes prefix notation convenient for programs that process expressions recursively. After reading an operator, a program knows that it must next read the complete expressions representing that operator's operands. The notation records essentially the same parent-before-children structure as a preorder traversal of the expression tree.

Inorder and Infix Notation

An inorder traversal places each operator between its left and right operands, producing infix notation. This is the form people most commonly use when writing arithmetic: \[ a+b,\qquad c-d,\qquad (a+b)(c-d). \]

However, a direct inorder traversal of the example tree would output \[ a+b*c-d. \] This sequence contains the nodes in inorder, but it does not preserve the grouping represented by the tree. Under the usual rules of operator precedence, it would be interpreted as \[ a+(b*c)-d, \] which is not the expression represented by the tree.

To preserve the tree's structure, we can surround the expression represented by each internal node with parentheses. The operator is still processed between the left and right subtrees, so the central part of the algorithm remains inorder. However, the algorithm also outputs an opening parenthesis before traversing the left subtree and a closing parenthesis after traversing the right subtree. 

writeInfix(node):
  if node is a leaf:
      output node.value
      return

  output "("
  writeInfix(node.left)
  output node.value
  writeInfix(node.right)
  output ")"

Applied to the example tree, this algorithm produces \[ ((a+b)*(c-d)). \] The outermost pair of parentheses may be omitted when the expression is displayed, giving \[ (a+b)*(c-d). \]

Infix notation is usually easier for people to read, but it requires parentheses, precedence rules, and associativity rules to determine the intended structure. Prefix and postfix notation avoid that additional ambiguity by placing each operator in a position that identifies how its operands are grouped.

Remark

It is possible to omit some unnecessary parentheses by considering operator precedence and associativity. Determining exactly which parentheses may be removed requires more information than an ordinary inorder traversal uses. Fully parenthesizing the expression represented by every internal node is the simplest way to preserve the exact tree structure.

Postorder, Postfix Notation, and Evaluation

A postorder traversal visits each operator after traversing the subtrees that represent its operands. It therefore places every operator after its operands, producing postfix notation.

For the example tree, postorder produces \[ a,\ b,\ +,\ c,\ d,\ -,\ *, \] or a b + c d - *.

As with prefix notation, parentheses are unnecessary. When an operator is encountered, the expressions representing both of its operands have already appeared. For example, a b + represents \(a+b\), and c d - represents \(c-d\). The final multiplication operator combines those two completed expressions.

Postfix notation can be evaluated efficiently using a stack, as discussed on the Stacks page. Scan the expression from left to right. When an operand is encountered, push its value onto the stack. When an operator is encountered, pop its two operands, apply the operator, and push the result back onto the stack. When the scan finishes, the remaining stack value is the value of the expression.

Postorder also gives the natural recursive order for evaluating the expression tree directly. The values of the left and right subexpressions are computed before the operator stored at their parent is applied. 

evaluate(node):
  if node is a leaf:
      return node.value

  leftValue = evaluate(node.left)
  rightValue = evaluate(node.right)

  return apply(node.value, leftValue, rightValue)

The evaluation begins at the multiplication node and descends into its left subtree. Recursive tree evaluation and stack-based postfix evaluation express the same bottom-up dependency: operands are processed before the operator that combines them.

Detailed Example: Finding a Node at Minimum Depth

Level-order traversal is especially useful when we want to find a node that satisfies some condition and is as close to the root as possible. Because level order examines every node at depth \(0\), then every node at depth \(1\), then every node at depth \(2\), and so on, the first matching node must have minimum depth.

For example, the following algorithm returns a shallowest leaf in a binary tree: 

findShallowestLeaf(root):
  if root is null:
      return null

  create an empty queue
  enqueue root

  while the queue is not empty:
      node = dequeue

      if node is a leaf:
          return node

      if node.left is not null:
          enqueue node.left

      if node.right is not null:
          enqueue node.right

The algorithm stops as soon as it removes a leaf from the queue. At that point, every node at a smaller depth has already been examined.

The leaves are \(F\), \(G\), \(H\), \(I\), and \(J\). Node \(F\) has depth \(2\), while the other leaves have depth \(3\).

A level-order search visits the nodes in the order \[ A,\ B,\ C,\ D,\ E,\ F,\ldots \] and stops when it reaches \(F\). Since every node at depths \(0\) and \(1\) has already been examined, and \(F\) is the first leaf encountered at depth \(2\), \(F\) is a shallowest leaf.

Notice that nodes \(G\), \(H\), \(I\), and \(J\) have already been added to the queue when \(F\) is removed. However, they are all at depth \(3\), so they appear behind \(F\) and do not need to be examined.

Why Depth-First Search Does Not Give the Same Guarantee

A depth-first traversal may descend far into one subtree before examining a shallower node in another subtree. For example, preorder traversal of the same tree begins \[ A,\ B,\ D,\ G,\ldots \] and encounters the leaf \(G\), at depth \(3\), before it reaches the shallower leaf \(F\), at depth \(2\). Thus, the first matching node found by a depth-first traversal need not have minimum depth.

Remark

Level order guarantees that the first matching node has minimum depth, but there may be several matching nodes at that depth. Which one is returned first depends on the order in which children are added to the queue. In the algorithm above, left children are added before right children, so nodes at the same depth are examined from left to right.

The same idea applies whenever the goal is to find a node closest to the root, such as the shallowest node containing a particular value, the nearest descendant with an available position, or the first node at which some property holds. It is also the central idea behind breadth-first search in graphs, where vertices are explored in order of increasing distance from a starting vertex.
