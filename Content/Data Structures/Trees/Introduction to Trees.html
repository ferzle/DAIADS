Introduction to Trees

Overview

Trees (somtimes called rooted trees) are structures that organize data hierarchically. Unlike arrays and linked lists, where items are arranged in a single linear order, trees branch. One item may lead to several smaller substructures, and each of those may lead to still smaller substructures.

The word tree describes a general branching structure rather than one fixed abstract data type. Different tree structures use this branching shape in different ways. Some trees are mainly used to represent hierarchy, while others are designed for searching, sorting, indexing, priority queues, parsing, or storing strings.

Trees appear throughout computer science. Common examples include:

  • file systems, where folders contain files and other folders;
  • organization charts and family relationships;
  • arithmetic expressions and syntax trees;
  • decision trees and game trees;
  • binary search trees and balanced search trees;
  • heaps, which support priority queues;
  • tries, which store strings by prefix; and
  • B-trees, which are used in databases and file systems.

This section introduces vocabulary and concepts that apply to many tree structures, but not every term or property applies to every kind of tree in exactly the same way. Later pages focus especially on binary trees, tree traversals, binary search trees, and balanced search trees. Other tree structures, such as general trees, \(m\)-ary trees, 2-3 trees, red-black trees, B-trees, tries, and heaps, are important as well, but not all of them will be studied in equal depth here.

Remark: Trees versus acyclic graphs

In graph theory, a tree is often defined as a connected graph with no cycles. In data structures, we usually mean something more specific when we say tree: a rooted tree, where one node is chosen as the root and edges are interpreted as parent-child relationships. This root gives the structure its hierarchical meaning.

Because the same word is used in both settings, be careful when you see the term tree. Check whether it refers to a graph-theoretic tree or to a rooted tree data structure.

Basic Structure

Trees are made of nodes connected by edges. In a rooted tree, one node is distinguished as the root. Edges are usually viewed as leading downward from a node to its children. Every node except the root has exactly one parent, and every node is reached by following edges downward from the root.

Different tree structures place different restrictions on this basic parent-child structure: how many children a node may have, what information each node stores, and whether child positions matter. For example:

  • a general tree allows a node to have any number of children;
  • a binary tree allows at most two children per node;
  • a ternary tree allows at most three children per node;
  • a 2-3 tree is a multiway search tree whose internal nodes have two or three children; and
  • a B-tree allows nodes to store many keys and have many children.

Another difference is whether the children of a node have a meaningful order. In some trees, only the parent-child relationships matter. In others, positions such as first child, second child, left child, or right child have different roles. Binary trees are an important ordered case because the left and right child positions are distinct. We will study those details more carefully on the Binary Trees page.

Tree Terminology

The following terms are used throughout the study of trees.

Term Meaning
Node An individual position in a tree. A node usually stores data and may have zero or more children.
Edge A connection between a node and one of its children. Edges are usually not stored as separate objects; they are represented by references, links, or child lists.
Root The distinguished node from which the tree is viewed. Every node in the tree is reached by starting at the root and repeatedly moving to a child.
Parent For a non-root node \(v\), the parent of \(v\) is the unique node whose child is \(v\). Every node except the root has exactly one parent.
Child A node \(v\) is a child of a node \(u\) if \(u\) is the parent of \(v\). Equivalently, \(v\) is reached from \(u\) by one downward step in the tree.
Siblings Nodes that have the same parent.
Leaf A node with no children.
Internal node A node with at least one child. In this book, the root is an internal node if it has at least one child.
Ancestor A node \(u\) is an ancestor of a node \(v\) if \(u\) lies on the path from the root to \(v\). In this book, \(v\) is considered an ancestor of itself.
Descendant A node \(v\) is a descendant of a node \(u\) if \(v\) can be reached by starting at \(u\) and repeatedly moving to a child. In this book, \(u\) is considered a descendant of itself.
Subtree The subtree rooted at a node \(u\) consists of \(u\) and all descendants of \(u\), viewed as a smaller tree with root \(u\).

Some authors use ancestor and descendant to exclude the node itself. In this book, a node is both an ancestor and a descendant of itself. When we need to exclude the node itself, we will say proper ancestor or proper descendant.

Depth, Height, and Level

Several measurements describe where a node is located in a tree and how tall the tree is.

  • The depth of a node is the number of edges from the root to that node. The root has depth \(0\).
  • The level of a node is often used as another name for depth, although some authors count levels starting at \(1\) instead of \(0\).
  • The height of a node is the number of edges on the longest downward path from that node to a leaf.
  • The height of a tree is the height of its root.

In this book, unless otherwise stated, height and depth are counted by edges. Thus a tree with one node has height \(0\), and an empty tree is usually treated as having height \(-1\). This convention is especially useful when writing recursive formulas and code.

Consider the following tree.

Node \(A\) has depth \(0\). Nodes \(B\), \(C\), and \(D\) have depth \(1\). Nodes \(E\), \(F\), and \(G\) have depth \(2\), and node \(H\) has depth \(3\).

The height of \(F\) is \(1\), since the longest downward path from \(F\) to a leaf is \(F \rightarrow H\). The height of \(B\) is \(2\), since the longest downward path from \(B\) to a leaf is \(B \rightarrow F \rightarrow H\). The height of the whole tree is \(3\), because the longest path from the root to a leaf is \(A \rightarrow B \rightarrow F \rightarrow H\).

Recursive View of Trees

Trees are naturally recursive structures. Once a root is chosen, each child of the root is itself the root of a smaller tree, called a subtree. This means that a large tree can be understood in terms of smaller trees with the same general form.

Many specific tree families are also defined recursively. For example, a binary tree is either empty or consists of a root, a left subtree, and a right subtree, where the left and right subtrees are themselves binary trees. Similarly, a general rooted tree consists of a root together with zero or more subtrees rooted at its children.

This recursive structure is one reason trees are closely connected to recursive algorithms. A recursive tree algorithm usually follows this pattern:

  1. Handle the empty tree or leaf case.
  2. Process the root, if needed.
  3. Recursively process one or more subtrees.
  4. Combine the results from the subtrees, if needed.

For example, to count the nodes in a tree, we count the root and then recursively count the nodes in each subtree. The total is \(1\) plus the sum of the subtree counts. To compute the height, we recursively compute the heights of the subtrees, take the maximum subtree height, and then add \(1\). The added \(1\) counts the edge from the root to the tallest subtree.

The exact recursive structure depends on the kind of tree. In a binary tree, there are at most two recursive subproblems: the left subtree and the right subtree. In a general tree, there may be any number of subtrees. In a 2-3 tree or B-tree, a node may store multiple keys and have several children, but each child still roots a smaller tree of the same type.

Common Tree Types

There are many different kinds of trees. They differ in how many children a node may have, whether children have a left-to-right order, whether keys are stored in sorted order, and whether the tree tries to keep its height small. These categories can also overlap; for example, an AVL tree is a binary tree, a binary search tree, and a balanced tree.

Tree Type Basic Idea Typical Role
General tree A node may have any number of children. Represents hierarchical data with no fixed branching limit, such as folders or organization charts.
\(m\)-ary tree Each node has at most \(m\) children, for some fixed number \(m\). Models structures where each node has a fixed maximum number of possible child positions.
Binary tree Each node has at most two children, usually distinguished as left and right. Provides a simple recursive structure used in traversals, expression trees, and search trees.
Binary search tree A binary tree with an ordering rule: keys in the left subtree are smaller, and keys in the right subtree are larger. Maintains a sorted set of keys while supporting search, insertion, deletion, and sorted traversal.
AVL tree A self-balancing binary search tree that keeps the heights of left and right subtrees tightly controlled. Guarantees efficient search by preventing the tree from becoming too tall.
Red-black tree A self-balancing binary search tree that uses color rules to enforce a looser form of balance. Provides efficient search-tree operations with fewer rotations than stricter balancing methods in many cases.
2-3 tree A balanced search tree where each internal node has two or three children and stores one or two keys. Illustrates multiway balancing and provides a conceptual model for other balanced search trees.
B-tree A balanced multiway search tree whose nodes can store many keys and have many children. Keeps trees shallow when data is stored in large blocks, as in databases and file systems.
Heap A tree-based structure where each parent has priority over its children according to a heap-order rule. Supports efficient access to the highest-priority or lowest-priority item.
Trie A tree for storing strings or sequences, where paths correspond to prefixes. Supports prefix-based operations such as dictionary lookup, autocomplete, and prefix search.

This chapter focuses primarily on binary trees and search trees. Heaps and tries are also tree-based structures, but they are usually studied separately because their organizing rules and applications are different from those of binary search trees.

Ordered and Unordered Trees

In some trees, the order of a node's children matters. In others, only the parent-child relationships matter.

An unordered tree is a tree where only the parent-child relationships matter. For example, in an organization chart, the people reporting to the same manager may not have a meaningful left-to-right order. Rearranging those children in a drawing does not necessarily change the underlying structure.

The two drawings below represent the same unordered tree. The children are shown in a different left-to-right order, but the parent-child relationships are unchanged.

In both drawings, \(A\) has children \(B\), \(C\), and \(D\), and \(B\) has children \(E\) and \(F\). Only the visual order changed.

An ordered tree is a tree where the children of a node have distinct positions or a meaningful left-to-right order. Binary trees are ordered because a node's left child and right child play different roles. Swapping the left and right children of a node usually creates a different binary tree.

Example 10: Ordered tree: different order, different tree

In an ordered tree, child positions matter. The two binary trees below are different because the left and right children of the root have been swapped.

In the first tree, \(B\) is the left child and \(C\) is the right child. In the second, those roles are reversed. For an ordered tree such as a binary tree, that changes the structure.

This distinction is important because many tree algorithms depend on child order. For example, inorder traversal only makes sense for trees where child positions are meaningful, and binary search trees rely on the difference between the left subtree and the right subtree.

Why Height Matters

The height of a tree can strongly affect the efficiency of algorithms that use it. Many tree algorithms follow paths from the root down toward a leaf. If the height is small, those paths are short. If the height is large, those paths may contain almost all of the nodes in the tree.

This matters most for trees that are used to support operations such as search, insertion, deletion, or finding a minimum or maximum value. In those settings, the running time often depends on the height \(h\), not just on the number of nodes \(n\). A tree with many nodes can still support efficient operations if its height is small, but the same operations can become slow if its height grows too large.

For example, a binary search tree with \(n\) nodes can have height as small as \(\Theta(\log n)\) or as large as \(\Theta(n)\). Since search, insertion, and deletion in a binary search tree take time proportional to the height, the height of the tree can change the running time from logarithmic to linear.

Example 11: Same number of nodes, different heights.

Both trees below have 7 nodes. The first has height \(2\), while the second has height \(6\). Algorithms that follow a path from the root to a leaf may do much more work on the taller tree.

Shorter tree: height \(2\)

Taller tree: height \(6\)

In the shorter tree, every root-to-leaf path has length at most \(2\). In the taller tree, the only root-to-leaf path has length \(6\). This is why many search-tree structures try to keep height close to \(O(\log n)\) instead of letting it grow close to \(n\).

Important Point.

For many tree algorithms, the key cost is not just the number of nodes \(n\), but the height \(h\) of the tree. Balanced trees are designed to keep \(h\) small, usually \(O(\log n)\), so that root-to-leaf paths stay short.

Different tree structures control height in different ways. AVL trees and red-black trees use rotations to keep binary search trees balanced. 2-3 trees and B-trees use nodes with multiple keys and multiple children to keep the tree shallow. These ideas will appear later in the chapter.

The Path Ahead

The rest of this section develops tree structures in stages. We begin with the basic structure of binary trees, then study algorithms that process trees, and finally look at search trees whose height is controlled to support efficient operations.

  1. Binary Trees: Introduces trees where each node has at most two children, usually distinguished as left and right.
  2. Tree Traversals: Studies systematic ways to visit every node in a tree, including preorder, inorder, postorder, and level-order traversal.
  3. Binary Search Trees: Adds a recursive ordering rule that supports search, insertion, deletion, and sorted traversal; these operations are efficient when the tree has small height.
  4. Balanced Search Trees: Explains why ordinary binary search trees can become inefficient and introduces the general goal of keeping height logarithmic.
  5. AVL Trees: Presents a self-balancing binary search tree that uses rotations to maintain a strict height-balance condition.
  6. 2-3 Trees: Presents a balanced multiway search tree where nodes may contain one or two keys and all leaves stay at the same depth.
  7. Red-Black Trees: Gives a brief look at another widely used self-balancing binary search tree, especially important in many library implementations.
  8. B-Trees: Briefly introduces multiway search trees designed to keep trees shallow when data is stored in large blocks, as in databases and file systems.

The main theme connecting these topics is height. Many tree operations are fast when the height is small, so much of the chapter is about how different tree structures organize data while keeping paths from the root short.

Reading Comprehension Questions

  1. Linear versus Hierarchical: How is a tree different from a linear structure such as an array or linked list?
  2. Basic Relationships: In a rooted tree, what is the relationship between a parent and a child?
  3. Leaves: What makes a node a leaf?
  4. Subtrees: What nodes are included in the subtree rooted at a node \(x\)?
  5. Depth and Height: What is the difference between the depth of a node and the height of a node?
  6. Binary Trees: What extra restriction does a binary tree have compared with a general tree?
  7. Ordered Trees: Why is a binary tree considered an ordered tree?
  8. Shape and Efficiency: Why does the height of a tree matter for many tree algorithms?
  1. Answer: A linear structure arranges items in one sequence. A tree arranges items hierarchically, so one node may lead to several children and each child may root another subtree.
  2. Answer: A parent is the node directly above another node, and a child is a node directly below that parent.
  3. Answer: A node is a leaf if it has no children.
  4. Answer: The subtree rooted at \(x\) contains \(x\) and all descendants of \(x\).
  5. Answer: The depth of a node counts edges from the root down to that node. The height of a node counts edges on the longest downward path from that node to a leaf.
  6. Answer: In a binary tree, each node has at most two children, usually called the left child and the right child.
  7. Answer: A binary tree is ordered because the left child and right child are distinguished. Swapping them usually produces a different binary tree.
  8. Answer: Many tree algorithms follow paths from the root downward. If the tree has small height, those paths are short. If the tree has large height, those paths can be long, making the algorithm slower.

In-Class Activities

  1. Label the Tree: Give students a diagram of a rooted tree with 8 to 12 nodes. Have them label the root, leaves, internal nodes, parents, children, siblings, ancestors, descendants, and at least three different subtrees.
  2. Depth and Height Table: For a provided tree, make a table listing each node, its depth, its height, and whether it is a leaf or internal node.
  3. Same Nodes, Different Shape: Give students the same set of node labels and ask them to draw two different rooted trees using those labels. Compare which relationships changed and which labels stayed the same.
  4. General or Binary: Show several tree diagrams. For each one, students decide whether it is a general tree, an \(m\)-ary tree for some small \(m\), a binary tree, or not enough information is given.
  5. Ordered or Unordered: Give examples such as a file system, expression tree, organization chart, and binary search tree. Students decide whether sibling order matters in each case and explain why.
  6. Build a Physical Tree: Use index cards or sticky notes as nodes. Students arrange them into a rooted tree, then answer questions about parent-child relationships, subtrees, depth, and height.
  7. Shape and Cost: Draw a balanced-looking binary tree and a long skinny binary tree with the same number of nodes. Students compare the maximum root-to-leaf path length in each tree and discuss why this matters for searching.
  8. Classify Tree Families: Give brief descriptions of binary trees, binary search trees, AVL trees, 2-3 trees, B-trees, heaps, and tries. Students match each description to the correct tree family.

Homework Problems

  1. Identify Relationships: Draw the tree with root \(A\), children \(B\), \(C\), and \(D\); children \(E\) and \(F\) under \(B\); child \(G\) under \(C\); and children \(H\) and \(I\) under \(D\).
    1. List all leaves.
    2. List all internal nodes.
    3. List the siblings of \(C\).
    4. List the descendants of \(D\).
    5. List the nodes in the subtree rooted at \(B\).
  2. Depth and Height: For the tree in Problem 1, compute the depth and height of every node. Use the convention that height is counted by edges and that a leaf has height \(0\).
  3. Draw from Relationships: Draw a rooted tree satisfying the following conditions:
    1. The root is \(R\).
    2. \(R\) has children \(A\), \(B\), and \(C\).
    3. \(A\) has children \(D\) and \(E\).
    4. \(C\) has child \(F\).
    5. \(F\) has children \(G\) and \(H\).
    Then identify the leaves, internal nodes, and height of the tree.
  4. Binary or Not: For each description below, decide whether the structure must be a binary tree. Explain briefly.
    1. Every node has at most two children.
    2. Every node has exactly two children.
    3. The root has three children, but every other node has at most two children.
    4. Every node has a left child and a right child, either of which may be empty.
  5. Subtree Counting: In any nonempty rooted tree, every node roots a subtree. Explain why a tree with \(n\) nodes has exactly \(n\) subtrees if we count one rooted subtree for each node.
  6. Ordered versus Unordered: Consider a node with children \(A\), \(B\), and \(C\).
    1. How many different left-to-right orders are possible for these children?
    2. Would these orders represent different ordered trees?
    3. Would these orders represent different unordered trees?
  7. Tree Shape: Draw two binary trees with 7 nodes:
    1. One tree with height \(2\).
    2. One tree with height \(6\).
    3. Explain why the second tree is less efficient for algorithms that may need to follow a path from the root to a leaf.
  8. Tree Type Matching: Match each description to the most appropriate tree type: general tree, binary tree, binary search tree, AVL tree, 2-3 tree, B-tree, heap, or trie.
    1. Used to support priority queue operations.
    2. Stores strings by following characters along paths.
    3. Allows each node to have at most two children.
    4. Keeps search efficient by enforcing a strict height-balance rule.
    5. Uses many keys per node and is useful for database indexes.
    6. Stores keys so that smaller values are found to the left and larger values to the right.
