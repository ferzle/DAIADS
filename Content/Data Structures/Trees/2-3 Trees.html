2-3 Trees

Overview

A 2-3 tree is an ordered search tree designed to solve essentially the same problem as a binary search tree: maintain a changing collection of comparable keys while supporting search, insertion, removal, minimum, maximum, predecessor, successor, sorted traversal, and range queries. Both structures use key comparisons to rule out entire subtrees. In that sense, a 2-3 tree is not a different kind of abstract data type; it is a different way to implement the same ordered-set or ordered-map behavior.

The difference is balance. A plain binary search tree orders its keys but does not control its shape. An unfavorable insertion order can turn it into a chain and make an operation take \(O(n)\) time. A 2-3 tree prevents that degeneration by allowing a node to hold either one or two keys—and, when the node is internal, to have two or three children. That flexibility lets updates preserve one powerful rule: every leaf is at the same depth.

A 2-3 tree is therefore a perfectly height-balanced search tree. Search still follows a single downward path, as it does in a BST, but insertion and removal may restructure nodes along that path. Insertion splits full nodes and promotes keys into their parent nodes; removal redistributes keys or merges nodes when a node becomes deficient. The repairs preserve a logarithmic height, so search, insertion, and removal are guaranteed to take \(O(\log n)\) time regardless of the order in which keys arrive.

Defining Properties

A nonempty 2-3 tree is an ordered rooted tree satisfying the following conditions:

  1. Legal node types: Every node is either a 2-node, which stores one key, or a 3-node, which stores two keys in increasing order. A leaf has no children. An internal 2-node has exactly two children, and an internal 3-node has exactly three children.
  2. Search order: The keys in an internal node separate the ranges represented by its children, so we call them separator keys.
    1. For a 2-node containing \(a\), the left subtree contains keys less than \(a\), and the right subtree contains keys greater than \(a\). Thus \(a\) separates the two child ranges.
    2. For a 3-node containing \(a<b\), the left, middle, and right subtrees contain keys less than \(a\), between \(a\) and \(b\), and greater than \(b\), respectively. Thus \(a\) separates the left and middle child ranges, while \(b\) separates the middle and right child ranges.
  3. Uniform leaf depth: Every leaf lies at the same depth. Equivalently, every path from the root to a leaf has the same length.

2-node

Stores one key \(a\). If it is internal, child subtree \(T_0\) contains keys less than \(a\), and child subtree \(T_1\) contains keys greater than \(a\).

3-node

Stores ordered keys \(a<b\). If it is internal, child subtree \(T_0\) contains keys less than \(a\), \(T_1\) contains keys between \(a\) and \(b\), and \(T_2\) contains keys greater than \(b\).

Its left child contains keys less than 20, and its right child contains keys greater than 20 but still less than 40, because the entire subtree lies to the left of the root key 40. An internal 2-node is much like a node in a binary search tree: it stores one key, has two children, and uses that key to separate smaller values from larger values.
  • 3-node: The node containing 50 and 60 is a 3-node. Since it has two keys, it has three children. Because the entire node lies between 40 and 70, its left child contains keys between 40 and 50, its middle child contains keys between 50 and 60, and its right child contains keys between 60 and 70. A 3-node is a natural extension of a binary search tree node: two separator keys divide its children into three ordered ranges rather than two.
  • Order: Order is crucial. Keys inside a node are stored in increasing order, and each child subtree must contain exactly the keys in the range determined by its parent key or keys.
  • Balance: Every leaf is at the same depth, so every root-to-leaf path has the same length. A successful search may stop earlier if its key is stored in an internal node, but every unsuccessful search reaches a leaf at the same depth.
Terminology warning: A 2-node stores one key, while a 3-node stores two keys. The numbers refer to the number of children these nodes have when they are internal, not the number of keys they store. Thus the name "2-3 tree" refers to the two possible numbers of children of an internal node.

This page treats a 2-3 tree as an ordered set of distinct keys. A map can store a value beside each key, and a multiset can store a count, but neither change affects the balancing ideas. Empty trees are allowed; a nonempty root may be either a 2-node or a 3-node.

The remaining challenge is to design search and update operations that preserve all three properties; the next sections explain how 2-3 trees search, split, promote, redistribute, and merge without violating them.

Core Operations

Overview

A 2-3 tree supports the standard operations of an ordered set or ordered map. Some operations only examine the existing structure, while insertion and removal may change it.

Category Operations Purpose
Search search(key) Locate a stored key or determine that it is absent.
Extreme keys minimum(), maximum() Find the smallest or largest stored key.
Neighbor queries predecessor(key), successor(key) Find the immediately preceding or following stored key.
Ordered reporting traverse(), range(low, high) Report all keys, or a requested interval, in increasing order.
Updates insert(key), remove(key) Add or remove a key while preserving all defining properties.
Container information isEmpty(), size() Report whether the tree is empty or how many keys it stores.

Every operation begins at the root. If the tree is empty, there is no root node, so searches and ordered queries report that no key was found, while insertion creates the first node. In a nonempty tree, search and the other ordered queries follow the key ranges downward without changing the structure. Insertion and removal may temporarily violate one of the defining properties, so they must repair the tree before returning. The following subsections develop these operations in that order.

Search

Search begins at the root and follows a single downward path. At each node, compare the target with the one or two keys stored there. If the target equals either key, the search succeeds. Otherwise, the comparisons identify exactly one child subtree that could still contain the target. The other subtrees can be ignored because they represent disjoint key ranges. If the current node is a leaf and does not contain the target, the search fails.

Current node Relationship to the target Next step
2-node containing \(a\) target \(=a\) Report that the key was found.
target \(<a\) Follow the left child.
target \(>a\) Follow the right child.
3-node containing \(a<b\) target \(=a\) or target \(=b\) Report that the key was found.
target \(<a\) Follow the left child.
\(a<\) target \(<b\) Follow the middle child.
target \(>b\) Follow the right child.

High-Level Search Procedure

  1. Begin at the root. If the tree is empty, report that the target is absent.
  2. Compare the target with the key or keys in the current node. If it matches a key, report that the target was found.
  3. If the current node is a leaf, report that the target is absent.
  4. If the current node is a 2-node containing \(a\), follow the left child when the target is less than \(a\), and the right child when the target is greater than \(a\).
  5. If the current node is a 3-node containing \(a<b\), follow the left child when the target is less than \(a\), the middle child when it lies between \(a\) and \(b\), and the right child when it is greater than \(b\).
  6. Return to Step 2 using the chosen child as the current node.
Why search follows only one path: The children of a node represent nonoverlapping key ranges. Once the comparisons identify the target's range, no other child subtree can contain the target.

Search is also the starting point for several other operations. Insertion follows a search path to the leaf where a new key belongs, removal first searches for the key to delete, and the ordered queries use similar downward navigation to locate extreme or neighboring keys.

Ordered Queries

Because a 2-3 tree preserves the keys in sorted order, it supports more than exact search. It can locate extreme keys, find neighboring keys, and report keys in increasing order or within a requested interval. These operations examine the existing structure without modifying it.

Minimum and Maximum

The search-order property makes the minimum and maximum easy to locate. Every key in a left child subtree is smaller than the key or keys in its parent, so the minimum is found by repeatedly following the left child. Similarly, every key in a right child subtree is larger than the key or keys in its parent, so the maximum is found by repeatedly following the right child.

When the path reaches a leaf, the minimum is the leaf's only key or its smaller key. The maximum is the leaf's only key or its larger key. An empty tree has neither a minimum nor a maximum.

High-Level Minimum Procedure

  1. Begin at the root. If the tree is empty, report that no minimum exists.
  2. If the current node is a leaf, return its only key or its smaller key.
  3. Otherwise, follow the left child and return to Step 2 using that child as the current node.

High-Level Maximum Procedure

  1. Begin at the root. If the tree is empty, report that no maximum exists.
  2. If the current node is a leaf, return its only key or its larger key.
  3. Otherwise, follow the right child and return to Step 2 using that child as the current node.
Why the extreme keys occur in these leaves: Every move to a left child enters a subtree containing only smaller keys, while every move to a right child enters a subtree containing only larger keys. Once a leaf is reached, no more extreme subtree remains to explore.

These operations work much as they do in a binary search tree: repeatedly follow the leftmost or rightmost child, except that the final leaf may contain two keys, so return its smaller or larger key.

Predecessor and Successor

For a stored key \(x\), its predecessor is the largest stored key smaller than \(x\), and its successor is the smallest stored key larger than \(x\). The minimum key has no predecessor, and the maximum key has no successor.

In a 2-3 tree, a neighboring key may occur in the same leaf, in an adjacent child subtree, or in an ancestor node. Which case applies depends on whether the key is stored in a leaf or an internal node.

Example 4: Predecessors and Successors
  • Neighbor in the same leaf: The predecessor of 80 is 75, and the successor of 75 is 80. Both keys are stored in the same leaf 3-node, so there is no child subtree containing a key between them.
  • Neighbor in a child subtree: The predecessor of 60 is the maximum key in the child subtree immediately to its left, which is 55. Similarly, the successor of 50 is the minimum key in the child subtree immediately to its right, which is also 55.
  • Neighbor in an ancestor: The predecessor of 45 is 40. The leaf containing 45 has no smaller key and no child subtree to its left, so the search moves upward until it reaches the separator 40. Similarly, the successor of 65 is 70.
  • No neighbor: Key 10 has no predecessor, and key 95 has no successor.

The examples illustrate the main cases. The following procedures describe them precisely.

High-Level Predecessor Procedure

  1. Search for the key. If it is absent, report that the operation is not defined.
  2. If there is a child subtree immediately to the left of the key, return the maximum key in that subtree.
  3. If the key is the larger key in a leaf 3-node, return the smaller key from that same node.
  4. Otherwise, let current be the node containing the key and move upward as follows:
    1. If current is the root, the key is the minimum and has no predecessor.
    2. Let parent be the parent of current.
    3. If current is not the leftmost child of parent, return the separator key in parent immediately to the left of that child.
    4. If current is the leftmost child of parent, make parent the new current node and return to part (a).

High-Level Successor Procedure

  1. Search for the key. If it is absent, report that the operation is not defined.
  2. If there is a child subtree immediately to the right of the key, return the minimum key in that subtree.
  3. If the key is the smaller key in a leaf 3-node, return the larger key from that same node.
  4. Otherwise, let current be the node containing the key and move upward as follows:
    1. If current is the root, the key is the maximum and has no successor.
    2. Let parent be the parent of current.
    3. If current is not the rightmost child of parent, return the separator key in parent immediately to the right of that child.
    4. If current is the rightmost child of parent, make parent the new current node and return to part (a).
Why the ancestor case works: For a predecessor, if the current node is its parent's leftmost child, every key in the parent is larger, so the search must continue upward. The first time the current node is not the leftmost child, the separator key in the parent immediately to its left is the closest smaller key. Successor is symmetric: continue upward from a rightmost child, and return the separator immediately to the right of the first child that is not rightmost.

These operations are similar to predecessor and successor in a binary search tree, but a 3-node adds one new possibility: the neighboring key may be stored in the same node.

If these procedures are not yet completely clear, do not be discouraged. Predecessor and successor are among the trickier 2-3 tree operations. Read through the examples and procedures a second time, paying particular attention to when the search moves downward and when it moves upward, and think about why each direction makes sense.

Traversal and Range Queries

A 2-3 tree can report all of its keys in increasing order. The traversal processes each node from left to right, visiting each child subtree in the position determined by the keys that separate it from the other subtrees. Here, to report a key means to output it or otherwise process it as part of the traversal.

Traversal in Increasing Order
  1. For a 2-node containing \(a\):
    1. Traverse its left child subtree.
    2. Report \(a\).
    3. Traverse its right child subtree.
  2. For a 3-node containing \(a<b\):
    1. Traverse its left child subtree.
    2. Report \(a\).
    3. Traverse its middle child subtree.
    4. Report \(b\).
    5. Traverse its right child subtree.
  3. At a leaf, skip the child-subtree steps and report the key or keys in increasing order.

Range Queries

A range query reports every stored key in a requested interval \([\mathit{low},\mathit{high}]\), in increasing order. It uses the same left-to-right order as the full traversal, but places a condition before each recursive call or report. These conditions allow it to skip subtrees and keys that cannot belong to the requested interval.

The procedure is almost identical to the traversal, except that it places a condition on each substep. If a key is not in the requested range, skip it; if a subtree cannot contain any keys in the range, skip the entire subtree.

  1. For a 2-node containing \(a\):
    1. If \(\mathit{low}<a\), traverse its left child subtree.
    2. If \(\mathit{low}\leq a\leq\mathit{high}\), report \(a\).
    3. If \(a<\mathit{high}\), traverse its right child subtree.
  2. For a 3-node containing \(a<b\):
    1. If \(\mathit{low}<a\), traverse its left child subtree.
    2. If \(\mathit{low}\leq a\leq\mathit{high}\), report \(a\).
    3. If \(\mathit{low}<b\) and \(a<\mathit{high}\), traverse its middle child subtree.
    4. If \(\mathit{low}\leq b\leq\mathit{high}\), report \(b\).
    5. If \(b<\mathit{high}\), traverse its right child subtree.
  3. At a leaf, skip the child-subtree steps and report only the key or keys that lie in the requested interval.
Example 6: A Range Query

On the tree in Example 5, the range query \([48,78]\) reports:

\(50,55,60,65,70,75\).

The query skips the entire subtree to the left of 40 because every key there is smaller than 48. It traverses the middle subtree in order, reporting the keys from 50 through 65, and then reports 70 at the root. In the right subtree, it visits only the portion that may contain keys no larger than 78, so it reports 75 but does not examine the subtree containing 90 and 95.

A range query is an ordered traversal with pruning: It considers children and keys in exactly the same order as the full traversal, but skips any key outside the requested interval and any child subtree whose possible key range does not overlap the interval.

These operations generalize inorder traversal and range reporting in a binary search tree. The difference is that a 3-node contributes two keys and divides its children into three ordered ranges.

Structural Update Operations

Search and ordered queries do not change the tree, but insertion and removal may temporarily create a node that is not a legal 2-node or 3-node. A small collection of local structural operations repairs the tree while preserving the sorted order of the keys and the common depth of the leaves.

Temporary states: Insertion may temporarily create an overfull node containing three keys. Removal may temporarily create a deficient node containing no keys. These states may occur while an update is in progress, but neither is allowed in the finished 2-3 tree.

Split and Promote

When a Leaf Becomes Overfull

As we will see in the insertion section, a new key is first placed in a leaf. If that leaf was a 2-node, it simply becomes a legal 3-node. If it was already a 3-node, adding the new key temporarily creates an overfull leaf containing three keys \(a<b<c\). To repair the overflow, we split the leaf: \(a\) and \(c\) become two separate 2-node leaves. The middle key \(b\) is then promoted into the parent. In the parent, the one child position that previously referred to the overfull leaf is replaced by two consecutive child positions referring to the new leaves, with the promoted key \(b\) between them. Together, these actions are called split and promote.

Example 7: Split and Promote at a Leaf

To illustrate this repair operation, suppose an insertion is adding 30 to the following tree. Since \(30<50\), the search reaches the left leaf, which already contains two keys.

  1. As part of an insertion, the new key 30 is directed to the full leaf containing 10 and 20.
  2. Adding 30 in sorted order temporarily produces the overfull leaf \([10\mid20\mid30]\).
  3. Split: Divide the overfull leaf into two 2-node leaves, one containing 10 and the other containing 30.
  4. Promote: Move the middle key 20 into the parent. Replace the parent's former child containing \([10\mid20\mid30]\) with two children: the leaf containing 10 to the left of 20 and the leaf containing 30 to its right. The parent becomes \([20\mid50]\).

The middle key is always promoted because it separates the two keys that remain below it: every key in the left node is smaller than the promoted key, and every key in the right node is larger. If the parent has room for the promoted key, the repair is complete. If the parent is already a 3-node, however, the promotion temporarily makes the parent overfull. That internal-node case requires one additional idea.

When Promotion Overfills an Internal Node

An internal node does not become overfull because a new key is inserted directly into it. Instead, one of its children splits and promotes a key into the internal node. If the internal node is already a 3-node, inserting the promoted key gives it three keys and four children.

For example, suppose a full internal node contains 40 and 70, with child subtrees \(A\), \(B\), and \(C\). If the root node of child subtree \(B\) splits and promotes 55, then \(B\) is replaced by two child subtrees, \(B_L\) and \(B_R\). The parent temporarily becomes the overfull node \([40\mid55\mid70]\), with four ordered children \(A,B_L,B_R,C\).

Example 8: A Promotion Overfills an Internal Node
  1. The full internal node \([40\mid70]\) initially has three child subtrees \(A\), \(B\), and \(C\).
  2. The root node of subtree \(B\) splits into \(B_L\) and \(B_R\) and promotes 55. The parent inserts 55 between 40 and 70 and replaces its former child \(B\) with the two children \(B_L\) and \(B_R\). It is now temporarily \([40\mid55\mid70]\), with four children \(A,B_L,B_R,C\).
  3. Split: The overfull internal node becomes two 2-nodes. The node containing 40 receives the first two children, \(A\) and \(B_L\). The node containing 70 receives the last two children, \(B_R\) and \(C\).
  4. Promote: Move the middle key 55 into the grandparent. Replace the grandparent's former child \([40\mid55\mid70]\) with the two new children containing 40 and 70.

Subtree \(U\) has the same height as the other child subtrees, as required in a 2-3 tree. It is drawn higher only to keep the main split-and-promote operation visually clear.

The four child subtrees remain in their original left-to-right order. In this example, their key ranges are:

  • every key in \(A\) is less than 40;
  • every key in \(B_L\) is between 40 and 55;
  • every key in \(B_R\) is between 55 and 70; and
  • every key in \(C\) is between 70 and 100.
General rule: An overfull internal node has three ordered keys and four ordered child subtrees. When the node splits, the new node containing the smallest key receives the first two child subtrees, and the new node containing the largest key receives the last two. The middle key is promoted, and the left-to-right order of the child subtrees never changes.
Which Key Is Promoted?

Suppose the full internal node originally contains \([p\mid q]\), where \(p<q\). One of its three children splits and promotes a key \(r\) into the node. The position of \(r\) depends on which child split:

Child that split Temporary overfull node Key promoted next
Left child \([r\mid p\mid q]\), with \(r<p<q\) \(p\)
Middle child \([p\mid r\mid q]\), with \(p<r<q\) \(r\)
Right child \([p\mid q\mid r]\), with \(p<q<r\) \(q\)

In every case, the middle key of the temporary three-key node is promoted to the next level. Therefore, the key \(r\) that arrived from the child is promoted again only when the middle child split. If the left or right child split, one of the parent's original keys is promoted instead.

After promoting the middle key, the smallest key remains in one new node with the first two child subtrees, and the largest key remains in the other new node with the last two child subtrees.

If the grandparent has room for the promoted key, the repair is complete. If the grandparent is already a 3-node, the promotion makes it overfull, and the same split-and-promote process repeats one level higher. A split may therefore continue upward through several levels. If the process reaches an overfull root, the special root case described later creates a new root.

Redistribute Through the Parent

As we will see in the removal section, deleting a key may temporarily leave a node with no keys. Such a node is called a deficient node. Repair depends on the deficient node's adjacent siblings:

  • If an adjacent sibling is a 3-node, it has an extra key, so the deficiency can be repaired by redistribution through the parent.
  • If every adjacent sibling is a 2-node, no sibling has an extra key. In that case, redistribution is impossible, and the deficient node must be merged with a sibling as described in the next subsection.

If both adjacent siblings are 3-nodes, either one can be used for redistribution; an implementation may choose one consistently. Because redistribution differs slightly for leaves and internal nodes, we consider the two cases separately.

Redistribution at a Leaf

A deficient leaf contains no keys and has no children. If an adjacent sibling is a 3-node, the separator key between the deficient leaf and its sibling moves down into the deficient leaf, and the sibling key nearest that separator moves up into the parent.

Example 9: Redistributing from a Right Sibling
  1. Move 40, the separator key in the parent, down into the deficient leaf.
  2. Move the sibling key nearest the separator, 60, up into the parent.
  3. The repaired leaf contains 40, the parent contains 60, and the sibling retains 70.

After the redistribution, both leaves are legal 2-nodes, and the parent still contains one key. The sorted order is preserved: \(40<60<70\).

Redistribution at an Internal Node

A deficient internal node usually results from repairing one of its deficient children. If that child must merge with a sibling, as described in the next subsection, one of the internal node's keys moves down into the merged child. The two original child positions are then replaced by the one merged child. If the internal node was a 2-node, it therefore loses its only key and is left with one child subtree. It is now deficient and must be repaired at the next level up, unless it is the root.

If an adjacent sibling of this deficient internal node is a 3-node, redistribution again moves a sibling key through the parent. Because the nodes are internal, one child subtree must also move from the sibling to the repaired node.

Example 10: Redistributing Between Internal Nodes
  1. Move 50, the separator key in the parent, down into the deficient internal node.
  2. Move the nearest sibling key, 70, up into the parent.
  3. Move the sibling child subtree nearest the separator, \(B\), into the repaired node. It becomes the child immediately to the right of 50.

The subtree transfer is required to preserve the search ranges. Before redistribution, every key in \(B\) lies between 50 and 70. After 50 moves into the repaired node, \(B\) therefore belongs immediately to its right. The sibling retains key 90 with child subtrees \(C\) and \(D\). Before and after redistribution, the ranges occur in the order \(A<50<B<70<C<90<D\), where each subtree symbol represents all of the keys in that subtree.

General rule: Move the separator key between the deficient node and the chosen sibling down into the deficient node, move the sibling key nearest the separator up into the parent, and, for internal nodes, move the sibling child subtree nearest the separator along with it. Redistribution from a left sibling is symmetric.

Redistribution repairs the deficient node without changing the number of keys or children in the parent. Therefore, unlike a merge, it does not create a new deficiency at the next level up.

Redistribution is sometimes described as borrowing from a sibling. The key does not move directly between siblings, however; the sibling key and the separator key in the parent exchange roles.

Merge Through the Parent

If none of a deficient node's adjacent siblings is a 3-node, redistribution is impossible because no sibling has an extra key. The deficient node must instead be combined with an adjacent 2-node sibling and the separator key between them. This operation is called merge through the parent.

If the deficient node has two adjacent 2-node siblings, either one may be used for the merge; an implementation may choose one consistently. As with redistribution, we first consider leaves and then internal nodes.

Merge at a Leaf

A deficient leaf has no keys. To repair it, move the separator key between the deficient leaf and the chosen sibling down and combine it with the sibling's key. The deficient leaf and the sibling are replaced by one legal 3-node leaf.

Example 11: Merging with the Left Sibling
  1. Move 40, the parent key between the sibling and the deficient leaf, down and combine it with 20 to form the 3-node leaf \([20\mid40]\).
  2. Replace the sibling and the deficient leaf with this one merged leaf.
  3. The parent loses 40 and one child position. It retains 80 and becomes a legal 2-node.

In this example, the merge repairs the deficient leaf. The parent began as a 3-node, so losing 40 changes it into the legal 2-node \([80]\). The repair therefore stops at this level.

Merge at an Internal Node

A deficient internal node has no keys and one child subtree. An adjacent 2-node sibling has one key and two child subtrees. To merge them, move the separator key between the two nodes down and combine it with the sibling key. The two keys and all three child subtrees form one legal 3-node.

Example 12: Merging Internal Nodes
  1. Move 50, the separator key in the parent, down and combine it with the sibling key 30, forming the merged 3-node \([30\mid50]\).
  2. Combine the sibling's child subtrees \(A\) and \(B\) with the deficient node's child subtree \(C\), preserving the order \(A,B,C\).
  3. Replace the sibling and the deficient node with the one merged internal node. The parent loses 50 and one child position, leaving the legal 2-node \([100]\).

The child-subtree order preserves the search ranges. Every key in \(A\) is less than 30, every key in \(B\) is between 30 and 50, and every key in \(C\) is between 50 and 100. The unaffected right child and its subtrees remain in place.

Both examples above merge with a left sibling. Merging with a right sibling is symmetric: move the separator key between the two nodes down, combine it with the sibling key, and preserve the left-to-right order of any child subtrees.

When a Merge Propagates Upward

In both examples above, the parent was a 3-node. After losing one key and one child position, it became a legal 2-node, so the repair stopped at that level. The more complicated case occurs when the parent is already a 2-node.

If a 2-node parent loses its only key and one child position, it is left with no keys and one child subtree. The parent is now deficient and must itself be repaired one level higher, either by redistribution or by another merge. This process may continue toward the root. If this deficient parent is the root, the special root case described in the next subsection applies.

Redistribution stops; merging may propagate: Redistribution leaves the parent with the same number of keys and children. A merge removes one key and one child position from the parent. If that parent was a 2-node, the merge creates a new deficiency one level higher.

Changes at the Root

The root requires special treatment because it has no parent. A structural change that reaches the root may change the height of the tree.

Example 13: Root Split and Root Contraction

An overfull root creates a new level above it, while a deficient root with one child is removed and replaced by that child.

  • Root split: If the root becomes overfull, split it and create a new root containing the promoted middle key. The two pieces of the old root become its children, and any child subtrees are distributed between them in sorted order. The height increases by one.
  • Root contraction: If the root loses its final key and has one remaining child, remove the empty root and make that child the new root. The child may be a leaf or an internal node. The height decreases by one.
  • Empty tree: If the root loses its final key and has no child, remove the root and leave the tree empty.

Summary of Structural Repairs

The structural operation used depends on whether a node temporarily has too many keys or too few keys and, for a deficient node, on the type of sibling available.

Temporary problem Condition Repair
Overfull node The node temporarily contains three keys Split the node and promote its middle key
Deficient node An adjacent sibling is a 3-node Redistribute through the parent
Deficient node No adjacent sibling is a 3-node Merge with an adjacent 2-node sibling through the parent
Change reaches the root The root has no parent Split, contract, or remove the root as appropriate
Only changes at the root alter the tree's height: Structural changes below the root rearrange keys and entire child subtrees locally. A root split increases every leaf depth by one, while a root contraction decreases every leaf depth by one. In either case, all leaves remain at the same depth.

Insertion uses splitting and promotion to repair overfull nodes. Removal uses redistribution and merging to repair deficient nodes. The next two sections apply these structural operations as part of the complete update procedures.

Insertion

Insertion begins by following the same downward path used by search. If the key is already present, the tree is unchanged because this page treats a 2-3 tree as a set of distinct keys. Otherwise, the search ends at the leaf where the new key belongs.

The new key is first inserted into that leaf in sorted order. Although the key may later be promoted into an internal node, placing it first in a leaf preserves the common depth of the existing leaves. What happens next depends on how many keys the leaf contained before the insertion.

  • The tree is empty: Create a root leaf containing the new key.
  • The leaf is a 2-node: Insert the new key in sorted order. The leaf becomes a legal 3-node, so the insertion is complete.
  • The leaf is a 3-node: Inserting the new key temporarily creates an overfull leaf with three keys. Split the leaf and promote its middle key into the parent.

A promotion may make the parent overfull. If so, split that internal node and promote its middle key one level higher. The same process continues until a promoted key enters a parent with room or an overfull root is split. Thus the only possible remaining violation moves upward one level at a time; each node below it has already been repaired.

High-Level Insertion Procedure

  1. If the tree is empty, create a root leaf containing the new key and finish.
  2. Search for the key, following child ranges until either the key is found or a leaf is reached.
    1. If the key is found, report that it was already present and leave the tree unchanged.
    2. Otherwise, let the reached leaf be the current node.
  3. Insert the new key into the current leaf in sorted order.
  4. If the current node now contains at most two keys, it is legal and the insertion is complete.
  5. While the current node is overfull:
    1. Split its three ordered keys around the middle key. The smallest and largest keys remain in two separate 2-nodes.
    2. If the current node is the root, create a new root containing the middle key, make the two split nodes its children, and finish.
    3. Otherwise, promote the middle key into the parent. In the parent, replace the one child position formerly occupied by the overfull node with two consecutive child positions for the split nodes.
    4. Make the parent the current node. If it is legal, the insertion is complete. If it is overfull, repeat the split-and-promote process one level higher.
Example 14: An Insertion That Reaches the Root

In this example, we show the result of inserting 55 into the following 2-3 tree. The search reaches the middle leaf. Inserting 55 there creates a temporary overflow. Splitting that leaf promotes 55 into the root, which then becomes overfull and must also be split.

Step 1: Insert into the leaf

Since \(40<55<80\), the search follows the middle child and reaches the leaf \([50\mid60]\). Inserting 55 in sorted order temporarily produces the overfull leaf \([50\mid55\mid60]\).

Step 2: Promote into the root, then split the root

Splitting the overfull leaf leaves \([50]\) and \([60]\) below and promotes 55 into the root. That makes the root temporarily overfull: \([40\mid55\mid80]\). Splitting the root produces the new root \([55]\), with children \([40]\) and \([80]\). The height increases by one, but all leaves remain at the same depth.

Why Insertion Preserves the 2-3 Tree Properties

  • Search order: The new key is inserted in sorted order. Every split promotes the middle key, leaving smaller keys and child ranges on one side and larger keys and child ranges on the other.
  • Legal node types: A successful insertion may temporarily create overfull nodes, but each is split before the operation finishes. When the operation finishes, every node therefore contains one or two keys.
  • Uniform leaf depth: A nonroot split replaces one node with two nodes at the same depth. A root split adds one new level above the entire tree, increasing the depth of every leaf together.
Insertion repairs only overflow: Insertion may create overfull nodes, so its structural repair is split and promote. Redistribution and merging repair deficient nodes and are used only during removal.

A successful insertion adds exactly one key to the collection, regardless of how many nodes split. The implementation section later gives precise pseudocode for searching to the leaf, inserting the key, and carrying promotions upward.

Removal

As with insertion, removal begins by searching for the target key. If the key is absent, the tree is unchanged. If the key occurs in a leaf, it can be removed there. If it occurs in an internal node, however, removing it immediately would leave two child ranges without the separator key between them. The operation therefore first replaces the internal key with its predecessor or successor and then removes that replacement key from its original leaf.

First Move an Internal-Key Removal to a Leaf

Suppose the target key \(x\) occurs in an internal node. Its predecessor is the maximum key in the child subtree immediately to the left of \(x\). Copy that predecessor into the position formerly occupied by \(x\), then remove the original predecessor from its leaf. Alternatively, the successor, which is the minimum key in the child subtree immediately to the right of \(x\), can be used.

This substitution preserves the search order because the predecessor is the largest key smaller than the removed key. The structural problem is now confined to a leaf. During the substitution there may temporarily be two copies of the predecessor, but the copy in the leaf is removed before the operation finishes.

Removing a Key from a Leaf

Once the removal has been reduced to a leaf, there are three cases:

  • The leaf is a 3-node: Remove the key. The leaf retains one key and becomes a legal 2-node, so the removal is complete.
  • The leaf is a 2-node and is not the root: Removing its only key leaves a deficient leaf. Repair it by redistribution if an adjacent sibling is a 3-node; otherwise, merge it with an adjacent 2-node sibling through the parent.
  • The leaf is the root: Removing its only key makes the tree empty.

Repairing a Deficient Node

A deficient nonroot node is repaired using the structural operations introduced earlier:

  1. If an adjacent sibling is a 3-node, redistribute through the parent. Redistribution repairs the deficiency without changing the number of keys or children in the parent, so the repair stops.
  2. If no adjacent sibling is a 3-node, merge the deficient node with an adjacent 2-node sibling and the separator key between them.
    1. If the parent remains a legal 2-node or 3-node, the repair stops.
    2. If the parent loses its only key, it becomes deficient, and the same repair decision is repeated one level higher.
  3. If a deficient root has one child, remove the empty root and make its child the new root. If it has no child, the tree becomes empty.

High-Level Removal Procedure

As mentioned earlier, either the predecessor or successor may be used when the key to be removed is in an internal node. For consistency, the procedure below always uses the predecessor.

  1. Search for the target key. If it is absent, report failure and leave the tree unchanged.
  2. If the target occurs in an internal node:
    1. Find its predecessor in the child subtree immediately to its left.
    2. Copy the predecessor into the target's position.
    3. Continue the removal at the leaf containing the original predecessor.
  3. Remove the key from the leaf.
  4. If the leaf still contains one key, it is legal and the removal is complete.
  5. If the leaf is the root and now has no keys, make the tree empty and finish.
  6. Otherwise, let the deficient leaf be the current node.
  7. While the current node is deficient:
    1. If the current node is the root, replace it with its one remaining child, or make the tree empty if it has no child. Then finish.
    2. If an adjacent sibling is a 3-node, redistribute through the parent and finish.
    3. Otherwise, merge the current node with an adjacent 2-node sibling through the parent.
    4. Make the parent the current node. If it still contains a key, it is legal and the removal is complete. If it has no keys, continue the repair one level higher.
Example 15: A Removal That Reaches the Root

Remove 40 from the tree below. Because 40 is stored in the root, first replace it with its predecessor, 30. Removing the original 30 then causes a leaf merge, an internal-node merge through the root, and finally a root contraction.

Step 1: Replace the Internal Key with Its Predecessor

The predecessor of 40 is the maximum key in its left child subtree, which is 30. Copy 30 into the root. The original 30 must still be removed from its leaf.

Step 2: Remove the Leaf Key and Merge the Leaves

Removing 30 leaves a deficient leaf. Its sibling \([10]\) is a 2-node, so redistribution is impossible. Merge the leaves using the separator key 20, producing \([10\mid20]\). The parent loses its only key and becomes a deficient internal node with one child.

Step 3: Merge the Internal Nodes Through the Root

The deficient internal node has only one adjacent sibling, \([60]\), which is a 2-node. Merge the two internal nodes using the root key 30. The resulting 3-node \([30\mid60]\) receives the three child subtrees in their existing order. The old root has lost its only key and its two former child positions have been replaced by the one merged child. It is therefore temporarily an empty root with one child.

Step 4: Contract the Empty Root

Remove the empty root and make its only child, \([30\mid60]\), the new root. The height decreases by one, and all leaves remain at the same depth.

Why Removal Preserves the 2-3 Tree Properties

  • Search order: An internal target is replaced by its predecessor or successor, so it remains between the same neighboring child ranges. Redistribution and merging move separator keys and child subtrees without changing their left-to-right order.
  • Legal node types: Removing from a 3-node directly produces a legal 2-node. Any deficient nonroot node is repaired by redistribution or merging before the operation finishes.
  • Uniform leaf depth: Redistribution and nonroot merging rearrange nodes at existing depths. A root contraction removes one level above the entire tree, decreasing every leaf depth together.
Removal repairs missing capacity: Redistribution repairs a deficient node without affecting the parent, so it stops immediately. Merging removes a key and child position from the parent, so the deficiency may continue upward. Only an empty root ends the propagation by contracting the tree or making it empty.

A successful removal deletes exactly one stored key, regardless of how many keys move during substitution, redistribution, merging, or root contraction. The implementation section later gives precise pseudocode for locating the removable leaf and carrying any deficiency upward.

Implementation

Representation

We represent a 2-3 tree as a linked multiway tree. The tree stores a reference to its root and a size equal to the number of keys in the collection. The number of nodes is not tracked because the size of the represented collection is the number of stored keys.

A single node type represents both 2-nodes and 3-nodes. Each node stores fixed-size arrays with enough room for the temporary states created during updates:

Why one flexible node type is used: Updates frequently change a 2-node into a 3-node or a 3-node into a 2-node. In addition, insertion may temporarily create a node with three keys and four children, while removal may temporarily create a node with no keys. A single node type with enough capacity for these temporary states avoids replacing and reconnecting nodes whenever their contents change. 
TwoThreeTree:
    root = reference to a Node, initially null
    size = 0

Node:
    keys = new array of length 3
    keyCount = 0

    children = new array of length 4, filled with null
    childCount = 0

    parent = null

The active keys occupy keys[0] through keys[keyCount - 1] and are stored in strictly increasing order. The active child references occupy children[0] through children[childCount - 1]. Algorithms ignore all array positions beyond the corresponding count.

Node state keyCount childCount
2-node leaf 1 0
3-node leaf 2 0
2-node internal node 1 2
3-node internal node 2 3
Temporary overfull leaf 3 0
Temporary overfull internal node 3 4
Temporary deficient leaf 0 0
Temporary deficient internal node 0 1

In a valid 2-3 tree, keyCount is 1 or 2. A node is either a leaf with no children or an internal node with exactly one more child than it has keys. The additional array positions are used only while insertion repairs an overflow or removal repairs a deficiency.

Child indexes correspond to the ranges separated by the keys. For a 2-node containing \(k_0\), child 0 contains keys smaller than \(k_0\), and child 1 contains keys larger than \(k_0\). For a 3-node containing \(k_0<k_1\), child 0 contains keys smaller than \(k_0\), child 1 contains keys between \(k_0\) and \(k_1\), and child 2 contains keys larger than \(k_1\).

The pseudocode uses parent references so that insertion and removal can repair the tree while moving upward. Whenever a child reference is inserted, moved, or removed, the corresponding parent reference must also be updated. An implementation could instead store the search path in a stack, but that alternative is not used here.

The counts define the current structure: The arrays provide capacity, but keyCount and childCount determine which positions are part of the node. This allows the same representation to describe legal nodes and the temporary overflow or deficiency states used during updates.

Node and Array Helpers

The update algorithms repeatedly search within a node, insert or remove array entries, and locate a child within its parent. Defining these actions as small helpers keeps the later insertion and removal procedures focused on the structure of the tree rather than on array manipulation.

Basic Node Helpers

A node is a leaf exactly when it has no active children. 

isLeaf(node):
    return node.childCount == 0

The helper findPosition returns the first index whose key is not smaller than the target. Its result is between 0 and node.keyCount, inclusive. 

findPosition(node, target):
    index = 0

    while index < node.keyCount and
          node.keys[index] < target:
        index = index + 1

    return index

The returned index has several related uses:

  • If index < node.keyCount and node.keys[index] == target, the target is stored at that index.
  • If the target is absent from a leaf, the index is the position where the target would be inserted.
  • If the current node is internal and the target is absent, the index is the child position whose key range could contain the target.

Updates that move upward also need to locate a node within its parent's child array. 

childIndex(parent, child):
    index = 0

    while index < parent.childCount:
        if parent.children[index] == child:
            return index

        index = index + 1

    return -1

When child.parent == parent, this helper should always find the child. A result of -1 therefore indicates that the parent and child references are inconsistent.

Key-Array Helpers

To insert a key at a given index, shift the keys at that index and to its right one position farther right. The caller is responsible for choosing an index that preserves the sorted order. 

insertKeyAt(node, index, key):
    i = node.keyCount

    while i > index:
        node.keys[i] = node.keys[i - 1]
        i = i - 1

    node.keys[index] = key
    node.keyCount = node.keyCount + 1

This helper may increase keyCount from 2 to 3, temporarily creating an overfull node. The array has enough capacity for that third key.

Removing a key performs the reverse shift. The contents of the newly inactive array position do not matter because all algorithms access only positions below keyCount. 

removeKeyAt(node, index):
    removedKey = node.keys[index]
    i = index

    while i < node.keyCount - 1:
        node.keys[i] = node.keys[i + 1]
        i = i + 1

    node.keyCount = node.keyCount - 1
    return removedKey

This helper may decrease keyCount from 1 to 0, temporarily creating a deficient node that must be repaired.

Child-Array Helpers

Child references are also stored in left-to-right order. Inserting a child shifts the existing references to the right and updates the inserted child's parent reference. 

insertChildAt(node, index, child):
    i = node.childCount

    while i > index:
        node.children[i] = node.children[i - 1]
        i = i - 1

    node.children[index] = child
    node.childCount = node.childCount + 1

    if child != null:
        child.parent = node

This helper may increase childCount from 3 to 4 when a child split causes a temporary overflow in an internal node.

Removing a child shifts the references to its right one position to the left. The last formerly active position is set to null so it does not retain a stale reference. 

removeChildAt(node, index):
    removedChild = node.children[index]
    i = index

    while i < node.childCount - 1:
        node.children[i] = node.children[i + 1]
        i = i + 1

    node.childCount = node.childCount - 1
    node.children[node.childCount] = null

    if removedChild != null and
       removedChild.parent == node:
        removedChild.parent = null

    return removedChild

This helper may decrease childCount from 2 to 1 when a merge makes an internal node deficient.

Helper responsibilities: These helpers maintain the active portions of the arrays, the corresponding counts, and parent references. Because key and child operations are performed separately, an individual helper does not ensure that the node as a whole is consistent. They also do not decide where a key or child belongs or repair an overflow or deficiency. The calling algorithm is responsible for choosing valid indexes, coordinating related key and child changes, and performing any required structural repair.
All node helpers take constant time: Although several helpers contain loops, a node has room for only three keys and four children. Each loop therefore performs only a constant number of steps.

Search

Search operations do not modify the tree. They use findPosition to interpret the keys within a node and follow the corresponding child ranges. Several operations return a location, represented by a node and key index, so later operations can reuse that location rather than searching for the key again.

Locating a Key or Insertion Position

The locate helper searches for a key. It returns a node, a key index, and a Boolean indicating whether the key was found. If the key is present, the node and index identify its location. If the key is absent, they identify the leaf where the key belongs and the index where it would be inserted. 

locate(key):
    node = root

    while node != null:
        index = findPosition(node, key)

        if index < node.keyCount and
           node.keys[index] == key:
            return (node, index, true)

        if isLeaf(node):
            return (node, index, false)

        node = node.children[index]

    return (null, -1, false)

The final return occurs only when the tree is empty. In every nonempty tree, an unsuccessful search reaches a leaf and returns a valid insertion position. An unsuccessful result from locate is later used by insertion.

Given locate, implementing search is straightforward. The version below returns the node containing the key and the index at which the key is stored. 

search(key):
    (node, index, found) = locate(key)

    if found:
        return (node, index)

    return (null, -1)
Returning multiple values: The pseudocode uses tuples to return related values together. This is straightforward in languages such as Python. In Java, a record or class can be used to return one object containing several fields. In C++, an implementation could similarly use a struct or std::tuple.
Locations are reusable: An unsuccessful result from locate identifies both the leaf where a new key belongs and the index where it should be inserted. More generally, returning locations as node-index pairs allows later operations to reuse them. For example, removal uses predecessorLocation (which we will see shortly) to find the leaf key that replaces a key stored in an internal node.

Ordered Queries

Maximum

The helper method maximumLocation(node) finds the maximum key in the subtree rooted at node by repeatedly following the rightmost active child until reaching a leaf. It returns the node and index containing that key so the location can be reused by methods such as predecessor and removal. The wrapper method maximum() calls maximumLocation(root) to find and return the maximum value in the entire tree. 

maximumLocation(node):
    while not isLeaf(node):
        node = node.children[node.childCount - 1]

    return (node, node.keyCount - 1)

maximum():
    if root == null:
        return NOT_FOUND

    (node, index) = maximumLocation(root)
    return node.keys[index]
Representing unsuccessful results: Methods that return a location use (null, -1) to indicate that no valid location exists. Methods that return a key use NOT_FOUND, which is a distinguished result rather than a special key value such as -1. A real implementation can represent NOT_FOUND using an optional value, such as OptionalInt or Optional<K> in Java or std::optional<Key> in C++.

The omitted minimumLocation(node) helper and minimum() wrapper are symmetric. They repeatedly follow child 0 and return the first key in the reached leaf.

Predecessor

The predecessorLocation helper assumes that node.keys[keyIndex] is the stored key whose predecessor is requested. It returns (null, -1) when the key is the minimum. 

predecessorLocation(node, keyIndex):
    if not isLeaf(node):
        return maximumLocation(node.children[keyIndex])

    if keyIndex > 0:
        return (node, keyIndex - 1)

    current = node

    while current.parent != null:
        parent = current.parent
        index = childIndex(parent, current)

        if index > 0:
            return (parent, index - 1)

        current = parent
    return (null, -1)

If the key is internal, its left child has the same index as the key, so the predecessor is the maximum key in that child subtree. At a leaf, the preceding key may be stored in the same node. Otherwise, the procedure moves upward until it first reaches a node that is not its parent's leftmost child.

Finding the predecessor of a given key value is a simple matter of finding the location of that key and calling the helper method. 

predecessor(key):
    (node, index) = search(key)

    if node == null:
        return NOT_FOUND

    (node, index) = predecessorLocation(node, index)

    if node == null:
        return NOT_FOUND

    return node.keys[index]

The omitted successorLocation(node, keyIndex) helper and successor(key) wrapper are symmetric to predecessorLocation(node, keyIndex) and predecessor(key). Their implementations reverse the directions and comparisons used by the predecessor methods.

Traversal in Increasing Order

A single loop handles both 2-nodes and 3-nodes. Before reporting key \(i\), recursively traverse child \(i\). After all active keys have been reported, traverse the final child. 

traverseNode(node):
    for index = 0 to node.keyCount - 1:
        if not isLeaf(node):
            traverseNode(node.children[index])

        report node.keys[index]

    if not isLeaf(node):
        traverseNode(node.children[node.keyCount])

traverse():
    if root != null:
        traverseNode(root)

For a 2-node, this processes child 0, key 0, and child 1. For a 3-node, it processes child 0, key 0, child 1, key 1, and child 2. This is a direct extension of inorder traversal in a binary tree.

Range Queries

A range query follows the same order as the full traversal but skips a child subtree when its key range cannot intersect \([\mathit{low},\mathit{high}]\). The procedure below assumes \(\mathit{low}\leq\mathit{high}\). 

rangeNode(node, low, high):
    for index = 0 to node.keyCount - 1:
        key = node.keys[index]

        if not isLeaf(node) and low < key and
           (index == 0 or node.keys[index - 1] < high):
            rangeNode(node.children[index], low, high)

        if low <= key and key <= high:
            report key

        if key >= high:
            return

    if not isLeaf(node) and node.keys[node.keyCount - 1] < high:
        rangeNode(node.children[node.keyCount], low, high)

range(low, high):
    if root != null and low <= high:
        rangeNode(root, low, high)

Before key \(i\), child \(i\) contains keys between the preceding separator, when one exists, and the current key. The two conditions on the recursive call test whether that interval can overlap the requested range. Once a key is at least high, every remaining key and child range in that node lies too far to the right, so the procedure returns.

Insertion

Recall that insertion follows three main steps:

  1. Use locate to determine whether the key is already present and, if not, where it belongs.
  2. Insert the new key into the appropriate leaf.
  3. If that node becomes overfull, split it and promote its middle key to the parent. Continue upward if the parent also becomes overfull.

The implementation below separates the two main parts of the repair: splitting an overfull node and incorporating the result of that split into its parent.

Splitting an Overfull Node

The splitOverfullNode(node) helper divides an overfull node into two nodes. It modifies node so that it becomes the left half, creates a new node containing the right half, and returns both the middle key and the new right node. The caller is responsible for promoting the middle key and attaching the right node to the appropriate parent. 

splitOverfullNode(node):
    promotedKey = node.keys[1]
    rightKey = node.keys[2]

    node.keyCount = 1

    rightNode = new Node
    insertKeyAt(rightNode, 0, rightKey)

    if node.childCount == 4:
        child = removeChildAt(node, 2)
        insertChildAt(rightNode, 0, child)

        child = removeChildAt(node, 2)
        insertChildAt(rightNode, 1, child)

    return (promotedKey, rightNode)

Both child removals use index 2. After the first child is removed, the original fourth child shifts into position 2. The child helpers also update the parent references of the moved children.

After the helper finishes, the original node contains the smallest key and, for an internal node, the first two children. rightNode contains the largest key and the final two children. The middle key is no longer stored in either node because it will be promoted.

The helper does not attach rightNode because the required action depends on whether node was the root. If it was the root, insertion creates a new root. Otherwise, the split is incorporated into the existing parent.

Promoting a Split to the Parent

Splitting a nonroot node produces three pieces: the original node, which becomes the left half; a key that must be promoted to the parent; and a new node containing the right half. The promoted key is inserted into the parent at the index of the original child, and the new right node is inserted immediately after that child. 

promoteToParent(parent, leftIndex, promotedKey, rightChild):
    insertKeyAt(parent, leftIndex, promotedKey)
    insertChildAt(parent, leftIndex + 1, rightChild)

The original node is already stored at parent.children[leftIndex]. After the two helper calls, parent.keys[leftIndex] contains the promoted key, and parent.children[leftIndex + 1] contains the new right half. The promoted key separates the key ranges of those two children. This promotion may temporarily make the parent overfull.

Complete Insertion

The public insert method returns false when the key is already present and true when a new key is inserted. Because the tree represents a set, duplicate keys are not added. 

insert(key):
    (node, index, found) = locate(key)

    if found:
        return false

    if node == null:
        root = new Node
        insertKeyAt(root, 0, key)
        size = 1
        return true

    insertKeyAt(node, index, key)
    size = size + 1

    while node.keyCount == 3:
        (promotedKey, rightNode) = splitOverfullNode(node)

        parent = node.parent

        if parent == null:
            newRoot = new Node
            insertKeyAt(newRoot, 0, promotedKey)
            insertChildAt(newRoot, 0, node)
            insertChildAt(newRoot, 1, rightNode)

            root = newRoot
            return true

        leftIndex = childIndex(parent, node)

        promoteToParent(parent, leftIndex, promotedKey, rightNode)

        node = parent

    return true

Inserting into an empty tree creates a root containing one key. Otherwise, locate supplies the destination leaf and insertion index. The key is counted exactly once, before any structural repairs occur; promoted keys are existing keys being moved and do not change size.

After a split, the algorithm continues with the parent because that is the only node that may now be overfull. If the overfull node has no parent, it was the root. A new root is then created containing the promoted key, and the height of the tree increases by one. No other insertion case changes the height of the tree.

Insertion repairs upward: A new key is inserted only at a leaf. Every later change consists of splitting one overfull node and promoting one key to its parent. The repair therefore follows a single path from the insertion leaf toward the root.

Removal

Recall that removal follows four main steps:

  1. Locate the key. If it is not present, report that no removal occurred.
  2. If the key is stored in an internal node, replace it with its predecessor. The predecessor is stored in a leaf, so that leaf becomes the location from which a key is physically removed.
  3. Remove the key from the leaf.
  4. If the leaf becomes deficient, repair it by redistribution or merging. A merge may make the parent deficient, so repair may continue upward.

As in the conceptual description, a deficient node temporarily contains no keys. A deficient leaf has no children, while a deficient internal node has one child.

Redistributing from a Sibling

Redistribution is possible when a sibling contains two keys. One key from the sibling moves to the parent, and the separator key from the parent moves into the deficient node. If the nodes are internal, one child reference must move with the keys.

The parameter nodeIndex is the index of the deficient node in its parent's child array. When redistributing from the left, the separator is immediately before that child. 

redistributeFromLeft(parent, nodeIndex):
    node = parent.children[nodeIndex]
    leftSibling = parent.children[nodeIndex - 1]
    separatorIndex = nodeIndex - 1

    separatorKey = parent.keys[separatorIndex]
    replacementKey = removeKeyAt(leftSibling, leftSibling.keyCount - 1)

    parent.keys[separatorIndex] = replacementKey
    insertKeyAt(node, 0, separatorKey)

    if not isLeaf(node):
        child = removeChildAt(leftSibling, leftSibling.childCount - 1)
        insertChildAt(node, 0, child)

The largest key in the left sibling replaces the parent separator. The old separator becomes the key in the deficient node. For internal nodes, the rightmost child of the left sibling becomes the leftmost child of the repaired node.

Redistribution from the right is symmetric. The separator immediately after the deficient node moves down, and the smallest key in the right sibling replaces it. 

redistributeFromRight(parent, nodeIndex):
    node = parent.children[nodeIndex]
    rightSibling = parent.children[nodeIndex + 1]
    separatorIndex = nodeIndex

    separatorKey = parent.keys[separatorIndex]
    replacementKey = removeKeyAt(rightSibling, 0)

    parent.keys[separatorIndex] = replacementKey
    insertKeyAt(node, 0, separatorKey)

    if not isLeaf(node):
        child = removeChildAt(rightSibling, 0)
        insertChildAt(node, node.childCount, child)

For internal nodes, the leftmost child of the right sibling becomes the rightmost child of the repaired node. After either redistribution, both siblings and the parent are valid, so no further repair is needed.

Merging Two Children

If neither adjacent sibling contains two keys, redistribution is not possible. The deficient node is then merged with a sibling and the separator key between them. The helper below merges two adjacent children into the left child.

The parameter separatorIndex identifies both the separator key and the child immediately to its left. Thus, the two children being merged are children[separatorIndex] and children[separatorIndex + 1]. 

mergeChildren(parent, separatorIndex):
    left = parent.children[separatorIndex]

    separatorKey = removeKeyAt(parent, separatorIndex)
    right =  removeChildAt(parent, separatorIndex + 1)

    insertKeyAt(left, left.keyCount, separatorKey)

    while right.keyCount > 0:
        key = removeKeyAt(right, 0)
        insertKeyAt(left, left.keyCount, key)

    while right.childCount > 0:
        child = removeChildAt(right, 0)
        insertChildAt(left, left.childCount, child)

All keys in the left child precede the separator, and all keys in the right child follow it, so appending the separator and the right child's keys preserves their sorted order. The children are appended in the same left-to-right order.

This helper is called only when one child is deficient and the other is a 2-node. The merged node therefore finishes with two keys. Removing the separator from the parent may, however, leave the parent with no keys.

Repairing a Deficiency

The repair procedure first checks whether an adjacent sibling can redistribute a key. If neither can, it merges the deficient node with a sibling and continues with the parent. 

repairDeficiency(node):
    while node != root and node.keyCount == 0:
        parent = node.parent
        nodeIndex = childIndex(parent, node)

        if nodeIndex > 0:
            leftSibling = parent.children[nodeIndex - 1]

            if leftSibling.keyCount == 2:
                redistributeFromLeft(parent, nodeIndex)
                return

        if nodeIndex + 1 < parent.childCount:
            rightSibling = parent.children[nodeIndex + 1]

            if rightSibling.keyCount == 2:
                redistributeFromRight(parent, nodeIndex)
                return

        if nodeIndex > 0:
            mergeChildren(parent, nodeIndex - 1)
        else:
            mergeChildren(parent, nodeIndex)

        node = parent

    if root.keyCount == 0:
        if root.childCount == 0:
            root = null
        else:
            oldRoot = root
            root = removeChildAt(oldRoot, 0)

The procedure prefers redistribution from the left when both directions are possible, although either choice is valid. If no sibling can spare a key, it merges with the left sibling when one exists; otherwise, it merges with the right sibling.

A merge reduces the number of keys in the parent. If the parent becomes deficient, the loop repairs it in the same way. If an empty root has one child, that child becomes the new root and the height decreases by one. If the root is an empty leaf, the tree becomes empty.

Complete Removal

The public remove method returns false when the key is absent and true when a key is removed. 

remove(key):
    (node, index, found) = locate(key)

    if not found:
        return false

    if not isLeaf(node):
        (predecessorNode, predecessorIndex) =
            predecessorLocation(node, index)

        node.keys[index] =
            predecessorNode.keys[predecessorIndex]

        node = predecessorNode
        index = predecessorIndex

    removeKeyAt(node, index)
    size = size - 1

    if node.keyCount == 0:
        repairDeficiency(node)

    return true

When the requested key is stored in an internal node, its predecessor is copied into that position. The predecessor is then physically removed from its leaf. Thus, every structural removal and every possible deficiency begins at a leaf.

The size decreases exactly once, regardless of whether the requested key was originally stored in a leaf or an internal node. Redistribution and merging move existing keys and therefore do not change size.

Removal repairs upward: Redistribution repairs a deficiency immediately and ends the process. A merge repairs the current node but removes a key from its parent, so the deficiency may move one level upward. The process ends after a redistribution, upon reaching a valid parent, or after contracting the root.

Validation and Implementation Notes

The insertion and removal algorithms temporarily create overfull or deficient nodes, but every public operation should finish with a valid 2-3 tree. During implementation and testing, it is useful to run a validation procedure after each update.

A validator should check all of the following conditions:

  • The root is null exactly when size is 0, and a non-null root has no parent.
  • Every node contains one or two active keys.
  • The active keys within each node are in strictly increasing order.
  • Every key lies within the range determined by the keys in its ancestors.
  • Every node is either a leaf with no children or an internal node with exactly one more child than key.
  • Every active child reference is non-null and points back to the correct parent.
  • All leaves occur at the same depth.
  • The total number of keys in the nodes equals size.

The key-range check can be performed recursively. Each call receives lower and upper bounds for the keys in the current subtree. The keys in the node divide that range into the ranges passed to its children. Recording the depth of the first leaf allows every later leaf depth to be compared with it.

Temporary states should not remain: A node may contain three keys during insertion or no keys during removal, and an internal node may temporarily contain four or one child. These states are part of the repair process, but none should remain after insert or remove returns.

Additional Implementation Notes

  • The helper methods assume that their indexes and node relationships are valid. A practical implementation can use assertions to detect an invalid index, a missing child, or an inconsistent parent reference.
  • Whenever a child is moved, its parent reference must be updated. Whenever the root changes, the new root's parent must be null.
  • Keys outside the active portion of the key array are ignored. Child positions outside the active portion should be set to null so that stale references are not retained.
  • The implementation presented here repairs overflows and deficiencies while moving upward from a leaf. Other implementations use top-down algorithms that prepare nodes before descending, but they maintain the same 2-3 tree invariants.
Validation tests the representation, not just the output: A traversal may return the keys in sorted order even when child counts, parent references, or leaf depths are incorrect. A complete validator checks every structural invariant of the tree.

Analysis

Height

Let \(n\) be the number of stored keys and let \(h\) be the height of a nonempty 2-3 tree, measured in edges from the root to a leaf. Because all leaves occur at the same depth, trees of the same height differ in size according to how many of their nodes are 2-nodes or 3-nodes.

A tree of height \(h\) contains the fewest keys when every node is a 2-node. There are \(2^i\) nodes at depth \(i\), and each node stores one key. Thus the minimum number of keys is

\[ n_{\min}(h) =\sum_{i=0}^{h}2^i =2^{h+1}-1. \]

A tree of height \(h\) contains the most keys when every node is a 3-node. There are \(3^i\) nodes at depth \(i\), and each node stores two keys. Thus the maximum number of keys is

\[ n_{\max}(h) =2\sum_{i=0}^{h}3^i =3^{h+1}-1. \]

Minimum and Maximum Occupancy at Height Two

In general, a 2-3 tree of height \(h\) contains at least \(2^{h+1}-1\) keys and at most \(3^{h+1}-1\) keys. For \(h=2\), these formulas give \(2^3-1=7\) and \(3^3-1=26\), matching the two trees shown above.

Therefore, every 2-3 tree of height \(h\) satisfies

\[ 2^{h+1}-1\leq n\leq 3^{h+1}-1. \]

Solving these inequalities for the integer height gives

\[ \lceil\log_3(n+1)\rceil-1 \leq h\leq \lfloor\log_2(n+1)\rfloor-1. \]

Thus every 2-3 tree has height \(\Theta(\log n)\). Unlike an ordinary binary search tree, it cannot become a chain, regardless of the order in which keys are inserted or removed.

Cost Per Node

Each node contains at most two keys and three children in a valid tree, with temporary capacity for only three keys and four children. Searching within a node, shifting its active array entries, splitting it, redistributing a key, or merging two children therefore takes \(\Theta(1)\) time.

Consequently, operations that follow or repair a single root-to-leaf path perform only constant work at each of \(O(\log n)\) levels.

Search and Ordered Queries

The locate and search methods examine one node per level and follow only one child from each internal node. Their worst-case running time is therefore \(\Theta(h)=\Theta(\log n)\). A search may finish in \(\Theta(1)\) time when the tree is empty or the key is found in the root.

Finding the minimum or maximum follows one extreme-child path, so each takes \(\Theta(\log n)\) time in the worst case. Predecessor and successor also examine at most one downward path and one upward path, giving the same \(\Theta(\log n)\) worst-case bound.

A complete traversal reports all \(n\) keys and therefore takes \(\Theta(n)\) time. A range query that reports \(k\) keys takes \(O(\log n+k)\) time: \(O(\log n)\) work reaches and leaves the boundary of the requested interval, and the remaining work is proportional to the reported keys.

Insertion

Insertion first calls locate, which takes \(O(\log n)\) time. Inserting the key into the reached leaf takes \(\Theta(1)\) time because the key array has constant size.

If the leaf becomes overfull, it is split in \(\Theta(1)\) time. The promotion may make the parent overfull, but at most one node is split at each level. Even when the repair reaches the root, there are only \(O(\log n)\) levels to process. Thus insertion takes \(O(\log n)\) worst-case time.

When the key is already present, insertion performs only the search and returns without changing the tree. A duplicate found near the root may be detected in \(\Theta(1)\) time, but the worst-case bound remains \(O(\log n)\).

Removal

Removal first locates the key in \(O(\log n)\) time. If the key is in an internal node, finding its predecessor follows an additional path of length at most \(h\), which is still \(O(\log n)\).

Removing the key from its leaf takes \(\Theta(1)\) time. Redistribution repairs a deficiency in \(\Theta(1)\) time and stops. A merge also takes \(\Theta(1)\) time, but may move the deficiency to the parent. At most one merge occurs at each level, so even a repair that reaches and contracts the root takes \(O(\log n)\) time.

Therefore removal takes \(O(\log n)\) worst-case time. As with insertion, a simple case near the root may finish in \(\Theta(1)\) time, but no removal requires more than logarithmic time.

Space Complexity

Every node stores a constant-size key array, child array, counts, and a parent reference. Since every valid node contains one or two keys, a tree storing \(n\) keys contains between \(\lceil n/2\rceil\) and \(n\) nodes. It therefore uses \(\Theta(n)\) total space.

The unused positions reserved for a temporary third key and fourth child add only constant space per node. Parent references also add only constant space per node, so neither changes the \(\Theta(n)\) total-space bound.

The iterative search, predecessor, insertion, and removal algorithms use \(\Theta(1)\) auxiliary space because parent references allow them to move upward without storing the search path. Without parent references, an explicit stack of \(O(h)=O(\log n)\) references would be needed.

A cascading insertion may allocate one new node for each split, for as many as \(O(\log n)\) new nodes during one operation. These nodes remain in the tree and are part of its stored \(\Theta(n)\) space rather than temporary auxiliary space.

The recursive traversal, range-query, and validation procedures use a recursion stack of depth \(O(h)=O(\log n)\). Traversal additionally produces \(n\) reported keys, while a range query produces \(k\) reported keys; output space is normally counted separately from auxiliary space.

The balance rule gives a worst-case guarantee: Every valid 2-3 tree has logarithmic height. Search and updates therefore remain efficient for every sequence of operations, not merely on average or for favorable insertion orders.

Applications

A 2-3 tree can implement an ordered set or ordered map with worst-case logarithmic search, insertion, and removal. It is useful when updates must remain efficient and keys must also be processed in sorted order.

  • Ordered sets and maps: Keys remain searchable and traversable in sorted order while updates retain worst-case \(O(\log n)\) performance.
  • Indexes for ordered data: Records can be indexed by names, identifiers, dates, scores, or other comparable keys. Range queries can retrieve all records whose keys lie within a specified interval.
  • Event and schedule indexes: Predecessor and successor locate the events immediately before and after a given time, while a range query retrieves all events during a specified period.
  • Persistent ordered collections: An immutable version can create a new tree by rebuilding only the nodes on the modified root-to-leaf path while sharing untouched subtrees with earlier versions.

Connections and Comparisons

A 2-3 tree belongs to the search-tree family, but its multi-key nodes give it a different way to maintain balance. Comparing it with other structures clarifies both the advantages of this representation and the additional work required by updates.

  • Versus a plain BST: Both preserve sorted order, but a plain BST may reach height \(n-1\). A 2-3 tree guarantees logarithmic height for every sequence of updates.
  • Versus AVL trees: An AVL tree uses one-key binary nodes and restores balance with rotations. A 2-3 tree instead changes the number of keys and children stored in a node through splitting, redistribution, and merging.
  • Versus red-black trees: A red-black tree uses colored binary-tree nodes to represent a related multiway search tree. Standard red-black trees correspond closely to 2-3-4 trees, while some variants correspond to 2-3 trees. The multiway view can make the purpose of the balancing rules easier to visualize.
  • Versus a sorted array: Both support logarithmic search, but an array may shift \(\Theta(n)\) entries during an insertion or removal. A 2-3 tree changes only nodes along a root-to-leaf path.
  • Versus a hash table: Hashing often gives expected \(O(1)\) exact-key operations, but it does not naturally support sorted traversal, predecessor, successor, or range queries.
  • Versus B-trees: A 2-3 tree is a restricted B-tree in which every internal node has two or three children. Practical database and file-system B-trees store many more keys and children per node so that each storage access retrieves a large block of useful information.

Strict 2-3 trees are more common in teaching than as the direct implementation of standard mutable collections. Their variable-size nodes and removal cases require careful bookkeeping. Their ideas remain practically important, however, because the same split, promotion, redistribution, and merge operations appear in wider multiway search trees, and closely related structures can be encoded using binary nodes.

A useful comparison must consider both asymptotic cost and representation cost. A 2-3 tree guarantees short paths, but each node needs several key and child positions and each update has more cases than in a plain BST. Arrays are compact, hash tables often perform better for exact lookup, and wider B-trees reduce external-memory transfers. The appropriate structure depends on the complete operation mix.

Why 2-3 trees matter: They provide a direct and visual model of the balancing ideas used by red-black trees and larger multiway search trees.

Variations and Extensions

Several related structures extend the 2-3 tree by allowing different numbers of keys and children within each node.

  • 2-3-4 trees: Allow nodes with one, two, or three keys and therefore two, three, or four children. The additional legal node size changes the available insertion and removal strategies.
  • B-trees: Generalize the minimum and maximum numbers of keys and children allowed in a node. Practical implementations use much wider nodes than a 2-3 tree.
  • B+ trees: Store records or record references in the leaves while internal nodes mainly contain separator keys used for routing. The leaves are commonly linked to support efficient sequential and range access.

Although their capacity rules differ, these structures use the same basic ideas: separator keys divide ordered child ranges, and updates repair local overflows or deficiencies while preserving logarithmic height.

Common Pitfalls

  • Confusing keys with children in the node names: A 3-node contains two keys and has three child ranges, not three keys.
  • Treating a 3-node as two unrelated BST nodes: Both keys belong to one node at one depth. Search must compare against both keys before choosing a child.
  • Promoting the wrong key during a split: Only the median key correctly separates the smaller and larger halves.
  • Attaching split children in the wrong order: The four original child ranges must remain in the same left-to-right order when they are divided between the two resulting nodes.
  • Moving a key directly between siblings: Redistribution moves a sibling key up to the parent and moves the separator key down into the deficient node. Moving a key directly across would violate the child-range boundaries.
  • Stopping after replacing an internal key: The predecessor or successor copied into the internal node must still be removed from its original leaf.
  • Ignoring cascading repairs: A split can make the parent overfull, and a merge can make the parent deficient. Continue toward the root until every node is valid.
  • Updating keys without coordinating children: Key-array and child-array helpers operate separately. Splits, promotions, redistributions, and merges must preserve the relationship between the active keys and child ranges.
  • Allowing leaves at different depths: Correct key order alone is not enough. Uniform leaf depth is the invariant that gives the tree its worst-case height guarantee.
  • Measuring size by nodes: Nodes contain different numbers of keys. The size of the represented set is the total number of stored keys, not the number of nodes.

Summary

A 2-3 tree implements the same kind of ordered set or ordered map as a binary search tree. Comparisons within each node identify the only child range that can contain a target key. The ordering also supports minimum, maximum, predecessor, successor, increasing-order traversal, and range queries. Unlike a plain BST, however, a 2-3 tree uses nodes of different capacities to keep every leaf at the same depth.

A 2-node contains one key and, when internal, has two children. A 3-node contains two ordered keys and, when internal, has three children. The keys act as separators between nonoverlapping child ranges. In a valid 2-3 tree, every node contains one or two keys, every internal node has exactly one more child than it has keys, and every leaf lies at the same depth.

Search follows one downward path. Insertion searches to a leaf, inserts the new key in sorted order, and splits any temporary three-key node around its middle key. The middle key is promoted into the parent, so splitting may continue toward the root. Removal replaces an internal target with its predecessor or successor and then removes that replacement key from its original leaf. A deficient node is repaired by redistribution through the parent when an adjacent sibling has two keys; otherwise, it is merged with an adjacent 2-node sibling and a separator key from the parent. A merge may make the parent deficient and continue the repair upward.

The height increases only when an overfull root splits and decreases only when an empty root is replaced by its sole child. Both changes affect all leaves together. Because each internal node has at least two and at most three children, the number of keys grows exponentially with the height, giving \(h=\Theta(\log n)\). Search, insertion, and removal therefore have worst-case time \(\Theta(\log n)\). A complete traversal takes \(\Theta(n)\) time, and the structure uses \(\Theta(n)\) total space.
