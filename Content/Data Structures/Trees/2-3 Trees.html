2-3 Trees

Overview

A 2-3 tree is an ordered search tree designed to solve essentially the same problem as a binary search tree: maintain a changing collection of comparable keys while supporting search, insertion, removal, minimum, maximum, predecessor, successor, sorted traversal, and range queries. Both structures use key comparisons to rule out entire subtrees. In that sense, a 2-3 tree is not a different kind of abstract data type; it is a different way to implement the same ordered-set or ordered-map behavior.

The difference is balance. A plain binary search tree orders its keys but does not control its shape. An unfavorable insertion order can turn it into a chain and make an operation take \(O(n)\) time. A 2-3 tree prevents that degeneration by allowing a node to hold either one or two keys—and, when the node is internal, to have two or three children. That flexibility lets updates preserve one powerful rule: every leaf is at the same depth.

A 2-3 tree is therefore a perfectly height-balanced search tree. Search still follows a single downward path, as it does in a BST, but insertion and removal may restructure nodes along that path. Insertion splits full nodes and promotes separator keys; removal borrows keys or merges nodes when a node becomes too empty. The repairs preserve a logarithmic height, so search, insertion, and removal are guaranteed to take \(O(\log n)\) time regardless of the order in which keys arrive.

Defining Properties

A nonempty 2-3 tree is an ordered rooted tree satisfying the following conditions:

  1. Legal node types: Every node is either a 2-node, which stores one key, or a 3-node, which stores two keys in increasing order. A leaf has no children. An internal 2-node has exactly two children, and an internal 3-node has exactly three children.
  2. Search order: The keys in a node separate the ranges represented by its children.
    1. For a 2-node containing \(a\), the left subtree contains keys less than \(a\), and the right subtree contains keys greater than \(a\).
    2. For a 3-node containing \(a<b\), the left, middle, and right subtrees contain keys less than \(a\), between \(a\) and \(b\), and greater than \(b\), respectively.
  3. Uniform leaf depth: Every leaf lies at the same depth. Equivalently, every path from the root to a leaf has the same length.

2-node

Stores one key \(a\). If it is internal, child subtree \(T_0\) contains keys less than \(a\), and child subtree \(T_1\) contains keys greater than \(a\).

3-node

Stores ordered keys \(a<b\). If it is internal, child subtree \(T_0\) contains keys less than \(a\), \(T_1\) contains keys between \(a\) and \(b\), and \(T_2\) contains keys greater than \(b\).

This example illustrates the most important structural ideas:

  • 2-node: The node containing 20 is a 2-node. Since it has one key, it has two children. Its left child contains keys less than 20, and its right child contains keys greater than 20 but still less than 40, because the entire subtree lies to the left of the root key 40. An internal 2-node is much like a node in a binary search tree: it stores one key, has two children, and uses that key to separate smaller values from larger values.
  • 3-node: The node containing 50 and 60 is a 3-node. Since it has two keys, it has three children. Because the entire node lies between 40 and 70, its left child contains keys between 40 and 50, its middle child contains keys between 50 and 60, and its right child contains keys between 60 and 70. A 3-node is a natural extension of a binary search tree node: two separator keys divide its children into three ordered ranges rather than two.
  • Order: Order is crucial. Keys inside a node are stored in increasing order, and each child subtree must contain exactly the keys in the range determined by its parent key or keys.
  • Balance: Every leaf is at the same depth, so every root-to-leaf path has the same length. A successful search may stop earlier if its key is stored in an internal node, but every unsuccessful search reaches a leaf at the same depth.
Terminology warning: A 2-node stores one key, while a 3-node stores two keys. The numbers refer to the number of children these nodes have when they are internal, not the number of keys they store. Thus the name "2-3 tree" refers to the two possible numbers of children of an internal node.

This page treats a 2-3 tree as an ordered set of distinct keys. A map can store a value beside each key, and a multiset can store a count, but neither change affects the balancing ideas. Empty trees are allowed; a nonempty root may be either a 2-node or a 3-node.

The remaining challenge is to design search and update operations that preserve all three properties; the next sections explain how 2-3 trees search, split, promote, borrow, and merge without violating them.

Core Operations

Overview

A 2-3 tree supports the standard operations of an ordered set or ordered map. Some operations only examine the existing structure, while insertion and removal may change it.

Category Operations Purpose
Search search(key) Locate a stored key or determine that it is absent.
Extreme keys minimum(), maximum() Find the smallest or largest stored key.
Neighbor queries predecessor(key), successor(key) Find the immediately preceding or following stored key.
Ordered reporting traverse(), range(low, high) Report all keys, or a requested interval, in increasing order.
Updates insert(key), remove(key) Add or remove a key while preserving all defining properties.
Container information isEmpty(), size() Report whether the tree is empty or how many keys it stores.

Every operation begins at the root. If the tree is empty, there is no root node, so searches and ordered queries report that no key was found, while insertion creates the first node. In a nonempty tree, search and the other ordered queries follow the key ranges downward without changing the structure. Insertion and removal may temporarily violate one of the defining properties, so they must repair the tree before returning. The following subsections develop these operations in that order.

Search

Search begins at the root and follows a single downward path. At each node, compare the target with the one or two keys stored there. If the target equals either key, the search succeeds. Otherwise, the comparisons identify exactly one child subtree that could still contain the target. The other subtrees can be ignored because they represent disjoint key ranges. If the current node is a leaf and does not contain the target, the search fails.

Current node Relationship to the target Next step
2-node containing \(a\) target \(=a\) Report that the key was found.
target \(<a\) Follow the left child.
target \(>a\) Follow the right child.
3-node containing \(a<b\) target \(=a\) or target \(=b\) Report that the key was found.
target \(<a\) Follow the left child.
\(a<\) target \(<b\) Follow the middle child.
target \(>b\) Follow the right child.

Consider the following 2-3 tree. The highlighted nodes and edges show the search path for 65.

  1. The root contains 40 and 70. Since \(40<65<70\), search follows the middle child.
  2. The next node contains 50 and 60. Since \(65>60\), search follows the right child.

A search for 58 first follows the middle child of the root because \(40<58<70\). At the node containing 50 and 60, it then follows the middle child because \(50<58<60\), reaching the leaf containing 55. Because 58 is not in that leaf and there is no child to follow, the search reports that 58 is absent.

High-Level Search Procedure

  1. Begin at the root. If the tree is empty, report that the target is absent.
  2. Compare the target with the key or keys in the current node. If it matches a key, report that the target was found.
  3. If the current node is a leaf, report that the target is absent.
  4. If the current node is a 2-node containing \(a\), follow the left child when the target is less than \(a\), and the right child when the target is greater than \(a\).
  5. If the current node is a 3-node containing \(a<b\), follow the left child when the target is less than \(a\), the middle child when it lies between \(a\) and \(b\), and the right child when it is greater than \(b\).
  6. Return to Step 2 using the chosen child as the current node.
Why search follows only one path: The children of a node represent nonoverlapping key ranges. Once the comparisons identify the target's range, no other child subtree can contain the target.

Search is also the starting point for several other operations. Insertion follows a search path to the leaf where a new key belongs, removal first searches for the key to delete, and the ordered queries use similar downward navigation to locate extreme or neighboring keys.

Ordered Queries

Because a 2-3 tree preserves the keys in sorted order, it supports more than exact search. It can locate extreme keys, find neighboring keys, and report keys in increasing order or within a requested interval. These operations examine the existing structure without modifying it.

Minimum and Maximum

The search-order property makes the minimum and maximum easy to locate. Every key in a left child subtree is smaller than the key or keys in its parent, so the minimum is found by repeatedly following the left child. Similarly, every key in a right child subtree is larger than the key or keys in its parent, so the maximum is found by repeatedly following the right child.

When the path reaches a leaf, the minimum is the leaf's only key or its smaller key. The maximum is the leaf's only key or its larger key. An empty tree has neither a minimum nor a maximum.

Example 3: Finding the Minimum and Maximum

In the tree below, the orange path leads to the minimum and the green path leads to the maximum.

To find the minimum, follow the left child of the root, then the left child of the node containing 20. The reached leaf contains 10, so the minimum is 10.

To find the maximum, follow the right child of the root, then the right child of the node containing 85. The reached leaf contains 90 and 95, so its larger key, 95, is the maximum.

High-Level Minimum Procedure

  1. Begin at the root. If the tree is empty, report that no minimum exists.
  2. If the current node is a leaf, return its only key or its smaller key.
  3. Otherwise, follow the left child and return to Step 2 using that child as the current node.

High-Level Maximum Procedure

  1. Begin at the root. If the tree is empty, report that no maximum exists.
  2. If the current node is a leaf, return its only key or its larger key.
  3. Otherwise, follow the right child and return to Step 2 using that child as the current node.
Why the extreme keys occur in these leaves: Every move to a left child enters a subtree containing only smaller keys, while every move to a right child enters a subtree containing only larger keys. Once a leaf is reached, no more extreme subtree remains to explore.

These operations work much as they do in a binary search tree: repeatedly follow the leftmost or rightmost child, except that the final leaf may contain two keys, so return its smaller or larger key.

Predecessor and Successor

For a stored key \(x\), its predecessor is the largest stored key smaller than \(x\), and its successor is the smallest stored key larger than \(x\). The minimum key has no predecessor, and the maximum key has no successor.

In a 2-3 tree, a neighboring key may occur in the same leaf, in an adjacent child subtree, or in an ancestor node. Which case applies depends on whether the key is stored in a leaf or an internal node.

Example 4: Predecessors and Successors
  • Neighbor in the same leaf: The predecessor of 80 is 75, and the successor of 75 is 80. Both keys are stored in the same leaf 3-node, so there is no child subtree containing a key between them.
  • Neighbor in a child subtree: The predecessor of 60 is the maximum key in the child subtree immediately to its left, which is 55. Similarly, the successor of 50 is the minimum key in the child subtree immediately to its right, which is also 55.
  • Neighbor in an ancestor: The predecessor of 45 is 40. The leaf containing 45 has no smaller key and no child subtree to its left, so the search moves upward until it reaches the separator 40. Similarly, the successor of 65 is 70.
  • No neighbor: Key 10 has no predecessor, and key 95 has no successor.

The examples illustrate the main cases. The following procedures describe them precisely.

High-Level Predecessor Procedure

  1. Search for the key. If it is absent, report that the operation is not defined.
  2. If there is a child subtree immediately to the left of the key, return the maximum key in that subtree.
  3. If the key is the larger key in a leaf 3-node, return the smaller key from that same node.
  4. Otherwise, let current be the node containing the key and move upward as follows:
    1. If current is the root, the key is the minimum and has no predecessor.
    2. Let parent be the parent of current.
    3. If current is not the leftmost child of parent, return the separator key in parent immediately to the left of that child.
    4. If current is the leftmost child of parent, make parent the new current node and return to part (a).

High-Level Successor Procedure

  1. Search for the key. If it is absent, report that the operation is not defined.
  2. If there is a child subtree immediately to the right of the key, return the minimum key in that subtree.
  3. If the key is the smaller key in a leaf 3-node, return the larger key from that same node.
  4. Otherwise, let current be the node containing the key and move upward as follows:
    1. If current is the root, the key is the maximum and has no successor.
    2. Let parent be the parent of current.
    3. If current is not the rightmost child of parent, return the separator key in parent immediately to the right of that child.
    4. If current is the rightmost child of parent, make parent the new current node and return to part (a).
Why the ancestor case works: For a predecessor, if the current node is its parent's leftmost child, every key in the parent is larger, so the search must continue upward. The first time the current node is not the leftmost child, the parent separator immediately to its left is the closest smaller key. Successor is symmetric: continue upward from a rightmost child, and return the separator immediately to the right of the first child that is not rightmost.

These operations are similar to predecessor and successor in a binary search tree, but a 3-node adds one new possibility: the neighboring key may be stored in the same node.

If these procedures are not yet completely clear, do not be discouraged. Predecessor and successor are among the trickier 2-3 tree operations. Read through the examples and procedures a second time, paying particular attention to when the search moves downward and when it moves upward, and think about why each direction makes sense.

Traversal and Range Queries

A 2-3 tree can report all of its keys in increasing order. The traversal processes each node from left to right, visiting each child subtree in the position determined by the keys that separate it from the other subtrees. Here, to report a key means to output it or otherwise process it as part of the traversal.

Traversal in Increasing Order
  1. For a 2-node containing \(a\):
    1. Traverse its left child subtree.
    2. Report \(a\).
    3. Traverse its right child subtree.
  2. For a 3-node containing \(a<b\):
    1. Traverse its left child subtree.
    2. Report \(a\).
    3. Traverse its middle child subtree.
    4. Report \(b\).
    5. Traverse its right child subtree.
  3. At a leaf, skip the child-subtree steps and report the key or keys in increasing order.

Range Queries

A range query reports every stored key in a requested interval \([\mathit{low},\mathit{high}]\), in increasing order. It uses the same left-to-right order as the full traversal, but places a condition before each recursive call or report. These conditions allow it to skip subtrees and keys that cannot belong to the requested interval.

The procedure is almost identical to the traversal, except that it places a condition on each substep. If a key is not in the requested range, skip it; if a subtree cannot contain any keys in the range, skip the entire subtree.

  1. For a 2-node containing \(a\):
    1. If \(\mathit{low}<a\), traverse its left child subtree.
    2. If \(\mathit{low}\leq a\leq\mathit{high}\), report \(a\).
    3. If \(a<\mathit{high}\), traverse its right child subtree.
  2. For a 3-node containing \(a<b\):
    1. If \(\mathit{low}<a\), traverse its left child subtree.
    2. If \(\mathit{low}\leq a\leq\mathit{high}\), report \(a\).
    3. If \(\mathit{low}<b\) and \(a<\mathit{high}\), traverse its middle child subtree.
    4. If \(\mathit{low}\leq b\leq\mathit{high}\), report \(b\).
    5. If \(b<\mathit{high}\), traverse its right child subtree.
  3. At a leaf, skip the child-subtree steps and report only the key or keys that lie in the requested interval.
Example 6: A Range Query

On the tree in Example 4, the range query \([48,78]\) reports:

\(50,55,60,65,70,75\).

The query skips the entire subtree to the left of 40 because every key there is smaller than 48. It traverses the middle subtree in order, reporting the keys from 50 through 65, and then reports 70 at the root. In the right subtree, it visits only the portion that may contain keys no larger than 78, so it reports 75 but does not examine the subtree containing 90 and 95.

A range query is an ordered traversal with pruning: It considers children and keys in exactly the same order as the full traversal, but skips any key outside the requested interval and any child subtree whose possible key range does not overlap the interval.

These operations generalize inorder traversal and range reporting in a binary search tree. The difference is that a 3-node contributes two keys and divides its children into three ordered ranges.

Structural Update Operations

Search and ordered queries do not change the tree, but insertion and removal may temporarily create a node that is not a legal 2-node or 3-node. A small collection of local structural operations repairs the tree while preserving the sorted order of the keys and the common depth of the leaves.

Temporary states: Insertion may temporarily create an overfull node containing three keys. Removal may temporarily create a deficient node containing no keys. These states may occur while an update is in progress, but neither is allowed in the finished 2-3 tree.

Split and Promote

When a Leaf Becomes Overfull

As we will see in the insertion section, a new key is first placed in a leaf. If that leaf was a 2-node, it simply becomes a legal 3-node. If it was already a 3-node, adding the new key temporarily creates an overfull leaf containing three keys \(a<b<c\). To repair the overflow, we split the leaf: \(a\) and \(c\) become two separate 2-node leaves. The middle key \(b\) is then promoted into the parent. In the parent, the one child position that previously referred to the overfull leaf is replaced by two consecutive child positions referring to the new leaves, with the promoted key \(b\) between them. Together, these actions are called split and promote.

Example 7: Split and Promote at a Leaf

To illustrate this repair operation, suppose an insertion is adding 30 to the following tree. Since \(30<50\), the search reaches the left leaf, which already contains two keys.

  1. As part of an insertion, the new key 30 is directed to the full leaf containing 10 and 20.
  2. Adding 30 in sorted order temporarily produces the overfull leaf \([10\mid20\mid30]\).
  3. Split: Divide the overfull leaf into two 2-node leaves, one containing 10 and the other containing 30.
  4. Promote: Move the middle key 20 into the parent. Replace the parent's former child containing \([10\mid20\mid30]\) with two children: the leaf containing 10 to the left of 20 and the leaf containing 30 to its right. The parent becomes \([20\mid50]\).

The middle key is always promoted because it separates the two keys that remain below it: every key in the left node is smaller than the promoted key, and every key in the right node is larger. If the parent has room for the promoted key, the repair is complete. If the parent is already a 3-node, however, the promotion temporarily makes the parent overfull. That internal-node case requires one additional idea.

When Promotion Overfills an Internal Node

An internal node does not become overfull because a new key is inserted directly into it. Instead, one of its children splits and promotes a key into the internal node. If the internal node is already a 3-node, inserting the promoted key gives it three keys and four children.

For example, suppose a full internal node contains 40 and 70, with child subtrees \(A\), \(B\), and \(C\). If the root node of child subtree \(B\) splits and promotes 55, then \(B\) is replaced by two child subtrees, \(B_L\) and \(B_R\). The parent temporarily becomes the overfull node \([40\mid55\mid70]\), with four ordered children \(A,B_L,B_R,C\).

Example 8: A Promotion Overfills an Internal Node
  1. The full internal node \([40\mid70]\) initially has three child subtrees \(A\), \(B\), and \(C\).
  2. The root node of subtree \(B\) splits into \(B_L\) and \(B_R\) and promotes 55. The parent inserts 55 between 40 and 70 and replaces its former child \(B\) with the two children \(B_L\) and \(B_R\). It is now temporarily \([40\mid55\mid70]\), with four children \(A,B_L,B_R,C\).
  3. Split: The overfull internal node becomes two 2-nodes. The node containing 40 receives the first two children, \(A\) and \(B_L\). The node containing 70 receives the last two children, \(B_R\) and \(C\).
  4. Promote: Move the middle key 55 into the grandparent. Replace the grandparent's former child \([40\mid55\mid70]\) with the two new children containing 40 and 70.

Note that the subtree \(U\) is the same depth as the other subtrees, since that is one of the requirements of a 2-3 tree. It is drawn as it is just to keep it out of the way of the focus of the example.

The four child subtrees remain in their original left-to-right order. In this example, their key ranges are:

  • every key in \(A\) is less than 40;
  • every key in \(B_L\) is between 40 and 55;
  • every key in \(B_R\) is between 55 and 70; and
  • every key in \(C\) is between 70 and 100.
General rule: An overfull internal node has three ordered keys and four ordered child subtrees. When the node splits, the new node containing the smallest key receives the first two child subtrees, and the new node containing the largest key receives the last two. The middle key is promoted, and the left-to-right order of the child subtrees never changes.
Which Key Is Promoted?

Suppose the full internal node originally contains \([p\mid q]\), where \(p<q\). One of its three children splits and promotes a key \(r\) into the node. The position of \(r\) depends on which child split:

Child that split Temporary overfull node Key promoted next
Left child \([r\mid p\mid q]\), with \(r<p<q\) \(p\)
Middle child \([p\mid r\mid q]\), with \(p<r<q\) \(r\)
Right child \([p\mid q\mid r]\), with \(p<q<r\) \(q\)

In every case, the middle key of the temporary three-key node is promoted to the next level. Therefore, the key \(r\) that arrived from the child is promoted again only when the middle child split. If the left or right child split, one of the parent's original keys is promoted instead.

After promoting the middle key, the smallest key remains in one new node with the first two child subtrees, and the largest key remains in the other new node with the last two child subtrees.

If the grandparent has room for the promoted key, the repair is complete. If the grandparent is already a 3-node, the promotion makes it overfull, and the same split-and-promote process repeats one level higher. A split may therefore continue upward through several levels. If the process reaches an overfull root, the special root case described later creates a new root.

Redistribute Through the Parent

As we will see in the removal section, deleting a key may temporarily leave a node with no keys. Such a node is called a deficient node. Repair depends on the deficient node's adjacent siblings:

  • If an adjacent sibling is a 3-node, it has an extra key, so the deficiency can be repaired by redistribution through the parent.
  • If every adjacent sibling is a 2-node, no sibling has an extra key. In that case, redistribution is impossible, and the deficient node must be merged with a sibling as described in the next subsection.

If both adjacent siblings are 3-nodes, either one can be used for redistribution; an implementation may choose one consistently. Because redistribution differs slightly for leaves and internal nodes, we consider the two cases separately.

Redistribution at a Leaf

A deficient leaf contains no keys and has no children. If an adjacent sibling is a 3-node, the parent separator moves down into the deficient leaf, and the sibling key nearest that separator moves up into the parent.

Example 9: Redistributing from a Right Sibling
  1. Move the parent separator 40 down into the deficient leaf.
  2. Move the sibling key nearest the separator, 60, up into the parent.
  3. The repaired leaf contains 40, the parent contains 60, and the sibling retains 70.

After the redistribution, both leaves are legal 2-nodes, and the parent still contains one key. The sorted order is preserved: \(40<60<70\).

Redistribution at an Internal Node

A deficient internal node usually results from repairing one of its deficient children. If that child must merge with a sibling, as described in the next subsection, one of the internal node's keys moves down into the merged child. The two original child positions are then replaced by the one merged child. If the internal node was a 2-node, it therefore loses its only key and is left with one child subtree. It is now deficient and must be repaired at the next level up, unless it is the root.

If an adjacent sibling of this deficient internal node is a 3-node, redistribution again moves a sibling key through the parent. Because the nodes are internal, one child subtree must also move from the sibling to the repaired node.

Example 10: Redistributing Between Internal Nodes
  1. Move the parent separator 50 down into the deficient internal node.
  2. Move the nearest sibling key, 70, up into the parent.
  3. Move the sibling child subtree nearest the separator, \(B\), into the repaired node. It becomes the child immediately to the right of 50.

The subtree transfer is required to preserve the search ranges. Before redistribution, every key in \(B\) lies between 50 and 70. After 50 moves into the repaired node, \(B\) therefore belongs immediately to its right. The sibling retains key 90 with child subtrees \(C\) and \(D\). Before and after redistribution, the ranges occur in the order \(A<50<B<70<C<90<D\), where each subtree symbol represents all of the keys in that subtree.

General rule: Move the parent separator down into the deficient node, move the sibling key nearest the separator up into the parent, and, for internal nodes, move the sibling child subtree nearest the separator along with it. Redistribution from a left sibling is symmetric.

Redistribution repairs the deficient node without changing the number of keys or children in the parent. Therefore, unlike a merge, it does not create a new deficiency at the next level up.

Redistribution is sometimes described as borrowing from a sibling. The key does not move directly between siblings, however; the sibling key and parent separator exchange roles through the parent.

Merge Through the Parent

If the deficient node's adjacent sibling is only a 2-node, the sibling has no extra key to redistribute. The deficient node, the sibling, and the parent separator between them are therefore combined into one 3-node.

Example 11: Merging with the Left Sibling

The separator 40 moves down from the parent and joins the key 20 in the left sibling. The deficient middle node disappears, and the parent loses one key and one child position.

If the merged nodes are internal, their child subtrees are combined in sorted order. The merged node becomes a valid 3-node, but the parent has lost a key. If the parent becomes deficient, the same repair process continues one level higher.

A merge with the right sibling follows the same principle: move the separator between the deficient node and that sibling down, and combine the keys and child subtrees in sorted order.

Changes at the Root

The root requires special treatment because it has no parent. A repair that reaches the root may change the height of the tree.

Example 12: Root Split and Root Contraction

Although the root is a special case, it is very easily dealt with.

  • Root split: If the root becomes overfull, split it and create a new root containing the promoted middle key. The two pieces of the old root become its children. The height increases by one.
  • Root contraction: If the root loses its final key and has one remaining child, make that child the new root. The height decreases by one.
  • Empty tree: If the root loses its final key and has no child, the tree becomes empty.
Temporary problem Condition Repair
Overfull node The node temporarily contains three keys Split the node and promote its middle key
Deficient node An adjacent sibling is a 3-node Redistribute a key through the parent
Deficient node An adjacent sibling is a 2-node Merge using the parent separator
Problem reaches the root The root has no parent Split, contract, or empty the root as appropriate
Only changes at the root alter the tree's height: Repairs below the root rearrange keys and entire child subtrees locally. A root split increases every leaf depth by one, while a root contraction decreases every leaf depth by one. In either case, all leaves remain at the same depth.

Insertion uses splitting and promotion to repair overfull nodes. Removal uses redistribution and merging to repair deficient nodes. The next two sections apply these structural operations as part of the complete update procedures.

Core Operations and Implementation

Representation

A 2-3 tree is naturally represented as a linked multiway tree. The tree stores a reference to its root and a size equal to the number of stored keys. Unlike a binary search tree, a 2-3 tree may store more than one key in a node, so the number of nodes is not the size of the collection and generally does not need to be tracked.

Each node stores:

  • an ordered collection keys containing one or two active keys;
  • an ordered collection children, which is empty for a leaf and otherwise contains exactly one more active reference than the number of active keys. Each child position corresponds to the key range determined by the surrounding keys; and
  • optionally, a parent reference used when an operation must move upward through the tree.

Thus a 2-node has one active key and, when internal, two active child references. A 3-node has two ordered active keys and, when internal, three active child references. A single node type can represent both cases; the numbers of active keys and children determine whether the node is currently a 2-node or a 3-node.

An implementation may use small dynamic lists, or fixed arrays together with counts recording how many positions are active. Fixed arrays often provide space for three keys and four children. A valid completed node uses at most two keys and three children, but insertion may temporarily create an overfull node with three keys and four children before splitting it. Similarly, removal may temporarily leave a node with no keys while an underflow is repaired.

At first, it may seem more natural to define separate TwoNode and ThreeNode classes. The difficulty is that updates frequently change one kind of node into the other. Inserting into a 2-node turns it into a 3-node, removing a key from a 3-node turns it into a 2-node, and splitting or merging creates further transitions. Separate classes would require repeatedly replacing nodes, reconnecting them to their parents and children, or duplicating much of the operation code for both node types.

A single flexible node class avoids those conversions. The unused array positions require only a small, constant amount of extra space per node, while making key insertion, removal, splitting, borrowing, and merging easier to express. Because each node stores only a few positions, this modest space cost is usually preferable to the added complexity of maintaining separate node classes.

The discussion below therefore assumes one node type with ordered keys and children collections. Whether those collections are implemented as fixed arrays or small dynamic lists does not change the 2-3 tree algorithms.

Representation Summary

The following pseudocode summarizes the representation used throughout the rest of this page. Each node contains two fixed-size arrays. The keys array has room for three keys, and the children array has room for four child references. A valid completed node does not use all of this capacity; the extra positions allow insertion to create a temporary overflow before splitting the node. 

TwoThreeTree:
    root = reference to a Node, initially null
    size = 0

Node:
    keys = new array of length 3
    keyCount = 0

    children = new array of length 4, filled with null
    childCount = 0

    parent = null

The counts identify which array positions are active. The active keys are stored in keys[0] through keys[keyCount - 1], and the active child references are stored in children[0] through children[childCount - 1]. The contents of unused key positions do not matter because the algorithms access only active positions. Unused child positions contain null because they represent references to absent subtrees.

In a valid completed node, keyCount is 1 or 2. A leaf has childCount == 0, while an internal node has childCount == keyCount + 1. Although the child count can be inferred from the key count in these normal states, storing both counts simplifies updates. During splitting, borrowing, and merging, keys and child references may be inserted or removed in separate steps, and a node may temporarily be overfull or underfull.

At the tree level, root is a reference to the root Node, or null when the tree is empty. The tree also stores size as the number of keys currently in the collection. It does not maintain a separate count of nodes, because the number of nodes is an irrelevant implementation detail.

Structure and Search

The three invariants

A valid 2-3 tree maintains all three of the following conditions after every completed operation.

  1. Node capacity: every nonempty node stores one or two keys in increasing order.
  2. Search order: for keys \(a<b\) in a 3-node, the left subtree contains keys below \(a\), the middle subtree contains keys strictly between \(a\) and \(b\), and the right subtree contains keys above \(b\). A 2-node uses the corresponding two ranges.
  3. Uniform leaf depth: all leaves are at the same depth. Equivalently, all children of a node root subtrees of equal height.

A partially completed insertion may temporarily create an overfull node with three keys. A partially completed deletion may temporarily create an underfull node with no keys. These are repair states, not valid steady states.

How search chooses a child

Search compares the target with the one or two keys in the current node. Equality finishes the search. Otherwise, the comparisons identify exactly one possible child. No backtracking is needed because the other subtrees contain disjoint ranges.

Current nodeTarget relationshipNext child
2-node \([a]\)target \(<a\) / target \(>a\)left / right
3-node \([a\mid b]\)target \(<a\)left
\(a<\) target \(<b\)middle
target \(>b\)right

Searching for 52 visits only three nodes. Within a node, at most two key comparisons decide whether the search succeeds or which edge to follow.

The helper findPosition returns the first key index whose value is not smaller than the target. If that key equals the target, search succeeds. Otherwise, the same index names the only child range that can still contain the target. 

findPosition(node, target):
    i = 0
    while i < node.keyCount and node.keys[i] < target:
        i = i + 1
    return i

search(target):
    node = root

    while node != null:
        i = findPosition(node, target)

        if i < node.keyCount and node.keys[i] == target:
            return (node, i)
        if node is a leaf:
            return NOT_FOUND

        node = node.children[i]

    return NOT_FOUND

Minimum, Maximum, and Ordered Queries

The minimum is the first key in the leftmost leaf, and the maximum is the last key in the rightmost leaf. To find the minimum, begin at the root and repeatedly follow child 0 until a leaf is reached; return that leaf's first key. Maximum is symmetric: repeatedly follow the last child and return the leaf's last key. An empty tree has neither result. 

minimum():
    if root == null:
        return NOT_FOUND

    node = root
    while node is not a leaf:
        node = node.children[0]

    return node.keys[0]

A generalized inorder traversal interleaves keys and children. For a 2-node \([a]\), visit child 0, key \(a\), then child 1. For a 3-node \([a\mid b]\), visit child 0, key \(a\), child 1, key \(b\), then child 2. Because each child occupies precisely the range between its neighboring separator keys, this traversal reports every key in increasing order.

Predecessor and successor require one additional detail that does not occur in a one-key BST node. If two keys share a node, the predecessor of the second key may be the first key in that same node, and the successor of the first may be the second. Otherwise, the operation either takes an extreme key from an adjacent child subtree or moves upward until it crosses an appropriate separator. Range queries begin with an ordered search for a boundary and then traverse only child ranges that can intersect the requested interval.

The multiway representation changes the mechanics, but not the ordered-set meaning of these operations. Minimum, maximum, predecessor, successor, sorted traversal, and range reporting answer the same questions they answer in a binary search tree.

Insertion

Insertion first follows an ordinary search path to the appropriate leaf. Because all existing leaves are at the same depth, adding the new key to that leaf is the only place where it can go without immediately breaking the balance rule. What happens next depends on the leaf's current size.

Leaf has one key

Insert the new key into sorted position. The 2-node becomes a 3-node, and the operation is finished.

Leaf has two keys

The new key creates three temporary keys. Split around the median: keep the smallest and largest in separate nodes and promote the median to the parent.

Parent is full

The promoted key may overflow the parent. Split and promote again. Repairs continue upward until a nonfull parent accepts the key or the root splits.

A split and promotion

Suppose 25 is inserted into the full leaf \([10\mid20]\). Sorting gives the temporary keys \([10,20,25]\). The median 20 moves into the parent, while 10 and 25 become separate children. Promoting the median is what preserves the search-order ranges.

When the split reaches the root

If an overfull root \([a,b,c]\) splits, its median \(b\) has no parent to receive it. Create a new root containing \(b\), then attach the two split pieces as its children. This is the only way insertion increases the height, and it increases every root-to-leaf path at once. Uniform leaf depth is therefore preserved.

Why splitting works: a split is local, but its promoted median summarizes the boundary between the two resulting subtrees. The parent gains one key and one child, so its own search ranges remain consistent. If the parent overflows, exactly the same argument applies one level higher.

High-level insertion procedure

  1. Search for the key. If it already exists, leave the set unchanged.
  2. Insert the key in sorted order into the leaf reached by the search.
  3. While the current node has three keys, split around its median and promote the median with the new right child into the parent.
  4. If the overflowing node was the root, create a new root from the median and stop.

The pseudocode treats split(node) and insertPromotion as small helpers. Splitting leaves the smallest key and first two children in node, creates a right node from the largest key and last two children, and returns the median with that new node. 

insert(key):
    if root == null:
        root = new Node(key)
        size = 1
        return true

    leaf = searchToLeaf(key)
    if leaf contains key:
        return false

    insert key into leaf.keys in sorted order
    node = leaf

    while node.keyCount == 3:
        (median, rightNode) = split(node)

        if node.parent == null:
            root = new Node(median)
            root.children = [node, rightNode]
            node.parent = root
            rightNode.parent = root
            break

        parent = node.parent
        insertPromotion(parent, node, median, rightNode)
        node = parent

    size = size + 1
    return true

Removal

Deletion is the more subtle update. Removing a key from a 3-node leaf is easy: the leaf still has one key. Removing the only key from a 2-node leaf creates an underfull node with zero keys. The tree must repair that missing key without moving the leaf to a different depth.

First reduce removal to a leaf

If the target is in an internal node, replace it with its inorder predecessor (the largest key in the child immediately to its left) or its inorder successor. That replacement key occurs in a leaf because following the appropriate extreme-child pointers ends at a leaf. The problem is now to delete a key from a leaf, while the ordering of the internal node remains correct.

Important: copying the predecessor into an internal node is not the end of the operation. The original predecessor must still be removed from its leaf, and that removal may create an underflow.

Repair option 1: borrow through the parent

If an adjacent sibling is a 3-node, it has a spare key. A separator key moves from the parent down into the empty node, and the sibling key nearest that separator moves up to the parent. For internal nodes, one child pointer crosses with the rotating key. This redistribution keeps the keys ordered and ends the repair without changing the number of nodes.

Repair option 2: merge

If both adjacent siblings are 2-nodes, neither can spare a key. Merge the empty node with one sibling and pull the separating parent key down between them. The result is one valid 3-node. The parent loses one key and one child. If that makes the parent underfull, repair continues upward.

Root shrinkage and the complete procedure

An empty nonroot node is always repaired. An empty root is different: if it has one child, discard the empty root and make that child the new root. Every leaf then becomes one level closer to the root together. This is the only way deletion decreases the height. If an empty root has no child, the whole tree is empty.

  1. Search for the target; report failure if it is absent.
  2. If it is internal, exchange it with a predecessor or successor key in a leaf.
  3. Remove the key from the leaf. Stop if the leaf still has one key or is the root.
  4. For an underfull node, borrow from an adjacent 3-node sibling if possible; otherwise merge with a sibling and pull down the intervening parent key.
  5. After a merge, repeat at the parent if it underflows. If the root becomes empty, replace it with its only child.
remove(key):
    location = search(key)
    if location == NOT_FOUND:
        return false

    (node, keyIndex) = location

    if node is internal:
        (leaf, leafIndex) = predecessorLocation(node, keyIndex)
        node.keys[keyIndex] = leaf.keys[leafIndex]
        node = leaf
        keyIndex = leafIndex

    remove node.keys[keyIndex]

    while node != root and node.keyCount == 0:
        if node has an adjacent sibling with two keys:
            borrowThroughParent(node, that sibling)
            break
        else:
            node = mergeWithSibling(node)  // returns the parent

    if root.keyCount == 0:
        if root has a child:
            root = root.children[0]
            root.parent = null
        else:
            root = null

    size = size - 1
    return true
Insertion repairs excess capacity by splitting upward. Deletion repairs missing capacity by redistributing or merging upward. Both operations change the height only at the root, which is why all leaves stay synchronized.

Representation and Implementation

The easiest representation uses one node class with room for the maximum legal contents: two keys and three child references, plus counts recording how many positions are active. Many implementations instead use dynamic arrays or small lists because overflow repair is easier when a temporary third key and fourth child can be inserted before splitting.

FieldPurposeInvariant

parent (optional)Supports upward repair and predecessor/successor navigationEvery child's parent reference points back to its owner
size (tree field)Number of stored keys, not number of nodesChanges once for a successful insertion or deletion

Child indexes matter

For a node with keys \(k_0,k_1\), child 0 is below \(k_0\), child 1 lies between the keys, and child 2 is above \(k_1\). The lower-bound index introduced for search is useful throughout the implementation. It identifies where a new key belongs, which child produced a promoted key, and which parent separator lies next to an underfull child.

Splitting an internal node

A leaf split distributes three keys as \([k_0]\), promoted \(k_1\), and \([k_2]\). An internal split does the same with keys and also distributes four children: children 0 and 1 stay with the left result; children 2 and 3 move to the right result. Forgetting to move those child references—or failing to update their parent references—is a common implementation bug.

Implementation strategy

Two broad strategies are common. A bottom-up implementation performs the update, permits a temporary overflow or underflow, and repairs while returning toward the root. A top-down implementation rearranges nodes before descending so the child entered will be safe for the next step. Top-down algorithms can avoid parent references, but their case analysis is often harder to learn. Whichever strategy is used, keep node primitives—insert key, remove key, split, rotate, merge—small and test them independently.

Validate after every test operation: keys are sorted; each internal node has one more child than key; every child's ranges obey its parent separators; every nonroot node has one or two keys; all leaves have the same depth; and the counted keys equal the tree size. A recursive invariant checker turns difficult pointer bugs into failures near their cause.

Analysis

Why the height is logarithmic

Let the root be at depth 0 and let every leaf be at depth \(h\). A sparsely filled tree has one key per node and two children per internal node. It therefore has at least \(1+2+\cdots+2^h=2^{h+1}-1\) keys. A maximally filled tree has two keys per node and three children per internal node, for at most \(2(1+3+\cdots+3^h)=3^{h+1}-1\) keys. Thus

\[2^{h+1}-1 \le n \le 3^{h+1}-1.\]

Rearranging the left inequality gives \(h\le \log_2(n+1)-1\); the right inequality gives \(h\ge \log_3(n+1)-1\). The exact height depends on how full the nodes are, but in every case \(h=\Theta(\log n)\).

At the same height, fuller nodes hold more keys, but both extremes grow exponentially by level. That exponential growth forces logarithmic height.

Operation costs

The tree occupies \(\Theta(n)\) total space. Iterative operations with parent references use \(O(1)\) auxiliary space; recursion or an explicit path stack uses \(O(\log n)\). Although each node search is constant time in a strict 2-3 tree, larger B-tree nodes usually use binary search or hardware-friendly linear scans within a node.

Applications

A 2-3 tree can implement any ordered set or ordered map operation supported by a BST while adding a worst-case height guarantee. The structure is especially important as a clean model for understanding how multiway search trees balance themselves.

  • Ordered sets and maps: Keys remain searchable and traversable in sorted order while insertions and removals retain worst-case logarithmic performance.
  • Event and schedule indexes: Predecessor and successor locate the events immediately before and after a time, while range queries retrieve all events in an interval.
  • In-memory indexes: Records can be indexed by names, identifiers, dates, scores, or other comparable keys when both updates and ordered reporting matter.
  • Foundations for external-memory trees: The same ideas scale to B-trees and B+ trees, whose wider nodes reduce the number of storage blocks accessed by a search.
  • Functional ordered collections: Immutable variants can create new versions by rebuilding only the search path and sharing untouched subtrees.

Strict 2-3 trees are more common in teaching than in standard mutable libraries because their variable-size nodes and removal cases require careful implementation. The structure remains practically important as a model: it exposes the balancing logic used by larger multiway indexes and helps explain binary encodings such as red-black trees.

Connections and Comparisons

A 2-3 tree belongs to the search-tree family, but its multi-key nodes give it a different way to maintain balance. Comparing representations clarifies what the extra update work achieves.

  • Versus a plain BST: both preserve sorted order, but a plain BST may reach height \(n-1\). A 2-3 tree guarantees logarithmic height for every update order.
  • Versus AVL and red-black trees: these use ordinary one-key binary nodes and repair balance with rotations or recoloring. A red-black tree can be interpreted as a binary encoding of a 2-3-4 tree; the multi-key view often makes the balancing logic easier to visualize.
  • Versus a sorted array: both support logarithmic search, but an array may shift \(\Theta(n)\) entries per update. A 2-3 tree changes only a root-to-leaf path.
  • Versus a hash table: hashing often gives expected \(O(1)\) exact-key operations, but it does not naturally support sorted traversal, predecessor/successor, or range reporting.
  • Versus B-trees: a 2-3 tree is a small-order B-tree. Practical database and file-system B-trees use far more keys per node so each expensive storage access brings in a large block of useful separators and children.

A useful performance comparison needs both asymptotic cost and representation cost. A 2-3 tree guarantees short paths, but each node needs multiple key and child positions and each update has more cases than a plain BST. Arrays are compact; hash tables often win for exact lookup; wider B-trees reduce external-memory transfers. The right structure depends on the complete operation mix, not on search time alone.

Variations and Extensions

  • 2-3-4 trees: Allow nodes with one, two, or three keys and therefore two, three, or four children. The extra capacity makes top-down splitting and deletion strategies convenient.
  • B-trees: Generalize the minimum and maximum node capacities. Large nodes are chosen to match disks, SSD pages, database pages, or cache behavior.
  • B+ trees: Store records or record references in linked leaves while internal nodes serve mainly as routing indexes. This makes sequential and range access especially effective.
  • Red-black encodings: Represent a multi-key node using linked binary nodes and colored edges or nodes. Rotations and recoloring simulate splitting, promotion, redistribution, and merging.
  • Augmented trees: Store subtree key counts, interval summaries, or other metadata to support rank, selection, range counting, and application-specific queries.
  • Persistent trees: Copy only nodes on an updated root-to-leaf path and share all other nodes, preserving access to older versions.

These structures differ in capacity rules and representation, but the central pattern remains: separator keys divide ordered child ranges, updates repair local capacity violations, and the repairs preserve a logarithmic-height search structure.

Common Pitfalls

  • Counting keys instead of children in the name: a 3-node has two keys and three child ranges.
  • Treating a 3-node as two unrelated BST nodes: both keys belong to one node at one depth. Search must consider both before choosing a child.
  • Promoting the wrong key during a split: only the median can separate the smaller and larger results correctly.
  • Attaching split children in the wrong order: the four old child ranges must remain T0, T1, T2, T3 from left to right.
  • Borrowing directly from a sibling: redistribution rotates through the parent separator. Moving a sibling key straight across would cross a range boundary.
  • Stopping after internal-key substitution: the predecessor or successor still has to be deleted from its original leaf.
  • Ignoring cascading repairs: a split can overflow the parent and a merge can underflow it. Continue toward the root until the node is legal.
  • Allowing leaves at different depths: local key order is not enough. Uniform leaf depth is the invariant that supplies the worst-case guarantee.
  • Measuring size by nodes: nodes contain different numbers of keys. The abstract set size is the total number of keys.

Summary

A 2-3 tree implements the same kind of ordered set or map as a binary search tree. Search comparisons identify one possible child range, and the ordering supports minimum, maximum, predecessor, successor, sorted traversal, and range queries. The difference is structural: a 2-3 tree uses nodes with one or two keys so it can keep every leaf at the same depth instead of allowing an unfavorable update order to create a long chain.

A 2-node contains one key and has two children when internal. A 3-node contains two ordered keys and has three children when internal. In either case, the keys act as separators between nonoverlapping child ranges. A valid node contains one or two keys, every internal node has one more child than key, and every leaf lies at a common depth.

Search follows one downward path. Insertion searches to a leaf, adds the key in sorted order, and splits any temporary three-key node around its median. The median is promoted, so a split may cascade toward the root. Removal first moves an internal target to a leaf by substituting a predecessor or successor. An underfull node then borrows through a parent separator when a sibling has two keys; otherwise, it merges with a sibling and pulls a separator down. A merge can make the parent underfull and continue the repair upward.

The height increases only when a full root splits and decreases only when an empty root is replaced by its sole child. Both events affect every leaf together. Since each internal node has at least two and at most three children, the number of keys grows exponentially with the height, giving \(h=\Theta(\log n)\). Search, insertion, and removal therefore take worst-case \(O(\log n)\) time, while a complete traversal takes \(\Theta(n)\) time and the structure uses \(\Theta(n)\) space.
