Balanced Search Trees

Overview

A balanced search tree is a search tree that maintains additional structural rules to keep its height \(O(\log n)\), where \(n\) is the number of stored keys. Since searching, inserting, and removing keys require following paths through the tree, controlling the height guarantees that these operations remain efficient even as the collection changes.

A plain binary search tree preserves the ordering of its keys but places no restriction on its shape. An unfavorable sequence of insertions or removals can therefore produce a long, nearly linear tree. Balanced search trees prevent this degeneration by detecting when their structural rules have been violated and maintaining or restoring those rules during updates. Different tree families use different balance rules and different repair operations.

Balanced search trees use different strategies to control their height. AVL trees and red-black trees are balanced binary search trees. They retain the ordinary binary search tree structure and use rotations, together with height or color information, to control the shape of the tree. Multiway search trees, such as 2-3 trees and B-trees, allow nodes to store multiple keys and have more than two children. They maintain balance using operations such as splitting, redistribution, and merging rather than binary-tree rotations. This page briefly compares these approaches and then focuses on rotations. Multiway balancing operations will be developed on the 2-3-tree and B-tree pages.

Balanced does not mean perfect: A balanced search tree does not necessarily have every level filled, nor must the two subtrees of every node have exactly the same height. The word balanced refers to the particular structural conditions imposed by the tree family. What these definitions have in common is that they prevent the height from growing faster than \(O(\log n)\).

Why Balance Matters

The running time of the main binary search tree operations depends on the height \(h\) of the tree. Search and insertion follow a single path from the root, and removal follows only a constant number of such paths. Therefore, search, insert, and remove are all \(O(h\)).

When a tree is balanced, its height is \(\Theta(\log n)\), so these operations take \(O(\log n)\) time. A plain binary search tree, however, can become degenerate, with each node having only one child. Such a tree has height \(n-1\), and its operations may take \(O(n)\) time. Thus, the same set of keys can support very different performance depending on the shape of the tree.

Example 1: The Same Keys in Different Shapes

The two ordinary binary search trees below contain the same seven keys. The first happens to have a balanced shape, while the second is degenerate. The balanced tree results from inserting the keys in the order \[ 40,20,60,10,30,50,70, \] while the degenerate tree results from inserting them in increasing order.

Searching for \(70\) visits only three nodes in the balanced tree but all seven nodes in the degenerate tree. As the number of keys grows, this difference becomes much more significant: logarithmic paths grow slowly, while linear paths grow in direct proportion to the number of stored keys.

Maintaining balance adds work to insertion and removal because an update may need to repair the tree's structure. These repairs are worthwhile because they preserve logarithmic height, preventing later searches and updates from degrading to linear time. Balanced search trees therefore trade a limited amount of additional update work for a strong guarantee on the performance of the main search-tree operations.

What Does Balanced Mean?

There is no single balance rule shared by all balanced search trees. Instead, each tree family maintains its own balance invariant: a structural condition strong enough to guarantee that the tree's height remains \(O(\log n)\). Some invariants compare subtree heights, some constrain paths using additional labels, and others constrain node occupancy and require all leaves to occur at the same depth. Here are some of the most common structures and the rules they have.

Structure General Balance Rule Primary Repair Operations
AVL tree At every node, the heights of the left and right subtrees differ by at most one. Single and double rotations
Red-black tree Each node has a color, and rules involving those colors limit the difference between the lengths of root-to-leaf paths. Recoloring and rotations
2-3 tree Each internal node has two or three children, and all leaves occur at the same depth. Splitting, promotion, redistribution, and merging
B-tree Each node stores a bounded number of keys and children, subject to minimum and maximum occupancy rules, and all leaves occur at the same depth. Splitting, promotion, redistribution, and merging

These rules produce trees with different shapes and require different repair procedures, but they serve the same purpose: no root-to-leaf path can become disproportionately long as the number of stored keys grows. As a result, search paths remain logarithmic even after an unfavorable sequence of insertions and removals.

Maintaining Balance During Updates

Searching normally does not change the structure of a search tree, so it cannot create a new balance violation. Insertion and removal are different: both modify the tree, and the modified portion may no longer satisfy the balance invariant. A balanced search tree must therefore check for violations after an update and repair them before the operation is complete.

Although the exact order varies among implementations, balanced-tree updates generally involve the following tasks:

  1. Follow the search-tree ordering to locate the insertion or removal position.
  2. Perform the update, making structural repairs during or after it as required.
  3. Determine whether the tree's balance invariant has been violated.
  4. Repair the violation using the operations appropriate for that tree family.
  5. Continue toward the root if the repair may have created or exposed another violation.

Many balanced binary search trees, including AVL and red-black trees, repair their structure with rotations, which change a small collection of parent-child relationships while preserving the search tree property. AVL trees use height information to choose among single and double rotations. Red-black trees use colors to guide a combination of recoloring and rotations.

Multiway search trees use different repair operations because a node may contain several keys and have more than two children. A node that becomes too full may be split, with one of its keys promoted to its parent. During removal, keys may be redistributed between neighboring nodes, or underfull nodes may be merged. Despite these differences, the goal is the same: restore the tree's balance invariant while preserving the sorted order of its keys.

Rotations in Balanced Binary Search Trees

Purpose and Anatomy of a Rotation

A rotation is a local transformation that changes the shape of a binary search tree without changing the keys it stores or their sorted order. Rotations are used by balanced binary search trees to shorten one side of a subtree and lengthen the other.

A rotation changes only a small number of parent-child relationships. Most of the tree is unaffected, and the subtrees attached to the rotated nodes retain their internal structure. However, one of those subtrees may need to be transferred from one rotated node to the other.

  • A left rotation moves a right child above its parent.
  • A right rotation moves a left child above its parent.
  • The node that moves upward is sometimes called the pivot.
  • The root of the rotated subtree may change, but its connection to the rest of the tree is preserved.
A rotation is not a complete balancing algorithm: A rotation can improve, preserve, or worsen the balance of a tree. A particular balanced-tree algorithm must determine when a rotation is necessary, where it should occur, and which direction should be used.

Left and Right Rotations

Left and right rotations are mirror images of one another. The pseudocode below assumes that each node stores left, right, and parent references and that the tree stores a root reference.

Left Rotation

Given a node x with right child y, a left rotation at x:

  • moves y into x's position,
  • makes x the left child of y, and
  • makes the left subtree of y, labeled \(B\) in the diagram, the right subtree of x.
Example 2: Left Rotation

The following diagram illustrates a left rotation. It is important to remember that a left rotation at x requires that x have a right child, y.

Here is pseudocode for the left rotation:

rotateLeft(x):
  y = x.right

  if y == null:
      return

  x.right = y.left

  if y.left != null:
      y.left.parent = x

  y.parent = x.parent

  if x.parent == null:
      root = y
  else if x == x.parent.left:
      x.parent.left = y
  else:
      x.parent.right = y

  y.left = x
  x.parent = y

Before the rotation, \(B\) is the left subtree of y, so every key in \(B\) is less than the key at y. Because \(B\) lies in the right subtree of x, every key in \(B\) is also greater than the key at x. Therefore, when y moves above x, \(B\) becomes the right subtree of x, preserving the binary search tree property.

Right Rotation

Given a node y with left child x, a right rotation at y:

  • moves x into y's position,
  • makes y the right child of x, and
  • makes the right subtree of x, labeled \(B\) in the diagram, the left subtree of y.
Example 3: Right Rotation

The following diagram illustrates a right rotation. It is important to remember that a right rotation at y requires that y have a left child, x.

Here is pseudocode for the right rotation:

rotateRight(y):
  x = y.left

  if x == null:
      return

  y.left = x.right

  if x.right != null:
      x.right.parent = y

  x.parent = y.parent

  if y.parent == null:
      root = x
  else if y == y.parent.left:
      y.parent.left = x
  else:
      y.parent.right = x

  x.right = y
  y.parent = x

A symmetric argument to the one above shows that the right rotation preserves the binary search tree property.

What Rotations Preserve

We have already argued informally that rotations preserve the binary search tree property. We now justify this claim a little more formally.

Theorem 1: Rotations preserve the binary search tree property.

A left or right rotation preserves both the set of stored keys and their inorder sequence. Therefore, if the tree satisfies the binary search tree property before the rotation, it also satisfies the property afterward.

Proof

Consider a left rotation involving nodes \(x\) and \(y\) and subtrees \(A\), \(B\), and \(C\). Because the original tree is a binary search tree, the keys occur in the following order:

\[ A < x < B < y < C. \]

Here, \(A < x\), for example, means that every key in subtree \(A\) is less than the key stored at \(x\). The same notation applies to the other subtrees. Before the rotation, an inorder traversal visits

\[ A,\ x,\ B,\ y,\ C. \]

After the rotation, \(y\) occupies the former position of \(x\), \(x\) becomes the left child of \(y\), and \(B\) becomes the right subtree of \(x\). An inorder traversal still visits

\[ A,\ x,\ B,\ y,\ C. \]

Thus, the rotation changes the shape of the tree without changing either its keys or their relative order. Since the inorder sequence remains increasing, the binary search tree property is preserved. The corresponding argument for a right rotation is the same with left and right reversed.

Example 5: Inorder Order Before and After a Rotation

The following example performs a left rotation at node \(70\). Node \(80\) moves into \(70\)'s former position, \(70\) becomes the left child of \(80\), and the subtree rooted at \(75\) becomes the right subtree of \(70\). The second arrow shows the inverse operation: a right rotation at \(80\) returns the tree to its original shape. The rest of the tree is unchanged.

The two arrows emphasize that these operations are inverses: a left rotation at \(70\) transforms the tree on the left into the tree on the right, and a right rotation at \(80\) transforms the tree on the right back into the tree on the left.

Although the structure of the right subtree changes, both trees have the same inorder sequence:

\[ 20,\ 30,\ 40,\ 50,\ 55,\ 60,\ 65,\ 70,\ 75,\ 80,\ 90. \]

Thus, the rotation preserves the relative order of every key, including keys outside the rotated subtree.

How Rotations Change Depth and Height

The preceding example illustrates how a rotation changes node depths. A rotation affects depths only within the rotated subtree. Consider a left rotation at a node x with right child y and subtrees \(A\), \(B\), and \(C\).

  • y and every node in \(C\) move up by one level.
  • x and every node in \(A\) move down by one level.
  • Every node in \(B\) remains at the same depth.
  • Every node outside the rotated subtree remains at the same depth.

In the preceding example, after the left rotation at \(70\), nodes \(80\) and \(90\) move up one level, while \(70\) and the subtree rooted at \(60\) move down one level. Node \(75\), whose subtree is transferred from \(80\) to \(70\), remains at the same depth.

Rotation Locality. A single rotation changes the depth of each node by at most one. It also changes the height of the rotated subtree by at most one and, consequently, changes the height of the entire tree by at most one.

The height of a subtree is determined by the maximum depth of one of its nodes relative to the subtree root. Since every node in the rotated subtree moves up one level, moves down one level, or remains at the same level, the height of that subtree can decrease by one, remain unchanged, or increase by one. The rotated subtree remains attached at the same position in the larger tree, so the height of the entire tree can also change by at most one.

The internal structures and heights of \(A\), \(B\), and \(C\) do not change; only their attachment points change. However, the heights stored at x and y may change and must be recomputed. Height information stored at their ancestors may also need to be updated.

A rotation does not necessarily reduce the height of either the rotated subtree or the entire tree. A balancing algorithm chooses a rotation whose particular effect repairs a detected imbalance.

Double Rotations

Sometimes a single rotation is enough to repair the shape of a subtree. In other cases, the path through the affected nodes changes direction, so one rotation is not enough. A double rotation is not a separate primitive operation. Instead, it is a sequence consisting of one left rotation and one right rotation.

Conceptually, the first rotation straightens the "bend" in the subtree, and the second rotation completes the restructuring.

Left-Right Rotation

A left-right rotation applies when a subtree rooted at z has a left child y, and y has a right child x. First perform a left rotation at y. Then perform a right rotation at z. This leads to the following pseudocode: 

rotateLeftRight(z):
    rotateLeft(z.left)
    rotateRight(z)
Example 6: Left-Right Rotation as Two Single Rotations

The initial path from z to y to x turns left and then right. A left rotation at y first straightens this path. A right rotation at z then completes the double rotation.

After the first rotation, x becomes the left child of z, with y as its left child. The second rotation moves x to the root of the local subtree. The subtrees remain in the inorder sequence \(A, y, B, x, C, z, D\).

Right-Left Rotation

A right-left rotation is the mirror-image case. It applies when a subtree rooted at z has a right child y, and y has a left child x. First perform a right rotation at y. Then perform a left rotation at z. The mirror-image sequence gives the following pseudocode: 

rotateRightLeft(z):
    rotateRight(z.right)
    rotateLeft(z)
Example 7: Right-Left Rotation as Two Single Rotations

The initial path from z to y to x turns right and then left. A right rotation at y first straightens this path. A left rotation at z then completes the double rotation.

After the first rotation, x becomes the right child of z, with y as its right child. The second rotation moves x to the root of the local subtree. The subtrees remain in the inorder sequence \(A, z, B, x, C, y, D\).

In the activities, we will explore a slightly more efficient implementation that performs each double rotation directly rather than calling two separate rotation methods. We will study double rotations in more detail on the AVL-tree page, where subtree heights determine when they are needed. Red-black trees also sometimes use two rotations in succession, although they select rotations according to color and structural conditions rather than height balance.

Complexity of Rotations

The rotation algorithms may appear somewhat long because they must carefully update the affected child and parent references, including the reference to the transferred subtree. However, none of these steps traverses the tree or depends on the number of stored nodes. A single rotation reads or changes only a constant number of references and therefore takes \(O(1)\) time.

A double rotation performs two single rotations, so it also takes \(O(1)\) time. If the nodes store height, balance factor, or similar information that can be recomputed from their children, updating that information at the rotated nodes also takes constant time. Both single and double rotations use \(O(1)\) extra space.

Comparing Balanced Search Trees

Balanced search-tree families achieve the same broad goal in different ways. Each maintains \(O(\log n)\) height, but the trees differ in how strictly they control their shape, what information is stored at each node, and which operations are used to maintain balance. These differences affect the lengths of search paths, the amount of restructuring required during updates, and the environments in which each structure is most useful.

Structure Node Type Balance Approach Typical Advantage
AVL tree Binary The heights of the two child subtrees of every node differ by at most one. Strict balance keeps search paths especially short.
Red-black tree Binary Color rules limit how much root-to-leaf path lengths can differ. Looser balance often requires less restructuring during updates than an AVL tree.
2-3 tree Multiway Internal nodes have two or three children, and all leaves occur at the same depth. Provides a conceptually clean model of balancing through splitting, promotion, redistribution, and merging.
B-tree Multiway Nodes store many keys and children within occupancy limits, and all leaves occur at the same depth. Broad nodes reduce the number of storage accesses needed to follow a search path.

No one structure is best in every setting. AVL trees favor shorter search paths, while red-black trees allow more flexibility during updates. The 2-3 tree provides a simple introduction to multiway balancing, and the B-tree extends the same general ideas to nodes designed for external storage. The following pages examine some of these in more detail, including their balance rules and the operations used to maintain them.

Common Rotation Pitfalls

  • Treating a rotation as a complete balancing algorithm: A rotation only changes the local shape of a tree. The balance rules of the particular tree family determine whether a rotation is needed, where it should occur, and which direction to use.
  • Confusing the direction of a rotation: A left rotation moves a right child upward, while a right rotation moves a left child upward. The direction names the way the original subtree root moves, not the direction from which the new root comes.
  • Forgetting the transferred subtree: During a left rotation, the left subtree of the node moving upward must become the right subtree of the node moving downward. A right rotation performs the symmetric transfer. Omitting this step can lose an entire subtree or violate the binary search tree property.
  • Updating only the two rotated nodes: The parent of the original subtree root must point to the new subtree root. If the rotation occurs at the root of the entire tree, the tree's root reference must be updated instead. All affected parent references must agree with the corresponding child references.
  • Forgetting stored balance information: If nodes store heights, balance factors, colors, or other information used by the balancing algorithm, that information may need to be updated after the references change.

Summary

Balanced search trees maintain structural rules that keep their height \(O(\log n)\). This prevents the long paths that can occur in an ordinary binary search tree and guarantees logarithmic-time search, insertion, and removal. Different tree families use different balance invariants, but all are designed to prevent the tree from becoming too tall.

Balanced binary search trees such as AVL and red-black trees use rotations to change the local shape of a tree. A rotation preserves the stored keys, their inorder sequence, and therefore the binary search tree property. A single rotation changes only a constant number of references and takes \(O(1)\) time. Left-right and right-left rotations are sequences of two single rotations and also take \(O(1)\) time.

Rotations are only repair operations; the balance rules of a particular tree determine when and where they are used. AVL trees make these decisions using subtree heights, while red-black trees use color-based rules. Multiway search trees, including 2-3 trees and B-trees, maintain logarithmic height using operations such as splitting, redistribution, and merging rather than binary-tree rotations. The following pages develop these tree families and their balancing procedures in more detail.
