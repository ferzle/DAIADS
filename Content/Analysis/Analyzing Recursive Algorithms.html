Analyzing Recursive Algorithms

Prerequisites

This section assumes familiarity with recurrence relations and the basic idea of solving them. If you need a review, see the Recurrence Relations section of the appendix. In fact, there are a few examples of analyzing recursive algorithms in that section, so you may want to review those as well.

Analyzing Recursive Algorithms

Introduction

In the appendix section on solving recurrence relations, we already saw a few examples of analyzing recursive algorithms. We will provide a few more examples in this section. The most common method for analyzing a recursive algorithm is to write a recurrence relation for its running time and then solve that recurrence.

We begin with merge sort, a classic recursive sorting algorithm, because its running time leads to a clean divide-and-conquer recurrence. We then look at the Towers of Hanoi, where the recurrence counts the number of moves made by the recursive process. Finally, we practice setting up and solving recurrences for several additional recursive algorithms, including examples where the subproblem sizes are less familiar.

Merge Sort

The basic idea behind merge sort is simple: divide an array in half, sort the first half, sort the second half, and then merge the two sorted halves together. The two halves are sorted recursively using merge sort again. The base case occurs when the subarray has size 0 or 1, since such a subarray is already sorted.

That leaves two main tasks: describing how the merge step works and using that cost to analyze the full recursive algorithm. We will provide enough detail about the algorithm to support the analysis, but the focus of this section is on setting up and solving the recurrence relation.

Example 1: Merge

The Merge algorithm needs to take two sorted arrays and combine them into a single sorted array. More accurately, it takes as input an array \(A\) which is sorted from \(left\) to \(mid\) and from \(mid+1\) to \(right\), and modifies \(A\) so it is sorted from \(left\) to \(right\).

For instance, we might have \(left=5\), \(right=15\), \(mid=9\), and

\[ A=[73, 23, 45, 67, 34, \underline{23, 37, 41, 45, 65}, \overline{12, 28, 39, 59, 68, 89}, 12, 34, 48, 47], \]

where the underlined portion, indexed from \(left\) to \(mid\), is sorted, and the overlined portion, indexed from \(mid+1\) to \(right\) is also sorted, and we want merge to return the array

\[ A=[73, 23, 45, 67, 34, \underline{12, 23, 28, 37, 39, 41, 45, 59, 65, 68, 89}, 12, 34, 48, 47] \]

in which the underlined portion, indexed from \(left\) to \(right\) is now fully sorted (check carefully that it is correct).

Now that we better understand what Merge is supposed to do, we can present an algorithm that accomplishes the task.

void merge(int[] A, int left, int mid, int right) {
    int n = right - left + 1;
    int m = mid - left + 1;
    int[] B = new int[n];

    // Copy first half forward.
    for (int i = 0; i < m; i++) {
        B[i] = A[left + i];
    }

    // Copy second half backward.
    for (int j = m; j < n; j++) {
        B[j] = A[right - j + m];
    }

    int i = 0;
    int j = n - 1;

    // Merge back into A.
    for (int k = left; k <= right; k++) {
        if (B[i] < B[j]) {
            A[k] = B[i++];
        } else {
            A[k] = B[j--];
        }
    }
}

If we set \(n=right-left+1\), the size of the portion of the array that we are dealing with, we should be able to easily see that Merge takes \(O(n)\) time since it executes two loops whose total number of iterations is \(n\), and the third loop which has \(n\) iterations, and the rest of the code takes constant time.

Example 2: Merge Sort

Now that we have the Merge algorithm, implementing merge sort is pretty straightforward given the description above.

void mergeSort(int[] A, int left, int right) {
    if (left < right) {
        int mid = (left + right) / 2;
        mergeSort(A, left, mid);
        mergeSort(A, mid + 1, right);
        merge(A, left, mid, right);
    }
}

Notice that if \(left\geq right\) the algorithm does nothing. Also notice that this corresponds to subarrays with 0 or 1 elements, which clearly do not need to be sorted. This is the base case we mentioned above.

Example 3: Analyzing Merge Sort

What is the worst-case running time of merge sort?

Solution

The algorithm for MergeSort is below. Let \(T(n)\) be the worst-case running time of MergeSort on an array of size \(n=right-left\). Recall that Merge takes two sorted arrays and merges them into one sorted array in time \(\Theta(n)\), where \(n\) is the number of elements in both arrays. Since the two recursive calls to MergeSort are on arrays of half the size, they each require time \(T(n/2)\) in the worst-case. The other operations take constant time. Below we annotate the MergeSort algorithm with these running times.

Algorithm Time required
MergeSort(int[] A,int left,int right) { \(T(n)\)
if (left < right) { \(C_1\)
int mid = (left + right)/2; \(C_2\)
MergeSort(A, left, mid); \(T(n/2)\)
MergeSort(A, mid + 1, right); \(T(n/2)\)
Merge(A, left, mid, right); \(\Theta(n)\leq C_3n\)
}
}

Given this, we can see that

\[ \begin{aligned} T(n)&=C_1+C_2+T(n/2)+T(n/2)+\Theta(n)\\ &=2 T(n/2) +\Theta(n). \end{aligned} \]

Notice that we absorbed the constants \(C_1\) and \(C_2\) into the \(\Theta(n)\) term. For simplicity, we will also replace the \(\Theta(n)\) term with \(cn\) (where \(c\) is a constant) and rewrite this as

\[ T(n)=2 T(n/2)+c n. \]

We could use the Master Theorem to prove that \(T(n)=\Theta(n\log n)\), but that would be too easy. Instead, we will use induction to prove that \(T(n)=O(n\log n)\), and leave the \(\Omega\)-bound to the reader.

By definition, \(T(n)=O(n\log n)\) if and only if there exists constants \(k\) and \(n_0\) such that \(T(n)\leq k n\log n\) for all \(n\geq n_0\).

For the base case, notice that \(T(2)=a\) for some constant \(a\), and \(a\leq k 2\log 2= 2 k\) as long as we pick \(k\geq a/2\). Now, assume that \(T(n/2)\leq k(n/2)\log (n/2)\). Then

\[ \begin{aligned} T(n)&=2 T(n/2) + c n\\ &\leq 2\left(k(n/2)\log(n/2)\right)+ c n\\ &=k n \log(n/2)+ c n\\ &=k n \log n - k n\log 2 + c n\\ &=k n\log n + (c-k)n\\ &\leq k n\log n \,\,\,\,\, \mbox{ if } k\geq c \end{aligned} \]

As long as we pick \(k=\max\{a/2,c\}\), we have \(T(n)\leq k n\log n\), so \(T(n)=O(n\log n)\) as desired.

Exercise 1

We stated in the previous example that we could use the Master Theorem to prove that if \(T(n)=2 T(n/2)+c n,\) then \(T(n)=\Theta(n\log n)\). Verify this.

We have \(a=2\), \(b=2\), and \(d=1\). Since \(2=2^1\), we have that \(T(n)=\Theta(n\log n)\) by the second case of the Master Theorem.

Question 1

Answer the following questions about points that were made in Example 3.

  1. Why were we allowed to absorb the constants \(C_1\) and \(C_2\) into the \(\Theta(n)\) term?

  2. Why were we able to replace the \(\Theta(n)\) term with \(cn\)?

  1. \(C_1\) and \(C_2\) are of lower order than \(n\).
  2. We know that the \(\Theta(n)\) represents some function \(f(n)\). By definition of \(\Theta\), there are constants, \(c_1\) and \(c_2\) such that \(c_1n\leq f(n)\leq c_2n\) for all \(n\geq n_0\) for some constant \(n_0\). So we essentially replaced \(f(n)\) with \(c_2n\) (since we are looking for a worst-case). Note that it doesn't matter what \(c_2\) is. We know there is some constant that works, so we just call it \(c\).

Towers of Hanoi

Example 4: Towers of Hanoi

The following legend is attributed to French mathematician Edouard Lucas in 1883. In an Indian temple there are 64 gold disks resting on three pegs. At the beginning of time, God placed these disks on the first peg and ordained that a group of priests should transfer them to the third peg according to the following rules:

  1. The disks are initially stacked on peg A, in decreasing order (from bottom to top).
  2. The disks must be moved to another peg in such a way that only one disk is moved at a time and without stacking a larger disk onto a smaller disk.

When they finish, the Tower will crumble and the world will end. How many moves does it take to solve the Towers of Hanoi problem with \(n\) disks?

Solution

The usual (and best) algorithm to solve the Towers of Hanoi is:

  • Move the top \(n-1\) disk to from peg 1 to peg 2.
  • Move the last disk from peg 1 to peg 3.
  • Move the top \(n-1\) disks from peg 2 to peg 3.

The only question is how to move the top \(n-1\) disks. The answer is simple: use recursion but switch the peg numbers. Here is an implementation of this idea:

void solveHanoi(int N,int source,int dest,int spare) {
  if(N==1) {
    moveDisk(source,dest);
  } else {
    solveHanoi(N-1,source,spare,dest);
    moveDisk(source,dest);
    solveHanoi(N-1,spare,dest,source);
  }
}

Don't worry if you don't see why this algorithm works. Our main concern here is analyzing the algorithm.

The exact details of moveDisk depend on how the pegs/disks are implemented, so we won't provide an implementation of it. But it doesn't actually matter anyway since we just need to count the number of times moveDisk is called. As it turns out, any reasonable implementation of moveDisk will take constant time, so the complexity of the algorithm is essentially the same as the number of calls to moveDisk.

Let \(H(n)\) be the number of moves it takes to solve the Towers of Hanoi problem with \(n\) disks. Then \(H(n)\) is the number of times moveDisk is called when running solveHanoi(n,1,2,3). It should be clear that \(H(1)=1\), since the algorithm simply makes a single call to moveDisk and quits. When \(n>1\), the algorithm makes two calls to solveHanoi with the first parameter being \(n-1\) and one call to moveDisk. Therefore,

\[ H(n)=2H(n-1)+1. \]

You have almost certainly seen this solution before, but let's go through the details of solving this recurrence relation anyway—it never hurts to review the basics. We can easily do it by repeated substitution:

\[ \begin{aligned} H(n) &= 2H(n-1)+1 \\ &= 2(2H(n-2)+1)+1 \\ &= 2^2H(n-2)+2+1 \\ &= 2^2(2H(n-3)+1)+2+1 \\ &= 2^3H(n-3)+2^2+2+1. \end{aligned} \]

After continuing this pattern for \(k\) steps, we get

\[ H(n)=2^kH(n-k)+(2^{k-1}+2^{k-2}+\cdots+2+1). \]

We reach the base case when \(n-k=1\), so \(k=n-1\). Since \(H(1)=1\),

\[ \begin{aligned} H(n) &= 2^{n-1}H(1)+(2^{n-2}+2^{n-3}+\cdots+2+1) \\ &= 2^{n-1}+\sum_{i=0}^{n-2}2^i \\ &= \sum_{i=0}^{n-1}2^i \\ &= 2^n-1. \end{aligned} \]

The third line simply combines \(2^{n-1}\) with the lower powers of 2 to form one geometric sum.

Thus, the Towers of Hanoi algorithm makes exactly \(2^n-1\) moves, so its running time is \(\Theta(2^n)\), assuming each call to moveDisk takes constant time.

Exercise 2

Let \(T(n)\) be the complexity of blarg(n). Give a recurrence relation for \(T(n)\).

int blarg(int n) {
  if(n>5) {
    return blarg(n-1)+blarg(n-1)+blarg(n-5)+blarg(sqrt(n));
  } else {

\(T(n)=2 T(n-1)+T(n-5)+T(\sqrt{n})+1\) if \(n>5\), \(T(1)=T(2)=T(3)=T(4)=T(5)=1\). You can also have \(+c\) instead of \(+1\) in the recursive definition.

Exercise 3

Give a recurrence relation for the running time of stoogeSort(A,0,n-1). (Hint: Start by letting \(T(n)\) be the running time of stoogeSort on an array of size \(n\).)

void stoogeSort(int[] A,int L,int R){
  if(R<=L) return; // Array has at most one element
  if(A[R]<A[L]) {  // Swap first and last element
    Swap(A,L,R); // if they are out of order
  }
  if(R-L>1){ // If the list has at least 2 elements
    int third=(R-L+1)/3;
    stoogeSort(A,L,R-third); // Sort first two-thirds
    stoogeSort(A,L+third,R); // Sort last two-thirds
    stoogeSort(A,L,R-third); // Sort first two-thirds again
  }
}

Beyond the recursive calls, StoogeSort does only a constant amount of work—we'll call it \(1\). Then it makes three calls with sub-arrays of size \((2/3)n\). Therefore, \(T(n)=3T((2/3)n)+1\) or \(T(n)=3T(2n/3)+1\), with base case \(T(1)=1\).

Exercise 4

Solve the recurrence relation you developed for StoogeSort in the previous exercise. (Make sure you verify your solution to the previous problem before you attempt to solve your recurrence relation).

We can use the Master Theorem for this one. \(a=3\), \(b=3/2\) and \(d=0\). (Notice that \(b\neq 2/3\)! If you made this mistake, make sure you understand why it is incorrect.) Since \(3>1=(3/2)^0\), the third case of the Master Theorem tells us that \(T(n)=\Theta\left(n^{\log_{3/2}(3)}\right)\). Although this looks weird, we can have a rational number as the base of a logarithm (in fact, the base of \(ln(n)\) is \(e\), an irrational number). It might be helpful to compute the \(\log\) since it isn't clear how good or bad this complexity is. Notice that \(\log_{3/2}(3)\approx 2.71\), so \(T(n)\) is approximately \(\Theta(n^{2.71})\), but \(T(n)\neq \Theta(n^{2.71})\), so resist the urge to place an equals sign between these.

Question 2

Which sorting algorithm is faster, MergeSort or StoogeSort? Justify your answer.

The complexity of MergeSort is \(\Theta(n\log n)\) and the complexity of StoogeSort is \(\Theta\left(n^{\log_\frac{3}{2}(3)}\right)\) which is \(\Omega(n^{2.7})\). Clearly \(\Theta\left(n^{\log_\frac{3}{2}(3)}\right)\) grows faster than \(\Theta(n\log n)\), so MergeSort is faster. Remember: Faster growth rate means slower algorithm!

Exercise 5

Give and solve a recurrence relation for the running time of an algorithm that does as follows: The algorithm is given an input array of size \(n\). If \(n<3\), the algorithm does nothing. If \(n\geq 3\), create 5 separate arrays, each one-third of the size of the original array. This takes \(\Theta(n)\) to accomplish. Then call the same algorithm on each of the 5 arrays.

Let \(T(n)\) be the running time of this algorithm on an array of size \(n\). If \(n<3\), the algorithm does only constant work, so \(T(n)=\Theta(1)\). If \(n\geq 3\), it creates five arrays of size \(n/3\), which takes \(\Theta(n)\) time, and then makes five recursive calls on inputs of size \(n/3\). Therefore,

\[ T(n)= \begin{cases} \Theta(1), & n<3,\\ 5T(n/3)+cn, & n\geq 3. \end{cases} \]

Using the Master Theorem with \(a=5\), \(b=3\), and \(d=1\), we compare \(a\) with \(b^d\). Since \(5>3^1\), the third case applies, so

\[ T(n)=\Theta\left(n^{\log_3 5}\right). \]

Since \(\log_3 5\approx 1.46\), this is approximately \(n^{1.46}\) growth, but the exact asymptotic form is \(\Theta\left(n^{\log_3 5}\right)\).

These examples illustrate the main pattern: identify the recursive calls, account for the nonrecursive work, include the base case, and then solve the resulting recurrence.

Reading Comprehension Questions

  1. Setting Up a Recurrence: When analyzing a recursive algorithm, what are the two main parts of the algorithm that usually determine the recurrence relation?
  2. Merge Sort Recurrence: Why does the merge sort analysis lead to the recurrence \[ T(n)=2T(n/2)+cn? \]
  3. Cost of Merge: In the merge sort analysis, why does the call to merge take \(\Theta(n)\) time?
  4. Base Case: What is the base case for merge sort, and how does it appear in the code?
  5. Using the Master Theorem: For the recurrence \[ T(n)=2T(n/2)+cn, \] what are \(a\), \(b\), and \(d\), and which case of the Master Theorem applies?
  6. Towers of Hanoi Recurrence: Why does the Towers of Hanoi algorithm satisfy \[ H(n)=2H(n-1)+1? \]
  7. Exact Versus Asymptotic Answer: The Towers of Hanoi algorithm makes exactly \(2^n-1\) moves. Why is its running time written as \(\Theta(2^n)\)?
  8. Stooge Sort Subproblem Size: In the recurrence for Stooge Sort, why is \(b=3/2\) rather than \(2/3\) when applying the Master Theorem?
  9. Comparing Algorithms: Why is merge sort faster than Stooge Sort, even though both are recursive sorting algorithms?
  1. Answer: The recurrence usually comes from the recursive calls and the nonrecursive work. The recursive calls determine how many subproblems there are and how large they are. The nonrecursive work accounts for everything else the algorithm does outside those recursive calls.
  2. Answer: Merge sort makes two recursive calls, each on roughly half of the array, giving the term \(2T(n/2)\). After the recursive calls return, the algorithm merges the two sorted halves in linear time, giving the \(cn\) term.
  3. Answer: The merge method copies the relevant portion of the array into a temporary array and then scans through that temporary array to merge the values back into the original array. Each loop processes only a linear number of values, so the total time is \(\Theta(n)\).
  4. Answer: The base case occurs when the subarray has 0 or 1 elements, since such a subarray is already sorted. In the code, this is handled by the condition if (left < right). If \(left\geq right\), the method does not make any recursive calls.
  5. Answer: For \(T(n)=2T(n/2)+cn\), we have \(a=2\), \(b=2\), and \(d=1\). Since \(a=b^d\), because \(2=2^1\), the second case of the Master Theorem applies. Therefore, \(T(n)=\Theta(n\log n)\).
  6. Answer: To solve Towers of Hanoi with \(n\) disks, the algorithm first moves \(n-1\) disks to the spare peg, then moves the largest disk once, and then moves the \(n-1\) disks onto the destination peg. The two recursive parts each take \(H(n-1)\) moves, and the largest disk move adds 1 more move, so \(H(n)=2H(n-1)+1\).
  7. Answer: The exact number of moves is \(2^n-1\). In asymptotic notation, subtracting 1 does not change the growth rate. Thus, \(2^n-1=\Theta(2^n)\), so the running time is \(\Theta(2^n)\) if each move takes constant time.
  8. Answer: In the Master Theorem, the recurrence is written in the form \(T(n)=aT(n/b)+f(n)\). Stooge Sort makes recursive calls on subarrays of size \(2n/3\). Since \(2n/3=n/(3/2)\), the correct value of \(b\) is \(3/2\), not \(2/3\).
  9. Answer: Merge sort has running time \(\Theta(n\log n)\), while Stooge Sort has running time \(\Theta\left(n^{\log_{3/2}3}\right)\), which is approximately \(\Theta(n^{2.71})\). Since \(n^{2.71}\) grows much faster than \(n\log n\), Stooge Sort is slower and merge sort is faster.
