Algorithm Analysis

Overview

Algorithm analysis is the study of how the resources used by an algorithm grow as the input size grows. Most often, we focus on running time, but the same ideas can also be used to discuss memory use and other resources. Analysis gives us a language for comparing algorithms without tying the comparison too closely to a particular computer, programming language, compiler, or test input.

This chapter gives a deeper treatment of some of the same ideas introduced in the Foundations chapter on basic algorithm analysis. There, the goal was to build intuition: count important operations, recognize common patterns, and describe growth rates informally. Here, we make those ideas more precise. We define asymptotic notation carefully, compare common growth rates, and practice analyzing algorithms in a more systematic way.

Prerequisites

This chapter assumes the mathematical maturity of a first course in discrete mathematics. In particular, we will use functions, algebra, inequalities, logarithms, summations, and basic proof techniques. Some examples also use limits, derivatives, and l'Hopital's Rule to compare growth rates.

Main Ideas

The central question in this chapter is:

As the input size \(n\) grows, how does the cost of the algorithm grow?

Here, cost means some resource used by the algorithm. Most often, we measure cost by counting how many basic operations the algorithm performs, such as comparisons, assignments, arithmetic operations, array accesses, loop iterations, or recursive calls. Sometimes we measure cost by counting extra memory instead. The exact operation we count depends on what we are trying to understand, but the goal is always to describe how the amount of work or memory grows as the input gets larger.

To answer that question, we will separate several related ideas:

  • Input size: Identify what variable or variables measure the size of the input, such as the number of array elements, characters, vertices, or edges.
  • Cost measure: Decide what operation or resource we are counting, such as comparisons, assignments, loop iterations, recursive calls, or extra memory.
  • Growth rate: Express the cost as a function of the input size and simplify it by focusing on its long-term behavior.
  • Asymptotic notation: Use notation such as \(O\), \(\Omega\), and \(\Theta\) to describe upper bounds, lower bounds, and tight bounds.
  • Cases: Distinguish best case, worst case, and average or expected case behavior when the running time depends on the arrangement of the input.

A common early mistake is to associate the three notations \(O\), \(\Omega\), and \(\Theta\) with the three cases: best case, worst case, and average case. These are different ideas. A case tells us which inputs of size \(n\) we are considering, while asymptotic notation tells us what kind of bound we are giving for that case. For example, it is possible to talk about a worst-case \(O(n^2)\) bound, a worst-case \(\Theta(n^2)\) bound, or a best-case \(O(n)\) bound. We will say more about this distinction after defining the notations more carefully.

What This Chapter Covers

The chapter begins with asymptotic notation. We define the major notations, explain how they are related, and practice proving asymptotic claims using both definitions and limits. Technically, these notations describe functions. When we say an algorithm is \(O(n^2)\), we mean that some cost function for the algorithm, such as the number of comparisons, loop iterations, recursive calls, or extra memory cells, grows no faster than a constant multiple of \(n^2\) for large \(n\). The goal is not just to use symbols like \(O(n^2)\), but to understand what such statements actually mean.

Next, we compare common growth rates. Cost functions such as \(O(\log n)\), \(O(n)\), \(O(n \log n)\), \(O(n^2)\), and \(O(2^n)\) behave very differently as \(n\) becomes large. Recognizing these growth rates helps us predict which algorithms will remain practical and which will quickly become too slow.

Finally, we apply these tools to actual algorithms. We analyze loops, nested loops, conditionals, recursive algorithms, searching algorithms, basic sorting algorithms, and simple data structure operations. The examples emphasize how to identify the input size, choose a cost to measure, and connect that cost to the structure of the code.

Why It Matters

Algorithm analysis helps explain why two correct programs for the same problem can behave very differently. For small inputs, implementation details or constant factors may dominate. For large inputs, the growth rate often determines which approach is feasible.

This is why algorithm analysis is not just a mathematical add-on to programming. It is one of the main tools we use to choose between algorithms, understand tradeoffs, predict performance, and design better solutions.
