Algorithm Analysis Basics

Overview

The central question in algorithm analysis is simple to ask: given an algorithm, how good is it? To answer that question, we must first decide what "good" means. An algorithm might be elegant, easy to implement, easy to modify, memory efficient, or fast. In this part of the course, we usually focus on time and space, especially time.

This page connects the mathematical notation from the previous pages to the practical work of analyzing code.

Why Not Just Time It?

Measuring wall-clock time can be useful, but it is not a stable way to compare algorithms. The result depends on the computer, the language, compiler settings, the operating system, background processes, cache behavior, and many implementation details. If two programs are run on different machines, a faster time may say more about the machine than about the algorithm.

CPU time is better, but it still compares implementations rather than algorithmic ideas. It also requires us to implement both algorithms before we know whether they are worth implementing. For algorithm analysis, we usually count abstract operations instead.

Quick check: Sue's program takes 1 hour and Stu's takes 3 minutes. Can we conclude Stu's algorithm is more efficient?

Not from that information alone. We need to know whether they used the same machine, comparable implementations, comparable input data, and comparable measurement conditions.

Input Size

Running time is described as a function of input size. Choosing the input-size variable is part of the analysis. If an algorithm processes an array of \(n\) elements, we usually call the input size \(n\), even if the method also receives a target value or a few numeric parameters. Those extra parameters add only a constant amount to the input description in the simple models used here.

Input Typical size measure
Array or list Number of elements, \(n\)
\(n\) by \(m\) matrix Number of entries, \(nm\), or two parameters \(n\) and \(m\)
Graph Number of vertices, number of edges, or both
String Number of characters

Abstract Operations

We almost never count every machine instruction. Instead, we choose an operation that captures the algorithm's repeated work. For sequential search, a natural operation is the comparison between the current array element and the value being searched for. For sorting, comparisons and swaps are often useful. For matrix multiplication, the multiply-add inside the innermost loop is the important repeated operation.

The chosen operation must be counted honestly. If a line of code calls a helper method, that call is not automatically constant time. A method such as contains, get, or insert may have a cost that depends on the data structure.

Example: Sequential Search

Sequential search scans an array from left to right until it finds the target or reaches the end. 

int sequentialSearch(int[] a, int val) {
    for (int i = 0; i < a.length; i++) {
        if (a[i] == val) {
            return i;
        }
    }
    return -1;
}

Let \(n\) be the length of the array, and count comparisons of the form a[i] == val.

  • Best case: The target is at index 0, so there is 1 comparison. The best-case time is \(\Theta(1)\).
  • Worst case: The target is last or missing, so there are \(n\) comparisons. The worst-case time is \(\Theta(n)\).
  • Average case: If the target is equally likely to be in any position, the expected number of comparisons is \[ \frac{1}{n}\sum_{k=1}^{n}k=\frac{n+1}{2}=\Theta(n). \]

Notice that best case, worst case, and average case are all measured for the same input size \(n\). The best case is not the case \(n=1\). It is an input of size \(n\) that lets the algorithm finish as quickly as possible.

Best, Worst, and Average Cases

  • Best case: The least work the algorithm can do on any input of size \(n\).
  • Worst case: The most work the algorithm can do on any input of size \(n\). This is a guarantee.
  • Average case: The expected work over inputs of size \(n\), after specifying how likely different inputs are.
  • Expected running time: Often used informally for how long the algorithm usually takes, but a formal average case requires a probability model.

Average-case analysis is often harder than worst-case analysis because we must define what "average input" means. For sequential search, several reasonable probability models still lead to \(\Theta(n)\), but for more complex algorithms the assumptions can matter.

How to Report an Analysis

When asked for the complexity of an algorithm, a complete answer should usually include:

  1. The input-size variable: State what \(n\), \(m\), \(|V|\), or \(|E|\) measures.
  2. The case being analyzed: Give best, average, and worst case unless the question specifies one case or the average case is beyond the current scope.
  3. A simple asymptotic bound: Prefer \(\Theta(f(n))\) when you have a tight bound. Use \(O(f(n))\) when only an upper bound is justified.
  4. A justification: Explain what operation you counted and why the count has that growth rate.

Common Mistakes

  • Using wall-clock time as the only evidence: Timing can support analysis, but it does not replace it.
  • Choosing a smaller input for best case: Cases compare inputs of the same size.
  • Assuming every function call is constant time: Data structure operations may be linear, logarithmic, or worse.
  • Reporting \(O\) when a tight \(\Theta\) bound is available: \(O(n^2)\) is true for a linear algorithm, but it is not precise.
  • Leaving loop variables in the final answer: Final bounds should use input-size variables, not local variables from the code.

Reading Comprehension Questions

  1. Why is "my algorithm ran in 5 minutes and yours ran in 15 minutes" not a complete argument?
  2. If one algorithm always takes three times as long as another, do they necessarily have different asymptotic complexities?
  3. Why can a method call inside a loop change the complexity of the loop?
  4. Why is the best case for sequential search \(\Theta(1)\) even when the array has \(n\) elements?
  5. Why does average-case analysis require assumptions about input probabilities?
  1. Answer: We need to know the machines, implementations, inputs, and measurement conditions. Timing alone may compare environments rather than algorithms.
  2. Answer: No. A constant-factor difference does not change asymptotic growth. If the times are \(f(n)\) and \(3f(n)\), they have the same growth rate.
  3. Answer: If the method call is not constant time, its cost must be multiplied by the number of loop iterations or otherwise included in the count.
  4. Answer: The best input of size \(n\) has the target in the first position, so the algorithm does one comparison regardless of \(n\).
  5. Answer: An average is computed over possible inputs. Without probabilities, there is no precise meaning to "average input."

In-Class Activities

  1. Operation choice: For maximum, sequential search, sorting, and matrix multiplication, decide what operation you would count and why.
  2. Same \(n\), different input: For sequential search on an array of length 8, give a best-case input, a worst-case input where the target appears, and a worst-case input where it does not.
  3. Average search: Derive the expected number of comparisons when the target is equally likely to be in any array position or missing entirely.

Homework Problems

  1. Analyze an algorithm that takes an \(n\) by \(m\) matrix, an integer \(v\), and a real number \(r\). What input-size measure would you use?
  2. Write best-case and worst-case analyses for a method that returns whether an array contains any negative value.
  3. For an array search algorithm with \(\Theta(n\log n)\) time, explain whether that is a good approach to the ordinary search problem.
  4. Give at least two reasons why a double-nested loop does not automatically imply \(\Theta(n^2)\) time.
